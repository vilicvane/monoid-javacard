# Security Key 凭证与派生缓存优化

[user] 对于 secret key，可以按不可修改理解，不需要在实现中特别禁止修改；异常修改造成的问题由用户自行处理。Client Applet可以按自己的场景缓存必要数据，不必完全依赖Monoid的缓存机制。对能合理利用缓存的API修改持开放态度。

[user] “通过缓存hash获取资源”只是举例，不要求采用显式缓存，也没有指定hash索引、句柄或某个新接口。

[agent] 后续优化先按签名来源seed/私钥稳定的前提考虑客户端数据缓存、会话内资源复用，避免仅为用户异常原地修改密钥而引入通用版本追踪和自动修复。不把这项前提扩大为所有Safe Item都不可变，也不因此忽略客户端自身的凭证创建、替换、删除和Reset。客户端自行维护其缓存生命周期。

[agent] 私有密钥运算仍留在Monoid；缓存资源的使用仍受调用方及当前授权约束。授权撤销、PIN验证与普通数据缓存是不同问题，本次讨论未授权取消这些检查。先根据具体重复工作选择最简单的缓存位置，只有现有接口阻碍有效复用时才提出接口调整，不预设独立缓存框架或hash目录。

## 最终实现

[agent] Security Key 保留最多4条、每条最多256B的持久凭证解析缓存，安装时创建4个缓存对象。每条保留payload及22B解析偏移快照，执行时使用transient short[11]；deselect/reset清空执行状态后才恢复偏移。先使旧source失效，再读取、核验元数据、通过APDU窗口批量保存偏移，最后发布source；断电不会发布部分写入的缓存。FIFO游标只写一次有效的0–3值，避免绕回时中间值4被持久保留。清缓存时不重复向已经为null的槽写null。

[agent] 每次命中通过当前已认证Monoid会话核验原快照的Safe、item、data身份及当前Type/nonsecret权限；同长度替换、删除重建仍会失效。注册查重继续直接读取，不为一次性扫描构造缓存。save及局部Reset清缓存；超过容量正常淘汰，长记录与较多记录保留原读取路径。客户端仍核验完整credential ID、RP及当前派生公钥。四槽工作集已实卡覆盖，超过四槽的淘汰行为由模拟器覆盖。

[agent] MonoidSession复用当前seed item/private data与最近一个DerivedKey；目录变化重新定位，正常setData换数组或context变化清最近结果。全局32槽派生缓存保持不变，签名每次仍导入私钥、初始化native Signature并复核当前授权。

[agent] AppletGrants按Safe实例惰性共享SHA-256引擎及32B RESET scratch，减少跨reset重新创建会话时的资源分配；每个会话的授权状态仍独立，Safe整体reset释放共享资源。

[agent] 本轮新增两项Monoid SIO（用户已授权必要缓存API修改、事后列明）：

```java
SafeDataShareable getData(
  byte[] index,
  short indexOffset,
  byte[] expectedKey,
  short keyOffset,
  short keyLength
);

boolean isDataCurrent(SafeDataShareable data);
```

getData按10B index和exact key取得现有数据快照；缺失/不匹配返回null，权限失败抛错。isDataCurrent用当前会话检查旧快照，foreign/删除/重建/data替换返回false，权限或secret失败仍抛6982；不会恢复旧会话。SafeSessionData以RESET引用保存原session，另持久保存Safe归属；reset后旧reader仍失效，同时释放旧session及其RAM。缓存不跨Applet重装，卸载仍先client再provider。CTAP/APDU及凭证格式未改。

[agent] 模拟器增加SIO返回自身owner时还原原对象的语义；交给别的owner仍保留代理/firewall上下文。CAP转换触发旧SDK exception reference gap缺陷，JDB确认264B、addTwoByteOffset失败；将既有6985映射移到公开API边界后最大间距232B，无新增错误吞掉或SDK改动。

## GC调整与边界

[user] 大量基本只读的数据改为持久对象后，不需要激进地请求GC；关注紧凑内存场景与运行时自身的回收行为。

[agent] round15取消成功填充空缓存槽时的GC请求：新建对象全部被缓存保留，并未产生需要丢弃的reader。stale、淘汰、长记录及错误路径的清理保持原有行为。单独对比round14，首次known-ID由474.0降至347.6ms，首次三账户由838.2降至776.7ms，warm基本不变。此前批量保存偏移也减少持久逐字段写入，不能把整个优化收益都归因于GC或EEPROM。

[agent] 本轮未进行“关闭所有Applet内部requestObjectDeletion”的独立自动GC实验。补充测试中“没有显式collection”只指主机未额外发送诊断回收命令；不能据此断言固件没有请求回收。最终未做连续峰值RAM采样；相对round13直接执行持久short偏移的中间版本，4槽transient偏移合计增加88B RAM，不能据此推算整套程序峰值。

[agent] 用户追问requestObjectDeletion何时重新加入后，提交记录核对发现：2025-07-19的b39129d已在Command.runCommand finally请求，2026-10-12的8abf0c5移至process finally，这一路并非近期全删后恢复。本轮MonoidApplet.createSession、MonoidSession.getDerivationInput及KeyDerivation.derive里的请求则是新增，首次出现在round05源码快照（2026-10-22 01:46:18，UTC+8），round04没有。它们伴随Security Key不再为无分配的warm路径请求回收而添加，不能作为“实卡自动GC失效”的实验依据。
