[agent] Source and specification review found:

- secp256k1 and secp256r1 identify specific named curve parameter sets. ECDSA
  on either curve is appropriate for an API accepting precomputed digests.
  ES256 additionally requires SHA-256; it is not a synonym for generic ECDSA.
- Current ECDSA selects SIG_CIPHER_ECDSA_PLAIN and signPreComputedHash with a
  SHA-256 length configuration. Input is 32 bytes, is not hashed again, and the
  card cannot determine which hash produced it. Output is 64-byte big-endian
  r || s. LibECDSA enforces low-S using secp256k1's hardcoded order; the P-256
  implementation must use its own order, as already noted in record 99.
- Random versus deterministic ECDSA nonces change signature bytes without
  changing verification compatibility. DER versus raw r || s is an encoding
  distinction. doc/bitcoin.md incorrectly claimed DER output; corrected it to
  the actual raw output and the client's Bitcoin DER conversion responsibility.
  Signer.java's ASN.1 allocation comment is also stale; no code changed here.
- secp256k1 plus Schnorr does not uniquely identify a signature scheme: BCH and
  BIP340 differ in challenge hashing, public-key handling and point selection.
  The original firmware fixed schnorr to LibBIP340. The updated API names that
  scheme bip340.
- The mathematical curve is edwards25519. Ed25519 is a concrete signing/key
  parameter set, and also a conventional crv identifier in COSE. Do not treat
  curve:ed25519 as an erroneous name requiring a mathematical-layer rename.
- EdDSA on the same mathematical curve has pure Ed25519, Ed25519ctx and
  Ed25519ph variants with incompatible signatures. Current LibED25519 performs
  pure Ed25519: SHA-512(prefix || M), SHA-512(R || A || M), no dom2/prehash, and
  encoded R || little-endian S output. Existing README explicitly says pure.
  The previous pair ed25519/eddsa is precise under that convention (also used
  by COSE); the broad EdDSA name alone does not select a variant. The updated
  README uses ed25519 for the cipher as well. Future ctx/ph support must not
  silently reuse the existing meaning.

Evidence: Signer.java, OneShot.java, LibECDSA.java, LibED25519.java,
