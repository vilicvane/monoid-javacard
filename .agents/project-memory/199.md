# 固件性能基线：D321 / ACR1552（2026-10-27）

[user] 怀疑近期 firmware 有性能回退，要求实卡运行通用 benchmark，考虑保留为今后随时对照的基线；不按主观慢点缩小范围，使用非接触式读卡器。

[agent] 同一张 D321、同一 ACR1552，PC/SC T=1 接口的非接触通信；对照 daac97082856 与 12eee6523e70。两版均使用完整五 CAP 布局，C0/C5/C2/C4/C6 隔离命名空间，相同测试 Authority URL、公钥、公开种子、数据大小和用例顺序；无 Bundle、无 alias。保留原卡已有应用。只重命名包和完整 AID，没有固件计时插桩，也没有性能修复。

## 本轮观察

- Hello：351.16 → 409.31 ms，+58.15 ms / +16.56%。五次各自稳定。源码新增 alias 与 allowPeerExtension，各走一次 requireIdentity（SIO、缓存 token 的 global 副本和冗余比较）。响应 CBOR165 →192B（包含状态字为167 →194B），仍一条 APDU，不是分片阈值变化。代码支持该增量解释，未做逐方法插桩归因。
- Access 认证161.20 →161.63 ms；Secret315.59 →318.98 ms。List16条1806.99 →1820.18 ms。普通64/600/1536B存取没有与 Hello 同幅度的退化。
- SLIP-0010 Ed25519 签名64B：2353.90 →2351.53 ms；1232B：2590.48 →2588.35 ms。直接 Ed25519 64B为2851.66 →2851.22 ms；BIP340为778.71 →779.08 ms。没有观察到这些签名的整体回退。
- FIDO PIN 握手346.39 →349.60 ms；驻留单凭证 allowList 登录555.99 →576.55 ms；三账户发现1345.72 →1246.47 ms。五次序列包含首次缓存未命中和随机签名差异，不能把全部差值当作稳定改善/退化。
- 非驻留注册1157.51 →954.28 ms。新版不存 F101，旧版存记录；这是相同业务请求的比较，内部工作不同。
- OTP SHA1单账户三码 Calculate528.55 →503.76 ms；SHA256544.86 →518.60；SHA512581.25 →553.01；三账户九码1107.09 →1046.94。新版账户与秘密合并，减少一次数据引用读取，观察结果符合该方向。
- 带 Authority 的 OTP 完整卡端流程包含3次SELECT、Challenge、Prepare、一次授权、Calculate，共7次APDU。单账户SHA1为1636.47 →1630.33 ms；三账户为2243.61 →2199.76 ms。离线生成合法时间证明，排除HTTP/APP/UI/用户时间；两版URL均为https://authority.monoid.app，但仅临时Identity使用公开测试标量1，不访问生产服务。

## ECDSA 中位数陷阱

Monoid-001/P256五次中位数622.47 →723.99 ms，不能据此认定新增101ms计算开销。原始暖样本排序：

- baseline：618.11、618.80、622.47、715.07、715.33 ms。
- current：628.74、723.80、723.99、724.41、724.61 ms。

直接P256则出现反方向中位数609.99 →506.51 ms：baseline514.22、514.52、609.99、610.03、610.15；current506.23、506.50、506.51、506.58、602.75。两版均有约96–97ms的快慢档，样本占比不同让中位数跳档。Signer/OneShot/LibECDSA/LibMath在两版间未改；高S规范化分支的32次持久数组逐字节写入是强候选解释，但未插桩证实，返回的已规范化S也不能反推分支。不要丢弃慢样本或声称已定位硬件分支。若要严谨估算ECDSA总体均值，应追加20–30次以上并交换版本顺序。

## 可复用工具与验证

- scripts/benchmark 提供冻结指定commit、离线编译、身份与AID占用检查、安装、完整RPC/CTAP测试、统计比较、按依赖卸载及registry复核；用法见doc/benchmark.md。
- 每版372条成功计时样本，按名称/phase分成104项，包含嵌套flow和stage，不能求和。常规重复5次，部分首次调用1次。首次不等于断场冷启动，Sign是在ViewKey之后测量。FIDO序列包含首次调用。
- 全部签名、公钥/chainCode、读回数据、TOTP都由host独立算法校验。OTP host oracle通过10个RFC4226、18个RFC6238向量和合法/篡改时间签名检查。
- 两版共10个隔离CAP转换/验证通过；20项host单元测试通过；格式和diff检查通过。没有修改生产Java源码，不需要因纯host工具重跑702项生产Java测试。
- 两版完整运行及清理成功。最终全部C0/C5/C2/C4/C6包和实例删除，原卡registry与测试前相同，释放读卡器。没有重新部署正式应用，没有提交或推送。
- 本轮是一次A→B对照，未交换安装顺序；没有手机端到端耗时、网络、物理内存峰值或GP/Bundle/跨卡加解密性能测量。小差异不据此宣称统计显著。

原始证据位于忽略目录 .research/firmware-benchmark-20261026/，baseline-full2与current-full2各含results.json、events.jsonl、manifest.json、artifacts.json、ledger.json、host-sources及GP日志。两版19份host源码哈希一致；源码另行按匹配哈希归档。最初full目录是仅构建失败的隔离包名替换脚本调试，不曾安装，不是性能数据。已修复误把monoid局部变量当包名替换的问题并加测试。收尾工具只进一步增加host源码/依赖/字段顺序辅助文件归档，移除无效iterations选项，测量行为未改变；历史已测工具仍在上述host-sources中。

## 博客兴趣点

- **切入问题**：为什么相同算法的五次签名中位数，会同时表现为一个场景变快100ms、另一个变慢100ms？
- **关键事实**：[blog] 两版随机ECDSA样本均有约97ms的双峰。固定长度APDU与未变的签名源码帮助排除响应分片和近期算法修改；高S规范化的持久写入是待插桩验证的解释。
- **适用边界**：D321、同卡同读卡器、暖签名路径、五次小样本；不能由中位数跳档推导普遍回退，也不能把源码推断当作实测分支。
- **参考**：本记录的ECDSA原始排序样本，以及Signer、OneShot、LibECDSA.ensureLowS、LibMath.sub。
