# Identity 共享 AES-GCM 实例

## 请求与实现

- [user] 批准将通信密钥与条目数据两条路径改为共享同一个 AES-GCM 实例，保留 16B 缓冲，并要求实卡对照内存与性能。
- [agent] `MonoidIdentityApplet` 按需创建一个实例，通过构造器注入 `CommunicationCipher` 和 `ItemCipher`。两者继续独立持有 AESKey 和各自的协议状态；共用的是 AES 引擎、GHASH 与工作缓冲。未改变 APDU、SIO、密文格式或原有 transient-first 分配策略。
- 通信密钥封装/解封及 tag 获取或三轮核验完成后，才开始条目数据的 GCM。每次 `init` 重新初始化模式、计数器、GHASH 和 tag，失败后的下一操作同样重新初始化。既有 `communicationOperation` 保护覆盖外部数据回调，避免处理中重入通信或改变 Bundle。
- `AESGcmCipher` 与 GHASH 本轮没有改动，沿用 record143 的 16B RAM 块批量写出。没有增加 static 引用或额外 dispose 管理。
- 被去掉的一份实例含 81B 显式 transient 数组载荷：counter/block/tag 共 48B、mode 1B、GHASH h/y 共 32B。实际可分配容量收益还包含原生对象分配和对齐影响，以实卡读数为准。

## 离线验证

- 三个现有测试类改为共享 AES-GCM fixture，使独立 host 向量、交替密钥、tag 篡改与失败恢复用例实际经过共享实例。Bundle 测试补充入组校验失败后的有效入组、Bundle 条目往返以及非对称条目解密。
- 完整 310 项测试、39 个 suite，零失败、错误和跳过。两份正式 CAP 转换零错误/警告、Verifier 通过；定向 Prettier 通过。生产改动仅三个 Identity 类。
- 测试日志：忽略目录 `.research/gcm-shared-20261019/production-check.log`。

## 实卡对照方法

- 实际 CPLC `51433520`，ACS ACR1552 PICC，T=1。开始时没有 Monoid 应用，仅使用 E0 Identity / E2 Monoid 临时包；不部署正式 AID。
- 两组均使用当前 16B 批量写出与原有分配策略。基线保留两个 AES-GCM 实例，共享版仅改变本轮三个类；没有采用 record143/144 的私有数组全部持久化实验。
- 常规未插桩性能：每组 71 次完整命令、14 个场景；每场景一次预热、三次正式样本，共 42 个正式样本/组。包含 32/256/1024B 的非对称与 Bundle 传输、三成员 Bundle 创建和导入。
- 时间为业务请求及 GET RESPONSE 的 PC/SC transmit 总和；排除 host 密码学、编码、SELECT 和准备命令。Import 正式样本是相同条目的重试，CreateBundle 正式样本替换已有 Bundle。逐笔时间已与原始 APDU 日志独立核对。
- 两组按基线→共享顺序分别安装，未随机交错；不能将小幅耗时差全部归因于共享本身或随机噪声。
- 内存使用另一组匹配的插桩固件，保留相同 checkpoint 映射与命令顺序。探针没有增加 transient RAM；移除插桩和 AID/包名替换后，82 个生产源文件与冻结源码匹配，基线仅反向恢复本轮三处共享改动。插桩耗时不用于性能比较。

- 总最低 RESET39→142B、DESELECT32→128B，均出现在 Bundle 重新入组相关检查，包括篡改拒绝、有效包、幂等和冲突拒绝。两组初始化前 15 条操作的 RESET 最低读数相同，其余 137 条每条恰好增加 103B，没有更差的匹配操作。
- 传输预热后、Ed25519 后、BIP32 后各重复三轮 32/256/1024B Bundle 导出/导入。同一阶段的三轮最低读数一致；签名后 256B 导出/导入最低 RESET356/371→459/474B，1024B 为 707/629→810/732B，两种签名之后读数相同。初始 Export 与重复阶段的请求元数据不同，不混为同一条请求的回归。
- 测试最后的空闲容量 RESET1441→1544B、DESELECT1440→1536B，均比纯传输预热阶段少 96B，来自该套件后续保留的签名工作区。共享收益仍保持。
- 这是各 checkpoint 上 `JCSystem.getAvailableMemory` 给出的可分配容量上界，不是精确物理 RAM 用量；看不到原生方法内部瞬时分配并释放的峰值。RESET/DESELECT 不能相加。持久空间读数饱和于 32767B，不能据此比较实际持久占用、寿命或满卡 GC。
- 最低 142B 仍然紧张。该套件的重新入组发生在签名之前，签名之后重复的是条目传输；不能把 142B 当作所有操作排列的保证余量，也不能据此保证更少 RAM 的卡片能运行。
- 用户确认关心的旧 Export/Import 也确实紧张：256B 非对称路径原先只有 68/69B。1024B 数组转持久存储后反而留更多 RAM，原因是现有 helpers 仍按长度和分配失败回退，没有主动保留 RAM 预算。创建后主要读取的临时私有数组直接持久化，仍是 record143/144 的实验方案，本轮没有采用。
