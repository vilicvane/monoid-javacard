The useful common result is the complete pre-Taproot derived key: 64B
private material plus chain code for BIP32/SLIP-0010, and a 32B scalar for
Monoid-001. ViewKey and Sign can reuse the same result. Current command
and Safe authorization/source existence checks must still run on cache
hits. SafeSessionItem.setData can replace source bytes without changing
index, including through another authorized applet. A cache identity must
therefore bind the actual current source bytes (or a full strong digest),
source interpretation, concrete derivation scheme and complete path/context;
index alone is insufficient. Library identity must not accidentally make
different algorithms share an entry.

The prior assumption that transient contents may disappear between every
operation means a cross-operation cache needs persistent storage. Cache
entries are derived key material, separate from shared curve/signature
contexts. Return operation-local copies: existing SLIP-0010 and Taproot
paths modify working data, so passing the cache's persistent array directly
would corrupt the reusable result. No external API changes are proposed.

[user] Requested continuing with derivation caching inside KeyDerivation.

[agent] Added one most-recent successful entry per derivation instance.
The entry contains persistent copies of the complete master, path/context
and derived result. Matching compares complete byte arrays and lengths,
without an index-based shortcut or hashing. Each instance identifies its
algorithm implicitly. A hit returns a new CLEAR_ON_DESELECT result copy
and performs no persistent writes. A miss computes first, snapshots all
three arrays into a new private CacheEntry, then publishes the entry with
one reference assignment. Failed computation leaves the old entry usable.
Seed-to-master remains outside the cache, so a seed request still performs
that HMAC; a corresponding saved master can share the resulting entry.

Single persistent-field updates are atomic under Oracle Java Card RE
[section 7.1](https://docs.oracle.com/javacard/3.1/related-docs/JCCRE/JCCRE.pdf).
The old entry is never overwritten in place; partially copied new arrays
cannot be reached through the cache until construction completes. No
transaction around payload copies, extra validity flags, static references
or explicit cache GC/disposal calls are added. Existing command cleanup
requests GC, and existing Keystore ownership handles uninstall reachability.
This reasoning uses the runtime guarantee; simulator/reset testing does
not constitute physical interrupted-write fault testing.

Source removal does not immediately erase the cache's private retained
master/result; that entry lasts until replacement or applet removal.
Existing Safe lookups and authorization checks remain mandatory before
cache access, so deletion cannot be bypassed through ViewKey/Sign. No
cross-Applet invalidation API or deletion-erasure guarantee is introduced.

[agent] Replaced the per-instance cache with one static 32-slot persistent
pool shared by all three derivation instances. Each entry also records its
owner, keeping algorithms distinct even when master and input bytes match.
The policy is FIFO: hits return transient copies without refreshing order
or writing persistent state. Misses construct all persistent copies first,
then publish the entry and advance the insertion cursor in one short
transaction. A failed derivation leaves the pool and cursor unchanged.
The limit counts retained entries; storage size still depends on input
length. No additional large-context policy or public API is introduced.

KeyDerivation.init/dispose now participates in MonoidApplet installation
and uninstallation, in the same order as the other shared resources.
Disposal releases the static pool and its references to derivation owners.
This supersedes the single-entry ownership/lifecycle description above.

modulo cursor expression; increment plus an explicit wrap avoids it.
