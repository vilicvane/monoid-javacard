# AES-GCM 按 16B 分组写出

## 目标与实现

- [user] 在 record142 的持久存储对照后，批准优先优化 AES-GCM 的逐字节输出，再测完整结果持久化的代价。沿用 AES 的 16B 分组，不扩大缓冲。
- [agent] 正式修改仅在 `monoididentity/AESGcmCipher.java`：在现有 transient `block` 中完成 XOR，再用 `Util.arrayCopyNonAtomic` 写出本块。加密的 GHASH 直接读取刚生成的 RAM 密文；解密仍先读取原密文做 GHASH，再覆盖输出。
- 不增加数组或持久引用，不改变协议、API、分配策略或共享上下文生命周期；末尾不足 16B 时只复制有效部分，保留精确原地加解密。
- 本轮持久化 helper 变体仅用于研究：两个 `makePrivateByteArray` 直接分配 persistent，其余 RAM 工作区、global 数组及传输缓冲保持原逻辑。不得把该变体描述为正式代码已全部持久化。

## 验证方法

- 现有 310 项 JUnit 全通过，无失败、错误或跳过；两份正式 CAP 转换均无错误/警告且 verifier 通过。
- 现有 AES-GCM 测试已覆盖独立 NIST/host 对照、0/1/15/16/17/31/32/33 字节边界、非零偏移和哨兵、原地加解密到 4096B、计数器进位、重复初始化及损坏密文/nonce/tag；未增加镜像实现的测试。
- 隔离卡仍为 APP 测试卡 CPLC `51433520`，ACS ACR1552 PICC，T=1。开始时重新查询 registry，与 record142 的结束状态一致，无 Monoid 应用。使用 E0/E2 临时包及对应实例，不安装正式 AID。
- 新研究目录 `.research/gcm-bulk-20261019/`；`bulk-original` 仅在上一轮 baseline 上应用 AES 改动，`bulk-persistent` 仅在上一轮 private-all 上应用 AES 改动。586 项原/冻结/生成输入及四个未插桩 CAP 哈希核对通过。
- 性能脚本严格复用 record142 的 63 次命令、14 个用例、34 个正式计时样本，独立密码学核对方式不变。每项 32/256B 和 Bundle 管理为一次预热后三次样本，取中位数；1024B 仍仅一次正式样本。
- 计时为业务 PC/SC transmit 总和，包含分片与 GET RESPONSE，排除 host 计算/编码/SELECT/setup。Item Import 和 Import Bundle 的正式计时是幂等重试，Create Bundle 是产生新 key 的替换。顺序独立安装比较，不能排除跨轮漂移，也不是单独存储带宽测量。
- 峰值探针从 record142 的已插桩源码生成，仅更新 AES 和两个私有分配 helper；103 个采样位置的编号/调用序列保持一致。统计载荷仍为 520B 持久空间，不增显式 transient 数组。原生调用内部临时空间仍不可见；查询值是可分配上界，RESET/DESELECT 不可相加。

- 原策略 32/256B 约 -0.4% 到 +0.3%，没有明显退化；1024B 已在原策略使用持久结果，批量写出省约 2.65–2.75 秒，四个单样本降低 25.7–28.9%。

- 这些为整版同卡对照，不是每字节存储指令的独立成本；1024B 的几个百分点以内差异不作为稳定结论。

## 实卡内存结果

插桩版本 152/152 次操作通过，卡片、操作标签、顺序和检查点编号均与 record142 一致。这里比较的是「原分配策略、优化前」与「私有数组持久化、批量写出」的组合，不是 AES 批量写出单项带来的 RAM 改善；正式源码的分配策略仍未改变。

下表为检查点处 RESET 可分配容量的最低读数，单位 B：

| 操作                      | 原策略、优化前 | 持久策略、批量写出 |
| ------------------------- | -------------: | -----------------: |
| 非对称 Import 32B         |            293 |                702 |
| 非对称 Import 256B        |             69 |                702 |
| 非对称 Import 1024B       |            327 |                702 |
| 非对称 Export 32B         |            804 |               1222 |
| 非对称 Export 256B        |             68 |                710 |
| 非对称 Export 1024B       |            468 |                710 |
| Bundle Import 256B        |            467 |                829 |
| Bundle Export 256B        |            262 |                710 |
| Create Bundle，三成员     |            329 |                589 |
| 重新导入 Bundle，四条路径 |             39 |                249 |
| 签名后 Bundle Import 256B |            371 |                733 |
| 签名后 Bundle Export 256B |            356 |                739 |

- 全流程最低 RESET 从 39B 增到 249B，DESELECT 从 32B 增到 240B；四条重新导入路径分别为损坏包拒绝、有效 host 包、幂等导入、冲突导入拒绝。RESET 的 210B 差额对应 65B 本卡公钥副本、113B HPKE 包和 32B 解密密钥移到持久存储。
- 重新导入原路径：起始 1537 → 请求分块 1025 → 解码副本 657 → global 副本 281 → 预留响应 hash 249 → 私有 65B 后 184 → 私有 113B 后 71 → 私有 32B 后 39。新路径在预留 hash 后保持 249B，仍不是充裕余量；请求/解码/global 数组尚占用 RAM。
- 152 个同标签操作中，99 项最低 RESET 读数提高、53 项不变、没有下降；各操作起始 RESET 读数均相同。Ed25519/ECDSA 的 View 和 Sign 四项本身不变；两类签名后的数据传输各三轮读数一致，最终 idle 仍为 RESET1441/DESELECT1440B。
- 四条重新导入 Bundle 均发生在签名上下文初始化之前；签名后仅重复条目传输。因此 249B 不是所有操作顺序的保证下限。
- 这些是采样点的 API 可分配容量上界，不是精确的原生 RAM 峰值；RESET/DESELECT 不能相加。插桩版本耗时不用来判断性能。持久空间查询仍饱和于 32767，未证明长期 GC、满卡行为或写入寿命。
