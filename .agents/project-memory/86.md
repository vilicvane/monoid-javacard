# Safe session authorization — 2026-10-14

Record [87](./87.md) updates interface reacquisition to reuse an authorized
session and adds physical-card validation. The validation below describes the
earlier simulator-only milestone; use record 87 for the current behavior.

[user] The user requires treating arbitrary applet installation as possible,
including modified code installed under a Monoid AID. The user explicitly
approved restricting SafeShareable data access and PIN changes to the caller
that successfully verifies the Safe PIN. After reviewing the initial single
active authorization design, the user authorized independent authorization for
alternating callers if feasible; otherwise the fallback is a single active
caller without a separate SafeSession. Independent authorization is feasible
and implemented below. This supersedes global revocation on every interface
acquisition or PIN check. Shareable method signatures and APDU formats remain
unchanged. The user also requires
considering realistic execution order: exclude impossible sequences, but handle
paths an attacker can actually arrange.

[user] The user additionally accepts applet isolation as a useful boundary:
the card owner may not thoroughly inspect another applet's source code.

[agent] Distinguish the owner's knowledge of a PIN from authorization granted
to installed code. Authorizing A does not authorize B merely because the same
person installed both. Also, the existing API separates Access and Safe PIN:
`CommandSign`, ViewKey, View and List accept Access authentication, but
`CommandGet` requires Safe authentication before returning raw stored data.
An Access-authenticated signing call uses A's cached Safe PIN internally and
therefore validated the old shared Safe OwnerPIN without granting the user
Safe-level command authorization. B could then exploit that global state to
export keys or change the Safe PIN. If an attacker already knows the Safe PIN
(including a deployment using identical PINs), this path does not increase that
attacker's rights; isolating code that was not given the PIN remains useful.

## Implementation

[agent] `MonoidSafeApplet` no longer directly implements `SafeShareable`.
It returns a new `SafeSession` containing the requesting JCRE AID. Each call
checks `JCSystem.getPreviousContextAID()` against that caller. The AID-prefix
filter remains an eligibility rule, not proof of code authenticity.

Each SafeSession owns a two-short `CLEAR_ON_RESET` authorization array containing
`0x5AFE` and its complement, with `0/0` meaning unauthenticated. Invalid encodings
fail with `6982`. Only successful native PIN comparison followed by an independent
`OwnerPIN.isValidated()` check can publish this state. Subsequent access checks
the session state, caller and shared PIN try counter, not the global native
validated flag: that flag changes when any caller attempts PIN verification.
A and B can therefore both authenticate and repeatedly SELECT back and forth
without authenticating again. A failed check in B does not revoke A unless it
exhausts the shared try counter.

Safe holds only a `CLEAR_ON_RESET` head reference for currently authorized
sessions. Each session's next reference also lives in a `CLEAR_ON_RESET` array.
Publishing authorization links the session first, then writes its complementary
state. Revocation clears authorization before unlinking and clearing its next
reference. There is at most one authorized session per caller. Acquiring another
interface or checking the PIN revokes only that caller's previous session.
Reset clears the head, links and all authorization arrays; Safe retains no
persistent registry of callers or removed applets. Client-held SIOs survive
reset as objects but contain no grant until authenticated again.

`CLEAR_ON_DESELECT` is unsuitable for these Safe-owned arrays because the
selected applet during SIO calls is the client. Safe does not receive the
client's deselect event; no client-deselect revocation is claimed here.
Monoid's separate Command authorization still uses `CLEAR_ON_DESELECT`.

`SafeItem` is internal storage, no longer a Shareable object.
`SafeSessionItem` checks its issuing session before every read, update and
remove. Reacquiring and authenticating a different session does not revive old
item views. Each get/list/create returns new views; callers must not depend on
view object identity. Views and sessions are ordinary objects eligible for GC
when no longer referenced. No static references or reset epoch counters were
introduced.

PIN checking invalidates that caller's existing grant and resets the native
validation flag before invoking `OwnerPIN.check` once. False results and
exceptions leave that caller unauthenticated; a wrong PIN consumes one shared
attempt. A `finally` branch revokes all sessions if the try counter reaches zero,
including when the final attempt throws an exception. Other sessions are not
revoked by failed attempts while the PIN remains unblocked. New interface
acquisition does not call native `pin.reset()` or disturb another caller's grant.
Updating the PIN checks authorization at entry and again inside the transaction,
then invalidates every session and updates the PIN and its initialized-state
encoding. Initialization uses complementary `0xA501`/`0x5AFE` state values rather
than an unprotected boolean. Initial PIN setup is permitted, while all data
access before setup is denied. A successful update requires authentication with
the new PIN; an oversized failed update leaves the original PIN usable and all
grants invalidated. These global invalidation rules are deliberate implementation
choices for a single shared PIN; callers do not receive independent passwords
or independent try budgets.

## Realistic execution order and limits

[agent] Applets do not execute autonomously in the background. The following
paths require a terminal to select/invoke the relevant applets, or another
applet to call their SIOs, while power is retained:

1. B acquires a Safe interface, A acquires its own interface and authenticates,
   then the terminal selects B. The original global OwnerPIN validation was
   insufficient to distinguish these callers. B must not read data or change
   the PIN without its own successful authentication.
2. The terminal can pass Shareable objects through another applet's Shareable
   interface. Possession of an item or Safe interface must not confer another
   session's grant. Tests exercise this with explicit BORROW APDUs and SIO
   getters in cooperating test applets.
3. A stronger replacement path additionally requires card-content-management
   authority: while continuously powered, select away from A, delete A, then
   install another instance using A's AID. B may retain its own Safe-owned SIO
   and forward it to the replacement without obtaining a new Safe interface.
   GP's specified install/delete flows do not mandate a reset, but deletion
   conditions and card policy still apply. Whether the target card reuses the
   old JCRE AID object identity is unverified. Binding the grant to the exact
   session avoids relying on either reuse or non-reuse.

AID-only authorization initially failed the third regression in jCardSim:
the replacement could use B's cached interface while the reused AID matched A's
grant. The session-bound implementation rejects it, and the corresponding
cached-item case. Deleting/recreating applets in these tests uses simulator
lifecycle APIs, not a verified physical GP exchange.

Card reset/actual power loss clears Safe's transient grant and native PIN
validation. Ordinary separate taps therefore do not inherit this grant.
Closing a terminal connection is not sufficient evidence of reset: PC/SC
supports `SCARD_LEAVE_CARD`. Selecting another applet alone does not reset
OwnerPIN. A malicious applet intentionally given the correct Safe PIN can
access secrets by design; this change cannot authenticate its code or prevent
exfiltration by an authorized caller.

## Validation

[agent] All 121 simulator tests pass, with no failures, errors or skips, including
20 Safe authorization tests and the 10 Command tests from record 85. Both
production CAP checks pass. Coverage includes bootstrap, independent
A/B authorization across repeated SELECTs, forwarded interfaces/items,
caller-local reacquisition and failed/throwing PIN checks, reset and PIN update
revocation of both callers, shared try-count exhaustion on both a wrong PIN and
a throwing final attempt, failed updates,
same-AID replacement, independent grants surviving native validation reset,
64 single-bit mutations across cleared/authenticated session states and 64
across both initialized-state encodings, and invalid complementary codes.
Reflection is confined to modeled state faults; normal storage and
reference-transfer operations use APDUs and SIOs. These modeled faults do not
demonstrate physical-fault resistance.

jCardSim 3.0.6 returns raw SIOs without implementing the context switches needed
by `getPreviousContextAID()`. `tests.ShareableSimulatorRuntime` adds test-only
SIO proxies, preserves object identity, switches to the owner and restores the
previous context after returns/exceptions. Applets in the same package retain
their shared context. This is not a complete Java Card firewall or GP emulator;
production code has no simulator fallback or relaxed caller check.

Both production CAPs convert and verify for Java Card 3.0.5 using the 3.1
converter, with zero converter errors/warnings. Logs and preliminary probes are
ignored under `.research/safe-auth/`; evidence above is recorded here so memory
does not depend on those temporary files. SafeShareable Javadoc and the
architecture note describe the current authorization boundary.

No physical card was accessed, no applets or card data were changed, and no
performance/physical fault-injection result is claimed. New Safe sessions and
item views allocate objects; target-card overhead remains unmeasured. The user's
staged Monoid changes and unrelated files were preserved. No commit or push was
performed.
