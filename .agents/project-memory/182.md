# Extend Bundle

[user] 恢复此前暂缓的 Extend Bundle，并明确批准分开数据互通资格与扩展审批资格，不为数据互通再刷 A。随后要求 A 阶段叫 extend、B 阶段叫 approve，并授权一起检查 Create、Join 的冗余输入输出后调整。最终批准拆出 Approve Bundle Extension，四条命令统一使用 data，批准响应直接作为 Join 请求。

[agent] 当前流程为 A Extend、B Approve、C Join。Extend 与 Approve 分别使用独立指令，不再使用 action；不维护待定成员、同步状态或公开双签安装凭据。APDU 仍由 Monoid 处理，Identity 独立持有全部密码学操作和 Secret PIN。

## 当前接口

所有步骤分别要求操作卡自身的 Secret PIN。

- `0x23 Create Bundle`：`{publicKeys: byte[][]}` → `{bundle: byte[], data: byte[][]}`。只传其他接收卡的公钥，至少一个，不得重复或包含本卡；Identity 自动加入自己的公钥。`data[i]` 严格对应 `publicKeys[i]`，删除每份包对公钥的重复回显。创建卡公钥已在前置收集中获得，不再返回；已有本地 Bundle 时拒绝 Create。
- `0x25 Extend Bundle`，A：`{publicKey:C}` → `{data}`。`data` 是绑定当前 Bundle、A 和 C 的已认证扩展请求，主机原样交给 B。
- `0x26 Approve Bundle Extension`，B：`{data}` → `{publicKey:B, data}`。验证同 root 的另一 Identity 发起的请求后，仅向已绑定的 C 加密入组包。返回 B 的实际 Identity 公钥，完整响应可直接作为 Join 请求；不重复返回未改变的 Bundle hash。
- `0x24 Join Bundle`，C：`{publicKey:B, data}` → `{bundle}`。HPKE Auth 需要实际发送方的完整公钥；返回实际加入的 Bundle hash，与 B 的 Hello 比较。初始 Create 入组同理使用创建卡公钥，hash 则与 Create 响应比较。

Create/Join 使用同一入组密文格式。输入公钥均为完整65B未压缩P-256点，Bundle hash为32B SHA-256；显示ID不参与授权。Create调用方只提交其他接收者；Identity内部排序的入组快照仍包括本卡。

A、B 不发布新名单；C 成功 Join 后立即能与旧成员互通，也能参与后续扩展。无须再次刷 A，也没有 sync 分支。

只有 Bundle Join 的 senderPublicKey 字段改为 publicKey；条目 Import 的 senderPublicKey 保持不变。内部密码学实现继续使用 request、senderPublicKey 等描述性变量名，不因外部字段统一而混淆各阶段数据的含义。

IdentityShareable 的对应入口：

```java
CommunicationDataShareable createBundle(byte[] publicKeys);

CommunicationDataShareable extendBundle(byte[] publicKey);

CommunicationDataShareable approveBundleExtension(byte[] request);

byte[] joinBundle(byte[] senderPublicKey, byte[] data);
```

`createBundle` 的 publicKeys 是拼接的其他接收者公钥，返回包严格按输入顺序拼接。扩展阶段命名及参数语义在 Monoid、Safe、Identity 全链条一致。以上入口只允许固定 Monoid AID，要求当前调用方已通过 Secret PIN，不允许在通信回调中重入。跨Identity入参为global数组，结果通过SafeDataSource流式输出，不把完整结果复制到RAM。

## 两种资格

数据解密检查同 Bundle hash、按实际发送身份及调用方 AID 派生的密钥和 GCM tag，继续拒绝自身发送身份。取消本地成员名单查询。Bundle root 未变化，所以 C 可以解开已有历史数据。

扩展请求同时证明：持有当前 Bundle root，并持有另一 Identity 的私钥。root-HMAC 和 Identity ECDSA 签名均绑定完整发起者公钥、目标公钥、Bundle hash 和版本。B 拒绝自己签发的请求。普通数据加密不提供扩展域的 MAC 或签名，也不能输出 root。

不能在 A 首次 Extend 后就赋予软件目标 C 审批资格：C 虽有自己的私钥，却没有 root，无法将 A 的请求改成以 C 为发起者、D 为目标的新请求。只有签名不够；只有 root-MAC 也不够，后者不能证明第二身份参与。

## 二进制格式

```text
statement = 01 || bundleHash[32] || initiatorPublicKey[65] || targetPublicKey[65]
domain = ASCII("Monoid Bundle Extension")
mac = HMAC-SHA256(root, domain || statement)
signature = ECDSA-SHA256(IdentityPrivateKey, domain || statement || mac)
request = statement || mac[32] || u8(signatureLength) || signature
```

字段偏移依次为0/1/33/98/163/195/196。ECDSA为DER，最大72B；长度必须与完整报文严格一致。HMAC覆盖前163B，ECDSA覆盖前195B，两者均先加域。BundleExtension只提供专用extend/requireRecipientPublicKey，不是通用签名入口；Reset丢弃旧Identity的复用引擎。字段改名未改变此二进制格式。

B验证后用现有01 HPKE入组格式，仅向绑定的C加密root。快照为B的本地入组快照加C并排序去重，仍绑定HPKE info。快照只表示该入组包的上下文，不再是实时授权表。同root重Join幂等并保留原快照，不因其他成员变化而失败；不同root拒绝。

## 边界与重试

请求无时限、无需同时在场，不是一次性nonce。重放仅允许相同目标，B可重新生成该目标入组包；A/B阶段没有需要回滚的Bundle状态。不能通过单身份Extend/Approve释放root。添加新成员不撤销旧成员，也不撤销历史请求或密文；资源迁移另行完成。

本方案依赖正常Identity代码和受保护的root。双卡及各自Secret PIN允许为软件目标入组并恢复数据，仍在已认可的恢复边界内。仅数据互通资格不自动构成第二卡审批证明。

## 代码组织整理

[user] 指出近期部分文件偏离仓库原有代码风格，并要求多用空行。

[agent] 对照早期 Command 和现有数据源结构收敛本轮实现：Extend 两种固定响应在对应分支直接写出；BundleExtension 用 requireApprovedPublicKey 表达验证后返回目标公钥，computeMAC 表达计算 MAC，长度常量替代重复数字。ItemCipher.Result 的跨 Identity 数据读取职责与条目密码学无关，原样移为包内 SafeIdentityData，由条目和 Bundle 共用，授权检查、global/APDU 缓冲路径及复制行为保持一致。Inplate 单个 HMAC 生成目标改为显式配置，生成内容不变。
