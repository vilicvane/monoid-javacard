# Monoid Java Card signing lifecycle

Source: `../records.md`, records 12–20, 34, 37–43, 47–51, 57–61, 63–71, 73–80, 106, 111–113, 115–116, 121–127 and 132–133. Treat these records and their references as authoritative and keep them up to date.

- Record133 promotes the P-256/Monoid-001 adaptations into production. Initialize version scratch, P-256 keys/public scratch, HMAC buffers/keys, Monoid001 scratch, Weierstrass public results and ECDSA outputs with RESET. DerivedKey returns RESET operation copies on both first use and cache hits. Relevant native factories use externalAccess=true; jCardSim alone gets a generated SHA-512 factory adaptation, never the CAP source. Command authentication/transport and other algorithms' own workspaces are unchanged. RESET still clears on reset and does not make a working buffer persistent or remove normal GC; the shared derivation cache policy stays the same. See133 for lifecycle tests, physical regression and boundaries.

- Record132 proves the selected-applet distinction on physical card55690320: entering Monoid through SIO restores its context but does not select it. Existing DESELECT access throws SecurityException and allocation throws ILLEGAL_TRANSIENT. P-256 SIO workspaces/keys need RESET; native engines must also support execution while their owner is not selected. An isolated SHA-512 externalAccess=true change fixes uncached derivation after RESET alone failed. Calling the engine only inside its owner context does not avoid its internal DESELECT restriction. KeyBuilder's final boolean is keyEncryption, not externalAccess. Keep ordinary Command auth DESELECT so switching back requires authentication; do not blanket-change transport/auth/all algorithms. Twelve complete APDU/SIO cycles have stable query-time RESET2130/DESELECT2128B, not measured peaks or independent pools. Confirmed unpower clears Safe auth; cached PIN revalidation restores it. Card.disconnect(true) did not actually clear the marker on this reader. That stage used research copies; record133 subsequently applies the P-256 adaptations to production. See132 for independent signing, replacement and cleanup evidence.

- Record121 replaced response-array growth with on-demand256B chunks; record122 supersedes its all-transient APDU storage policy. Promotion copies the written APDU prefix once, then growth retains every previous chunk. A persistent128-reference table preserves the existing short offset range without reserving payload RAM. - Record 116 diagnoses actual allocation failures before choosing lifecycle changes: response writer OOM (`6DF2`), redundant Import sender-public-key global copy (`6C42`), then 258B private plaintext OOM (`6E62`). Results are now global directly, CommandImport reads binary fields into global arrays without Safe wrapper recopying, and short responses borrow the current APDU buffer dynamically without storing its reference. - Record 116 measures initialized crypto-context RAM by within-version before/after queries: original reset availability 1880→667B (1213B increment), compact 2136→1508B (628B increment, 585B less). - Record 111 implements unified derivation caching after Monoid-001 commit 16070d4. The user selected directly converting the three static libraries: BIP32Derivation, SLIP10Ed25519Derivation and Monoid001Derivation extend KeyDerivation, with Keystore reusing their instances. The subsequent user request replaces the original single-entry design with one global persistent pool of 32 entries total, shared by all three instances. Lookup matches owner identity and complete master/input bytes. FIFO hits do not refresh order or write persistent state; each hit returns a fresh transient copy. Misses call protected deriveKey, construct all persistent copies, then transactionally publish the entry and advance the cursor. Failed derivation preserves entries and cursor. KeyDerivation.init/dispose participates in Applet installation/uninstallation to release static references. Seed-to-master HMAC remains outside the cache. Current Safe authorization/existence checks remain before cache access, so changed source bytes miss and deleted sources cannot be used. Retained cache bytes last until eviction/uninstall, without immediate deletion erasure. Taproot modifies only an operation-local copy. All 183 simulator tests and production/isolated CAP checks pass; see 111 for scope and evidence.

- Record 69 clarifies that application-level plaintext persistent storage is compatible with Java Card object isolation and controlled interfaces; Safe already stores seed/master this way. Do not require EncryptedBuffer merely because storage is persistent. Encryption with a transient key additionally makes interrupted-operation residue undecryptable, which is not an established requirement. - Pure Ed25519 requires two complete reads of the original Message, not simultaneous RAM residency of all bytes. Current ByteSource reads span the transient prefix and persistent overflow chunks directly. The complete request remains stored until the synchronous signature operation finishes, but its payload RAM allocation is bounded to 512B. Client replay would require strict consistency validation and is not approved. Do not repeat the earlier claim that full-message RAM storage is an algorithm requirement, or that encrypted persistent buffering has no value regardless of the signing interface.
- Use API availability only to select implementation branches. Card compatibility and behavior validation belong in documentation and development tests, not Applet self-tests or model/version tables. MathSupport and all card-type configuration have been removed. The byte-array refactor requires XY ECDH, as the full Applet already did for secp256k1; unused X-only/PACE/ECDSA recovery paths are removed. LibMath privately retains one shared RSA512 private key/Cipher and 160B of transient array scratch, with init/dispose managed by Applet installation/uninstallation. MathResources is removed. Each arithmetic method initializes the ranges it consumes without post-operation erasure; nested modExp preserves the outer modMult/modInv intermediates. CurveED25519 does not own the math resources. RSA arithmetic uses the established private/NOPAD implementation; simulator-specific adaptations live in gradle/simulator.gradle and are excluded from CAP.
- Prefer simple operation ownership and as much available RAM as possible, while preserving expensive initialization according to the threshold below. Clearing contents does not release allocated capacity. Retaining the current complete `CurveED25519` also retains its transient workspace; do not claim that shared context reuse already satisfies the earlier goal of returning all working RAM.
- Assume the execution environment is trusted. Do not wipe fetched key/master copies, crypto scratch or transport buffers merely to erase residual data. Preserve algorithmic initialization and padding, hash resets, key invalidation, reference release and GC requests. Preserve authentication state and unfinished request/response data until their own lifecycle ends; intermediate APDUs are not complete commands.
- Preserve the existing shared cryptographic objects. The user considers even tens of milliseconds enough reason to retain sharing; an initialization cost over 200 ms is substantial. Do not justify repeated construction by comparing it with seconds-long software Ed25519 signing, whose latency is tolerated because the card lacks native support. Decide reuse of newly integrated contexts using measured initialization costs. Reuse initialized resources and overwrite operation inputs before use; do not rely on previous operations' transient contents remaining valid.
- Request transport owns fixed 256B chunks: the first two use transient RAM, and overflow uses plaintext persistent arrays allocated only when needed. The 512B threshold counts the complete CBOR request including metadata. The persistent Object[32] reference table survives reset so SELECT can release their references even after transient length/state clears. Completion/errors/replacement/SELECT/deselect release every chunk; growth does not copy or discard earlier chunks. A new request replacing unfinished input explicitly requests GC. Ed25519 reads the Message range twice through ByteSource without allocating a Message copy or contiguous assembly array. Whole single frames borrow the APDU buffer dynamically, without retaining its global reference or erasing it after sendBytesLong. EncryptedBuffer remains removed. Record 116 similarly lets complete responses of at most 256B borrow the current APDU after request parsing; larger response arrays are allocated lazily, retained only while pending, and released on completion, cancellation, deselection or send failure (record 68; record 75 removes byte erasure). Other decoded copies can remain until GC/deselect; do not claim all command RAM is already erased or freed.
