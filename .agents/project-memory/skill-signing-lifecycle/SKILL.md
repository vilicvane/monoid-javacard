# Monoid Java Card signing lifecycle

Source: `../records.md`, records 12–20, 34, 37–43, 47–51.

Implementation status: the operation-lifecycle draft was stashed as `285d6abd37951dd46bf57b5cb5baf18ebe635525`; incremental rewriting starts from `af4f994`. The current Ed25519 split uses a `CurveED25519` context shared with `LibED25519`; signing clears scratch in `finally`, and the operation owner is responsible for clearing the key. `EdwardsCurve` now exposes explicit `init`/`dispose` and shared lookup methods matching `WeierstrassCurve`; Applet installation/uninstallation now call those lifecycle methods, and Keystore uses shared lookup. Keystore now connects SLIP derivation, shared key import and signing; it clears the fetched key copy, master/derived data and expanded key in finally. LibSLIP10Ed25519.derive and LibED25519.sign each allocate their scratch locally once per call and clear it in finally; native engines remain shared. Authenticated seed/master short-APDU paths are simulator-tested; hardware integration is still unverified. The draft's blanket policy of recreating all contexts per command is superseded by the initialization-cost preference in record 38. Measured results below describe the stashed draft, not current results.

- The core workload is one signature using one algorithm per operation.
- Use API availability only to select implementation branches. Card compatibility and behavior validation belong in documentation and development tests, not Applet self-tests or model/version tables. MathSupport and all card-type configuration have been removed. The byte-array refactor requires XY ECDH, as the full Applet already did for secp256k1; unused X-only/PACE/ECDSA recovery paths are removed. LibMath privately retains one shared RSA512 private key/Cipher and 160B of transient array scratch, with init/dispose managed by Applet installation/uninstallation. MathResources is removed. Each arithmetic method clears only its own scratch in finally; nested modExp preserves the outer modMult/modInv intermediates. CurveED25519 does not own the math resources. RSA arithmetic uses the established private/NOPAD implementation; simulator-specific adaptations live in gradle/simulator.gradle and are excluded from CAP.
- Prefer simple operation ownership and as much available RAM as possible, while preserving expensive initialization according to the threshold below. Clearing contents does not release allocated capacity. Retaining the current complete `CurveED25519` also retains its transient workspace; do not claim that shared context reuse already satisfies the earlier goal of returning all working RAM.
- Clear command-owned working data on both success and failure: decoded input copies, derivation intermediates, private keys and signing scratch. Erase sent response bytes and replaced buffers. Preserve authentication state and unfinished request/response data until their own lifecycle ends; intermediate APDUs are not complete commands.
- Preserve the existing shared cryptographic objects. The user considers even tens of milliseconds enough reason to retain sharing; an initialization cost over 200 ms is substantial. Do not justify repeated construction by comparing it with seconds-long software Ed25519 signing, whose latency is tolerated because the card lacks native support. Decide reuse of newly integrated contexts using measured initialization costs. Reuse initialized resources while clearing operation secrets, and do not rely on previous operations' transient contents remaining valid.
- Release request encryption working objects and response arrays at their respective transport completion/cancellation boundaries. Authentication and transport control state, plus deliberately retained reusable cryptographic resources, have separate lifetimes. The persistent ciphertext storage can be reused without retaining its working RAM.
- The tested card collects unreachable objects at an APDU boundary. Normal completed operations already provide one; a new single request replacing unfinished transport uses the existing empty `6100` / GET RESPONSE continuation at the transport layer.
- Selection/deselection cleanup must handle interrupted operation secrets and abandoned request/response references. Reset can clear transient contents while persistent references survive; this does not itself require discarding every reusable cryptographic resource.
- Measure initialization, key import and signing separately, along with full-operation latency and idle RAM after collection. State whether each result uses a fresh or reused context.
- Evaluate initialization cost before deciding which shared objects to retain. The old shared secp256k1/HMAC objects already coexisted with command-end GC requests; their original motivation is not established. Their constructors allocate native engines/key containers but do not perform the per-key signing/derivation work. Keep reuse within one derivation distinct from caching across commands.
- Historical 2026-10-10 card measurements estimated an approximately 1.713-second Ed25519 context recreation increment for the same seed/path; secp256k1/HMAC/exception objects together initialized in 266 ms. These are old APDU-level measurements, not individual current-constructor timings. Before record 47, Ed25519 initialization triggered two random EC keypair generations; an initial ignored simulator experiment passed all five RFC8032 vectors with those generations disabled, but that experiment alone did not establish physical-card compatibility or performance.
- The preceding historical keypair-generation limitation is resolved by record 47: current CurveED25519 allocates a shared native private-key container and XY engine directly, without generating random keypairs. Same-card 2026-10-12 isolated-probe comparison measured context+signer construction 1808→342ms, SLIP four-level derivation+import 939→673ms and 150B Solana signing 2088→1417ms (APDU times; derivation/signing exclude separate context/deriver initialization). Free deselect RAM after context+signer creation increased 1616→3088B, with imported key 1520→2992B. Ten physical groups verified shared-context reuse, explicit clear, deselect and reset/reimport; all signatures matched independent host results. These are component tests, not a completed Monoid Sign API flow. Keep shared resources while erasing secrets; no state depends on preserved transient contents.
- Verified on the 2026-10-11 test card: operation cleanup and reset/SELECT recovery return the same 3712-byte deselect-RAM reading, including the query's response allocation. Six independent 150-byte SLIP-0010/Ed25519 operations took 5.906–5.963 seconds; these are full-operation times, not constructor or primitive-only timings.
- Keep shared command cleanup in an outer `finally` around private execution. The current converter cannot encode exception-reference gaps of 255 bytes or more; duplicating a large `finally` across many catch branches can trigger this defect. Preserve failure cleanup and rethrow semantics when restructuring, and validate the generated CAP as well as simulator tests.

- Record 48 reorganized math resources into LibMath and moved erasure to individual arithmetic calls. Forty simulator tests, Hello 9000 and CAP conversion/verification passed; hardware timings and free-RAM figures from record 47 predate this change and have not been remeasured. The ignored historical card probe must be adapted before reuse.
