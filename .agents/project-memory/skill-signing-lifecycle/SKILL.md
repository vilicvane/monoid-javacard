# Monoid Java Card signing lifecycle

Source: `../records.md`, records 12–20, 34, 37–43, 47–51, 57–61, 63–71 and 73–76.

Implementation status: the operation-lifecycle draft was stashed as `285d6abd37951dd46bf57b5cb5baf18ebe635525`; incremental rewriting starts from `af4f994`. The current Ed25519 split uses a `CurveED25519` context shared with `LibED25519`; signing resets its hash in `finally`, and the operation owner invalidates the imported key. Record 75 establishes a trusted execution environment and removes defensive byte erasure; functional initialization, validity transitions and reference release remain. Record 76 verifies the current 0x0501 direct-item implementation and this cleanup with 74 simulator tests, CAP checks and 16 physical groups containing 32 independent signature checks. The baseline uses old record 73 Monoid logic with the same corrected Safe as current; both runs pass, including repeated curve switching and physical reset recovery. `EdwardsCurve` now exposes explicit `init`/`dispose` and shared lookup methods matching `WeierstrassCurve`; Applet installation/uninstallation now call those lifecycle methods, and Keystore uses shared lookup. Keystore connects SLIP derivation, shared key import and signing; it invalidates the expanded key in finally without wiping fetched or derived copies. LibSLIP10Ed25519.derive and LibED25519.sign each allocate their scratch locally once per call without wiping it afterward; native engines remain shared. Records 70–71 extend request buffering after response cleanup was committed as ecae74d: at most the first 512B of assembled request payload uses RAM, and later 256B chunks are plaintext persistent arrays allocated on demand. ByteSource reads these directly without a Message copy. All 69 simulator tests, CAP checks and nine physical groups pass, including 14 independently verified signatures up to exact 8192B requests containing seed 8096B/master 8114B Messages. Response arrays are released after completion or cancellation. The draft's blanket policy of recreating all contexts per command is superseded by the initialization-cost preference in record 38. Historical measurements below apply only to their named implementation stages.

- The core workload is one signature using one algorithm per operation.
- Record 76 provides the current same-card comparison after the type split and defensive-erasure removal. Each version passes 16 groups and 32 independently verified signatures, including Ed25519 → BIP32/ECDSA → Ed25519 reuse, direct Weierstrass queries/signing, maximum requests, cancellation and reset/re-authentication recovery. Both versions use the same Safe with its full-capacity remove bug corrected. Three-repeat median complete Sign times are direct Ed25519 0B 2.279→2.342s (+2.8%), direct Ed25519 1024B 2.519→2.570s (+2.0%), and BIP32 ECDSA 1.228→1.225s (effectively unchanged). These short-message results show no speedup; the tested maximum-size requests are slightly faster. The comparison includes all current Monoid changes and does not isolate the cost of erasure removal. Times include request transport, key import/derivation and response; they exclude authentication, host verification and memory probes, and are not primitive-only timings. Idle transient availability returns to 2320B in both versions after all recovery and removal tests, including the memory query allocation. These are not peak measurements. Persistent readings saturate at 32767 and do not prove absence of EEPROM growth. All 74 simulator tests and CAP checks pass. Probe packages were removed, registry snapshots match exactly, original applets remain selectable and both bridges exit successfully; detailed evidence is in 76.md.
- Record 73 adds independent Ed25519 items (initially 0x0402; record 74 changes the current type to 0x0501): store a 32B private-key seed, import it directly into the shared curve and skip SLIP-0010. Record 75 removes fetched-seed and expanded-key byte erasure while retaining key invalidation. For the frozen record 73 version, seventy-two simulator tests, CAP checks and six physical groups pass; seven signatures independently match, including random/all-zero seeds and a 1024B fragmented Message. Complete direct Sign takes 2.240–2.309s for tested 0–26B Messages and 2.517s for 1024B, including transport and key import. Post-group idle transient readings stay 2320B, including the query allocation, not peaks. Probe packages were removed, registry snapshots match and original applets remain selectable. Detailed evidence belongs in 73.md.
- Record 68 fixes the retained-response bug: storage is allocated on demand and erased/released after completion/cancellation/deselect/send failure, while the writer object remains shared. All 65 simulator tests, CAPs and six physical groups pass. A 600B value read no longer prevents seed 1184B/master 1458B signing; comparable memory-query readings recover to 2256B. These are tested sizes, not remeasured maximum limits. The following record 67 limits describe the code before this fix.
- Record 69 clarifies that application-level plaintext persistent storage is compatible with Java Card object isolation and controlled interfaces; Safe already stores seed/master this way. Do not require EncryptedBuffer merely because storage is persistent. Encryption with a transient key additionally makes interrupted-operation residue undecryptable, which is not an established requirement. Records 70–71 approve and implement plaintext persistent overflow after a 512B transient request budget. Successful uninstall/reinstall does not inherit old applet-owned objects; reset/power loss preserves persistent objects, and reinstalling only Monoid preserves separate Safe data. Interrupted transport data remains reachable for reference release on the next SELECT; record 75 removes byte erasure, and reset alone does not erase persistent bytes.
- Record 67 measured historical RAM-only capacity on the same card, with 255B frames, four-level hardened Solana path and warmed contexts: normally seed 1184B / master 1458B; after a 600B value response, seed 928B / master 946B. Every maximum-plus-one failed with INTERNAL; successful signatures and post-failure 150B recovery signatures independently verified. Idle post-signing RAM was respectively 2256B and 1904B. Retained response capacity affected later signing, and even the previously verified 1167B failed after this large response. These were scenario-specific boundaries, not a general API limit, worst-case guarantee or peak-memory profile. Records 68 and 71 supersede that storage behavior. No production changes were made during that capacity measurement; isolated packages were removed and original applets preserved.
- Pure Ed25519 requires two complete reads of the original Message, not simultaneous RAM residency of all bytes. Current ByteSource reads span the transient prefix and persistent overflow chunks directly. The complete request remains stored until the synchronous signature operation finishes, but its payload RAM allocation is bounded to 512B. Client replay would require strict consistency validation and is not approved. Do not repeat the earlier claim that full-message RAM storage is an algorithm requirement, or that encrypted persistent buffering has no value regardless of the signing interface.
- Use API availability only to select implementation branches. Card compatibility and behavior validation belong in documentation and development tests, not Applet self-tests or model/version tables. MathSupport and all card-type configuration have been removed. The byte-array refactor requires XY ECDH, as the full Applet already did for secp256k1; unused X-only/PACE/ECDSA recovery paths are removed. LibMath privately retains one shared RSA512 private key/Cipher and 160B of transient array scratch, with init/dispose managed by Applet installation/uninstallation. MathResources is removed. Each arithmetic method initializes the ranges it consumes without post-operation erasure; nested modExp preserves the outer modMult/modInv intermediates. CurveED25519 does not own the math resources. RSA arithmetic uses the established private/NOPAD implementation; simulator-specific adaptations live in gradle/simulator.gradle and are excluded from CAP.
- Prefer simple operation ownership and as much available RAM as possible, while preserving expensive initialization according to the threshold below. Clearing contents does not release allocated capacity. Retaining the current complete `CurveED25519` also retains its transient workspace; do not claim that shared context reuse already satisfies the earlier goal of returning all working RAM.
- Assume the execution environment is trusted. Do not wipe fetched key/master copies, crypto scratch or transport buffers merely to erase residual data. Preserve algorithmic initialization and padding, hash resets, key invalidation, reference release and GC requests. Preserve authentication state and unfinished request/response data until their own lifecycle ends; intermediate APDUs are not complete commands.
- Preserve the existing shared cryptographic objects. The user considers even tens of milliseconds enough reason to retain sharing; an initialization cost over 200 ms is substantial. Do not justify repeated construction by comparing it with seconds-long software Ed25519 signing, whose latency is tolerated because the card lacks native support. Decide reuse of newly integrated contexts using measured initialization costs. Reuse initialized resources and overwrite operation inputs before use; do not rely on previous operations' transient contents remaining valid.
- Request transport owns fixed 256B chunks: the first two use transient RAM, and overflow uses plaintext persistent arrays allocated only when needed. The 512B threshold counts the complete CBOR request including metadata. The persistent Object[32] reference table survives reset so SELECT can release their references even after transient length/state clears. Completion/errors/replacement/SELECT/deselect release every chunk; growth does not copy or discard earlier chunks. A new request replacing unfinished input explicitly requests GC. Ed25519 reads the Message range twice through ByteSource without allocating a Message copy or contiguous assembly array. Whole single frames borrow the APDU buffer dynamically, without retaining its global reference or erasing it after sendBytesLong. EncryptedBuffer remains removed. Response arrays are allocated lazily, retained only while pending, and released on completion, cancellation, deselection or send failure (record 68; record 75 removes byte erasure). Other decoded copies can remain until GC/deselect; do not claim all command RAM is already erased or freed.
- Record 71 validates the persistent extension with 69 simulator tests, CAP conversion/verification, nine physical groups and 14 independently verified signatures. Seed/master 4032B Messages and exact 8192B requests (seed Message 8096B, master Message 8114B) pass in both CBOR field orders. At the complete-request ceiling, full Sign transport with 255B frames plus derivation and signing takes seed 4.689–4.696s/master 4.525–4.528s. Cancellation, invalid continuation, physical reset, 8193B rejection/recovery and signing after a 600B response pass. Fresh idle transient RAM is 2416B and warmed RAM is 2320B; repeated large requests, large responses and recovery return to 2320B. The first query after the 600B Get reads 2304B, with the next returning to 2320B. Persistent-memory readings saturate at 32767 and cannot establish absence of EEPROM growth. Both isolated packages were removed, registry snapshots match exactly, original applets select successfully and the reader is released.
- Historical card tests observed collection at APDU boundaries. The rewritten receiver requests GC after completed/failed requests and transport cancellation, but does not use the draft's empty `6100` deferred-execution boundary; record 63 confirms that a last-frame 1024-to-1280-byte expansion leaves only 16 B free before parsing on the test card. A 192-byte-fragment diagnostic control succeeds because expansion occurs before the last APDU; this is evidence about GC timing, not an adopted workaround.
- Selection/deselection cleanup must reset interrupted operation state and release abandoned request/response references. Preserve super.deselect before Monoid cleanup rather than assuming the parent call is unnecessary. Reset can clear transient contents while persistent references survive; this does not itself require discarding every reusable cryptographic resource.
- Keep uninstall disposal separate from operation cleanup. Command.dispose only drops static references; clearTransport belongs to selection/deselection and request lifecycle handling. Use writer.reset directly rather than a clear wrapper with identical behavior.
- Measure initialization, key import and signing separately, along with full-operation latency and idle RAM after collection. State whether each result uses a fresh or reused context.
- Evaluate initialization cost before deciding which shared objects to retain. The old shared secp256k1/HMAC objects already coexisted with command-end GC requests; their original motivation is not established. Their constructors allocate native engines/key containers but do not perform the per-key signing/derivation work. Keep reuse within one derivation distinct from caching across commands.
- Historical 2026-10-10 card measurements estimated an approximately 1.713-second Ed25519 context recreation increment for the same seed/path; secp256k1/HMAC/exception objects together initialized in 266 ms. These are old APDU-level measurements, not individual current-constructor timings. Before record 47, Ed25519 initialization triggered two random EC keypair generations; an initial ignored simulator experiment passed all five RFC8032 vectors with those generations disabled, but that experiment alone did not establish physical-card compatibility or performance.
- The preceding historical keypair-generation limitation is resolved by record 47: current CurveED25519 allocates a shared native private-key container and XY engine directly, without generating random keypairs. Same-card 2026-10-12 isolated-probe comparison measured context+signer construction 1808→342ms, SLIP four-level derivation+import 939→673ms and 150B Solana signing 2088→1417ms (APDU times; derivation/signing exclude separate context/deriver initialization). Free deselect RAM after context+signer creation increased 1616→3088B, with imported key 1520→2992B. Ten physical groups verified shared-context reuse, explicit clear, deselect and reset/reimport; all signatures matched independent host results. These are component tests, not a completed Monoid Sign API flow. Keep shared resources; no state depends on preserved transient contents. Record 75 removes the historical byte-erasure requirement.
- Verified on the 2026-10-11 test card: operation cleanup and reset/SELECT recovery return the same 3712-byte deselect-RAM reading, including the query's response allocation. Six independent 150-byte SLIP-0010/Ed25519 operations took 5.906–5.963 seconds; these are full-operation times, not constructor or primitive-only timings.
- Keep shared command cleanup in an outer `finally` around private execution. The current converter cannot encode exception-reference gaps of 255 bytes or more; duplicating a large `finally` across many catch branches can trigger this defect. Preserve failure cleanup and rethrow semantics when restructuring, and validate the generated CAP as well as simulator tests.

- Record 48 reorganized math resources into LibMath and moved erasure to individual arithmetic calls. Forty simulator tests, Hello 9000 and CAP conversion/verification passed; hardware timings and free-RAM figures from record 47 predate this change and have not been remeasured. The ignored historical card probe must be adapted before reuse.

- Record 63 measured complete authenticated seed-derived 150-byte Sign requests at 2.634–2.660 seconds and 512-byte requests at 2.905–2.915 seconds. Idle transient RAM was 2320 B after short signing, dropping to 1968 B after the response writer expanded for a 600-byte value. Reset/re-authentication and subsequent signing passed, but reset did not release that retained capacity. These historical integration measurements predate records 65, 68 and 71 and must not be confused with the earlier component-only timings.
- Record 65 supersedes the contiguous-request implementation: all 14 physical groups pass, including 1167B seed/master Message first/last with 255B frames (seed 2.980–2.993 s), 600B Create/Get and replacing 1020B of abandoned input. Seed-derived 150B signatures take 2.750–2.775 s, about 0.1 s slower than the preceding baseline; 512B takes 2.913–2.923 s. Fresh idle transient RAM is 2352B (64B fixed-reference-table cost), 2256B after signatures and 1904B after large responses and subsequent signing. Request payload at the previous failure point is now 5×256B instead of 1024+1280B, excluding metadata/workspace. These observations establish the tested flows, not all possible message sizes, peak-memory profiles or large-signing-after-large-response combinations. Both isolated packages were fully removed and original applications preserved.
