# Encoded results and conservative repeated checks — 2026-10-15

[user] Identified that redundant authorization values still feed conditional
branches. Requested wrappers that repeat checks and return encoded truth values.
The conservative result depends on the predicate: validation must pass every
read, whereas one blocked result is enough to deny access. This is not a general
rule to always return false or use majority voting.

[user] Pointed out that a sign-bit flip can make a countdown negative. Initially
preferred a count such as 31 over 32, then explicitly reduced the count to 3 and
the goal to resistance against a single flip. Full-width short encodings and
existing auth/complement pairs should remain; iteration count and encoding width
are separate choices. This supersedes the earlier 31-round proposal.

[agent] LibSecurity.check(Condition, short conservativeResult) owns the reusable
three-round loop. Each round calls Condition.check afresh and encodes its boolean
as SAFE_TRUE/SAFE_FALSE before comparing with the full conservative short. A
conservative result or invalid/incomplete counters returns conservativeResult.
The countdown terminates on exactly zero, checks its range 1..3 each round, and
checks its independently updated completed count and final remaining count
separately. After all three non-conservative results, it returns the bitwise
complement of conservativeResult. Both valid codes are complements, so an
invalid code stays invalid rather than falling through to an allowed result.
Invalid policy arguments throw a security exception before evaluating the
condition; callback exceptions propagate.

MonoidSafeApplet holds one instance-owned anonymous Condition that reads its
current OwnerPIN.isValidated state; no per-authentication allocation or static
callback reference is introduced. After one OwnerPIN.check, the grant path uses
LibSecurity.check(pinValidation, SAFE_FALSE) and accepts only exact SAFE_TRUE.

[user] Requested migrating the next authorization check, one location at a
time. [agent] SafeSession.assertCaller now uses an instance-owned Condition
with SAFE_FALSE as its conservative result and accepts only exact SAFE_TRUE.
Each round checks that the stored caller is non-null and freshly reads
JCSystem.getPreviousContextAID, retaining reference identity rather than AID
content equality. The callback is created once per SafeSession.

SafeSession.isAuthorized is the next single-site migration. Its instance-owned
authorizationValidation callback re-reads the auth/complement pair each round:
both zero returns false, malformed values throw 6982, and the exact authorized
pair returns true. The package-private method now returns the encoded short
from LibSecurity.check with SAFE_FALSE as the conservative result. Its only
caller, MonoidSafeApplet.isPINValidated, compares with exact SAFE_TRUE; the
public Shareable boolean remains unchanged. This does not remove boolean
branches elsewhere in the authorization chain or change the stored auth pair.

[user] Approved completing the remaining similar migrations in one batch.
[agent] The remaining Safe gates now use direction-specific repeated reads:
PIN-set is conservative true when deciding whether initialization requires
authorization, conservative false before granting or using access; blocked is
conservative true before access and when deciding to revoke all grants after
PIN checking. assertAccess checks encoded caller, PIN-set, grant and blocked
results directly, without converting through the public boolean query.
Caller admission and authenticated-session reuse require three matching reads;
revocation treats any matching read as sufficient. A reusable CLEAR_ON_RESET
Object[2] passes AID/session arguments into the callbacks and is cleared in
finally. AID reference identity, public interfaces and independent grants stay
unchanged. isPINSet remains a raw validated boolean query for SIO consumers;

Monoid Command.getAuth now repeats exact cleared/Access/Safe pair predicates
and returns the matching constant. requireAuth separately repeats the required
permission predicate without calling getAuth inside the loop. Malformed or

ACCESS_DENIED. Successful Access and Safe authentication now repeats the
read-only native/SIO validation state before publishing a grant. Monoid's PIN
initialization, PIN update, cached Safe PIN existence and blocked gates also
use the corresponding conservative policies. Native/SIO PIN comparison and
PIN update still execute once. Failed PIN attempts preserve existing Command
