# Safe Shareable physical validation and session reuse — 2026-10-14

[user] Requested real-card validation with temporary AIDs because simulator
Shareable behavior is incomplete. Also clarified that acquiring the interface
again within one tap should not clear an existing authorization.

## Implementation

[agent] `getShareableInterfaceObject` now searches the active session list by
JCRE caller AID object identity and returns the existing authorized session.
There is no getter-side `clearAuth`. A caller without an active session receives
a new unauthenticated session. Existing item views remain usable when the same
authorized session is reacquired. PIN verification still revokes that caller's
previous grant before checking; PIN updates, lockout and actual reset revoke all
grants. This supersedes record 86's getter-side revocation policy.

The lookup uses the existing transient active list. No persistent client
registry, new APDU, Shareable method, callback protocol or static reference was
added. Tests also check that reacquisition returns the same SIO object.

## Physical results

[agent] The final implementation passed:

- Initial PIN setup and rejection of unauthenticated data access.
- B cannot borrow A's grant or change the PIN before authenticating itself.
- A and B independently authenticate, then repeatedly SELECT back and forth
  while both grants and item views remain usable.
- Forwarded item read/write/remove and forwarded Safe operations are rejected
  for the wrong caller. Recovering B's own interface preserves B's own grant.
- Wrong and throwing PIN checks revoke only the caller while tries remain;
  a wrong PIN consumes one attempt. Other callers retain access.
- Repeated interface acquisition retains authorization and previously acquired
  item access for both callers.
- Successful PIN update and oversized failed update revoke both grants;
  the failed update preserves the old PIN value.
- Verified cold reset clears both callers' grants even when cached SIO objects
  remain. Correct PIN verification restores access.
- A throwing check on the last shared PIN attempt blocks both callers and
  prevents reads or PIN changes.
- Same-AID deletion/reinstallation with a continuously open PC/SC connection
  gives the replacement no grant while B retains its authorization.

The last experiment used an independent `CLEAR_ON_RESET` marker set to `5A`.
Reports are `[marker, sameAIDReference, visitCountHi, visitCountLo,
firstReferencePresent, callerAInstalled]`:

| Stage                                   | Observer bytes |
| --------------------------------------- | -------------- |
| A authenticated, observer armed         | `5A0100010101` |
| A deleted                               | `5A0100010100` |
| A reinstalled, before its observer call | `5A0100010101` |
| Replacement A invokes observer          | `5A0000020101` |

The marker stayed `5A`: deletion and installation did not reset this card under
the continuous connection. The AID object reference changed. The replacement
called Safe's getter directly and remained unauthenticated; B could still read.
Earlier runs that disconnected between host tools sometimes cleared transient
state. That cannot be attributed to the INSTALL command itself.

## Reset and compatibility limits

[agent] Java 11 `Card.disconnect(true)` and native `SCardReconnect` with
`SCARD_RESET_CARD` both left the independent reset marker unchanged on this
contactless reader/card combination. Native `SCardReconnect` with
`SCARD_UNPOWER_CARD` cleared it, and then both Safe grants were cleared too.
The harness therefore uses verified cold reset; a successful warm-reset call
alone is not evidence of JCRE reset. The exact lower-level reason for this
reader's warm-reset mapping was not established.

The JCRE specification does not promise a fresh AID object after reinstallation.
Session reuse requires either a new JCRE AID identity or transient-state clearing
between applet installations to prevent a replacement from inheriting a grant.
This physical card satisfies the former condition. A runtime that preserves RAM
and reuses the exact AID object could return the old grant to the replacement.
The current API has no separate installation-generation identifier. This is a
documented runtime compatibility boundary, not protection verified for all cards.

In jCardSim, the earlier same-reference result came from the test passing the
same static AID object into `installApplet` again. Its registration code retains
that supplied object. Tests must explicitly distinguish same bytes/new identity
from exact-reference reuse; the former models the observed physical behavior.
The test-only SIO context adapter remains necessary and is not a complete JCRE
firewall or GP implementation.

References:

- [Java Card RE 3.0.5](https://docs.oracle.com/cd/E59935_01/JCCRE.pdf),
  applet deletion and AID handling.
- [SCardReconnect](https://learn.microsoft.com/en-us/windows/win32/api/winscard/nf-winscard-scardreconnect),
  warm reset versus cold reset dispositions.
- [ACS ACR1552 manual](https://www.acs.com.hk/en/download-manual/13473/REF-ACR1552U-Series-1.06.pdf),
  PC/SC and RF control; no inference that PC/SC warm reset powers off RF.
