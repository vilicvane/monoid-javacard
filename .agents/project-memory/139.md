# Hello after merging Safe into Monoid

[user] Proposes flattening Hello after the applet merge: move publicKey and
bundle to the top level, remove safe.id and unlocked, and rename/flatten the
two PIN states to accessPIN and safePIN. Subsequently asks to verify the
design before editing implementation.

[agent] Initial source review at b8898d7 confirmed that CommandHello still had the old
optional safe request flag and nested response. Both PIN owners now reside in
Monoid; publicKey and the future Bundle key belong to the separate Identity.
The proposed top-level fields align with the merged public API, and the two
PIN states should retain number|false (zero means blocked, false means unset).

[agent] The two existing IDs have different lifetimes: MonoidApplet.id is
generated during Monoid installation; safe.id delegates to Identity's persistent
random four-byte ID. Removing the latter loses a short display label, not the
ability to identify the retained Identity through its full public key. Do not
silently reinterpret outer id as an Identity-stable identifier. The explicit
user decision below subsequently authorizes that semantic change.

[user] Clarifies that outer id primarily keyed the APP's saved Access PIN.
The intended reinstall/upgrade flow will synchronize Access PIN and Safe PIN
automatically, so outer id should instead use the existing Identity ID.

[agent] Updated contract: Hello.id delegates to Identity.getId(), retaining
the existing four-byte random Identity ID. Keeping Identity across Monoid
reinstallation preserves id; reinstalling Identity changes it. The redundant
Monoid installation ID can be removed, along with nested safe.id. Full publicKey
continues to identify cryptographic peers. The baseline id remains present even
if optional publicKey/bundle discovery is not requested. Automatic PIN
synchronization is the user's desired future installer behavior, not a feature
already implemented by this Hello change; current ReinstallMonoid still clears
both PINs and Safe data. No APP code or installer behavior changes are implied
by this design discussion.

[agent] In that initial snapshot, unlocked meant persistent MonoidApplet.safePIN != null,
not current Command authorization. checkSafeUnlocked compared that cached
PIN against the local Safe PIN before storage access. The merged normal
lifecycle initializes/clears Safe and the cache together, so the former
new-Monoid/retained-Safe binding state is no longer needed. Nonetheless the
cache could differ after interrupted PIN updates or failed validation;
the old source contained those paths. Removing the public field needed to be
paired with deliberate cleanup of the obsolete cache/unlock mechanism, while
preserving actual Access/Safe authorization and fault checks. Do not claim
that merely deleting the response field removes the implementation state.

[agent] Earlier proposal kept discovery layout separate from optional work: both PIN states can
always be returned, while Identity publicKey/bundle can remain optional. The
existing user-approved safe request selector was added to avoid needless
Identity reads; recommend renaming it identity if retaining that behavior.
Alternatively always returning Identity data permits Request={}, but is a
separate choice from flattening. Record116's historical measured public-key
increment was about30.6ms including transport, not a current post-merge result.

[user] After the restructuring, prefers removing the previous safe selector
and returning all Hello information directly.

[user] Further refines the response to required bundle:byte[]|false and
pins:{access,safe}, and removes features from Hello.

[agent] Final discovery contract uses Request={} with no safe or identity
request switch. Response always contains version, id (the existing Identity
four-byte ID), publicKey, bundle and pins. bundle is SHA-256(K) when enrolled,
otherwise false. pins.access and pins.safe each remain number|false: remaining
tries, or false when unset. Features stay available through the existing System
Information command; only the Hello copy is removed. This supersedes the optional
identity selector, absent-bundle representation, top-level accessPIN/safePIN
fields and historical safe selector/nested response.

[agent] The initial source review did not change production code. The approved
contract is now implemented: Hello0x20 accepts {} and always returns
{version,id,publicKey,bundle,pins:{access,safe}}. id is the persistent4B Identity ID,
publicKey is its65B uncompressed P-256 key, bundle is SHA-256(K)[32] or false,
and each PIN value is remaining tries or false when unset. SystemInformation0x2F
continues to carry features. The former safe selector, nested safe block,
unlocked flag, duplicate features and Monoid-generated installation ID are gone.

[agent] The obsolete persistent Safe PIN copy and checkSafeUnlocked mechanism
are removed with the response cleanup. Safe.checkAccess validates current Command
Access/Safe authorization, verifies that Safe PIN is set and not blocked, and
grants internal storage access with the existing encoded/complement and repeated
checks. Sensitive operations still require Safe authorization. Ordinary
Access-authorized operations do not automatically recheck the Safe PIN or reset
its failed-attempt counter. This preserves actual PIN verification while removing
the former cross-applet unlock cache.

[agent] The Identity implementation and API now use monoididentity,
MonoidIdentityApplet and IdentityShareable; `MONOID_IDENTITY_*` retains the existing
AID allocation. README, cbor-field-order.json and current Identity/Bundle
documentation follow the implemented contract. Automatic APP PIN synchronization
is still outside this change; ReinstallMonoid still clears both PINs/data and
retains Identity and Bundle. These statements supersede the earlier optional
discovery, nested response, installation-ID and PIN-cache proposals.
