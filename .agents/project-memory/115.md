## Design findings and proposals

[agent] Keep dependency direction Monoid → Safe → Identity. Identity must not
import Safe classes or retain Safe-owned objects that prevent Safe deletion.
Long-lived keys survive Safe replacement. The initial proposal to retain recovery
authorization in Identity was rejected by the user below; PIN and authorization
remain in Safe. An AID identifies a caller but does not authenticate its code.
Explicitly complete backup before uninstalling; do not rely on an uninstall
callback for the only recoverable copy.

[agent] A retained Identity can also support same-card encrypted export and
restore around a Safe update. Its persistence is conditional on retaining that
Identity instance, not an immutable physical-card guarantee. A second-card backup
remains useful when the original card or Identity is lost.

[agent] Existing CommandGet and authorized SafeShareable access can return item
data in plaintext. An encrypted backup path can keep plaintext out of that path,
but cannot claim to defeat an APP already holding the Safe PIN. Likewise,
alternating cards and exchanging self-signed public keys cannot by themselves
authenticate the first peer key against a malicious intermediary. Initial trust,
pairing persistence and any changes to plaintext export permissions are unresolved.

[agent] Copy item index/key/alias/data without re-deriving the index. Existing Set
can change data, while ordinary Monoid Create checks the data-derived index for
known key types, so blindly replaying Create is not a complete restoration design.
PINs, applet IDs and derivation caches are not selected-item data.

## PIN-free Identity boundary

[user] Explicitly wants Identity to contain no PIN-related functionality. It
should retain only a long-lived key pair as this card's encryption/decryption
credential. This supersedes the PIN migration and IdentitySession proposal below.

[agent] This is coherent under the stated trusted card-execution environment.
Keep PIN values, retries and authorization in Safe; Identity needs no authorized
session state. Its proposed surface can be public-key access and authenticated
communication-key encryption/decryption. Exact signatures and cryptographic suite are not
approved. A shared interface can check the immediate Safe caller at acquisition
and use, without introducing PIN/session state. AID admission is a sandbox
boundary, not code authentication.

[agent] Recovery then depends on possession of the retained private key and the
backup ciphertext, together with access to an allowed Safe implementation. A
party able to replace Safe with callable code can recover without the previous
Safe PIN. Do not claim that the old PIN remains a cross-reinstallation recovery
condition. Identity deletion/reinstallation destroys this continuity. Cross-card
backup wraps the data key separately for the target card rather than copying the
source Identity private key. First-pairing public-key authenticity remains a
separate protocol question.

## Minimal interface proposal (implemented with the profile above)

[user] Requested a revised, minimal Safe Identity interface under the PIN-free
boundary. [agent] Proposed the following card-local SIO; the full signatures and
cryptographic profile remain subject to approval, with no Java implementation
added in this step:

```java
public interface SafeIdentityShareable extends Shareable {
  byte[] getPublicKey();

  byte[] encryptCommunicationKey(byte[] recipientPublicKey, byte[] context, byte[] key);

  byte[] decryptCommunicationKey(byte[] senderPublicKey, byte[] context, byte[] encryptedKey);
}
```

[user] Accepted encryptCommunicationKey/decryptCommunicationKey alongside
getPublicKey. Requested purpose-specific names to distinguish these keys from
Identity's own public/private key pair, and clarified that communication is the
purpose; backup is only one use. These names supersede wrapKey/unwrapKey and the
intermediate encryptBackupKey/decryptBackupKey suggestion.

[agent] Identity handles key material and opaque authenticated context, not Safe
records or transfer state. getPublicKey returns a copy of the stable public key
in the profile's fixed encoding. encryptCommunicationKey
uses the local private key to authenticate the source and the recipient public
key to protect the supplied symmetric key. decryptCommunicationKey uses the local private key
and an expected sender public key to verify and recover that key; the expected
sender must not be trusted merely because it appears in encryptedKey. Context must
match byte-for-byte and is covered by authentication. Authentication failure
returns no key and raises an exception.

[agent] The profile will fix curve, public-key encoding, allowed key length and
authenticated envelope format; no curve/cipher negotiation parameters are
proposed. HPKE Auth is a candidate, not an approved or hardware-tested choice.
Source authentication here does not constitute a publicly verifiable signature.
The interface performs independent operations without PINs, authorization
sessions, pairing tables or backup progress. The key pair is created at initial
Identity installation; no private-key read/replace/reset method is proposed.

[agent] For source A and target B, A wraps a data key for B, and B unwraps using A's
expected public key and the same context. Same-card restoration uses the retained
local public key for both roles. Safe performs item encryption and import and
maintains its PIN permissions. Call admission to Identity is checked on SIO
acquisition and each invocation; it does not attest the Safe code. Public keys
and wrapped key material can go to APP, but plaintext key inputs/results remain
on the Identity–Safe call path.

[user] Asked whether static methods could replace Shareable since Identity retains
ownership of the private key. [agent] Verified that JCRE 3.1 section 6.1.6 executes
static methods in the caller's context; objects referenced by static fields still
obey their creator's ownership and firewall rules. Shareable calls switch into
Identity's context to use its private key without exposing the private key to
Safe. A library CAP has no independent context (section 6.1.2), and the project's
applet-CAP export restriction was already confirmed in record 98.

[agent] The minimal implementation can have the Identity Applet itself implement
SafeIdentityShareable and return this after caller admission, without a separate
session or service object. A Safe-local static facade could delegate to that SIO
if useful, but does not replace the cross-context mechanism and is not proposed
as another required layer. No implementation change is made for this discussion.
Sources: https://docs.oracle.com/en/java/javacard/3.1/jc-re-spec/F12651_05.pdf and
https://docs.oracle.com/en/java/javacard/3.1/guide/extended-cap-accessibility-sample.html.

## Superseded interface and recovery proposal

[user] Asked for the intended Safe Identity interfaces and recovery authorization.
The following was an agent proposal for review, not approved API or implementation.
Its PIN migration and per-caller Identity sessions are superseded by the user's
PIN-free Identity requirement above.

[agent] Move the single Safe PIN, its set state and shared retry counter into
Identity. Keep Access PIN in Monoid and preserve existing external PIN method
signatures. Do not keep two synchronized OwnerPIN copies or introduce another
user-facing recovery PIN by default. Safe replacement must not reset the PIN,
retry counter or identity key. Changing the PIN must not change the key or make
previous backups unreadable; the PIN authorizes use and is not a KDF input.

[agent] Give each existing SafeSession a distinct IdentitySession. SafeSession
checks its original Monoid caller and delegates authorization to its own root
session instead of keeping a second grant. IdentitySession checks its immediate
Safe caller. A failed check revokes that IdentitySession; a PIN update, retry
exhaustion or reset revokes all Identity sessions. Preserve Safe's existing
same-Monoid-session revocation when necessary through a per-session clearAuth
operation. Do not revoke all root sessions merely by matching their immediate
caller AID, because they all belong to the same Safe. PIN comparison remains one
attempt; redundant checks do not repeat the comparison. This design needs no PIN
epoch. Reacquiring an existing SafeSession keeps its IdentitySession; a freshly
created session starts unauthorized.

[agent] Proposed SafeIdentityShareable surface: getPublicKey; isPINSet,
getPINTriesRemaining, checkPIN, updatePIN, isPINValidated, clearAuth; and
wrapBackupKey(recipientPublicKey, context, key) / unwrapBackupKey(senderPublicKey,
context, wrappedKey). The wrapping methods only handle fixed-profile backup key
material. The expected sender key is an input, not trusted merely because it is
embedded in the envelope. Context and source/recipient identities must be
authenticated, with complete envelope validation before returning a key to Safe.
No generic signature, raw ECDH, arbitrary plaintext decryption or private-key
export interface is proposed. HPKE is a candidate, not a tested or approved suite.

[agent] Safe generates the per-backup data key, serializes/encrypts items and
verifies each item before import. The key can be wrapped to this card or a backup
card. Same-card historical backups remain restorable after repeated authorized
updates; wrapping is not inherently a single-use token. Cross-card transfer
completion/replay bookkeeping belongs to Safe and is a separate protocol choice.
Only ciphertext and public wrapping material go to APP through the proposed
backup flow; card-local data keys stay inside Identity/Safe.

[agent] Identity retains only its own session objects and JCRE-owned caller AIDs,
not Safe-owned objects or callback references. Public key identity does not
authenticate installed code. A correctly authenticated malicious replacement Safe
could export a returned data key; the existing plaintext Get permission and
first-pairing trust still need to be considered separately. No claim of protection
against an endpoint already given the correct Safe PIN is made.

### Software and RSA-assisted GHASH comparison — 2026-10-17

[user] Authorized implementing both GHASH approaches and comparing performance
at the expected data sizes. [agent] Kept the experiment in ignored
`.research/ghash-20261017/`, without changing production crypto, public APIs or
the approved HPKE profile. The target is a 32B communication-key ciphertext with
empty AAD: two ciphertext blocks plus the final length block, or 48B of GHASH
input. Adjacent 16B/64B ciphertexts provide bounded comparisons.

[agent] `GHASHSoftware` implements the standard bit-serial multiplication with
eight short lanes, masked XORs and fixed iteration counts. `GHASHRsa` expands
binary coefficients into base-256 digits, obtains their integer product from
two RSA-2048 exponent-2 operations, extracts parity, and reduces modulo
x^128+x^7+x^2+x+1. Its public arithmetic modulus exceeds both integer squares;
this does not use RSA for encryption or depend on its private factors. Native
RSA with externalAccess=true works in the selected test applet; nested-SIO use
was not tested. Fixed Java loops are not a hardware side-channel guarantee.

[agent] Both Java implementations passed 441 independent host vectors, including
the NIST AES-GCM Example 2 intermediate GHASH result, edge/basis inputs and
300 host AES-GCM oracle cases. The host adapter changes only RSA externalAccess
to false for jCardSim. The isolated CAP passed conversion and verification.
On physical card 55690320, both implementations passed 16 initial checks each,
then all 110 warmup/timed hash comparisons. Every timed output was verified.

[agent] GCM uses 81B of explicit RESET array payload: GHASH 32B, three AES blocks
