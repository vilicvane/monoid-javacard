# 接近满卡时的 List 可读性

## 需求

[user] List已经完成实卡验证后，希望处理持久存储接近满载时无法为响应分配空间的问题；如果List失败且客户端没有index，已有数据可能无法定位读取。

[user] 指出先前条目数增加时RAM余量不变，要求先做持久空间不足时的实卡对照，确认临时持久对象的GC行为，再决定是否修改枚举接口。本轮先测试，不实施下面的接口提议。

## 源码确认

[agent] 记录123验证的是120条小元数据List和RAM/GC行为，没有填满持久存储，不代表满卡可读性已经验证。

- 当前`CBORApduWriter`先生成完整响应；超过512B的响应按256B分配持久数组，额外持久空间随列表长度增长。
- `MonoidSafeApplet.list`每次new一个`SafeSessionItemIterator`，每次`next`又new一个`SafeSessionItem`。Java对象本身也占持久空间，所以只改变writer仍不充分。
- 认证、枚举游标和metadata还使用动态global/transient数组；不能仅根据数组内容在RAM就承诺整条路径零持久分配，需要实卡核对。

证据边界：记录123只统计RESET/DESELECT可用RAM，没有测量持久空间峰值或填满后的失败。复用模式的1557B最低RESET读数不变，是因为响应只有前512B使用RAM。按当前代码和已测响应长度计算，10/40/120条的持久响应块内容分别为256/2048/7168B，不含对象开销；这些是源码推导，不是持久空间读数。动态包装对象的创建已由源码确认，但其持久GC时机及是否独立造成失败尚未实测，不能把RAM数组的回收行为直接套用到持久对象。

## 提议与待批准接口

[agent] 提议使用固定大小响应窗口，由GET RESPONSE驱动后续枚举和编码，保持原来的0x30请求、确定长度的`{items:[...]}`、字段顺序、打包响应及61xx机制。发送完整响应不再需要额外保存同等大小的持久副本。延续用户关于单条元数据较小的场景边界，不新增大字段能力或未经同意的字段长度限制。

涉及Safe Shareable的接口和生命周期语义，原确认现由上述“先测试再决定”要求取代；以下只是尚未批准的备选方案，不能视为必须修改的接口：

- `list(type, keyPrefix)`返回每个SafeSession复用的只读游标，同会话重新list重置旧游标。
- `next()`由返回独立`SafeItemShareable`改为boolean，只推进位置。
- 游标提供`getIndex/getKey/getAlias(byte[] dest, short offset)`及`isSecret()`读取当前项；保留count/所需metadata长度查询。
- 不把已有`SafeSessionItem`悄悄变成随next改变目标的可变对象。

固定工作对象应在写入大量数据前准备并复用；既有安装的正常读取与在已满卡上新安装/首次初始化一个客户端是不同边界。后者本身也需要安装和对象空间，不能以List改造承诺解决。

## 实现与验证要点

- global数组不能作为Command字段跨APDU保留。优先考虑当前APDU全局缓冲作为SIO传输区，并用Monoid自有的固定RAM窗口保留尚未发送的编码字节；具体缓冲装配仍需实现审查。
- GET RESPONSE当前绕过Command普通异常处理，增量生成后需要处理异常、中途取消、新命令、SELECT/deselect/reset的清理和授权撤销。
- 当前迭代器约定枚举时不修改Safe；跨APDU后需处理其他授权应用/逻辑通道的修改，避免返回混合或损坏的列表。
- 用模拟器验证拼接编码与既有响应一致、包边界、过滤、空字段、取消和恢复；用分配观测检查没有逐条持久包装或完整响应副本。
- 实卡只在隔离包中测试。建立测试条目和固定读取对象后，以独立filler Applet逐步占用剩余持久空间，比较旧/新路径；记录真实剩余空间，不能把大块分配失败误当成完全零余量。通过返回的index读取小条目，并验证复位及失败恢复。
- 不填满真实Safe，不删除已有数据；操作读卡器前仍先通知用户，完成后清理隔离包并核对注册表。

大Get/Export也可能需要响应持久空间，List改造不能被表述为所有读取路径已经解决。

## 单APDU持久空间对照

[agent] 在卡55690320上安装隔离Identity AC、Safe AD、Monoid AE及filler AF包。原有应用不动；filler只分配自己持有的数组，不向原有Safe写入填充数据。保留8192B应急释放数组及预分配引用表，查询/释放路径不新建对象。

- 120条fixture沿用记录123的index10B、key16B、alias9B、data1B；完整List为7569B、30个响应包。
- 模式0/1：完整List，无逐条GC/逐条GC；模式2/3：仅枚举和读取元数据，无逐条GC/逐条GC；模式4/5：同样仅枚举，但将全部wrapper保留到最后采样，无逐条GC/逐条GC。所有模式使用同一真实Safe iterator和getter。
- 单条读取放在helper中，返回后清空局部item引用，再按模式请求GC。统计数组、保留引用表预分配；每次采样不分配对象。使用32位`getAvailableMemory(short[], offset, type)`统计持久空间，同时记录RESET RAM。
- 六项隔离模拟器测试和四份CAP转换/验证通过；模拟器仅核对逻辑，不用于推断GC。
- 临时源码、冻结hash、CAP及原始APDU日志在忽略目录`.research/list-persistent-gc-20261018/`。生产Java源码不变。

空间充足时：认证消耗16B、iterator及其状态消耗48B、metadata的持久记账消耗16B；每个wrapper使持久余量再减少20B。120条仅枚举峰值消耗2480B；完整响应峰值消耗10128B。相差7648B，其中响应持久数据7168B，其余480B是本实验中的额外分配开销。RAM最低值在相同模式中与条目数无关，不能代表持久峰值。

| ------------------ | -------------- | ---------------- | ------------------------ |
| 16416B             | 120，成功      | 120，成功        | 无                       |
| 8224B              | 120，成功      | 97，失败         | writer分配，reason5      |
| 4128B              | 120，成功      | 48，失败         | writer分配，reason5      |
| 2080B              | 97，失败       | 26，失败         | next创建wrapper，reason5 |

- 每个空间档位的四种仅枚举模式结果完全一致；完整List的两个GC模式也一致。采样没有出现命令内持久余量净回升。
- 2080B/1056B的仅枚举分别在创建第98/33个wrapper时抛出`SystemException.NO_RESOURCE`，失败时仍报告60B/336B余量；可用空间数字不能等同于任意对象均可成功分配的容量，未归因到具体碎片或运行时保留机制。
- 544B时metadata分配报告`NO_TRANSIENT_SPACE`，但最低RESET余量仍2056B。这是持久空间压低后的实际运行时结果，不能把reason2直接解释为RAM内容空间已经耗尽。
- 36次主体对照与6次8条过滤枚举完成。过滤枚举在前五档成功；544B时在iterator阶段失败，reason5。所有成功响应均核对内容/checksum；所有成功完整响应的hash一致。
- 各档成功或失败后，后续诊断APDU都读到原来的持久余量和2064B RESET余量。这证明跨命令可回收，不代表同一List命令内已回收，也不能精确界定边界内部时序。
- 释放所有filler块的当次APDU报告560B余量，下一条查询才恢复42248B；这个独立路径同样观察到跨APDU回收。完整120条List以及已知index的Get再次成功。卡片没有因本轮分配失败失联。

## 对接口决定的影响

[agent] 现有完整响应持久副本确实独立造成失败；仅删除响应副本仍不能让单APDU任意长枚举依赖即时GC。逐条`requestObjectDeletion()`没有改善本次结果。

但这还不证明必须修改`next()`返回值：增量响应本来就跨GET RESPONSE，可让同一iterator每次只产生少量wrapper，再利用APDU边界回收。以下补充实验验证了这个方向；过滤出8条并重新创建iterator不能替代同一个iterator跨APDU的验证。

## 同一iterator跨APDU对照

[agent] 加装独立B0包，实例`F06D6F6E6F6964AE010001`沿用隔离Safe允许的调用方前缀。只调用现有Safe SIO，无生产接口改动。CAP转换/验证及host脚本语法检查通过。

- 先建立并认证Safe会话、预分配状态，再施加持久空间压力。start只创建一次iterator并保存引用；后续APDU推进同一个iterator，每批4或8条，使用APDU全局缓冲读取相同metadata getter。
- 每个诊断APDU末尾显式请求GC；使用预分配统计数组记录本次前后空间，后续APDU再检查是否回收。每个返回的index序号都逐项核对，累计metadata checksum核对到120条。
- 这是跨APDU枚举探针，尚未实现正式writer的渐进CBOR编码、GET RESPONSE或取消流程；没有把global/APDU缓冲保存在字段中。

| start前持久余量 | 创建iterator后每批开始余量 | 每批4条                    | 每批8条                                          |
| --------------- | -------------------------- | -------------------------- | ------------------------------------------------ |
| 2096B           | 2048B                      | 全120条成功，批内最低1968B | 全120条成功，批内最低1888B                       |
| 1072B           | 1024B                      | 全120条成功，批内最低944B  | 全120条成功，批内最低864B                        |

- 所有成功的4条模式：30次边界各恢复80B；8条模式：15次边界各恢复160B。完整遍历累计回收2400B，即120×20B；同一iterator存活期间，首批和末批开始的持久余量完全一致。
- 最低档8条模式失败后，下一条状态APDU恢复120B到512B，iterator仍存在。未把失败后的iterator继续推进当成恢复方案。
- 两组正常余量基线、六组压力测试及释放filler后的8条恢复，共9组完成；成功组均读完120条。filler释放后恢复40228B，最终批量读取成功。额外探针本身占用空间，因此该空闲基线与上一组42248B不同，不是泄漏。
- 最低档8条模式在报告392B可用时仍无法创建下一个wrapper，再次说明报告余量不是可承诺的连续分配预算。本轮不推断具体分配器实现，也不将512B视为正式List的最低工作空间。

## 结论与下一步范围

[agent] **当前证据支持保留`list()`/`next()`/`SafeItemShareable`接口，不必为消除总条数带来的累计包装对象占用而修改它们。** 原来“只改writer仍不充分”应细化：仅删掉响应持久缓存、仍在一条APDU里完成全部枚举确实不够；让writer随GET RESPONSE推进有限量枚举并逐包请求GC，则可同时限制响应缓存和wrapper的峰值，无需改为可变item或boolean next。

后续实现仍需处理固定响应窗口、每包临时分配、APDU/global缓冲边界、异常/取消/SELECT/deselect/reset及其他调用方修改Safe时的枚举一致性。当前`0xC0`分支绕过普通命令finally，不能假设已自动逐包请求GC。

当前`SafeSessionItemIterator.next()`先递增position再创建wrapper；若分配失败，不能简单发送当前包后重试`next()`，否则可能跳过失败项。本次失败批次只做诊断、清理并重建iterator，不以这种重试方式宣称恢复。

本实验不承诺零持久余量可读、不覆盖满卡时首次初始化客户端，也不是正式流式List实现的整体验收。4/8条是诊断批次，用于隔离对象行为；实际响应应继续按用户要求打包发送。没有新增长度上限、分页协议或生产API。
