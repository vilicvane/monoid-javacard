These ECDSA inputs are all 32B digests. Record 108 direct requests are 87B
in one APDU and perform no derivation. The roughly 400ms increase appears
between records 105 and 108, before the contextual KDF and shared cache.
These are historical observations, not a controlled same-session benchmark.
Do not explain all of the current latency by longer messages or derivation.

Other earlier hundreds-of-milliseconds results are direct BIP340 727.84ms
and direct-key BIP86 903.66ms in record 79. Record 77's 417.30ms BIP340 and
544.47ms TapTweak+BIP340 are minimal diagnostic-applet results and must not
be presented as the complete Monoid API. Current record 111 derived Ed25519
signing takes 3361.01ms for an empty message and 3419.46ms for 300B; message
growth cannot explain its overall seconds-long duration either.

Source comparison points to a plausible parsing cost: the explicit Key API
adds type decoding, three whole-map checks rejecting legacy seed/curve/path,
and a derivation check even for direct keys. Derived requests additionally
parse nested maps. CBORReader.key rescans from mapOffset and repeatedly
updates offset; offset/map state and snapshot arrays are persistent, despite
being operation-local parsing state. More scans may amplify persistent-write
cost. The parser and authorization primitives themselves are unchanged across
the frozen P-256 and explicit-Key versions; their call patterns changed.
No split timing has established how much of the regression this explains.

A future investigation should compare direct-key commands on the same
current firmware and separately measure parsing, authorization/key access
and signing, preserving public API semantics. This record authorizes no
optimization or API change by itself. Historical raw evidence is under
.research/item-key-20261015/ and .research/key-api-20261016/; durable figures
and scope are in records 98, 101, 105, 108 and 111.

[user] Questioned whether persistent parsing cursors are themselves a bug.

[agent] Lifecycle review confirms that all five scalar shorts and the four
eight-short snapshot arrays are command-local state. Command.process waits
until request reception is complete, resets the reader, then parses; partial
APDU frames do not use these cursors. No parser state needs to survive reset
or deselection. CLEAR_ON_DESELECT storage is suitable, including around Safe
SIO calls, which do not deselect the caller. Moving all this state would use
74B of RAM payload plus array metadata. Explicit command-start reset remains
necessary for the -1 array/map sentinels. Unnecessary persistent updates are
a confirmed storage-lifetime/performance design issue; their contribution
to the measured latency remains unquantified. This review changes no code.
