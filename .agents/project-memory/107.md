# Explicit derivation semantics and chain presets — 2026-10-15

[user] Questioned the implicit semantics behind the existing path input and
asked which specification governs seed-to-master generation. Suggested
retaining foundational entry points while later adding packaged BTC, EVM
and Solana configurations. This is a design discussion, not approval of a
particular API rewrite or implementation of chain presets.

[agent] Source audit of Keystore, LibBIP32 and LibSLIP10Ed25519:

- Path bytes are explicitly supplied; the derivation scheme is implicit in
  the requested curve and signing dispatch. secp256k1 selects LibBIP32;
  ed25519 selects hardened SLIP-0010. P-256 hierarchical derivation is not
  implemented. Paths concatenate four-byte big-endian child indices, with
  the high bit marking hardening. They do not encode their scheme or a
  BIP44 wallet layout.
- Keystore.deriveMasterFromSeed accepts only 64-byte stored seed material
  and computes HMAC-SHA512(request.seed, storedData). The request's seed
  text is a public HMAC key/domain label, not seed bytes or a mnemonic
  passphrase. It is not currently bound to the chosen curve or standard.
- The normal BIP32 master construction uses the fixed label Bitcoin seed.
  Standard Ethereum BIP32 wallets use this same construction; changing it
  to Ethereum seed would produce a different wallet. SLIP-0010 Ed25519
  uses ed25519 seed; SLIP-0010 P-256 uses Nist256p1 seed. The latter is a
  hierarchical scheme, distinct from record 104's contextual HKDF proposal.
- The 64-byte output is private-key material followed by chain code.
  For Ed25519 the first half is a private-key seed, not a ready scalar.
  Stored master items contain neither curve/scheme nor depth/parent data;
  their actual representation is an extended private node that can also
  be an imported descendant. Subsequent paths are relative to that node.
- BIP39 mnemonic/passphrase conversion is a preceding PBKDF2-HMAC-SHA512
  step (2048 iterations, 64-byte output). No mnemonic/PBKDF2 implementation
  was found in production Java sources. The current seed-to-master helper
  does not perform BIP39. BIP32/SLIP-0010 permit 16–64-byte seeds; accepting
  only 64 bytes is a current implementation subset.

Confirmed existing BIP32 conformance gaps, not yet fixed:

- Keystore's seed-to-master helper returns the HMAC output without checking
  whether the secp256k1 master scalar is zero or at least the group order.
- LibBIP32 child derivation does not check I_L >= n or a zero child and does
  not implement invalid-child handling. Its single subtraction also uses
  comparison > 0, so an exact sum of n is not reduced/rejected.
- These are static source findings against the specification, not newly
  reproduced hardware failures. Prior passing ordinary vectors/signatures
  do not establish coverage of these cases. No tests or card actions were
  performed for this discussion. They concern algorithm correctness, not
  the hypothetical large-data support deferred by record 106.
- The Ed25519 SLIP-0010 branch does not require scalar rejection: every
  32-byte private-key seed is valid, and it already rejects non-hardened
  path segments.

[agent] Initial design recommendation, reconsidered below on 2026-10-16;
no API changes were approved:

1. Describe source, derivation and signing separately. The stored index
   identifies source material; an explicit derivation scheme defines
   master generation, supported curves and child derivation. Path or
   context is an argument to that scheme, not a substitute for naming it.
   Record 104's context-only addition is an earlier incomplete proposal;
   reconsider it together with existing path-based derivation.
2. Standard scheme selection fixes its standard master HMAC label. If the
   foundation retains arbitrary-label functionality, name it explicitly
   as a custom operation rather than presenting it as standard BIP32.
   Keep raw input choice separate from chain policy; no field names or
   migration/compatibility behavior are approved yet.
3. Layer concrete presets over those primitives, such as BTC BIP84/P2WPKH,
   BTC BIP86/P2TR, an explicit EVM wallet account layout, and a specified
   Solana SLIP-0010 account layout. A chain name alone does not uniquely
   determine wallet paths or Bitcoin address type. Presets can bundle
   curve/scheme, path construction and signing/key-tweak choices.
4. Presets must specify the starting node: full root-based paths cannot be
   applied blindly to imported account/child nodes. Contextual P-256
   derivation remains a distinct scheme without a hierarchical chain code.
5. Prefer client-library presets expanding into clear foundational card
   requests. This is a placement recommendation, not authorization to edit
   the APP repository. Card-enforced policy would require a separate
   decision; a preset alone is not an authorization boundary.

[user, 2026-10-16] Asked how the existing API should be interpreted if HD
wallet conventions are supplied as its semantic context, since HD wallets
are an established industry model.

[agent] Revised recommendation: a documented HD contract can supply the
scheme semantics without requiring a new scheme field on each request.
The README already partially does this above Key: BIP32 for secp256k1 and
hardened SLIP-0010 for Ed25519. The earlier mandatory-selector suggestion
was unnecessarily general for the currently supported combinations.

- Define the HD branch as resolving the stored seed/master and supplied
  path under the curve's documented HD profile, then applying the existing
  signature cipher to digest/message. HD alone is not one universal
  derivation algorithm; the per-curve mapping must remain explicit in the
  contract, even when it is implicit in each individual request.
- Only consider a selector when a concrete requirement introduces another
  derivation profile for the same curve. Do not pre-build a general KDF API.
- Distinguish implementation acceptance from the public contract. The code
  operates relative to its supplied extended node, but the API can define
  master as an actual root node; this does not require runtime depth or
  origin metadata. If non-root imports are supported as a public feature,
  document relative paths at that point. No such contract change is approved.
- The request field seed remains a naming/abstraction concern: it actually
  supplies the master HMAC label. Standard profiles have fixed labels; the
  existing customizable primitive can be described accurately, but arbitrary
  label values must not be called standard BIP32/SLIP-0010. Whether to rename,
  default or move this parameter remains an API decision for the user.
- Chain presets can bind standard labels, paths and signing choices over
  the current foundations; they do not require a universal derivation
  framework. The contextual P-256 proposal is a separate operation, not an
  alternate interpretation of the existing HD numeric path.

Only project memory changed during this discussion. The previously noted
BIP32 correctness gaps remain independent and unfixed.

[user, 2026-10-16] Requested a concrete proposed Key type.

[agent] Proposed a source index plus optional discriminated derivation:

```ts
type Key = {
  index: byte[];
  derivation?:
    | {
        type: 'hd';
        curve: 'secp256k1' | 'ed25519';
        path: byte[];
      }
    | {
        type: 'context';
        context: byte[];
      };
};
```

The type discriminator distinguishes the two proposed derivation models,
not arbitrary KDF algorithms. HD accepts stored seed/master, with the fixed
per-curve profile above; an empty path selects the root. Context accepts
only a standalone secp256r1 source under the proposed fixed Monoid profile;
an empty context still derives. Omitted derivation selects a standalone key
directly. Invalid source/model combinations reject rather than falling back.
The index's existing item type supplies the source category; no duplicate
source-kind field is needed. ViewKey and Sign share the description, with
cipher and digest/message outside it.

Compared with the current API, this proposal moves curve/path under
derivation and removes the misnamed required seed label, using standard
labels for the standard HD branch. It is not approved or implemented;
arbitrary-label custom derivation remains a separate decision. The proposed
contextual P-256 profile itself still needs final algorithm/encoding rules.

Earlier draft approval statements in this record describe their own stage.

[user, 2026-10-16] Emphasized conceptual inclusion relationships and asked
whether secp256k1 necessarily implies BIP32.

[agent] Clarification: it does not. secp256k1 is an elliptic curve; standard
BIP32 is a particular HD derivation specification that uses it. SLIP-0010
also supports secp256k1, so even adding the general HD context does not make
the curve identify a unique specification. HD names the model; a concrete
derivation scheme constrains its curves and parameters. A documented
per-curve API profile is a product restriction, not a conceptual equivalence.

For a type intended to identify the complete derivation, prefer concrete
scheme names such as bip32/slip10 over hd alone. BIP32 then need not repeat
curve: secp256k1 because the specification fixes it. A SLIP-0010 branch may
select supported curves; the current firmware only implements its Ed25519
branch, even though the specification supports more. No generic registry or
unimplemented curve combinations are required. Likewise context is an input
kind, not a complete algorithm/profile identifier; record 104's exact
contextual derivation profile remains unsettled. The preceding Key shape is
still a draft and is not approved or implemented.

Primary references checked during this discussion:

  master generation, extended nodes, child-index encoding and invalid keys.
- [SLIP-0010](https://github.com/satoshilabs/slips/blob/master/slip-0010.md):
  curve-specific labels, hardened Ed25519 and retry differences from BIP32.
- [BIP39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki):
  mnemonic/passphrase conversion preceding HD derivation.
- [BIP44](https://github.com/bitcoin/bips/blob/master/bip-0044.mediawiki),
  [BIP84](https://github.com/bitcoin/bips/blob/master/bip-0084.mediawiki),
  [BIP86](https://github.com/bitcoin/bips/blob/master/bip-0086.mediawiki):
  wallet path conventions and Bitcoin script-type-specific derivation.

  default m/44'/60'/0'/0/0 and differing account/index enumeration layouts.

  example hardened path m/44'/501'/i'/0' and a separate direct seed-slice
  restoration example, reinforcing that a chain name is not a complete
  wallet derivation specification.
