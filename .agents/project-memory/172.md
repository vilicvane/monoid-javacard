# 实际射频断电后的对象回收行为

[user] 本项目关于Java Card 3.0.5的行为，以我们手头实测的3.0.5实体卡为准，不限定为某一张卡；不要反复把已经验证的行为描述为单张卡的特例。规范规定与实体卡实现仍需区分。这是项目采用的讨论与实现口径，不表示已经测试未实际上卡的型号。

[agent] 承接171的连续APDU实验，确认真实射频断电、再上电对垃圾回收的影响。连续执行时不回收，与断电后是否回收是不同问题。本条的项目口径更新171中把结论限定为单张卡特例的表达，不改写原实验的卡号、数据或实际验证范围；正式固件的回收策略未改变。

## 实验目标

[agent] 对失去引用的`CLEAR_ON_RESET`、`CLEAR_ON_DESELECT`及global数组，分别比较不调用和调用`requestObjectDeletion()`两组在断电前后可用空间的变化。RESET及DESELECT另做保留引用对照，区分内容清零与对象存储空间被回收；global数组不能用相同方式持久保留引用，未执行该对照。

[agent] 对失去引用的持久数组，比较无请求及有请求情况下的跨reset回收。另保留持久数组引用作为对照，避免把应用初始化、引用丢失或测试夹具改变造成的空间变化当作回收行为。

| 对象         | 引用状态    | 显式请求 | 核对目标                                       |
| ------------ | ----------- | -------- | ---------------------------------------------- |
| RESET数组    | 丢弃 / 保留 | 无 / 有  | 实际断电前后可用空间、保留数组的内容与可用性   |
| DESELECT数组 | 丢弃 / 保留 | 无 / 有  | 选择状态变化与实际断电分别造成的内容、空间变化 |
| global数组   | 丢弃        | 无 / 有  | global数组失去引用后的跨reset存储空间行为      |
| 持久数组     | 丢弃 / 保留 | 无 / 有  | 持久垃圾是否跨reset回收、保留数据是否仍可读    |

## 测量边界

[agent] 使用真正的RF关闭后重新开启，并通过卡内可观察状态核对发生了reset。单纯PC/SC重连或重新SELECT不算实际断电证据。记录探针、SELECT和RF控制的顺序，区分下一条APDU边界与reset边界的影响。

[agent] 空间探针只读、不临时分配、不附带GC请求；无请求分组不能被测试入口或命令清理中的隐式调用污染。对照组使用一致的对象大小、数量和探针，记录分配、丢弃引用、请求回收、下一APDU、断电及重上电后的状态。

[agent] RAM数值仍是采样边界的可用空间，不是连续峰值；RESET和DESELECT读数不相加。内容被清零不等于对象空间已释放，单次空间变化也不自动说明由哪一种回收机制触发。最终按具体操作顺序汇总证据与适用的项目行为约定。

## 结果

[agent] 2026-10-22完成四类独立新安装的实卡对照，原始证据对应测试卡55690320、ACS ACR1552。四组均通过，共33次实际RF关闭2秒再开启；每次都先写RESET标记`A5`、DESELECT标记`5A`，再核对RESET标记变为`00`，排除仅重连或重新SELECT。单独的reselect对照保留`A5`而清掉DESELECT标记，明确区分了两种事件。最终33次不含早期探索运行的6次RF操作。

[agent] 每组先连续分配并丢弃4个256B数组，不请求GC，逐次查询空间，再做reselect及两次真实RF reset。四类对象在这两次RF后均未出现空间恢复。随后显式请求GC，下一条APDU已能看到回收。为剔除首次启动的额外分配，再从清理后的稳定基线重复4次分配及显式请求，得到下表的精确增量。

| 对象         | 4×256B失去引用后，无请求跨两次RF | 稳定对照的显式请求后恢复量                              |
| ------------ | -------------------------------- | ------------------------------------------------------- |
| RESET数组    | 未恢复分配空间                   | RESET可用量+1024B、DESELECT可用量+1024B、persistent+64B |
| DESELECT数组 | 未恢复分配空间                   | RESET可用量+1024B、DESELECT可用量+1024B、persistent+64B |
| global数组   | 未恢复分配空间                   | RESET可用量+1024B、DESELECT可用量+1024B、persistent+64B |
| 持久数组     | 未恢复分配空间                   | persistent+1088B，两个RAM读数不变                       |

[agent] 上表两个RAM读数表示同一分配对可用量报告的影响，不能相加成2048B；这组transient数组payload是1024B。持久开销在本探针中对应每个数组16B，持久数组的4×256B payload连同开销共1088B。DESELECT无请求的第一组RESET可用量仅下降928B，而DESELECT下降1024B；它不是独立池的计量。清理后的第二组已获得两个读数均精确下降及恢复1024B的对照，不把初段差值解释成少分配了96B。

### 保留引用与释放引用对照

[agent] RESET、DESELECT各保留一个256B数组，内容先写`6D`。RF reset后内容变为`00`，引用和空间占用仍在；即使显式请求GC并再做RF也不会回收这个仍可达对象。之后主动释放引用，仅RF reset仍不恢复空间；再显式请求，下一APDU恢复256B的RAM可用量和16B persistent。

[agent] 同样保留持久数组时，RF及显式请求后内容仍为`6D`，空间不变。释放引用后，仅RF仍不恢复；显式请求后的下一APDU恢复272B persistent。global没有保留引用组，因此不把该项列为已验证的global引用或内容对照。

[agent] 这些结果区分了三件事：transient内容按生命周期清零；仍有引用的数组继续占用空间；失去引用的对象在本项目实测基线中不能仅靠RF reset自动回收。已失去引用的RESET、DESELECT、global和持久数组均通过显式请求得到回收，且本轮在下一条APDU就观察到了恢复，无需再经历一次RF。

### 首次RF的额外变化

[agent] 在尚未分配实验数组时，第一次空RF就使读数从RESET/DESELECT/persistent的1681/1776/33672B变为1470/1552/33360B；第二次空RF稳定。已将这个变化独立纳入每组对照，不能把它算作测试数组造成的泄漏，也不能把后来首次GC回收的全部空间都归因于4个数组。探针的SELECT及读取路径没有应用层分配，但具体运行时来源仍未定位；不称为已定位的native bug。

## 项目采用的行为与交付状态

[agent] 按手头实测3.0.5卡片作为项目基线：断电会清transient内容，但不能作为释放临时对象分配空间的替代方案；失去引用与回收是两个步骤，正常工作流仍需要适当安排显式请求。这不证明现有每处调用都有必要，也不否定减少无垃圾warm路径请求、复用对象或按实际压力安排清理。规范要求与本项目测量结论分开记录，不能仅凭版本号推导运行时会自动完成回收。

[agent] 本轮只修改忽略目录中的实验程序和文档。正式125个Java源文件仍与记录170的round15冻结哈希一致，没有改变正式GC策略、业务API或提交推送。C0/C2/C4临时实例与包已全部清理，管理脚本核对原registry保持一致。

## 博客兴趣点

- 入口问题：既然断电后RAM内容会清零，为什么下一次使用仍可能缺内存？用保留引用数组从`6D`变`00`但占用不变，以及丢引用后只有显式请求才恢复的对照，解释内容、引用和分配空间的差别。
- 实验方法：PC/SC重连与重新SELECT不能替代真实断电证据；用RF关闭2秒及RESET/DESELECT双标记，分开验证事件。再加入空RF基线，避免把运行时首次初始化的开销归错因。
- 已知结论与边界：四种数组的无请求/显式请求空间结果已完成；global没有保留引用组，首次空RF额外开销的具体来源尚未定位。不能从此结果推出每个命令都必须GC，或所有未实测的3.0.5型号都已验证。
