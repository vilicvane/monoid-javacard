## Mobile transport

Android exposes raw ISO-DEP exchanges through `IsoDep.transceive`, with
configurable timeout and a device-dependent maximum transfer size. An
ordinary NFC application can implement GlobalPlatform INSTALL/LOAD over
this transport for an external contactless Java Card. Extended APDUs are
not required: GlobalPlatform has its own LOAD blocks, independent of the
Monoid CBOR request-fragmentation protocol. Dangerous Things' published
GlobalPlatform Mobile application already advertises local CAP installation
and SCP02/SCP03 over NFC; this is product evidence, not a code audit or a
test of our phone/card combination.

iOS Core NFC exposes ISO7816 command/response exchanges. The application
needs the NFC entitlement and declared selectable AIDs, including the
card's management AID. The tag-reader session has a 60-second duration
limit documented by Apple. Installation is consequently plausible but
requires testing the complete CAP transfer and installation on a real
iPhone; do not promise successful installation based only on API access.
Do not confuse external-card reading with access to the phone's embedded
secure element or with HCE/CardSession APIs.

## Keeping keys off the phone

The most direct candidate for our current card is remote secure-channel
processing: a trusted owner computer, service, or HSM-backed service holds
the management keys and constructs the approved GlobalPlatform commands.
The phone forwards protected APDUs and their responses. Both long-term and
derived session keys can remain off the phone. GlobalPlatform's remote
application-management specification explicitly describes an intermediary
agent transporting scripts protected end to end with SCP02/SCP03.

The trusted endpoint must restrict the CAP hash, target card, AIDs,
privileges, and allowed management actions. It must not become a general
MAC/signing oracle for arbitrary phone-supplied commands. A server-side
single-use deployment job can authorize this restricted workflow; this
is different from an independently usable offline card token. Protocol
sessions still need fresh authentication after field loss. Where allowed
by the secure-channel mode and command sequence, batching prepared LOAD
APDUs can reduce network round trips, but this has not been implemented.

Keeping only the long-term key remote while sending session keys to the
phone grants the phone the associated session authority. It does not by
itself restrict the phone to installing one approved CAP. Ordinary SCP
authentication already avoids transmitting the long-term key itself in
plaintext over NFC; that is distinct from keeping it out of phone memory.

## Signed authorization

GlobalPlatform Delegated Management separates issuer authorization from
the application provider's secure channel. Load/Install/Delete tokens
authorize their defined operation parameters; load tokens can bind the
load-file hash. With asymmetric tokens, the issuer's signing key remains
off-card and the relevant Security Domain holds a verification key.
Normal direct INSTALL/LOAD/DELETE APDUs still require authenticated
communication (GP 2.3 table 11-2); a token does not replace this channel.

Tokens are not inherently single-use or bound to one physical card. Their
scope depends on the signed fields, verification-key provisioning, and
platform policy. Contactless Services amendment C v1.2 section 12 explicitly
notes that base tokens lack replay prevention. Its token-identifier
blacklist uses separate STORE DATA operations to add/remove identifiers;
it does not establish automatic atomic consumption upon successful
installation. A phone can omit a later blacklist command. Do not describe
this alone as a guaranteed one-time offline installation capability.

DAP verification authenticates the origin/integrity of the load file; it
is not a single-use installation authorization. SCP11 offers public-key
secure-channel alternatives on supporting platforms, but current-card
support has not been established and cannot be added merely by giving an
ordinary applet an ECC implementation.

## Monoid as the installation authorizer

[agent] Delegated Management Tokens fit the clarified design. A candidate
configuration keeps the authorization private key in Monoid/Safe, provisions
its public key in a Token Verification domain, and gives the phone SCP
access to a separate Delegated Management domain. The phone can obtain
the required Tokens from Monoid first, then select the delegated domain,
establish SCP, and submit the authorized loading/installation commands.
Signing and installation on the same card do not inherently conflict, and
this ordering does not require Monoid state to survive the switch.

The delegated-domain credential is distinct from the issuer/root key and
the Token signing private key. Its management powers still need to be
limited; it is not a harmless public credential. In particular, giving the
phone the ISD/Authorized Management owner's credential would allow that
owner to manage content without a Token (GP 2.3 section 9.1.3.2), defeating
mandatory Monoid authorization. Initial provisioning still needs trusted
administrative access. No such configuration has been applied.

For ECC256 Tokens, the phone can compute SHA-256 over GP's canonical
authorization structure and send that digest for signing. This is not
simply a hash of the CAP ZIP. The Load Token binds the load-file hash,
package AID, target domain and loading parameters; the Install Token binds
package/module/instance AIDs, privileges and installation parameters, plus
their prescribed control/length fields. A typical load-and-install workflow
needs both Tokens. The whole CAP need not pass through Monoid; the platform
checks the loaded bytes against the authorized load-file hash.

Current `Signer`/`OneShot` use precomputed SHA-256 and plain ECDSA r||s,
which match ECC256 Token hashing/signature encoding. Curve acceptance is
unverified: Monoid currently offers secp256k1 ECDSA, while the card reports
`ECCP256_SHA256`. That label alone proves neither secp256k1 acceptance nor
an exclusive NIST P-256 restriction. GP allows explicit ECC domain
parameters in PUT KEY (table 11-74). Test whether the domain accepts
secp256k1 before concluding a new curve is necessary. If another curve is
needed, existing `LibECDSA.ensureLowS` also contains secp256k1-specific
order constants and must not be applied unchanged.

This approach can avoid private-key export during installation. It does
not make an ordinary Safe key non-exportable: `CommandGet` currently returns
item data after Safe authentication. A stronger non-exportability policy
would be a separate design/API decision, not part of this research.

## What SCP03 changes

SCP03 uses symmetric AES keys, session-key derivation, cryptograms and
AES-CMAC. It does not turn an ECDSA/Ed25519 digest signature into installation
authority. With command MAC enabled, protection covers actual APDU bytes
and chained MAC state; one signature over the installation digest cannot
replace that protocol. A card-hosted SCP client would therefore be a
different, more stateful implementation from the requested Token signer.

SCP03 is neither wire-compatible with SCP02 nor a superset that implies
SCP02 support. A card/domain can implement both, or only one; each session
uses the applicable protocol and correctly provisioned key set. SCP02 uses
TDEA/3DES, whereas SCP03 uses AES. The INITIALIZE UPDATE response identifies
the protocol and key version. Capability and configured-key support must
be checked per card/domain, rather than inferred from the protocol number.
Clients supporting the user's mixed cards should implement both channel
variants below the common management-command/Token layer.

SCP03 also permits an authenticated session without subsequent secure
messaging where domain policy allows it (v1.1.1 table 7-3). Its handshake
authenticator grants session authority; it still does not bind an approved
CAP digest. Do not claim per-command MAC is mandatory in every SCP03 mode.
Giving session keys to the phone similarly grants session authority rather
than just permission for one named installation.

On one logical channel, selecting Monoid ends the previous domain's SCP
session (GP 2.3 section 10.2.3). A full same-card SCP proxy might use separate
logical channels, but card support and firmware handling are untested.
Pre-signing Tokens avoids this interleaving entirely. Tokens can be combined
with SCP02 or SCP03; SCP03 is not a prerequisite. The current installation
log advertises SCP02 only, so SCP03 availability is not established.

## Third-party applet boundary

An ordinary Java Card applet has no standard CAP loader or privileged
installation entry point. Calling another class's `install` method or
constructing an Applet object does not create the runtime's installation
context; `Applet.register` outside a runtime-initiated installation fails.
Shareable access does not grant this authority.

Java Card does not require GlobalPlatform as the installation protocol.
The runtime implementer may supply a proprietary installer, possibly
implemented as an applet, with vendor-defined AID/APDUs. JCRE 3.1 sections
11.1.1–11.1.6 explicitly reserve its special access and installation
privileges from ordinary applets. This requires platform/vendor support,
not just an installer CAP that users can load onto any existing card.

A third-party Security Domain may participate in authorized/delegated
management when provisioned with the required privileges and supported
platform services. OPEN still performs installation: this is a
GlobalPlatform route, not a bypass. Setting a privilege bit alone does not
create a portable Java API for loading CAP files. No supported proprietary
installation API has been identified for our current card.

## Current-card evidence and next boundary

Record 88's current replacement card advertises GP 2.3, and its installation
log confirms a working SCP02 i=55 channel. The capability list advertises
SecurityDomain, DelegatedManagement, DAPVerification and TokenVerification,
with several token-verification algorithms. This does not establish a
configured delegated-management domain, provisioned verification keys,
token replay protection, or a tested token-install workflow.

The existing installation still uses the public development management
keys. Keeping those values out of the phone would not make them secret.
A deployment requiring exclusive authority must first provision private
management keys, preferably distinct per card, through an authorized
workflow. No keys were rotated during this research, and key material is
not recorded here. The Monoid/Safe PINs are separate credentials and do
not authorize GlobalPlatform installation.

Following the user's clarification, the proposed first validation is Token
verification and an isolated delegated installation on the current card,
including whether its management domain accepts our existing secp256k1
signatures. This precedes mobile transport work. Remote SCP remains an
alternative, not the user's preferred architecture. This is a recommendation,
not authorization to modify the mobile app, install test applets, provision
keys/domains, or change card management policy.
