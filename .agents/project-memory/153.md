## 已确认的权限模型

- `types`、`keys`、`seed`均可选、独立，不互斥。
- `types`为`[type, writable]`，精确自定义Type；false只读，true读写，不再区分创建/修改/删除。
- `keys`可有多把，采用现有`Key`描述；客户端不能自行改变或延伸授权的派生描述。密钥材料更新后的授权行为见后续接入边界。
- `seed`最多一个，仅允许Monoid-001，并在该派生的context中加入授权domain；不恢复对外master支持。
- 管理授权需要Secret PIN；Security Key自行验证FIDO PIN，日常FIDO调用不要求先选中Monoid或输入其PIN。
- 私钥留在Monoid；Type授权不覆盖secret保护。暂不实现锁卡，不修改APP。

## 管理API

[user] 提议授权命令从`0x50`开始，并询问公共接口能否与Monoid Applet放在同一包。

[agent] 本版采用`0x50–0x52`，取代此前未批准的`0x26–0x28`。沿用现有Authenticate及错误响应格式，三条命令均要求Secret授权，并核对Identity的Secret PIN验证状态。

```ts
type AppletGrantOptions = {
  aid: byte[];
  // Exact custom Type, 0x1000 through 0xFFFE.
  types?: [type: number, writable: boolean][];
  keys?: Key[];
  seed?: {index: byte[]; domain: byte[]};
};

type AppletGrant = AppletGrantOptions & {
  tokenHash: byte[]; // SHA-256 of the installed client's private 32B token.
};

// 0x50 List Applet Grants
type Request = {};
type Response = {grants: AppletGrant[]};

// 0x51 Set Applet Grant
type Request = AppletGrantOptions;
type Response = {};

// 0x52 Remove Applet Grant
type Request = {aid: byte[]};
type Response = {};
```

同一完整AID一份授权；Set整体原子替换，省略或空数组表示没有该权限，不是保留旧值。全部省略合法。Set验证客户端已安装、类型范围、固定Key和seed来源。APP不能提供或覆盖tokenHash，Monoid通过客户端SIO取得；回调前后检查管理授权。删除不存在的授权成功返回空map。

Type在CBOR中沿用现有Java short编码，例如`0xF000`表示为`-4096`；权限按完整16位精确匹配，不使用List中低字节为零时的类别通配语义。本阶段不改变现有CBOR整数接口或普通List协议。

授权记录为Monoid内部独立持久目录，不是普通Safe Item，不出现在List/Export/Import中。只保存Monoid自有的权限描述、AID字节及tokenHash，不持久保存客户端AID对象或SIO。复用4KiB持久空间guard；准备完成后事务发布。

Monoid卸载会清除其条目、Access PIN和授权；保留Identity时，Secret PIN及其错误次数仍保留。`0xFF Reset`则须在现有事务中同时清除授权目录，与条目、派生缓存、双PIN和Identity轮换共同提交或回滚。不能沿用旧草案“重装Monoid保留Safe授权”或“Monoid卸载清除所有PIN”的结论。

## 客户端身份SIO

[user] 认为独立拆出Monoid API的现实收益不明显。[agent] 据此收敛为接口与实现同包：当前没有已经需要独立维护的客户端生态，Monoid重装仍需恢复数据和重新授权，额外接口CAP带来的安装与版本管理成本缺少对应收益。当前批准的是本节客户端身份接口，完整服务签名仍需后续确认。

[agent] 按用户提出的合包方向，公共接口可直接放在Java包`monoid`，与实现一起生成`monoid.cap`，不另建`monoidapi`包或`…03`库CAP。其他Applet仍位于各自独立CAP，通过Monoid的export文件链接公共Shareable接口。本阶段只需下述客户端身份接口；原Safe数据SIO已在合并时移除，不照搬134的迁移清单。Monoid的服务接口在下一步按实际调用确认。

这个组织方式会使客户端CAP依赖Monoid实现包。采用删除并重新加载CAP的代码升级方式时，须先删除依赖它的客户端包；仅删除/重建Monoid实例不等于更新代码，另外仍受存活对象引用约束。此前独立接口CAP方案的收益是隔离该代码包依赖，不是Shareable本身强制要求；独立库也不自动解决持久SIO引用或接口自身升级问题。依据：[Oracle包依赖删除规则](https://docs.oracle.com/en/java/javacard/3.1/guide/using-card-installer-deletion.html)。

```java
package monoid;

public interface MonoidClientShareable extends Shareable {
  /** Copies SHA-256 of the client's private 32B token; returns 32. */
  short getTokenHash(byte[] dest, short offset);
}
```

客户端以shareable parameter `0`提供此接口。dest为Monoid提供的global数组；客户端只返回hash，不向APP暴露私有token。客户端安装时生成随机32B token并自有保存；同AID重装产生新token，旧授权不能自动继承。这个token与Identity按AID稳定派生的绑定token用途不同，不能互换。公开hash不证明客户端代码可信，用户授权仍表示信任其实现。

[user] 询问此前Monoid生成token的讨论是否与此相关。[agent] 131最初只写卡内随机授权凭证及客户端私存，未限定生成方；135明确此前token就是这种capability，而134草案已经写成客户端安装时生成。当前查到的记录不足以确认曾批准Monoid生成/发放。由Monoid在用户授权时生成并经SIO交付也可实现，但须限定交付时机，新安装的同AID客户端不能直接领取旧token；这需要不同的客户端回调接口，仍待讨论。148/152已实现的Identity派生token则由Monoid保存，用来检测Identity更换，属于另一条绑定关系。

## 后续接入边界

授权管理落地后再接调用方绑定的Monoid会话、受限条目代理、固定Key选择及seed派生/签名。保留RESET生命周期、实时撤销、真实JCRE调用方核对及回调前后校验；不用普通APDU的DESELECT授权状态来要求每次FIDO先解锁Monoid。

当前`Safe.checkAccess()`仍从`Command.requireAuth()`建立本地存储访问状态。未来SIO必须从已认证的客户端会话建立独立、限于该次调用的入口，不伪造APDU授权，不沿用上一次命令留下的Safe授权状态。管理命令阶段仍走现有Secret认证与Safe访问路径，不提前放开数据或签名入口。

当前P-256/Monoid-001具有跨Applet实卡验证；BIP32、Ed25519等固定Key可在权限描述中表达，但尚需工作区生命周期适配，不能在管理API落地时宣称已经能通过SIO调用。精确签名SIO、domain编码和数据代理接口继续沿用134的待讨论状态，本次确认不隐含批准它们。

[agent] 当前`CommandSet`允许替换同一index的data，因此固定Key描述不自动等于永久固定私钥材料。接入签名SIO前须确定源数据变化后继续引用还是使授权失效；同样需确认固定Key的cipher/Taproot操作范围和keySlot选择签名。这些尚未决定的行为不在本阶段提前实现。
