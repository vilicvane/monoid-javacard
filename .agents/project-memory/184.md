# Security Key 凭证隔离与使用记录

[user] 同网站、同账户在不同卡上分别注册，本身就是不同凭证。暂不加入删除标记，希望按业务合并；要求考虑切换 seed，避免不同组的记录相互干扰。随后提出快速找到可能需要整理的记录，通过 recent 标记或使用序号帮助 APP 用户决定删除。

[user] 最终批准将账户名称附加索引与 seed/domain 隔离一起实现。

[user] 在明确无用户名登录会为多个候选都生成断言后，指出使用序号意义有限；有用户名、网站指定凭证的流程本身不需要靠这个记录筛选凭证。

[agent] 因此撤回新增 recent / lastAssertion 活动字段的建议，不继续推进其计数器或轻量写入接口。核心问题是无法从候选签名推知最终选择或有效性，优化字段更新成本也不能解决这个问题。以下方案仅保留为弃用理由，不是待实现事项。

## 讨论依据与边界

- 注册生成随机 32B Credential ID；Safe index 为 F101 加 ID 前 8B，查询核对完整 ID 和 RP。相同账户的独立注册不能据此合并成同一凭证。
- 修改前 CredentialStore 仅按 RP hash 筛选，再比较 user ID 做 resident 注册替换；切换 seed 后可能发现或替换另一组记录，公钥复核只能防止以错误派生密钥完成签名。
- 使用 seed 和授权 domain 对应的稳定派生身份隔离记录；不能使用卡片 ID、安装 token 或 seed 的本地 index 作为跨卡相同身份的依据。
- CTAP 注册不提供创建时间，当前卡片没有可用日历时钟。APP 首次发现的时间不是创建时间，不能用于判定两份凭证的新旧或失效。
- 网站提供 allowList 时只匹配列出的 ID；无用户名登录会发现多份本地 resident 凭证。卡片保留记录不会撤销网站端的撤销决定，但残留记录可能出现在账户选择列表。
- 无删除记录时，无法区分另一张卡从未接收某凭证和已经删除该凭证。不应将记录缺失、较旧或未被本次 allowList 列出视为删除证据。
- 当前 signCount 始终为 0；活动元数据不能直接替代它。继续保持 0 是建议，未因本轮讨论改变行为。

## 已撤回的活动记录方案

[agent] 相比相互排他的 recent 标记，建议记录递增的本地活动序号；只更新本次实际生成断言的记录，不扫描改写其他同组记录。APP 可按派生身份、RP、user ID 分组，辅助人工清理。

CommandGetAssertion.respond 在返回每份候选时生成签名。客户端可以先取完 GetAssertion/GetNextAssertion 的所有候选，再在卡外选择一个；卡片既不知道最终选择，也不知道网站是否接受。因此字段只能表示最近生成断言，而不是最近成功登录。同一轮 GetAssertion 和 GetNextAssertion 应共享活动序号，不能让候选枚举顺序成为虚假的使用先后。

序号只在同一计数来源内可比；不同卡或计数器重建后的值不能直接比较大小。跨卡导入时怎样保留本地活动信息、标识计数来源，尚未确定，不自动取最大值作为跨卡时间。

现有 SafeItemShareable.setData 会替换整条 data 并影响快照缓存。不能仅凭活动字段只有几个字节就声称更新廉价；若实现，需要核对轻量写入及缓存失效方式，必要的 API 变化先给用户确认。

注册替换规则、跨卡业务合并和人工清理是不同操作。记录活动不能自动替代 resident 新注册时已有的替换行为。Reset 当前删除整个 F101 Type 并清除单一 FIDO PIN；是否调整到派生身份范围须另行讨论，不随隔离方案静默缩小 Reset 范围。

## 已实现的账户显示标识

[user] 询问能否在系统验证界面的可用账户列表加入 credential index，方便发现失效凭证后到 APP 定位并删除。

[agent] CTAP 没有控制系统 UI 的自定义 index 列；GetAssertion 返回的 user.name/displayName 是平台账户选择的显示信息。可以在 Credential.writeUser 输出时附加由既有 item index 得到的标识，保留原始存储名称、user.id、完整 Credential ID、派生和签名。固定 Type F101 可省略，剩余 8B 用 16 位 hex 表示；若显示更短片段，APP 不能把片段当作唯一删除标识。

两种名称在输出时附加完整 16 位大写 hex 标识。原名称按 UTF-8 边界截断，使总长度不超过 64B；原存储名称不变，无名称时返回 displayName 为方括号中的标识。沿用现有 UV 后返回名称的限制。新增公共 CBORWriter.textLength 配合 rawBytes 输出分段文本，不为每次输出分配完整名称副本。系统选择 name/displayName、截断和账户去重行为仍需要 iOS/Windows 实测。标准依据：[CTAP2.0 GetAssertion response user](https://fidoalliance.org/specs/fido-v2.0-ps-20190130/fido-client-to-authenticator-protocol-v2.0-ps-20190130.html#authenticatorGetAssertion)。

## 已实现的隔离与验证

scope = SHA256(Monoid.getMonoid001PublicKey(scopeContext))，scopeContext 为 ASCII `monoid fido2 scope: ` 加 58 个零字节。总长 78B 与凭证 context 相同，避免 Monoid 在两种 context 长度之间反复分配持久 frame；用途前缀与凭证签名的 `monoid fido2: ` 不同。使用既有 SIO，不新增 APDU 或 Shareable 方法。

Credential CBOR 新增必填整数 field10（scope32），lookup key 改为 scope32 || rpHash32；index、完整 Credential ID、user ID 和实际签名派生输入不变。Make/Get/Next 每次重新取得 scope，覆盖同一 seed index 原位修改数据。查找、excludeList、resident 替换、缓存及两种枚举路径都按复合 key 匹配。GetNext 还比较本轮保存的 scope，拒绝跨 scope 延续列表。

新增编码使每条记录增加 35B、lookup key 增加 32B。四条持久缓存及短记录工作区的容量从 256B 调为 320B，避免原来能缓存的记录仅因新增字段退出缓存；不将这部分容量转为 transient RAM。旧凭证没有 scope，不自动认领或迁移，也不会被新 scope 的注册替换删除；升级已有凭证另需迁移或重新注册。

Reset 保留清除所有 F101 凭证和 FIDO PIN 的语义。派生身份用于凭证查找隔离，不是进一步收紧 Type 授权；被授予 F101 读写的客户端仍拥有其 Type 权限。

本地610项Java测试、69套件及四CAP构建/验证通过。单元覆盖名称/UTF-8/UV、schema完整性、暖缓存、切回恢复及大于四项枚举；真实组合模拟器通过domain切换、同index改seed后恢复、resident替换/排除隔离、多账户独立验签、不同卡/seed index相同配置的scope稳定性，以及独立ViewKey结果核对。GetNext的重新选卡终止列表已覆盖，未伪称测试了不经deselect的并发授权修改。此次没有实卡或iOS/Windows界面验证，也没有测量新增scope查询的延时。
