# BIP340 and BIP86 basic verification — 2026-10-12

The user approved basic validation after discussing Taproot feasibility. This
is an isolated experiment in the Java Card repository, not approval to change
the production signing API. Production source, Monoid APP, original card
applets and their data are unchanged. Experimental Java, host scripts, vectors,
CAPs and logs are under ignored `.research/taproot/basic/`.

The probe reuses current `CurveSECP256k1` hardware XY ECDH for scalar-to-point
multiplication, SHA-256, `LibMath` modular arithmetic and `LibBIP32`. It adds
software BIP340 tagged hashing, nonce generation, even-Y normalization and
`s = k + e*d mod n`, plus BIP341 private-key TapTweak. For BIP86 the Merkle root
is absent. Because the private scalar is available, the output point is derived
as `(normalized d + tweak)G`; no generic point addition or new curve engine is
needed. This confirms feasibility using existing hardware primitives, not a
native BIP340 signing implementation.

Both jCardSim and the physical card pass seven groups with 48 independently
verified signatures each:

- All eight official BIP340 signing vectors with private keys (indices 0–3,
  15–18), including 0/1/17/32/100-byte messages, match signatures byte for byte.
- Invalid private scalars zero and n return exactly 6A80 without data in the
  raw-sign, tweak and tweaked-sign commands. Valid signing immediately afterward
  succeeds.
- Thirty modular multiplication pairs modulo the secp256k1 order match a host
  BigInt oracle, including zero, one, n−1, odd/even half-order boundaries and
  carry-producing operands.
- Official BIP86 paths `m/86'/0'/0'/0/0`, `m/86'/0'/0'/0/1` and
  `m/86'/0'/0'/1/0` match the published internal and output keys. Complete card
  operations derive the master from the public mnemonic's 64-byte seed, derive
  all five BIP32 levels, apply TapTweak and sign a fixed 32-byte digest.
- Alternating even/odd public-key parity and negated private scalars reuse the
  same shared curve/math context correctly. Repeated operations and actual
  PC/SC reset/reselection reproduce valid signatures without relying on previous
  transient contents.

The host uses ethers HD derivation and noble Schnorr verification plus exact
deterministic signature comparison. Its own oracle check passes all 19 official
BIP340 verification vectors; those 19 verification cases run on the host, not a
new card verifier. The card has no Schnorr verification implementation.

Physical device: ACS ACR1552 1S CL Reader PICC 0, T=1, ATR
`3b8a800150564a434f503453494471`. Three-repeat complete-command timings in ms:

| Operation                       |  Median | Minimum–maximum |
| ------------------------------- | ------: | --------------: |
| Raw BIP340, 32-byte message     |  417.30 |   417.25–417.43 |
| TapTweak + BIP340               |  544.47 |   544.23–544.63 |
| BIP32 + TapTweak + BIP340, /0/0 | 1113.96 | 1113.69–1114.01 |
| BIP32 + TapTweak + BIP340, /0/1 | 1096.62 | 1096.60–1097.68 |
| BIP32 + TapTweak + BIP340, /1/0 | 1097.18 | 1096.75–1098.02 |

The first complete /0/0 operation after physical reset takes 1117.86ms. These
timings include APDU transport and explicit diagnostic public-key derivations:
raw sign returns an extra public key; tweaked sign returns the output public
key; full derivation returns both internal and output public keys. They exclude
host verification, SELECT and memory queries. They are not primitive-only
measurements, production Monoid latency or directly comparable to record 76's
authenticated application workflow.

Idle available memory is stable at RESET 3202B / DESELECT 3200B before and after
every sampled group, including reset. These are overlapping memory categories,
not additive pools, and not peak measurements. Persistent readings saturate at 32767. This minimal Applet initializes only required crypto resources; it does
not establish RAM capacity when integrated with the complete Monoid applet and
its Ed25519 context. Signing's local arrays total 194B, plus 130B allocated by
two existing point derivations, excluding object headers and shared resources.

Production integration remains unimplemented. It still needs explicitly
approved API/capability semantics, Safe/Keystore integration, full-app memory
validation and an auxiliary-randomness policy. The experimental aux input is
deterministic public test data. BIP340's signing self-verification step is not
implemented on card; independent host verification was used for this test.
Non-empty Merkle roots, script-path spending, transaction sighash construction,
address encoding, transaction broadcast and multisignature protocols are not
validated here. The extremely rare nonce-zero, tweak-at-least-n and tweaked-key-
zero branches exist but were not forced by the vectors.

Both isolated CAPs target Java Card 3.0.5 and pass conversion/verification with
zero errors or warnings. Initial simulator memory-query failure was traced to
the bridge omitting `com.licel.jcardsim.object_deletion_supported=1`: jCardSim
otherwise throws from `requestObjectDeletion` at command completion. Enabling
that simulator setting fixes the bridge; no card algorithm change was needed.
Simulator memory reports the constant 32767 and is not hardware evidence.

Cleanup is complete: probe package `F06D6F6E6F69647E` and its isolated Safe
dependency `F06D6F6E6F69647D` both uninstall successfully. Before/after GP registry
logs match exactly, both temporary instances return 6A82 and both original
Monoid/Safe instances return 9000. The reader connection was released.
