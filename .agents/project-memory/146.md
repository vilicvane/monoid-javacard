# 通信临时私有数组持久化

## 请求与实现

- [user] 在确认 record143 的实验支持采用持久化后，批准将这批临时私有数组直接改为持久化，保留共享 AES-GCM 和 16B 缓冲，再实卡测组合后的内存与性能。
- [agent] `monoid.Utils.makePrivateByteArray` 与 `monoididentity.CommunicationData.makePrivateByteArray` 直接返回 `new byte[length]`，删除 512B 阈值、transient 分配/异常回退分支及无用 import。保留既有分配入口与调用方组织方式。
- 涉及 CreateBundle 的成员公钥列表、Safe Import 的输入快照，以及 Identity 的公钥/元数据快照、context hash、通信密钥/HPKE 包和条目明密文结果。这里的“持久化”是存储介质选择，临时对象并不成为永久保存的记录。
- 共享 AES-GCM、16B 批量写出、AES/GHASH/HMAC 工作 RAM、跨 Applet global 缓冲和 APDU 传输逻辑不变。Safe 中一行旧注释同步为预留跨 Applet 读取缓冲；没有调整缓冲申请顺序或 API。
- Import 仍先完整验证 tag，再发布条目；Bundle 仍先准备好新状态，再事务性替换。失败产生的临时持久对象不发布，原条目/Bundle 保留。
- Export 的结果引用存活到 GET RESPONSE 完成或取消；writer reset、deselect/复位清引用及既有命令结束/续传 GC 请求继续工作。没有新增 static 引用、dispose 或 GC 调用。
- 代价是额外持久写入和临时持久空间占用。Safe 的 4KiB guard 仍在最终条目分配前执行，不能把它描述为对之前全部临时解密/快照分配的保证；本轮没有新增 guard 或满卡实验。

## 本地验证

- 三项既有测试首次失败，因为仍断言小数组为 transient；已将两份测试中的四处分配类型预期同步为持久对象，保留独立密码学与输入不变性断言，没有改动密码学实现。
- 最终 310 项测试、39 个 suite 全通过，零失败/错误/跳过。两份正式 CAP 转换零错误/警告、Verifier 通过；定向格式检查通过。
- 生产行为变化只有上述两个 helper，另有一行注释更新。其余源、共享实例和 16B 缓冲均核对冻结哈希。

## 实卡方法

- 测试卡 CPLC `51433520`，ACS ACR1552 PICC、T=1；开始时仅有系统 registry。使用 E0 Identity / E2 Monoid 临时包，不安装正式 AID。
- 性能两版均在本轮重新安装并运行：baseline 为 record145 的共享 AES/16B 加原 RAM 优先策略，persistent 为共享 AES/16B 加本轮持久策略。每版 71 次完整操作、14 个场景，各一次预热加三次正式样本，共 42 个正式样本/版。
- 保留相同请求顺序、长度、fixture、host 密码学验证和 PC/SC 计时边界；时间包括请求分片及 GET RESPONSE，排除 host 运算/编码/SELECT/准备命令。Import 的正式样本为幂等重试，CreateBundle 为替换已有 Bundle。
- 性能按 baseline→persistent 顺序独立安装，未随机化或交错；小差值仍受对象布局和运行顺序漂移影响。
- 内存基线直接复用 record145 同卡共享版本的完整 152 操作报告及相同 CAP，固定 SHA-256 校验，不伪装为本轮新测量。持久版重新跑相同的 152 操作和检查点协议。
- 持久版探针去掉两 helper 中已删除分支对应的采样调用，原编号保留为空槽，比较器验证这些点没有采样，其余检查点不变。移除插桩后候选源与生产源完全匹配；无新增 transient RAM。插桩时间不用于性能结论。

## 实卡结果

两组未插桩性能均 71/71 通过，共 142 次完整操作、84 个正式计时样本。以下均为三次样本的中位数，单位 ms；两版都已共享 AES-GCM 并使用 16B 批量写出。

| 操作                  | RAM 优先策略 | 私有数组持久化 | 持久化额外耗时 |
| --------------------- | -----------: | -------------: | -------------: |
| 非对称 Import 32B     |      1568.19 |        1627.84 |         +3.80% |
| 非对称 Export 32B     |      1506.68 |        1575.47 |         +4.57% |
| 非对称 Import 256B    |      2849.52 |        2954.50 |         +3.68% |
| 非对称 Export 256B    |      2927.86 |        3055.35 |         +4.35% |
| 非对称 Import 1024B   |      7473.64 |        7493.49 |         +0.27% |
| 非对称 Export 1024B   |      7677.65 |        7696.58 |         +0.25% |
| Create Bundle，三成员 |      2316.09 |        2373.78 |         +2.49% |
| Bundle Import 32B     |       901.64 |         932.84 |         +3.46% |
| Bundle Export 32B     |       816.11 |         851.27 |         +4.31% |
| Bundle Import 256B    |      2169.39 |        2258.99 |         +4.13% |
| Bundle Export 256B    |      2238.63 |        2318.35 |         +3.56% |
| Bundle Import 1024B   |      6818.86 |        6801.92 |         −0.25% |
| Bundle Export 1024B   |      6992.37 |        6980.34 |         −0.17% |
| Import Bundle，三成员 |      1001.28 |        1029.64 |         +2.83% |

- 32/256B 传输增加 31.19–127.49ms、3.46–4.57%；256B 四项为 79.72–127.49ms、3.56–4.35%。这是可见的持久化代价，并非共享实例的额外成本。
- record143 所说从约 31–35% 降至 3.9–4.7%，指持久策略相对同阶段 RAM 策略的额外耗时降低，仍然比 RAM 慢；不能解读为采用持久化会使小数据传输提速。本轮用户确认这一开销可以接受。
- 1024B 四项变化 −0.25% 到 +0.27%；原策略的大结果本就使用持久存储，不将这种小幅变化归因为稳定优化。
- 两组三样本极差占中位数分别 0.069–0.644% 和 0.113–0.913%，未发现明显离群。每项三次、独立顺序安装的限制仍保留。
- 两组 fresh 均 RESET2165/DESELECT2160B，warm 均 RESET1640/DESELECT1632B。临时数组改变的是操作内余量，不改变正常回收后的空闲 RAM。
- 142 次完整命令的计时均与原始 APDU 请求/GET RESPONSE 日志逐笔核对一致，所有条目及入组包由独立 host 密码学校验。

持久版内存流程 152/152 通过。与复用的 record145 基线逐操作比较，99 项的最低可用 RESET 增加，53 项不变，没有下降；DESELECT 读数也没有下降。本轮新执行合计 294 次完整实卡操作（142 次性能、152 次内存），不将历史基线的 152 次重复计数。

- 流程全局最低 RESET 从 142B 增至 352B，DESELECT 从 128B 增至 352B。两类读数不能相加。
- 签名阶段读数不变：Ed25519 View 936B、Sign 632B，BIP32 View 647B、ECDSA Sign 1152B；公钥、chainCode 和签名均独立核对通过。
- 签名后 256B Bundle Export/Import 从 459/474B 增至 842/836B；1024B 从 810/732B 增至 842/836B。各阶段、方向、长度连续三次传输读数稳定，没有累计 RAM 下降。两版最终签名预热后的空闲 RESET/DESELECT 仍为 1544/1536B。
- 重新入组发生在签名前；签名后重复的是条目传输，没有重新测入组。因此 352B 不是所有操作顺序或更低 RAM 卡片的保证。
- JCSystem 检查点报告的是可分配上界，原生算法内部创建又释放的瞬时内存不在采样内。持久空间读数饱和于 32767，不能据此声称持久占用没有增长；本轮没有满卡持久 GC 或写入耐久测试。
- 完成后删除 E0/E2 的全部临时实例及包，注册表与测试前一致；未安装正式 AID。最终格式及 diff 检查通过，363 项性能输入和 432 项内存输入冻结校验通过；暂存区和无关未暂存改动与本轮开始快照一致。

“重新入组”是测试先 Reset Bundle，再调用同一个 `0x24 Import Bundle` 恢复原配置的名称，不是新命令。处理32B Bundle key和成员名单，不复制Safe条目；与普通入组共用解密路径。验证成员、两次P-256 ECDH、HKDF、AES-GCM及tag完成后，计算hash并发布或核对已有配置。

当前三成员重新入组请求为403B。实测 RESET 可用读数依次为1640B（操作开始）→1128B（分片接收完成）→760B（字段解码完成）→384B（跨Applet global副本）→352B（预留返回hash）。请求分块/解码/global副本同时存活是当前主要RAM占用；这批私有数组持久化后，65B本卡公钥、113B封装、32B解密key不再将其压到142B。此处是API可分配上界的检查点读数，不是每个对象含头部的精确占用。

tag 是 AES-GCM 的 16B 认证标签；接收卡核对全部字节，验证成功后才返回解密得到的密钥。已有 Bundle 时，Import 完成同一套密码学验证后，比较实际 32B 密钥及规范化成员公钥列表。二者相同则返回当前 hash，不替换配置；任一不同则返回 6985 并保留原 Bundle。这里不要求密文字节相同，重复导入仍然执行解密与认证，并非仅比较公开 hash 或直接短路成功。
