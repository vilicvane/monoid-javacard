# Merged Monoid storage and future export lock

[user] Reconsiders merging Monoid and Safe. Their original separation allowed
more frequent Monoid updates, but a newly installed Monoid with the correct
Safe PIN can retrieve stored private keys. The intended meaning of secret is
that its contents stay on-card, at least after cross-card backup is disabled.
The user subsequently explicitly requests merging the two Applets, preserving
the existing code organization and style, without implementing the lock.

[user] The installer defaults to Install. Clearing Safe data and both PINs
requires explicitly choosing ReinstallMonoid. Do not block old installations
or add migration machinery: the prototype has no external users yet. Identity
keeps its existing name for now.

[user] Also approves merging the former MonoidSafeApplet storage implementation
and the Safe wrapper into Safe itself, rather than retaining the interim
SafeStore class and its forwarding layer.

[user] A future per-card lock may be applied after backup. A primary card can
be locked while a backup card stored away remains unlocked. The lock means
disabling key export and backup while retaining signing and Applet installation;
it is not a GlobalPlatform installation lock. This is a future direction only:
consider compatibility in current architecture/API design, do not implement or
expand its detailed design now. Reversibility and upgrade/recovery policy are
not settled.

[agent] Before merging, Safe admitted Monoid by AID prefix,
then a new caller verifies its own session using the Safe PIN. SafeSessionItem
getData and SafeSessionData.read return raw bytes without checking secret;
the secret restriction is in Monoid's CommandGet. This does not rely on
inheriting another caller's authorization or bypassing the Java Card firewall.
Export also accepts a caller-supplied recipient public key without
attesting that the recipient is a card. No export-lock feature exists yet.

[agent] Compatibility implication for the evolving grant proposal in 134:
do not promise that Type permission or knowledge of the Safe PIN overrides
secret protection. Keep key use and raw-data access distinct. A future lock
must be enforceable where secrets are held/used, rather than solely by an APP
or independently replaceable frontend. The lock remains deferred, and the
grant API itself still requires agreement before implementation.

[agent] The merged layout keeps package/applet 02 as Monoid and package/applet
00 as the separate Identity. Safe combines MonoidSafeApplet storage with the
existing type/index validation. The interim SafeStore and forwarding layer are
removed; raw creation is a private createItem helper beneath validated create
overloads. SafeItem
absorbs its session wrapper, SafeStoredData retains read snapshots, and

three-round checks, encoded results and authorization/complement state remain.
The public Monoid Shareable interface remains empty: this does not implement
the grant or CTAP API.
