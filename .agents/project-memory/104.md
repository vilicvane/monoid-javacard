# P-256 credential-key derivation discussion — 2026-10-15

[user] Wants derivation from the newly supported secp256r1 keys, using inputs
such as Credential ID for future Passkeys. Existing standards or a custom
scheme are acceptable candidates; requested ideas before implementation.

[agent] Recommended candidate: HKDF-SHA512 using the existing high-entropy,
32-byte P-256 private scalar as input keying material, followed by rejection
sampling of 32-byte candidates into the scalar range 1 <= d < n. Reuse
LibHMACSha512. A fixed versioned domain label and an unambiguous encoding of
curve, purpose, context and retry counter must be specified before coding.
This is a Monoid derivation profile built from standard components, not a
standardized Passkey KDF or the full RFC 9180 algorithm. Exact encodings and
API changes have not been approved. No production code or card was changed.

- [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869.html#section-3.2)
  defines HKDF context binding through info. Extract followed by one Expand
  block suffices for a 32-byte candidate; SHA-512 is suggested to reuse the
  current HMAC implementation, independently of ES256's message hash.
- [RFC 9180, section 7.1.3](https://www.rfc-editor.org/rfc/rfc9180.html#section-7.1.3)
  provides a deterministic P-256 key-generation precedent using labeled HKDF
  and rejection sampling. Its P-256 KEM specifically uses SHA-256; borrowing
  its sampling pattern does not make this proposal an HPKE implementation.
- [SLIP-0010](https://github.com/satoshilabs/slips/blob/master/slip-0010.md)
  already supports P-256, including retry rules and test vectors. Its nodes
  require private key plus chain code and its children use numeric paths.
  Current standalone P-256 items have no chain code; using them as seeds or
  mapping Credential IDs to paths requires further conventions. Current
  LibBIP32 intentionally supports only secp256k1.
- [SLIP-0022](https://github.com/satoshilabs/slips/blob/master/slip-0022.md)
  defines FIDO2 credential IDs for HD wallets: ChaCha20Poly1305-wrapped CBOR,
  RP ID hash as AAD, SLIP-0021 wrapping-key derivation and SLIP-0010 credential
  keys on hardened paths derived from the authentication tag. Full adoption
  is broader than adding a context-based P-256 derivation primitive, but is
  relevant if interoperability with that wallet format becomes a goal.

Passkey context should bind purpose/version, RP ID hash and Credential ID.
The low-level primitive can accept opaque context bytes; the Passkey layer
must encode them consistently and enforce the RP association. Credential ID
is generated by the authenticator and need not be secret; random 32-byte IDs
are a candidate for per-registration uniqueness. Arbitrary IDs producing a
key does not prove that a credential was issued: lookup records or an
authenticated credential format remain necessary.

Deterministic private-key recovery does not recover a credential inventory.
Discoverable credentials still need stored RP, Credential ID, user handle
and other required metadata. The lookup-key prefix filter from record 105
can enumerate keys beginning with RP ID hash. Backups need the root plus derivation
inputs/metadata; deleting metadata alone does not erase the mathematical
ability to derive a key. See [WebAuthn Credential ID](https://www.w3.org/TR/webauthn-3/#credential-id)
and [credential storage modality](https://www.w3.org/TR/webauthn-3/#sctn-credential-storage-modality).

No performance claims were measured for this proposed derivation.

[agent] A repeated plaintext root-key index in Credential IDs would enable
cross-RP correlation. Keeping the index in local credential metadata avoids
that identifier exposure. Locating the root still does not implement P-256
context derivation: current standalone-key Sign uses the stored scalar
directly, and adding derivation remains a separate, unapproved API proposal.
