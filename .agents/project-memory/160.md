# Plaintext recovery boundary with and without a Bundle

> Current scope: [162](./162.md) supersedes the proposal-only status below for the
> approved Secret PIN migration, per-member sending keys and full Identity Reset.
> The user deferred Extend Bundle; fixed membership remains. The discussion below
> records earlier design reasoning, not additional approved APIs or validation.

- [user] With a Bundle, plaintext recovery must require the Safe PIN and a second card. Without a Bundle, the Safe PIN alone is sufficient.
- [agent] This is the new target boundary, not a property established by the current implementation. Record159's Identity reset invalidates old local artifacts only when Reset executes; it does not prevent same-AID Monoid replacement that preserves Identity/Bundle and skips Reset. Its local tests do not establish this new boundary, and it has not been physically tested.

An agent proposal under review is to authenticate the actual sending Identity in each artifact and have Identity reject Bundle decryption on that same originating card. A sender value supplied by the APP cannot establish this property. The design must also prevent preexisting self-addressed HPKE artifacts from bypassing the restriction while a Bundle is installed. Exact protocol, API and authorization changes are not approved or implemented.

The user has not specified whether an offline recovery package previously produced by the second card is sufficient, or whether every recovery must physically present the second card again. These are different requirements and must not be conflated.

Record158's same-card transfer proposal conflicts with this boundary when bundled; the resolution is undecided. Do not treat it as an approved self-transfer exception. No production/public API documentation changes or new validation accompany this record.

- [user] Proposed one sending key per Bundle member: in a three-card Bundle, each card has three keys, but its own key is usable only for encryption and the other members' keys for decryption. This is a design proposal, not approval of exact APIs.
- [agent] Suggested deriving each member's key from the Bundle root, runtime caller AID and member identity instead of persistently storing N keys. Identity selects only its own sending key internally, rejects decryption under that key and permits other members' keys. The source identity must be authenticated, not trusted from an APP-supplied label. Symmetric keys have no inherent encryption-only property; trusted Identity code enforces this restriction. No production implementation accompanies this proposal.

## Preferred direction after dual-card experiments

- [user] Considered deriving a different GP management key set for each member, with each card authorizing management of the other members. Subsequently judged the management complexity too high and preferred the per-member data encryption/decryption keys above.
- [agent] GP management was not changed. Exporting a target's long-term SCP keys would let the phone retain management authority; keeping those keys on the authorizing card would still require the target's SCP session to survive. Pre-signed GP Tokens are another option, but do not inherently provide single-use authorization and require closing alternate management paths. This is background analysis, not the selected implementation.

## Safe PIN owned by Identity

- [user] Proposed moving Safe PIN into Identity and requiring successful Safe PIN verification before decryption, strengthening the intended workflow to two cards plus both cards' PINs. Users may choose different Safe PINs for the members.
- [agent] Current source still owns Safe PIN and its retry/authentication state in `monoid.Safe`; Identity does not verify a PIN. `CommandExport` requires Safe authentication, while `CommandImport` permits ordinary authentication. The proposed change would therefore tighten Import to require the receiving card's Safe PIN and preserve that PIN across Monoid replacement when Identity is retained.
- [agent] Recommend keeping PIN storage, retry accounting, verification, PIN-change authorization and the cryptographic operation gate together in Identity. A caller-supplied success flag is insufficient. To enforce both ends at the same trust boundary, also gate the sender's encryption/export with its Identity-owned PIN rather than relying solely on Monoid's check. Verification authority must not implicitly unlock unrelated caller AIDs.
- [agent] Migration trap: current `Safe.checkAccess()` accepts ordinary Command authentication and writes its internal `AUTH_SAFE` state to permit trusted Monoid storage access. That bridge is not proof of Safe PIN verification and must not become Identity's decryption gate; only successful PIN verification inside Identity may establish that authority.
- [agent] Replacing Monoid must not permit reinitializing an already configured Identity PIN. An unauthenticated factory Reset may clear the PIN only together with the identity keys/Bundle, so it cannot retain old decryption capability under a new PIN. Exact SIO/APDU semantics, authorization lifecycle and initialization changes remain to be agreed; no production implementation or hardware test accompanies this proposal.
- [agent] Both PINs are independently checked on their respective cards; they need not have different values. The requirement describes the authorized export/decryption chain, not fresh knowledge of both current PINs on every later use of previously released plaintext or recovery artifacts. The earlier offline-versus-live participation question remains distinct.

## PIN naming

- [user] Suggested renaming Safe PIN to Secret PIN because of its role in protecting `secret: true` data.
- [agent] Include the PIN terminology change in the planned work. Proposed public-field updates are `Hello.pins.safe` to `Hello.pins.secret` and Authenticate/Set PIN `safe?: true` to `secret?: true`, together with PIN-specific code names and documentation. These wire changes are part of the API proposal, not implemented changes.
- [agent] Treat this as naming, not an implicit narrowing of authorization to records whose flag is true. The proposed Identity gates still apply to export/encryption, import/decryption and Bundle management. Ordinary signing remains available through Access authorization, and Secret PIN does not turn `secret: true` into plaintext Get permission. Safe storage/item class names are a separate concept and are not renamed by this PIN proposal.

## Admission of another member

- [user] Proposed allowing a new card to join a Bundle with two-card participation.
- [agent] Interpret this as approval by two distinct existing members of the same Bundle, each verifying its own Safe PIN inside Identity. The joining card does not count as an existing authorizer. The user subsequently preferred the proposed flow below; exact APIs/protocol remain unapproved.
- [agent] Candidate flow: collect C's Identity public key; A verifies its Safe PIN and produces a recipient-bound admission approval; B verifies its Safe PIN, authenticates A as another existing member and checks approval of the same Bundle and C; only then may B encrypt enrollment material to C. C sets/verifies its own Safe PIN and installs the new membership. Ordinary one-member encryption/decryption APIs must not produce admission approvals or release enrollment root material.
- [user] Considered a nonce variant: collect C's key, A generates a nonce, B signs it, A verifies and encrypts enrollment data to C, and C joins. Then recognized that collecting C's public key first also closes the originally proposed flow and preferred the original C-to-A-to-B-to-C flow as easier to implement.
- [agent] The selected direction binds A's dedicated admission approval to the Bundle and C's full public key before B acts. B checks that A is another existing member of its current Bundle and verifies its own PIN before generating the recipient-bound envelope. C's public key survives ordinary power loss, so no live C session or return visit to A is needed. A need not retain a pending nonce across taps. Retrying an approval for the identical C identity is distinct from reusing it to authorize another member; exact replay/commit behavior remains to be specified.
- [agent] The alternative return-to-A nonce flow is viable if A securely preserves the nonce-to-C/Bundle binding across power loss and B signs within a dedicated admission domain bound to its own current Bundle. It was not selected, and no pending-nonce persistence or nonce API is authorized by this discussion.
- [agent] Proof of distinct approval must use the individual Identity authentication boundary. A MAC derived solely from the shared Bundle root cannot prove that two different members participated. Exact authenticated encoding, recipient binding and replay semantics remain design work.
- [agent] For portable membership updates, prefer two Identity signatures over the same dedicated admission statement: other offline members can later verify both approvals. An HPKE envelope addressed only to C is not by itself a publicly verifiable second approval. This proposes a constrained admission-signing capability, not a generic Identity signing oracle.
- [agent] Retaining the root and deriving sender keys by stable member identity avoids re-encrypting existing artifacts. Other members need an authenticated admission update before accepting the new sender; they need not all be present during admission. Root-based `Hello.bundle` remains the same and does not prove equal member lists. Handling offline membership updates is required design work, not an implemented capability.
- [agent] With the same root, C gains access to previously recorded Bundle ciphertext from other members; this is historical recovery access, not future-only access. A Bundle with only one surviving authorized member cannot add another card under the proposed two-existing-member rule. No production code, public API documentation or hardware state was changed for this discussion.
