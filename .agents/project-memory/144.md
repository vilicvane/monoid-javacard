# AES-GCM 16B 与 64B 输出缓冲对照

## 请求与实验范围

- [user] 希望对比 16B 与例如 64B 输出缓冲的区别。
- [agent] 使用四个隔离版本：当前分配策略的 16B/64B，以及 record143 私有临时数组持久化实验的 16B/64B。全部位于忽略目录 `.research/gcm-batch-size-20261019/`，正式源码保留 16B；本轮不修改 API、分配策略或正式固件。
- 64B 版本仍逐个 16B AES 分组计算、逐个最多 16B 分组调用 GHASH；将原 `block` 扩为 64B，在不同偏移存储四个输出分组，满 64B 或到消息尾部时才调用一次 `Util.arrayCopyNonAtomic`。
- 没有另配第二个输出数组。每个 AES-GCM 实例增加 48B transient RAM；`ItemCipher` 与 `CommunicationCipher` 各持有一个实例，两者初始化后合计增加 96B。初始化 hash key、长度块与 tag 临时结果仍只用数组前 16B。
- 解密每块在覆盖前先 GHASH 原密文；exact in-place 操作到一个批次读完才覆盖对应范围，尾部只写实际长度。

## 验证与计时方法

- 离线隔离副本沿用项目既有模拟器 Cipher shared-access 适配；16B 和 64B 各 8 项、共 16 项测试通过。增加 47/48/49、63/65、79/80/81、127/128/129、255/257 边界，129B 偏移/哨兵和跨批次篡改、不同长度重复初始化，保留 4096B 与计数器进位测试。
- 16B CAP 使用 record143 已校验且哈希相同的产物；两组 64B 的四份 CAP 重新转换，均零错误/警告、Verifier 通过。757 项输入/生成文件核对，四版本除指定 AES 改动和既有分配策略外保持一致。
- 测试卡实际 CPLC `51433520`，ACS ACR1552 PICC、T=1；开始 registry 无 Monoid。仅使用临时 E0/E2 实例与包，正式 AID 不安装。
- 保留 record143 的 fixture、独立 host 密码学验证、命令顺序和计时边界；每个版本计划 71 次完整命令、14 个用例、42 个计时样本。所有用例包括 1024B 均一次预热、三次正式计时，比较中位数。
- 耗时包含请求分片和 GET RESPONSE 的 PC/SC transmit，排除 host 运算、编码、SELECT 和准备命令。Import/ImportBundle 正式样本为幂等重试，CreateBundle 样本替换已有 Bundle。
- 四版本按当前 16→64、持久 16→64 顺序独立安装，未随机化/交错执行；对象布局和跨轮漂移未控制，小幅收益不能视为所有卡片的稳定保证。
- 本轮 SystemInformation 是回到空闲后的容量读数，不是峰值测量；不能用它推算每个操作的保证余量。

## 结果

当前策略 16B、持久策略 16B、持久策略 64B 各 71/71 次操作通过。当前策略 64B 在第 19 次操作 `v1-export-256-warmup` 返回 CBOR `INTERNAL`，前 18 次通过；APDU SW 本身为 9000。四组常规运行共 231/232 次操作通过、135 个正式样本。失败的预热和未执行用例不作为成功计时结果。

- 上述八对用例的两组样本区间均不重叠。256B 组内极差 3.88–16.81ms、CV 0.085–0.398%；1024B 极差 2.58–37.15ms、CV 0.018–0.255%。仍保留跨轮安装/布局差异的限制。

## 失败定位

- 单独创建研究诊断版：保持当前策略64B，只在 `Command` 加 `SystemException`→`0x6F10+reason`，在 `monoid.ItemCipher.Result.read` 的 global buffer 分配处加 `SystemException`→`0x6F20+reason`。不增加字段或数组，两份诊断 CAP 零错误/警告且验证通过。
- 重放完全相同前缀，再次在 `v1-export-256-warmup` 返回 **6F22**，明确确认 `ItemCipher.Result.read` 申请 64B global array 时发生 `NO_TRANSIENT_SPACE`。诊断前 18 次操作通过；诊断计时不参与性能比较。
- record142 的原16B检查点显示，加密结束剩644B，writer分配512B响应窗口后剩132B，再分配64B global后剩68B。多出的96B AES工作区使相同路径在global分配前预计只剩36B；这是旧检查点与对象尺寸推导，当前诊断直接证明的是分配位置和异常原因，没有重新测完整峰值。
- 两个 private-array helper 的持久回退无法处理该 global array；扩大常驻工作区会影响之后的响应读取，不能只看 AES 自身是否完成。

## 结论与清理

- [agent] 本次证据支持保留正式16B：持久策略下64B只有约1–2%的大消息收益，额外常驻96B却已使当前策略的已支持请求失败。64B和持久分配方案均继续只留在研究目录。
- 诊断后四个 E0/E2 实例/包全部删除，registry、Parent/From、权限与版本恢复到开始前基线，读卡器会话结束。未安装正式 AID，未提交或推送；正式源码、暂存区和其他已有改动保持。
- [user] 追问“两套 AES-GCM 上下文”的含义。[agent] 当前 Identity 内 `CommunicationCipher` 为 HPKE 的32B通信密钥/Bundle key加解密持有一套，`ItemCipher` 为条目数据持有另一套；都按需创建并保留。源码确认通信密钥的加解密与tag验证先完整结束，再开始条目GCM，因此这些当前调用路径不要求两份GCM状态交错存活，底层实例具备共享的可能性。尚未实现或测量共享实例，不推定其实际RAM收益。
