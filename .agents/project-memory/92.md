## Procedure and transport validation

Every comparison creates a fresh DAPVerification domain `F06D6F6E6F69749003`
from built-in package/module `A0000001515350` / `A000000151535041`, with explicit
SCP02 application parameters `81020255`. Preflight confirms the physical serial,
exact original ISD keys and absence of the test AID. Only the test domain receives
its own development SCP keys and verification-key fixtures. Finally it is deleted
through ISD and its absence/original ISD keys are verified.

A temporary helper reproduces GPShell's full-command SCP02 i55 MAC calculation
before short-APDU fragmentation. It uses the existing authenticated session's
ICV, updates it once, and sends the resulting fragments directly. Non-final P1
is80 with no Le; final P1 is00 with Le00; P2 remains the key ID. Before hardware,
247 short-input cases matched GPPro's original wrapper byte for byte, and
272/275B cases matched independent Node/OpenSSL MAC vectors. CLR preserves MAC
state. Failed imports are followed by a newly opened channel for key-table
inspection. No private test key or session key is saved.

## Results

Lengths below count the complete logical PUT KEY data before its 8B C-MAC.

| Request                                       | Length | Protection  | Results                                     |
| --------------------------------------------- | ------ | ----------- | ------------------------------------------- |
| P-256 public + full parameters, omit h=1/B7   | 272B   | MAC and CLR | First fragment9000, final6A86 in both cases |
| P-256 public + full parameters, include B7    | 275B   | MAC and CLR | First fragment9000, final6A86 in both cases |
| P-256 local parameters/reference60, omit B7   | 208B   | MAC         | Single short command6A80                    |
| RSA1024 public, single command                | 137B   | MAC         | 9000, key73/01 confirmed in table           |
| RSA1024 public, force two fragments           | 137B   | MAC         | First9000, final739000; key73/01 confirmed  |
| Two RSA1024 public keys in one command, P2=81 | 273B   | MAC         | First9000, final6A86; no new keys           |
| secp256k1 public + full parameters, omit B7   | 272B   | MAC         | First9000, final6A86; no new keys           |

P-256 MAC/omit-B7 wire headers are `84 D8 80 01 FF` and `84 D8 00 01 19`, with
255B and25B of protected data; only the last fragment carries Le. The forced
short RSA control splits its145B protected data into72B and73B. Both curves use
public scalar-one fixtures and full-width standard parameters. RSA keys are
generated for the probe; only their public components are transmitted.

The short RSA success rules out total lack of PUT KEY chaining and validates
our short-command MAC/framing path on this card. The long RSA failure shows
6A86 is not specific to ECC input. GP2.3 section11.1.5.1 explicitly assigns6A86
to unsupported chaining or an exceeded implementation chaining limit. A length
restriction is therefore a stronger lead, but the exact limit was not measured;
the long RSA control also changes key count, so it is not proof of a universal
255B maximum. The local-parameter failure remains a separate6A80 provisioning
obstacle. None of these results proves rejection of secp256k1 by the verifier.

No documented buffer-size adjustment was found. Community SD parameters
`82022020` and `87022020` are extradition permissions, not buffer lengths, as
confirmed by GPTool's --allow-to/--allow-from implementation. Do not change them
or volatile-memory quotas and claim this increases the built-in SD chain buffer.
