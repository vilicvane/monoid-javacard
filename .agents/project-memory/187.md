# Authority 与 Bundle Token

[user] Authority 部署规模很小，共用一把密钥处理时间和账户/卡授权，不区分根密钥与服务密钥。Authority 公钥在 Identity 安装时指定；安装配置和 Reset 保留 Card ID 的实现见188。

[user] Bundle 应比 Authority 更强。先讨论由 Authority 对卡公钥和账户签发证书，后选择 Authority 按账户/组派生秘密 Bundle Token，减少卡间复制所需的前置交互。

[user] 证书模式的 Authority 也能授权受其控制的新卡，因此接受 Authority 决定接收资格这一信任边界。先提出禁止 Authority 来源 token 的双卡扩展，随后改为签发时可选；最终明确命名为 `allowPeerExtension` 并要求实现。Authority 自身继续签发不受该选项限制。

[agent] 本轮实现卡端接收和策略执行，复用现有 Join Bundle、HPKE Auth 和 Bundle 数据传输，不新建 APDU/SIO 方法或并行存储模式。OTP、可信时间、证书互认、服务器和 APP 尚未实现。

## 已实现流程

1. 安装 Identity 时提供可信 Authority 的65B P-256公钥；此配置不等于已经入组。
2. APP取得目标卡完整公钥，Authority按账户/组选择32B秘密token及固定的 `allowPeerExtension`，用自身P-256密钥经HPKE Auth加密给该卡。
3. APP认证目标卡Secret PIN，调用现有 `0x24 Join Bundle {publicKey,data}`：publicKey是Authority公钥，data是完整认证入组包；响应仍为 `{bundle}`。
4. Identity使用安装公钥解密认证，并发布token、扩展策略和仅包含本卡的初始快照。APP不获取明文token。
5. Authority可独立向其他卡签发同一组token，无需已有成员参与；入组后同组卡可直接离线导出→导入。
6. `allowPeerExtension=true` 时额外允许A Extend→B Approve→C Join；false时两个入口均拒绝。由成员批准的新卡继承策略，不需要安装Authority配置，也无需回刷旧成员才能互通。

手动Create继续生成随机root，默认允许双卡扩展，不增加请求字段。既有Bundle只接受相同root及相同策略的重复Join，不接受Authority覆盖root或改变策略。

## 入组包与验证

```text
header = 01 || flags || u16(memberCount) || sortedPublicKeys
flags bit0 = allowPeerExtension
flags bit1 = 本次包由Authority签发
info = SHA256(domain || header)
data = header || enc[65] || ciphertext[32] || tag[16]
```

- Authority domain是ASCII `Monoid Authority Bundle`，count必须为1，成员必须为接收卡本身。请求publicKey必须匹配安装公钥；实际HPKE解密继续直接使用安装公钥，避免仅依赖比较分支。
- 成员入组domain是ASCII `Monoid Bundle Enrollment`，count至少2，包含发送和接收Identity，成员排序无重复。双卡批准的包清除bit1但保留bit0。
- bit1是认证路径，不是持久来源标签。未知flags拒绝；两类包的完整header均受认证，不允许改变策略或切换认证模式。
- 算法沿用RFC9180 Auth，DHKEM(P-256,HKDF-SHA256)/HKDF-SHA256/AES-128-GCM；Authority同一P-256私钥完成认证加密，不附加独立ECDSA签名或新增算法。
- 策略保存在Bundle，`BundleExtension`的发起和批准入口首先检查，Join匹配root和策略。Bundle hash仍是SHA256(root)，条目密文格式/派生不变。
- 新入组包比原格式增加1B flags，原型阶段保留version1且不加旧格式解析分支。旧入组包需重新生成；已导出的条目密文格式未改变。

## 策略和恢复边界

- 策略作用于整个token/组。Authority必须稳定绑定组标识和策略，不得把相同root分别按true/false发给不同成员。建议把用途、明确分隔的组ID和策略纳入KDF；不同策略得到不同root。卡只能执行本地已认证策略，不能审计Authority是否在别处违规签发。
- 不增加挑战/过期/在线撤销：相同目标、root、策略的入组包可重复提交；不同配置冲突。Reset保留ID及Authority配置，但更换Identity私钥并清除Bundle/数据/PIN，旧包无法用于新身份。此设计不声称签发新鲜性或离线撤权。
- 现有手动Bundle无法被Authority替换或放宽。Authority派生组按用户选定的Authority信任运行；同组仍保留Secret PIN、调用方AID隔离和禁止自产物自解密等Identity约束。
- Authority可以重算root，获得该模式历史密文即可解密。证书模式虽然同样信任签发者新增接收方，但要取得一份面向新公钥的密文，仍需要源卡及Secret PIN发起新导出。这是取得数据的条件不同，不能描述成证书消除了对Authority的信任。
- 用户选的关闭成员扩展，不阻止Authority继续签发，不等于固定成员名单。APP账户授权、Authority私钥保护及组配置一致性由未来服务负责。
- 卡ID是显示/查找标签，不是密码学身份；保留或恢复ID不会恢复旧密钥和token。证书/私钥持有证明也不证明真实芯片或可信Applet。

## 验证

独立JCE主机实现构造Authority HPKE包，模拟器覆盖Secret授权、错误/缺失Authority、目标绑定、字段篡改、重复/冲突Join、两种扩展策略、跨卡传输及Reset后旧包失效。最终 `gradlew check buildJavaCard` 通过626测试/70套件、四CAP编译/转换/验证；10项新增Authority APDU测试使用独立JCE发送端。Prettier、Inplate、安装脚本PowerShell解析和diff检查通过。无实卡测试或部署、提交或推送。

参考：RFC9180 Auth、RFC5869 HKDF；相关精确格式写入 `doc/authority.md` 和 `doc/bundle.md`。此前卡证书方案仅是候选：绑定用途、完整Identity公钥与Authority范围内账户，离线通常需要B读证书→A导出→B导入，缓存证书可省首次B；它不自动获得硬件认证或离线撤销能力。
