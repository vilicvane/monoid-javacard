## 当前实现的 RAM 测量

未插桩控制组通过 92/92 次检查，插桩组通过 152/152 次检查。包含非对称及 Bundle 的 32/256/1024B 条目传输、三成员 Bundle 管理、传输后 SLIP-0010/Ed25519 与 BIP32/ECDSA 签名，以及签名后的重复传输；公钥、签名和加密输出独立核对。

控制组与探针组刚安装时的查询结果均为 RESET 2165B / DESELECT 2160B。两个加解密上下文初始化后为空闲 RESET 1537B / DESELECT 1536B；签名上下文使用后为 1441B / 1440B。两池读数不能相加。

### 原因

- `Utils.makePrivateByteArray` 和 `CommunicationData.makePrivateByteArray` 对不超过 512B 的数组先申请 RAM；仅收到 `NO_TRANSIENT_SPACE` 才回退持久空间。超过 512B 则直接持久化。没有预留 RAM 预算。
- Import 256B 的 258B 明文数组进入 RAM，使 RESET 从 327B 降到 69B；Import 1024B 的 1026B 明文直接持久化，仍为 327B。两者都未触发分配失败回退。
- Export 256B 的 400B 完整密文进入 RAM；Export 1024B 的 1168B 密文直接持久化。后续相同阶段的最低值差 400B，即 68B 与 468B。
- 两个加解密上下文各使查询值降低约 314B，共 628B；显式 transient 数组载荷合计只有 290B，不能忽略原生对象等运行时开销。
- Create Bundle 的主要压力来自响应窗口、成员表、跨 Applet 公钥/成员表副本、hash 返回值和读取窗口，并非 32B Bundle 密钥本身。

### 计量边界

- 探针在 Java 数组分配与原生调用前后采样；原生调用内部申请后立即释放的工作区不可见。因此这是已采样的可用空间最小值，不是硬件完整高水位。
- 探针每包仅增加持久 `short[128]` 统计数组和 `short[2]` 查询 scratch，合计 520B 持久载荷，没有额外显式 transient 数组。对象头、代码及栈仍可能有影响；控制组的初始 RAM 查询值与其相同。
- `JCSystem.getAvailableMemory` 表示可分配量上界；对象开销、碎片及不同内存池的关联会影响实际分配，不能解释成精确物理空闲 RAM，也不保证能分配同等长度单对象。[Oracle API](https://docs.oracle.com/cd/E59935_01/api/javacard/framework/JCSystem.html)
- 原始 `checkpoint-map.json` 的 `exact byte counts` 说明过强，正确解释以上述 API 边界为准。保留原测试输入清单不追改；各检查点最小值也不能拼成一条严格连续的分配账目。
- 统计写入持久存储会影响耗时，插桩组时间不用于性能比较。

## 持久空间性能对照

同一卡依次重新安装三个未插桩版本，仅修改以下分配策略；AES/GHASH/HMAC 的高频更新工作区保持 RAM：

1. `baseline`：当前源码，仅映射测试包名/AID。
2. `snapshots-only`：仅两处 `duplicateAsPrivate` 使用持久数组，保留复制与 null 语义。
3. `private-all`：仅两个 `makePrivateByteArray` 改为持久分配；包含输入副本、context、临时通信密钥、明文与密文结果。其他直接申请的 RAM 不变。

三个版本共六份 CAP 转换与 verifier 通过，转换均无错误/警告；500 个源/生成输入及限定变换验证通过。

每版 63 次完整命令检查、14 个计时用例、34 个正式样本。32/256B 及 Bundle 管理为预热一次后测三次；1024B 为预热一次后单次对照，不报告中位数或波动结论。计时累加业务 PC/SC transmit，包含请求分片与 GET RESPONSE，不含 SELECT、host 编解码/密码学核对或设置步骤。

测量的 Item Import 为同密文幂等重试，预热才创建记录；Create Bundle 正式样本为生成新 key 的替换；Import Bundle 正式样本为已入组后的幂等导入。每次 Export 独立解密并比较内容、metadata、Secret；Create 的两份入组包独立核对；最终 Export 再确认导入 Bundle key 正确。

32B fixture 为 Secret，256/1024B 为普通项，各版本相同；跨长度结果不是纯粹的字节长度微基准。每版独立安装、顺序执行，没有随机交叉顺序；小差异不能全部归因于某个存储读写指令。

### 解释与下一步方向

- 仅输入副本持久化的四项 32/256B Import 中位增量为 21.84–26.36ms；Export 为 2.64–22.38ms。Bundle 创建/导入约 -3.71/+1.89ms，属于不应解读为确定收益的小波动。
- 两个私有数组 helper 全持久化后，32B 传输增加 119–242ms，256B 增加 750–890ms，约 31–35%；Create Bundle 增加 62.64ms，Import Bundle 增加 118.77ms。此策略的十个重复用例样本区间均与 baseline 不重叠，明显大于各组本次观察到的约 16.5ms 最大极差，但仍不是正式显著性检验。
- 源码中 `AESGcmCipher.doFinal` 使用 `out[...] = ...` 逐字节写入结果；小输出从 transient 转 persistent 后会进入逐字节持久写入路径，与 256B 退化相符。本实验比较的是整版分配策略，没有独立分离写入、GC、原生密码调用或持久对象布局的成本，不能声称精确测得每字节写入延迟。
- 较合理的方向是让批量写入后只读的副本直接使用持久数组，保留 GHASH/HMAC/计数器等频繁更新的工作区为 transient。完整结果也可以持久化，但应先验证批量输出的代价，而非直接把当前逐字节输出目标全部换成持久数组。
- 候选批量输出无需新增 RAM 数组：现有 AES `block` 是 16B 密钥流工作缓冲，可在其中完成与输入的 XOR，再通过 `Util.arrayCopyNonAtomic` 写出一整块；加密的 GHASH 应处理生成的密文，解密仍先认证输入密文，保持原地处理正确。16B 是 AES 固定块大小；32B 只是攒两块再输出，本轮已取消扩大尝试，尚未创建第四变体，也未实现或测试批量输出优化。
- 1024B 的大结果在 baseline 已持久化，因此全私有数组策略只改变其余小数组；单次 ±十几到百余 ms 的变化不用于证明稳定收益。
- 三组查询时 fresh RESET/DESELECT 均为 2165/2160B，所有 warm 阶段均为 1537/1536B。这是空闲读数；未重新插桩两种替代策略，不能量化其峰值改善。持久查询均饱和于 32767B，不能据此证明不存在持久临时对象增长，也不构成满卡 GC 或长期耐久性测试。
