## 当前实现范围

- 独立`monoidsecuritykey`包/CAP，包AID `F06D6F6E6F696403`，实例使用标准FIDO NFC AID `A0000006472F0001`。公共Monoid接口仍在`monoid.cap`，不另建API CAP。
- CTAP2.0 NFC：GetInfo、MakeCredential、GetAssertion、GetNextAssertion、ClientPIN协议1、Reset；仅ES256。包括带allowList的登录和resident credential发现。仅声明已实现的能力；UP使用已确认的软件策略，UV必须真实通过FIDO PIN协议。
- FIDO PIN、重试次数、PIN token及客户端安装token归Security Key；源seed、派生私钥及缓存留在Monoid。ClientPIN协议1使用P-256 ECDH、SHA-256、AES-256-CBC零IV和HMAC-SHA256；OwnerPIN保留8次重试，每次上电连续3次错误暂时阻塞；PIN至少4个UTF-8码点、最多63B。PIN测试输入用Unicode转义，避免Windows编译编码影响。
- 签名输出DER，使用packed self-attestation、零AAGUID和`signCount=0`，不主张厂家身份或跨备份恢复的单调计数。CTAP2.0无单条CredentialManagement命令，凭证删除沿用Monoid Remove；不声明credMgmt或内置uv。
- Credential记录保存在一个固定自定义Type `0xF101`，`key=SHA256(rpId)`，`secret=false`；数据保存随机credential ID、RP/user信息及rk等策略。每次签名先查记录并核对RP，删除后不能仅凭旧ID重建可用凭证。
- 初始只使用授权的`seed`和Type读写能力；固定`keys`的SIO签名不在本阶段顺带实现。授权domain由管理方提供并持久保存，恢复旧凭证须恢复同一seed、domain及记录。
- FIDO Reset先由`removeAll(0xF101)`独立提交凭证清理，再由ClientPIN独立提交PIN清理，成功后清协议会话；不调用Monoid的0xFF，不修改Monoid PIN、根seed、其他Type、Bundle或grant。resident替换先收集同RP/user的全部旧resident记录，逐条清理重复项但保留首条，再独立提交新记录并移除保留的旧记录；没有跨步骤的客户端外层事务。中途失败后的可见状态与重试语义见下文。

## 已批准的Monoid服务接口

以下接口均位于Java包`monoid`。`getAppletShareableInterfaceObject(..., 0)`返回绑定真实调用方的操作会话；原`MonoidClientShareable.getTokenHash`保持不变。

```java
public interface Monoid extends Shareable {
  void authenticate(byte[] token);

  /** Uses the grant's seed/domain; returns a 65B uncompressed P-256 point. */
  short getMonoid001PublicKey(byte[] context, byte[] dest, short offset);

  /** Signs a 32B digest with that derived key; returns 64B r || s. */
  short signMonoid001ECDSADigest(byte[] context, byte[] digest, byte[] dest, short offset);

  SafeItemIteratorShareable list(short type);
  SafeItemIteratorShareable list(short type, byte[] keyPrefix);
  SafeItemShareable get(byte[] index);
  SafeItemShareable create(
    byte[] index,
    byte[] key,
    byte[] alias,
    SafeDataShareable data,
    boolean secret
  );

  /** Removes this exact Type atomically; requires writable permission even when empty. */
  void removeAll(short type);
}

public interface SafeItemIteratorShareable extends Shareable {
  short getCount();
  SafeItemShareable next();
}

public interface SafeItemShareable extends Shareable {
  byte[] getIndex();
  byte[] getKey();
  byte[] getAlias();
  boolean isSecret();
  SafeDataShareable getData();
  void setAlias(byte[] alias);
  void setData(SafeDataShareable data);
  void setData(SafeDataShareable data, boolean secret);
  void setSecret(boolean secret);
  void remove();
}

public interface SafeDataShareable extends Shareable {
  short getLength();
  void read(short dataOffset, byte[] buffer, short bufferOffset, short length);
}
```

- 每次服务及代理调用核对真实JCRE caller、认证状态及当前不可变grant；grant替换/撤销、Monoid Reset或卡片复位后旧会话及代理失效。客户端在每个CTAP操作内取得并使用SIO，不持久保存。普通FIDO调用独立于Access/Secret PIN的APDU认证；Monoid建立限于该次调用的内部存储访问范围，不伪造`Command.auth`。
- 输入输出跨防火墙用global数组，Monoid不持久保留global或客户端对象。hash仅用于注册；调用认证必须提供私有32B token。metadata返回global副本，范围读取沿用现有接口概念。写入准备完成后才发布，并在外部data回调前后复核授权。
- list保留现有类别和key-prefix筛选语义，但结果仅含grant明确列出的Type；get不存在返回null。读写权限沿用writable，Type授权不能读取secret数据或绕过secret降级限制。代理不直接暴露内部SafeItem/SafeDataSource。
- 授权source仍按index引用当前seed；源不存在或不再是64B seed时拒绝。相同index替换seed会改变后续派生结果，因此Security Key记录生成时的公钥并在使用时核对，防止静默用另一把密钥签名；授权描述本身不自动绑定材料快照。
- SIO失败使用6982（未授权）、6985（状态不可用）、6A80（输入无效）、6A84（存储不足），不向客户端暴露Monoid内部异常类。

已批准并实现的派生context沿用134的domain方向：

```text
Monoid-001 input = ASCII("monoid applet: ") || u16be(domain.length) || domain || clientContext
Security Key clientContext = ASCII("monoid fido2: ") || rpIdHash[32] || credentialId[32]
```

两个标签都含末尾单个ASCII空格、无终止符。授权token、AID、卡ID不进入派生输入。credentialId为随机32B，Safe index为`F101 || credentialId[0:8]`；创建碰撞重选ID，读取时核对完整ID。记录包含规范版本及生成公钥；不宣称仅备份seed即可恢复随机ID和resident metadata。

## 实卡定位的RAM与事务问题

[agent] 早期实卡MakeCredential出现`SystemException.NO_TRANSIENT_SPACE`，诊断定位到同一命令内重复公钥查询和临时RAM副本累计。修正包括：只读私有context/hash/派生拼接数据用持久数组、直接缓存完整公钥点、新建凭证签名不重复查询刚生成的公钥、去掉重复私有RAM副本、跨SIO数据读写复用64B global窗口。已有凭证签名前仍核对派生公钥，防止seed更换后静默签错密钥。v7普通流程通过之后，仍在继续减少枚举等路径中的窗口分配；因此v7结果不自动覆盖后续改动，不把命令结束后的RAM读数当成峰值保证。

另一次分配失败触发外层事务的显式`JCSystem.abortTransaction()`后使卡片会话失联。移除首次创建的多余外层事务后，同一问题返回普通内存错误，从而确认分配失败和显式abort共同构成了故障路径；不能仅归因于读卡器或卡片移动。

Java Card 3.0.5 RE §7.6.1把programmatic abortion定义为显式调用abort；§7.6.3明确允许事务内创建对象后显式abort时锁住会话以等待reset。§7.6.2另规定JCRE在`process`正常或异常退出时自动回滚未完成事务。历史尝试曾保留替换/Reset外层事务，失败时不显式abort，而由CTAP传输层发送失败响应后在catch之外抛`ISOException(0x9000)`交回JCRE。§3.3使该异常保留9000；若只是正常return，未结束事务会导致6F00。该尝试已由下述分步提交方案替代，不再作为当前实现约定。

此路径有规范依据，但不能声称任何资源错误都不会锁卡：§10.1允许不可恢复VM错误停机。jCardSim既没有真实持久化回滚日志，也未在`process`退出时清事务深度；主机`ShareableSimulatorRuntime`只补APDU边界的深度清理。5项传输测试验证失败响应和交还JCRE的depth/status，另有1项模拟器边界测试；它们不是实体卡回滚证明。无写权限Reset的拒绝发生在凭证/PIN写入前，同样不能当成写入后回滚证据。

## 当前采用：分步提交与重试收敛

[agent] 曾提议新增`Monoid.prepareReplace`、`prepareRemoveAll`及返回的`SafeMutationShareable.apply`，将对象构建放在事务外。该提案已撤回，未获批、未采用，不新增这些公开接口。Identity原有的`prepareReset`属于已批准的Monoid整体Reset机制，不在本次调整范围。

resident注册先扫描并收集同RP/user的全部旧resident记录。若有多条，逐条删除`previous[1..]`并解除对应数组引用，保留`previous[0]`这条有效旧记录；随后创建并提交新记录，最后删除保留的旧记录。无重复项时仍是先新建后清旧。预清理失败时至少保留首条旧记录；新建失败时首条旧记录仍在；新建已提交、最后删除失败时新旧记录并存。下一次同账户注册重新扫描并预清理重复项，成功完成后仅保留该次新记录。其他账户不受影响。每次注册都生成新的随机credential ID；重试收敛指凭证目录和账户状态，不承诺响应重放或相同credential ID。

预清理避免重复项持续占用可回收的存储，但删除及解除引用后仅请求GC，不能保证当前APDU立即获得空间。允许出现预清理已提交、本次新建仍因空间不足被拒绝、之后重试才成功的情况；不保证任意资源不足都能自动解决。预清理保留有效旧凭证，不能为了腾空间删掉同账户最后一条旧记录再尝试创建。

FIDO Reset先调用`removeAll(0xF101)`并提交，再独立重置FIDO PIN。清理条目失败时不会开始清PIN；条目已提交、PIN清理失败时允许出现凭证已清空但旧PIN仍在的状态，再次Reset可完成剩余步骤。授权要求不变，精确Type可写检查即使目录为空仍执行；不允许通过撤销授权后重试来跳过检查。

## 早期性能审查（后续实现见记录166）

[user] 要求检查当前 Security Key 的优化空间。

[agent] 源码确认优先处理热状态与写入组织：Security Key 的 CBORReader.offset 是持久 short，未沿用 Monoid Reader 已在112实测的 transient 游标；共享源生成的 CBORWriter.offset 同样持久，写每个字段推进游标。CTAP 响应直接写持久 byte[1024]，小型元数据逐字节写入，可考虑借用 APDU 或小 RAM 写缓冲后成块复制，保持大请求和只读副本持久化。不要把 request/response 整块改 RAM，105段记录的 NO_TRANSIENT_SPACE 是实际约束。当前 CBORMap 一次建立字段索引，不是每次查字段都重新扫描整个 map。112的历史同卡对照证明持久游标有可观成本，但其降幅不能直接当成本轮收益。
