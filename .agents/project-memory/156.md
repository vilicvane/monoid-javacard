# Hello challenge and Monoid installation identity

- [user] Proposed signing a Hello nonce to detect replacement of the installed Monoid applet. Accepted the direction of a separate Monoid installation key; requested recording it first and continuing after the current Reset task is complete.
- [agent] Hello's existing `publicKey` belongs to Identity and intentionally survives Monoid reinstallation. Having Identity sign a nonce would prove control of that Identity key, not continuity of the Monoid installation.
- [agent] Proposed generating an independent P-256 key at Monoid installation and keeping it outside Safe items. Normal Monoid reinstallation would change it; `0xFF Reset` should preserve it. The client would pin the public key after trusted first use and verify a fresh challenge before sending sensitive input. This detects a changed installation against a saved pin; first use is not proof of official code. Legitimate updates need an explicit client trust/synchronization workflow.

## API proposal, not yet approved

One possible extension is Hello `{nonce?: byte[32]}` and, when supplied, an added `proof: {publicKey: byte[33], signature: byte[64]}`. The proof key would be the Monoid installation key, distinct from the existing outer Identity public key. These field names, sizes and optionality are agent proposals requiring explicit approval before implementation.

The signature should bind the nonce and the complete Hello state, with a dedicated domain. A fixed documented hash encoding could avoid changing the response writer or copying the complete CBOR response. Exact signed bytes, schema versioning, key pinning and legitimate-update behavior remain to be settled; no wire protocol is finalized.

Existing `CurveSECP256r1`, `Signer.signECDSADigest`, `OneShot` and low-S normalization provide reusable native P-256 signing components. Actual Hello cost and peak memory require measurement. A nonce proof alone does not authenticate later APDUs, prevent a live relay, or certify the initially installed binary.

No production code, README/API definitions, card operations or validation have been added for this proposal. The pending applet-authorization proposal153 remains separate and unapproved.
