# 分片请求按需使用持久存储

[user] 要求分片APDU接收全部按需使用持久存储，完整的单条短APDU继续借用APDU缓冲；实卡观察内存与完整流程。

[agent] 本轮只改 `monoidlib/CBORApduReader.java` 的动态接收存储策略：移除前512B transient特例，每个256B chunk按需分配持久数组。短请求借用、固定缓冲模式、8192B容量、协议、API与GC策略不变。578测试/65套件、四CAP转换验证及Inplate检查通过。

## 对照与计时范围

固定 `ACS ACR39U ICC Reader 0` / CPLC28767821 / 接触T=1，产品名J3R452由用户提供。基线直接复制记录177使用的四CAP；候选与其120个冻结生产源码相比仅上述Reader变化。两轮主机、命名空间、只读8075内存探针及收尾GC相同，不访问另一会话的ACR1552。

独立布局均从新安装开始，仅删除本轮Security Key C4/C401，保留Identity/Monoid/library C0/C2/C5；冷Hello、PIN初始化、64B读写之后测试同一600B Create。CBOR请求为666B，SHA256为 `46ab56ffca0fd4bdad92e7b33b77c611eb553400acdf882b16176ae3021b4d8b`，按255/255/156B三片发送。每片后插入只读内存探针，记录接收期间的可用量；探针不结束命令、不清传输、不请求GC。

600B Create是插入探针的场景，其请求APDU计时与探针计时分开；后续Get/Set不插入分片探针。PC/SC时间包含完整请求/响应及SW，不含主机校验和日志。RESET与DESELECT是不同可用量视图，不能相加，采样也不是连续峰值。首次失败立即停止，失败与intent保留，不重放。

## 完整布局仍未完成

记录177的基线诊断曾在此流程确认NO_TRANSIENT_SPACE；本轮候选没有新增trace，不能把旧诊断当作候选的新异常证据。Hello是单条短请求，本次分片存储变化不涉及该接收路径；单独改善长请求不代表完整多Applet布局已可用。

源码还有独立的响应RAM需求：600B Get由 `SafeDataResponse.start()` 进入流式响应，`CBORApduWriter.start()` 为256B块及256B最大输出单元分配512B transient窗口，命令还会有授权/Index等临时分配。这是下一处明确的资源压力点，但Get失败没有trace，不能把源码推断写成已经确认的异常原因；本轮未修改Writer。

## 博客兴趣点

- **切入问题**：命令结束时RAM一样充足，为什么接收较大的请求仍会失败？
- **关键事实**：基线在每片后采样可见519→263→7B，失败收尾后又回到519B；持久分片始终保留519B，以544B持久空间容纳前两块，Create通过。只看命令边界会漏掉接收期间的512B占用。
- **适用边界**：真实在途采样不是连续峰值；分片移入持久存储不自动解决PIN、算法上下文或响应路径的其他RAM需求。
- **参考**：本记录的同请求分片日志、源码与CAP冻结清单，以及记录177的完整布局限制。
