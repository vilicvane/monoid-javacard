## API and implementation at0686ab4

- `0x23 Create Bundle`: Safe authorization, `{publicKeys:byte[][]}` to `{bundle:byte[],packets:[{publicKey,data}]}`. Rejects any existing Bundle with6985, including an identical roster, before generating another key or packets.
- `0x24 Join Bundle`: Safe authorization, `{senderPublicKey:byte[],data:byte[]}` to `{bundle:byte[]}`. Authenticates the enrollment packet, installs only when no Bundle exists, accepts identical key/membership idempotently and rejects conflicting enrollment with6985.
- `0xFF Reset`: no PIN authorization, `{}` to `{}`. Atomically clears local items, derivation cache and Identity Bundle. Preserves both PINs including remaining attempts/blocked state, Identity key pair/ID/binding token and token cache. A failed transaction aborts the complete state change; success requests GC. It does not attest physical erasure, revoke old artifacts or affect other cards. Identity binding and fixed Monoid caller admission remain enforced.
- Anyone with Monoid APDU access may delete the local database through Reset. This deliberately accepts that availability impact; it is not a read/export capability and cannot reset/unblock either PIN. GP reinstallation remains a distinct lifecycle operation.
- `0x25` remains unsupported, with no Reset compatibility alias. Field-order configuration has an empty0xFF request.
- Rename CommandImportBundle to CommandJoinBundle and Safe/IdentityShareable/MonoidIdentityApplet.importBundle to joinBundle. Replace CommandResetBundle with CommandReset; retain the narrower IdentityShareable.resetBundle method inside the caller-owned reset transaction.
- Identity still completes packet encryption before publishing a newly created Bundle. That publication retains its original transaction ownership; Reset has its own caller-owned transaction.
- Saved asymmetric artifacts remain decryptable by the retained Identity after Reset. Saved enrollment packets can rejoin the original Bundle, after which its artifacts can be imported. Reset is local removal, not revocation.

## GP lifecycle

GP can delete an applet instance and create a new one from its existing loaded package; this differs from removing and loading the CAP again. Recreating Monoid clears its items, both PINs and caches but preserves Identity's Bundle. Recreating Identity too clears the Bundle and generates a new identity key pair, ID and binding secret. Old asymmetric artifacts and enrollment packets cannot be used by the new Identity. A retained Monoid refuses a changed Identity token instead of silently rebinding. Reinitialization requires GP management authorization, rather than Safe PIN authorization.

For general clients, delete dependent instances first and recreate providers first: Security Key (future) -> Monoid -> Identity for deletion, reverse order for recreation. A CAP import blocks deleting its imported package, not necessarily deleting an instance. An external persistent reference to a provider-owned SIO can block instance deletion; clients may instead release it or cache it in a CLEAR_ON_RESET object array and reset before maintenance. JCRE-owned AID references are not equivalent to provider-owned SIO references. An independent interface CAP avoids implementation-package imports but does not remove live-object dependencies. Reference: Java Card3.0.5 JCRE6.2.4 and11.3.4, https://docs.oracle.com/cd/E59935_01/JCCRE.pdf.

The agreed GP alternative does not authorize deleting any current physical card. No new installer/reset script is included. Other cards and previously exported artifacts are unaffected by local reinitialization.

The accepted two-card recovery workflow in record148 remains available. No APP changes or implementation of the pending authorization proposal153 are included.
