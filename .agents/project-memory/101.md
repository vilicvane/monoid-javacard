# ES256 signing — 2026-10-15

[user] Requested the first signing algorithm for future Passkey support. The
approved API and scope are recorded in 99–100. Keep the established curve,
Keystore, Signer and static Lib organization; no Monoid APP changes.

[agent] Independent secp256r1 keys now work through existing Create, Create Random
Key, List, Get, Set, Remove, ViewKey and Sign commands. Type 0x0402 stores a 32-byte
big-endian scalar in [1, n-1]. Import accepts the existing text type, numeric type
or explicit index forms. Random generation resamples invalid scalars using one
global array. Keystore trusts stored key data; record 102 removes an initially
added scalar recheck at key use. Set's general semantics and the Safe Shareable
interfaces remain unchanged.

CurveSECP256r1 follows CurveSECP256k1's native ECPrivateKey and shared XY ECDH
structure, without its BIP340 hash field. WeierstrassCurve owns both shared curve
instances and releases both in dispose. MonoidApplet calls the base class's
init/dispose directly. Public-key responses contain only the compressed 33-byte
publicKey. LibBIP32 rejects non-k1 curves before copying or returning for an empty
path; P-256 seed/master derivation is not exposed, even for an empty path.

The existing cipher:ecdsa branch signs a precomputed 32-byte digest and returns
64-byte big-endian r || s with low-S. ES256 clients supply SHA-256(message); the
card does not hash this digest again. Signer receives the resolved curve and
LibECDSA uses its order for normalization. Enabled Taproot and BIP340 remain
k1-only; omitted/false Taproot works for P-256. Hello and SystemInformation now
advertise secp256r1 with ecdsa alongside the existing curve/cipher combinations.
README contains the final API signatures and concise comments. This implements
ES256 primitives, not CTAP, WebAuthn or non-exportable credential storage.

## Native signature buffer correction

An earlier step reduced the ECDSA workspace from 76 bytes to the 64-byte returned
signature length. The first physical P-256 signature then failed with
IndexOutOfBoundsException despite correct public-key derivation.

An isolated native-only applet tested both k1 and r1 with d=1 and SHA-256(sample).
After init, Signature.OneShot.getLength() reported 72 for ECDSA_PLAIN on this card.
Output capacities 64/65/70/71 all failed inside signPreComputedHash; 72/73/76/80
all succeeded and returned independently verified 64-byte raw signatures. This
is an observed runtime capacity requirement, not a claim that the PLAIN wire
format is DER or that every Java Card implementation needs 72 bytes.

OneShot.sign now allocates its transient workspace using getLength after init,
returns only the actual signature bytes and closes the engine in finally. Signer
retains curve-specific low-S normalization; CommandSign validates the external
digest length after the simplification in record 102. No fixed card
model branch or magic buffer margin is used. On this card the workspace saves
4 bytes versus the original 76-byte allocation; the per-operation half-order
array adds 32 bytes, so the net array payload change is +28 bytes, excluding
object overhead. The earlier +20-byte estimate assumed an invalid 64-byte buffer.
