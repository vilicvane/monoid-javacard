# 完全禁用显式 GC 的实卡对照

[user] 要求对比完全不调用 `requestObjectDeletion()` 的实卡行为，观察持续创建和替换数据能否自动回收，以及耗时、剩余 RAM 和持久空间的变化。已允许使用主机 ACR1552；本轮只做隔离实验，不改变正式固件的回收策略。

## 实验设计

[agent] 使用测试卡 55690320、ACS ACR1552 1S CL Reader PICC 0，先核对 CPLC 和原有注册表。完整三个临时包使用 C0/C2/C4，顺序安装基线与禁用版本；保留原有应用及数据。输入固定为记录170的 round15 冻结源码，正式源码不参与临时修改。

[agent] 两版的唯一生成源码差异是禁用组移除三个包中的全部21处 `requestObjectDeletion()`。对167个编译类反汇编复核：基线28条调用指令（finally展开），禁用版0条；三个包的JCA输出也无该调用。两版均通过三份CAP转换及verify。

[agent] 两版在Monoid/Security Key中加入相同的只读空间探针，直接返回32位RESET、DESELECT和persistent剩余量，安装时各分配4B RESET scratch。探针绕过业务初始化及Command清理，不逐次分配、不请求GC。内存结果是APDU边界可用空间，不是峰值；RESET与DESELECT不是可相加的独立内存池。

[agent] 普通数据负载固定16条256B非secret记录：512次Set替换，再128次删除后创建；每次写入均读回核验，循环内不重新SELECT、不重连、不复位、不重新握手。主机保存每条APDU耗时、完整修改加读回周期及内存采样耗时，避免漏算延后到下一条APDU的回收。原计划另做FIDO同账户凭证替换；完全禁用组连标准初始化都无法完成，因此这组FIDO实验取消，没有运行，也不据此报告FIDO性能。

[agent] Safe原有4KiB空间guard可能在运行时分配器耗尽之前拒绝写入。因此Monoid另有相同的私有分配探针，每条APDU新建256B持久数组并替换唯一保留的anchor，不调用GC，不经过Safe guard；最多1024次，首个SystemException终止。标准runner在普通负载完成或明确6A84拒绝且连接正常时进入这个单独标记的诊断；后续诊断runner在确认初始化的SystemException后，也允许独立执行此分配器测试，不重发失败业务写入。此探针没有anchor读回，不能宣称实测了其OOM后的内容完整性。

[agent] 主机遇到首个失败便停止原工作负载；明确完成的业务错误可做失败条目及目录只读检查，通信结果不明确时不追加写操作。研究文件位于忽略目录 `.research/gc-auto-20261022/`，冻结CAP及原始运行记录位于 `.research/fido-performance-target-20261022/variants/gc-auto-*`。正式源码及原有暂存区保持不变。

## 结果

### 保留现有请求的完整基线

[agent] `gc-auto-baseline`完成16条256B记录创建、512次Set及128次删除/重建，全部逐次读回及最终16条核验通过，每轮完成后存活payload为4096B。创建完16条后，整个替换、删除/重建及最终读回的采样均为RESET 1599B、DESELECT 1584B、persistent 27812B，没有随累计写入继续下降。

| 完整周期                  | 次数 | 中位耗时 |     均值 |
| ------------------------- | ---: | -------: | -------: |
| Set + Get核验             |  512 | 1109.2ms | 1109.9ms |
| Remove + Create + Get核验 |  128 | 1606.4ms | 1608.8ms |

[agent] 上表包含读回及所有请求/响应分片，独立内存探针约6.1ms另外保留。不能将单独Set的耗时当作完整回收成本，因为运行时可能在下一条Get或空间探针之前执行此前请求的回收。这是本次存储负载，不是Security Key签名基准。

[agent] 基线普通负载完成后，另执行不请求GC的INS76。成功新建100个256B数组后，第101次返回SystemException reason5（NO_RESOURCE），persistent由27812B逐次下降至612B；每次只保留最后一个anchor，未观察到persistent上升。正式基线其他命令中的GC请求不等于此段分配循环会继续请求GC，不能用“基线版本”把这段解释为有显式回收对照。

### 完全禁用组的初始化与分配诊断

[agent] 原始`gc-auto-disabled`在标准provision的第6条正常命令`fixture-access-pin`返回`INTERNAL`，尚未进入16条记录工作负载。前5条依次为Hello、设置Secret PIN、认证、空List、空授权List。随后用新的诊断安装仅将SystemException错误编码为`0x6F20 | reason`，相同第6条返回`6F22`，确认该处为reason2（NO_TRANSIENT_SPACE）。两种错误返回不是同一份CAP的协议；`6F22`是临时诊断结果。

[agent] 诊断安装的逐条采样如下。此版本保留同样的零显式GC状态，只增加错误识别；它的初始persistent比原禁用组少20B，不能混用两版绝对空间数值。

| 阶段             | RESET剩余 | DESELECT剩余 | persistent剩余 |
| ---------------- | --------: | -----------: | -------------: |
| 安装后入口       |     1682B |        1776B |         34124B |
| Hello后          |     1274B |        1360B |         33716B |
| 设置Secret PIN后 |     1044B |        1136B |         33572B |
| 认证后           |      878B |         944B |         33460B |
| 空List后         |      460B |         448B |         33296B |
| 空授权List后     |      172B |         160B |         33264B |
| 第6条失败后      |       12B |           0B |         33168B |

[agent] 明确错误后停止原初始化，没有重试；同一连接继续独立的INS76持久数组诊断。成功121次256B分配，第122次返回reason5，persistent从33168B下降至256B；成功分配每次下降272B（256B payload加该卡本次观察到的16B开销），没有回升。RESET/DESELECT仍为12B/0B。因此此次持久分配没有被前面的RAM不足直接阻止，但后续分配压力也没有回收已失去引用的旧anchor。没有anchor内容读回，不据此宣称验证了OOM后的数组内容完整性。

### 跳过标准provision的最小普通读写

[agent] 为排除Hello、List、授权及seed初始化的影响，另做全新安装，完全不走标准provision。只设置Secret PIN、认证，然后Create/Get单条非secret记录，再按原计划做32次Set/Get及16次Remove/Create/Get。256B与64B各自独立安装；64B请求全为单条APDU。每条正常命令后紧接只读空间探针，首个失败停止，不重新SELECT或断电。两种数据长度均完成基线/禁用组实卡对照，使用相同冻结CAP、主机源码哈希及输入参数；仅比较共同成功前缀的耗时。

| payload | 保留请求的最小基线                      | 完全禁用组                                                        |
| ------- | --------------------------------------- | ----------------------------------------------------------------- |
| 256B    | 32次Set/Get、16次删除重建及读回全部通过 | 设置PIN、认证、Create成功；首次Get返回INTERNAL，未进入Set         |
| 64B     | 32次Set/Get、16次删除重建及读回全部通过 | Create/Get成功；第1次Set/Get成功；第2次Set成功，其Get返回INTERNAL |

[agent] 两组基线各116条普通命令通过，初始化后每条采样RESET/DESELECT均为1599B/1584B。64B存活记录存在时persistent为33656B，256B时为33464B；删除与重新创建之间回到33812B，没有随32次替换及16次重建累计下降。

| 两版共同完成的操作（含紧随其后的内存探针） | 保留请求 | 完全禁用 |
| ------------------------------------------ | -------: | -------: |
| 64B初次Create + Get                        | 1107.3ms |  632.2ms |
| 64B第1次Set + Get                          |  879.4ms |  553.2ms |
| 64B第2次Set（其Get在禁用版失败）           |  450.6ms |  297.4ms |
| 256B初次Create（其Get在禁用版失败）        |  760.1ms |  439.0ms |

[agent] 上表每项都是对应阶段的单次样本，不是稳定运行的中位性能；失败命令未混入成功耗时。64B第1次完整替换读回短期少326.2ms（约37.1%），但第2次读回已失败，不能把收益推广为可持续运行的方案。这里单条记录的初次Create有冷启动成本，不能与完整16条基线的Create中位数直接作差。

[agent] 256B禁用组从入口RESET/DESELECT 1682B/1776B，经设置PIN、认证下降到1075B/1152B；Create后441B/432B，Get失败后233B/224B。persistent最终仍有32872B。创建请求用了两片，故补做64B单包对照。

[agent] 64B禁用组Create后873B/944B，首次Get后681B/736B；第1次Set/Get后297B/336B，第2次Set后105B/128B，其Get失败后9B/32B。persistent最终仍有32424B。只有一条64B存活数据，并不是记录数量增加或持久空间接近4KiB guard。两项最小实验使用原禁用CAP，报错为INTERNAL；没有将每个INTERNAL直接当作诊断CAP的reason2，不过已观察到相同的可用RAM持续下降现象。

## 当前结论与边界

[agent] 这张卡在本次连续APDU场景下不能通过“删掉全部requestObjectDeletion，然后等待运行时在分配压力下自动回收”维持现有工作负载。普通初始化/最小读写先遇到RAM不足；不分配transient的独立压力探针则会耗尽persistent，两个维度均未观察到足以维持循环的自动回收。这是单张55690320、当前完整三包及其临时探针的实测结果，不是Java Card 3.0.5所有实现的结论。

[agent] 这些结果只否定本次“全部删除”的实验方案，不证明现有每一处请求都不可缺少，也不证明应每条命令都请求GC。正式代码和GC策略没有改变；后续若减少请求，应逐处区分无新垃圾的warm复用路径、产生临时transient/global数组的路径及持久垃圾增长，再单独对照。源码核对仍有CBORReader字段读取及APDU请求chunk使用transient/global数组；私有数据优先持久化并不等于每条命令完全不分配RAM。

[agent] 所有空间数值都是APDU边界采样，不能当作运行过程中峰值；RESET与DESELECT也不能相加。计时来自本机ACR1552的PC/SC transmit，不含手机交互、用户等待或主机日志时间。基线完整负载与失败的禁用组长度不同，不能拿总耗时或非共同前缀的均值做性能对照。共存原有应用的布局和安装顺序固定，不能把当前可用空间或短期收益推广到所有卡片和安装布局。

[agent] 最后一组结束后，C4/C2/C0临时实例及包全部按依赖顺序卸载；独立GP核对序列号55690320及注册表与实验前一致，所有owned槽为空、账本cleaned且没有未解决的操作意图。未向原有应用发送数据写命令，未操作RDP卡51574920。正式125份生产Java与round15冻结输入逐份哈希一致，基线/禁用生成差异再次核对仍为21处请求移除。没有正式部署、提交或推送；读卡器已释放。
