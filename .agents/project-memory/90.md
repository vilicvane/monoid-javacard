## Provisioning and tool findings

The built-in SD module is `A000000151535041`, package `A0000001515350`.
GPPro f2af9ef's automatic SCP02 SD creation parameter uses i=00 on this card
and INSTALL returns 6A80. Explicit application parameters `81020255` create
the test SD successfully. A separate AuthorizedManagement/TokenVerification
SD still fails with 6A80; the card does not advertise AuthorizedManagement
among its assignable DOM privileges. Do not change the card lifecycle to
work around this.

Temporary DAP SD `F06D6F6E6F69749003` initially inherits the ISD's SCP keys and
can authenticate, but RSA public-key import returns 6985. Giving this SD its
own development SCP02 keys (version 01, IDs 01/02/03) makes the identical RSA
public-key import at 73/01 succeed. Merely opening an inherited SCP session
therefore did not establish that verification-key personalization was ready.
The RSA entry was verified with GET DATA E0. This SD could not delete that key
itself (6985); the ISD successfully deleted the whole temporary SD, and it was
recreated and initialized for ECC tests.

GPPro's ordinary EC key importer maps all 256-bit keys to the P-256 parameter
reference 00; it cannot establish secp256k1 acceptance. Full explicit ECC
public-key data require 275 bytes. Its SCP02 wrapper rejects data over its
short-APDU limit before wrapping. Authenticated CLR mode avoids that host
restriction, but the card rejected the resulting GP-chained PUT KEY.
GPPro also reconstructs commands with Le and has an empty-data CLR splitter
bug. A temporary bridge preserves exact case-3 STORE DATA commands by using
the existing wrapper directly; no production transport code was changed.

## ECC results after initializing the temporary SD

- P-256 public key using named reference 00: 6A88 (reference not found).
- P-256 and secp256k1 standalone local parameters, reference 60, using PUT KEY:
  6A80. Parameters use the complete standard field widths.
- P-256 local parameters using standard STORE DATA DGIs, individually
  SCP-MACed short commands with P1=08/88: first block returns 6A80.
- P-256 and secp256k1 public keys with inline curve parameters using STORE
  DATA: first block returns 6A80. The CRT key length is 32 bytes (ECC256),
  while Q and G each have 65-byte uncompressed encodings; this interpretation
  has not been confirmed with a successful card-side STORE DATA control.
- P-256 and secp256k1 full public key plus own parameters using GP PUT KEY
  chaining under authenticated CLR: 6A86.
- Earlier direct extended P-256 PUT KEY: 6700. Earlier minimal-width secp256k1
  coefficient diagnostic: 6A80, but that encoding is nonstandard and cannot
  establish curve support.

These failures happen during provisioning, before ECDSA verification. There is
no successful P-256 verification control yet, so they do not prove that the
underlying card hardware cannot verify secp256k1, nor that adding P-256 to Monoid
would solve the installation workflow.

Standalone curve parameter objects are not normal versioned key slots. Later
GP clarification says PUT KEY P2/KVN do not identify them, and DELETE does not
provide their standard removal. Only try such parameters in disposable SDs;
do not add them to the ISD assuming key-version deletion will clean them up.

## Successful RSA Token control

Created delegated domain `F06D6F6E6F69749002`, with explicit SCP02 i=55 and its
own development keys at version 01. It became PERSONALIZED. The ISD remains
OP_READY. Its original key table was checked before adding an ephemeral
RSA-1024 public verification key at version 70 / ID 01 and an AES-128 fixture
receipt key at version 71 / ID 01. No existing key was replaced. The RSA private
key existed only in the host process; it was not sent to the card or saved.

The temporary CAP package `F06D6F6E6F697491`, instance/module
`F06D6F6E6F69749101`, has 297 bytes of load-file data. SHA-256 of those bytes:
`9D10D8E68475CAAF46CF9DBDA19C826C63E9D31D7F6A2A206A45C4C35107C6DF`.

Results using the delegated domain's SCP session:

- Missing Load Token: 6982; no package or instance appeared.
- Invalid 128-byte Load Token: 6982; no package or instance appeared.
- Correct RSA-1024 / SHA-1 / PKCS#1 v1.5 Load Token: INSTALL-for-load and LOAD
  completed successfully, approximately 574 ms total.
- Correct Install Token: INSTALL-and-make-selectable completed successfully,
  approximately 249 ms.
- Selecting the instance returned 9000; INS 01 returned `GPTOKEN` and 9000.

The signed preimage was P1 || P2 || unsigned-data-length || unsigned-data.
Load authorization included the CAP load-file-data SHA-256, package AID and
target domain; Install authorization included package/module/instance AIDs,
privileges and C900 application parameters. The tokens were independently
verified on the host before transmission. The key material given to GP for
this asymmetric verification was the public key, not the signing private key.

This establishes real-card delegated authorization using externally computed
RSA Tokens. It does not establish ECC Token acceptance, Monoid-generated
Tokens, phone transport, SCP03, replay prevention or a production choice of
RSA-1024/SHA-1. The small CAP timings are not deployment estimates for Monoid.
Receipt key provisioning succeeded, but receipt cryptograms were not independently
verified; do not claim receipt verification coverage.

## Cleanup and final state

Deleted the temporary instance and package, both temporary DAP/DM domains,
and both added ISD keys. The test SD's earlier RSA key was removed with that
SD. No standalone curve object was intentionally stored outside a disposable SD.

This card rejects DELETE with both D0 key ID and D2 version (6A80 on ISD;
the earlier DAP-domain attempt returned 6985). After confirming that versions
70 and 71 each contained only the one key added by this test, deleting each
whole version with `80 E4 00 00 03 D2 01 70` / `...71` returned 9000. Do not
generalize version-only cleanup to versions containing unrelated keys.

Final full GP registry output exactly matches the baseline, including all five
original applications, nine packages, parent relationships, privileges and
lifecycle states. Final ISD key table is exactly the original three DES3 entries
at version 01, IDs 01/02/03; CPLC identity and capabilities are unchanged.
The SCP sequence counter advanced from 0112 to 0133 as expected for authenticated
sessions; no attempt was made to roll back platform counters. The reader was
released. No PIN authentication or user-item command was sent, so user data were
not read or rewritten. No production source/API change or commit was made.

Next unresolved boundary: obtain a working vendor-supported ECC key/parameter
personalization route for this card, or validate it on another identified card.
Do not conclude that changing Monoid to P-256 is sufficient: its P-256 GP
provisioning control failed too. The RSA control confirms that the Token
authorization design itself works on this card.
