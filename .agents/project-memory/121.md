# 响应 writer 按需追加 chunk

## 范围与实现

- 用户批准把响应缓冲从连续数组反复扩容改为追加 chunk；保留首次搬出借用 APDU 内容的一次复制。
- `CBORBufferWriter` 使用按需分配的 256B `CLEAR_ON_DESELECT` 数组，单字节、批量写入及复制跨块处理。持久 `Object[128]` 只保存引用，覆盖既有非负 short 偏移范围，不预留响应 RAM，也不是新增的可用容量承诺。
- `CBORApduWriter` 保留单包响应借用当前 APDU 的行为，不持久保存 APDU 引用。响应超过 `min(256, APDU buffer length)` 时先复制已写前缀到首块，再写入后续内容；使用 write 参数中的 offset，避免单字节调用 `offset++` 与批量写入更新时机的差异。
- 已分配的块不再因增长被替换或复制。GET RESPONSE 直接发送对应块，仍每次最多 256B，状态字、List 及其他命令 API 不变。
- APDU writer 在完成、取消、deselect 和发送异常后清除全部 chunk 引用并请求 GC。清理先查连续前缀，再从尾向前释放；清理中断后仍保留连续前缀，后续清理不会遗漏引用。普通 BufferWriter 的 reset 继续复用已分配存储。
- 完整响应仍先生成于 RAM；没有引入分页、边生成边发送或持久响应回退。尾块最多有 255B 未使用空间；收益是消除增长时反复分配整块连续数组及复制旧内容，不能保证每种响应都比旧版少分配。

## 验证

- 12 项 writer 模拟器测试通过，包括小响应借用、256→257B 两种提升、逐项追加保留旧块对象、900B 单次 payload 写入、512/768B 整块响应、跨块复制及取消/deselect/发送失败释放。
- Java 11 下完整 242 项模拟器测试通过，0 失败、0 跳过；Identity、Safe、Monoid 三份 CAP 转换及验证通过，转换器 0 错误、0 警告。
- Prettier、Inplate assert 和 diff 检查通过。未安装或访问实体卡；实际 List 条目上限、RAM 峰值及性能仍未实测。
