## 逐组流程

每组先独立捕获三张卡的身份、registry、全部条目、grant、PIN 验证结果和 Bundle 状态，再逐张升级：

1. A 升级 → B Extend → C Approve → A Join、恢复并核验。
2. B 升级 → A Extend → C Approve → B Join、恢复并核验。
3. C 升级 → A Extend → B Approve → C Join、恢复并核验。

每次删除前，另外两张卡必须仍有原 Bundle，并支持 `allowPeerExtension:true`。上一张卡完成恢复和核验后，才开始下一张。重装后的 Identity 公钥变化，原身份导出的密文可由新身份恢复；这不放宽当前身份的自导入禁令。

本次已有固件与目标版本的条目封装及 Extend／Approve／Join 格式一致，不使用协议转换桥。脚本绑定精确读卡器、CPLC 和当前 registry；冻结源码、CAP 与主机工具的哈希。GP 或 APDU 写操作前持久记录 pending，结果不明确时停止并读取状态，不自动重放。五个 CAP 已从目标源码重新构建，构建日志、源码和实际 CAP 哈希另经核对；`build-provenance.json` 保留该对应关系，不仅依赖冻结后的文件哈希。
