The following helper types are grouped by the resulting curve; their type
field always describes the stored source. They encode the agreed signing
and Taproot combinations and add the P-256 contextual branch.

```ts
type KeySECP256k1 = {
  index: byte[];
} & (
  | {type: 'secp256k1'}
  | {
      type: 'seed' | 'master';
      derivation: {
        type: 'bip32';
        path: byte[];
      };
    }
);

type KeyED25519 = {
  index: byte[];
} & (
  | {type: 'ed25519'}
  | {
      type: 'seed' | 'master';
      derivation: {
        type: 'slip10';
        curve: 'ed25519';
        path: byte[];
      };
    }
);

type KeySECP256r1 = {
  index: byte[];
} & (
  | {type: 'secp256r1'}
  | {
      type: 'seed' | 'master';
      derivation: {
        type: 'monoid-p256-v1';
        context: byte[];
      };
    }
);

type Key = KeySECP256k1 | KeySECP256r1 | KeyED25519;

type Taproot = {
  /** Exactly 32 bytes when present; omit for BIP86. */
  merkleRoot?: byte[];
};

/** 0x40 */
type ViewKeyRequest = (KeySECP256k1 & {taproot?: Taproot | boolean}) | KeySECP256r1 | KeyED25519;

type ViewKeyResponse = {
  /** 33-byte compressed EC key; 32 bytes for Ed25519 or Taproot x-only. */
  publicKey: byte[];
  /** Present for BIP32/SLIP-0010 derivation; 32 bytes, before Taproot tweaking. */
  chainCode?: byte[];
};

/** 0x41 */
type SignRequest =
  | ((KeySECP256k1 | KeySECP256r1) & {
      cipher: 'ecdsa';
      /** Precomputed 32-byte digest; use SHA-256(message) for ES256. */
      digest: byte[];
    })
  | (KeyED25519 & {
      cipher: 'ed25519';
      /** Original message bytes for pure Ed25519. */
      message: byte[];
    })
  | (KeySECP256k1 & {
      cipher: 'bip340';
      /** Exactly 32 bytes. */
      digest: byte[];
      taproot?: Taproot | boolean;
    });

type SignResponse = {
  /** 64 bytes; ECDSA/BIP340 use r || s, and ECDSA uses low-S. */
  signature: byte[];
};
```

Semantic boundaries:

- type: seed generates a master with the selected scheme before derivation;
  BIP32 and SLIP-0010 use their fixed labels. type: master begins with stored node material;
  the proposed public contract treats it as the root. Its stored category
  cannot prove which scheme originally produced it; caller pairing remains
  necessary without adding provenance metadata.
- Standard BIP32 fixes secp256k1, so that derivation branch has no duplicate
  curve. SLIP-0010's curve field lists only the currently implemented
  Ed25519 branch, not every curve supported by the specification.
- Independent keys use their stored curve directly and do not accept
  derivation. Contextual P-256 derivation begins with seed/master; it is
  not a numeric HD path or a chain-code response source.
- monoid-p256-v1 is a provisional complete-profile name, not a settled
  algorithm. Final HKDF settings, domain label, encoding and rejection
  sampling must be fixed with vectors before that name is implemented.
- The required type, nested curve/path and removal of the existing seed
  string are now approved in the API agreement. Standard labels replace
  the caller-selected label. The existing implementation now uses the
  updated API; old top-level seed/curve/path fields are explicitly rejected
  rather than silently reinterpreting custom-label requests.
- Taproot is accepted only by secp256k1 ViewKey and BIP340 Sign. Supplying
  it to other branches is invalid even when its value is false. The
  documentation omits the property from those branches; it does not
  retain false-only compatibility from the old API.
- Top-level request composition is still Key plus operation fields, not
  a new key object envelope. ViewKey/Sign INS values and response payloads
  are unchanged in the proposal. The optional chainCode in the type merely
  describes existing response alternatives; HD still always returns it.

## Reconsidering the contextual derivation source

[user] Subsequently suggested requiring seed or master for the custom
derivation scheme, instead of allowing an independent signing key to serve
as another derivation root. The aim is to align source roles with the other
wallet derivation branches.

[agent] Recommended keeping independent secp256r1 items for direct use only,
and moving monoid-p256-v1/context into a required derivation branch for
type: seed | master. The user approved this revision and README now contains
the updated shape above.

The profile must define seed-to-master generation and context derivation
as separate stages. Starting from a seed or its corresponding saved master
must produce the same contextual key. Existing HD master material is 64B
(32B private material plus 32B chain code); its category does not identify
the generating scheme. Do not silently reinterpret arbitrary BIP32 or
SLIP-0010 masters as interchangeable roots or feed a saved master back
through seed-to-master generation. The custom profile may explicitly reuse
SLIP-0010 P-256 master generation, or define its own master generation and
representation; neither choice has been made. Context derivation remains
a custom profile, not standard HD-wallet interoperability. Exact KDF
details remain to be finalized. The contextual branch has no chainCode
response; the existing BIP32/SLIP-0010 responses retain theirs.
