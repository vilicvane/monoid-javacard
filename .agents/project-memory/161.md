# Dual-card activation and transient-memory retention on ACR1552 and Android

- [user] Requested that the temporary probes remain installed on both cards for continued Android testing; do not clean them up yet.
- [agent] Completed the ACR1552 and OPPO public-API experiments below. ACR1552 has a working reader-specific dual-card path; the tested phone did not reproduce simultaneous independent CID sessions retaining both cards' RAM. Neither result establishes a universal hardware capability limit.

## Observations

Both cards can remain ISO-DEP active together using distinct CIDs. After selecting each complete known UID and activating it with CID1 or CID2, the host routes APDUs to each card without protocol deactivation or another applet SELECT.

Both activation orders passed: Test 1→Test 2 and Test 2→Test 1. Each order ran 10 rounds reading both cards, giving 40 alternating reads in total. After 3 seconds idle in each order, both cards were read again, giving 4 additional checks. Every check retained both markers, and each card's SELECT counter stayed unchanged from its marker-setting baseline. The summaries were independently checked for these 44 observations.

The single-card controls distinguish three operations:

| Operation                                                                                      | Observed result                                                                                                                                    |
| ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| APDU SELECT to ISD, then back to the probe                                                     | Only the DESELECT marker cleared on both cards.                                                                                                    |
| Test2 ISO-DEP `S(DESELECT)`, reactivation and probe SELECT, without an explicit RF-off command | Both markers cleared. Keeping the RF command sequence powered is insufficient to preserve Java Card transient state through protocol deactivation. |
| Explicit RF off/on                                                                             | Both markers cleared.                                                                                                                              |

Test 1's PC/SC `disconnect reset` control retained its RESET marker; that API label alone must not be treated as evidence of a physical RF reset.

With both cards present, ordinary PC/SC polling reported `present:false`; raw discovery returned collision. Selecting a complete, already-known UID and then using CID activation worked. This does not establish general discovery of unknown colliding cards or stable UIDs across arbitrary readers/activations.

On this firmware, the manual's little-endian 1-second Timer object was accepted but I-block exchanges timed out after approximately 7 ms. Switching to `FWTI=12` made the same CID exchanges work. This is a measured workaround, not an established diagnosis of internal timer or endianness handling.

## Android public-API experiment

Device: OPPO `PKB110`, Android16/API36. A separate temporary APK, `com.monoid.research.dualcard`, uses public ReaderMode with flags385 and a250ms presence-check delay. The production APP was not changed.

Evidence under the same research directory:

- `android/events-final.jsonl`:130 ordered events, independently checked for the observations below; `android/verified-summary.json` contains the corresponding assertions.
- `android/tag-object-metadata.txt`: read-only JDI inspection of the two cached Tag objects.
- `android16-source-findings.md`: source comparison pinned to AOSP `android16-release` commit `bdd94b3be31253e756355e6e22f2fe8983da6b1e`, not the exact OEM firmware.

| Sequence           | Operation                                           | Result                                                                                   |
| ------------------ | --------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 16–36              | Hold Test1's connection and read10 times            | Persistent label TES1, both RAM markers and SELECT counter retained.                     |
| 37–45              | Close/connect the same Tag                          | Initial READ returned6E00; after probe SELECT, both markers were zero.                   |
| 54–74              | Keep Test1 present and add Test2, then read10 times | Only A was cached; all reads still reached TES1 and retained both markers.               |
| 75–85              | Reconnect with both cards present                   | Still reached TES1; both markers cleared.                                                |
| 86–98              | Remove Test1, allowing Test2 discovery              | Callback for B, correct TES2 label, then B's written markers read back.                  |
| 101–110 and121–130 | Put Test1 back and connect through cached A twice   | Both connects succeeded, but probe SELECT/READ returned TES2. They did not select Test1. |
| 111–120            | Connect through cached B                            | Also reached TES2.                                                                       |

The two10-read holds and the two reconnect results were checked directly against all130 events, as were both cached-A routing failures. There was one discovery callback for each card. Loss of both transient markers after close/connect is an observed clearing event; it does not establish whether this OEM interrupted physical RF power.

JDI confirmed two independent objects with the expected UIDs and generations: cached A was Tag object14, generation1, UID`047FA2A2971490`; B was object7, generation2, UID`047FA1A2971490`. Both had `mServiceHandle=1` but different cookies. The app had not accidentally overwritten A's cache slot with B's object. This OEM accepted the stale A object and routed traffic to the current card; `Tag.getId()` and successful `connect()` therefore did not identify the card actually answering APDUs.

The pinned AOSP implementation checks a current Tag cookie and routes I/O by service handle, with no public UID/CID selector. The tested OEM did not reject this stale object, but its exact cookie-check difference has not been decompiled or identified. Do not describe an internal vendor patch as established. The persistent probe label supplies the physical-card distinction in this experiment.

These public APIs did not reproduce ACR1552's simultaneous two-CID/RAM-retention path on this phone. This is not a claim that its NFC hardware, all Android phones or every vendor/private interface cannot support multiple cards.
