# Redundant authorization and PIN update checks — 2026-10-14

The user approved implementing the two discussed measures for code review:
redundant session authorization state and authorization checks at both command
entry and the PIN mutation boundary. This supersedes record 84's pending status
for these two measures. External APDU/CBOR APIs and session semantics are unchanged.

Implementation:

- `Command.auth` is now a two-element `CLEAR_ON_DESELECT` short array. Access is
  `0xA501`, Safe is `0x5AFE` (read as SAFE), and the second word contains the complement. Only
  these two exact pairs and the cleared `0/0` unauthenticated state are accepted.
  Invalid codes or complements fail with `UNAUTHORIZED`. Safe explicitly
  satisfies Access authorization; unknown requested permissions are rejected.
  At the user's request for more memorable hexadecimal values, these replace
  `0x5AA5`/`0xA55A`. The two complete authenticated encodings still differ in all
  32 bits, and each differs from the cleared state in 16 bits.
- Successful authentication invalidates the previous first word, writes the
  complement and then publishes the new state. PIN checking still occurs once;
  failed authentication retains the previous session authorization as before.
  Array data grows from 1B to 4B; actual card allocation overhead was not measured.
- `CommandSetPIN.run` calls `MonoidApplet.checkPINUpdate` before parsing the
  request. Both `updatePIN` and `updateSafePIN` call it again before mutation,
  rereading current authorization rather than reusing an entry-point local.
  Once either PIN exists, Safe user authorization is required. Even initial
  setup validates the authorization encoding.
- First-time Safe PIN setup still initializes Access PIN to the same value.
  That existing initialization now belongs inside `updateSafePIN`: calling the
  guarded public `updatePIN` after setting the first Safe PIN would incorrectly
  require authentication during bootstrap. Access-first setup remains rejected.
  Reinstalling Monoid while retaining Safe still requires Safe authentication.
- Cached Safe PIN validation remains storage access, not user authorization.
  No SensitiveResult support, repeated PIN comparison, new session policy,
  additional signing/export boundary check or defensive byte erasure was added.

Validation:

- `check` passes: all 101 simulator tests, including 10 new authentication tests.
  They cover all 96 single-bit mutations of the three legal stored states,
  complement-consistent illegal codes, permission containment, reset/deselect,
  bootstrap, retained-Safe reinstall, direct update calls and state changes
  between entry and mutation. A wrong PIN consumes exactly one attempt.
- `buildJavaCard` converts and verifies both production CAPs targeting Java Card
  3.0.5, with zero converter errors or warnings.
- The new simulator request helper omits `safe` for Access requests: the existing
  API is `safe?: true`, not `safe?: boolean`. jCardSim retains the loaded class
  after `deleteApplet`, so the reinstall test uses `createApplet` for the new
  instance instead of trying to load the same AID twice.

No physical card was accessed or changed. These tests demonstrate rejection of
modeled state corruption and authorization loss; they do not establish resistance
to physical fault injection or native PIN-result corruption.
