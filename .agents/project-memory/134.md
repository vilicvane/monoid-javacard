## Management commands

All three commands require explicit Safe PIN authentication through Monoid's
existing Authenticate command. Possessing Monoid's cached Safe PIN is not
equivalent to a user authorizing a management command. APP implementation is
outside this conversation's scope.

```ts
type AppletGrantOptions = {
  aid: byte[];
  // Exact custom Type, 0x1000 through 0xFFFE; false = read, true = read/write.
  types?: [type: number, writable: boolean][];
  keys?: Key[]; // Fixed results; the client cannot continue derivation.
  seed?: {index: byte[]; domain: byte[]}; // Monoid-001 only.
};

type AppletGrant = AppletGrantOptions & {
  tokenHash: byte[]; // SHA-256 of the token, read from the installed client.
};

// 0x23 ListAppletGrants
type Request = {};
type Response = {grants: AppletGrant[]};

// 0x24 SetAppletGrant
type Request = AppletGrantOptions;
type Response = {};

// 0x25 RemoveAppletGrant
type Request = {aid: byte[]};
type Response = {};
```

One grant belongs to one client AID. Set replaces the entire grant atomically.
Each listed Type grants read access; writable=true also permits creation, modification
and deletion. An unlisted Type grants no access. Omitted types or keys, like empty
arrays, grant no permissions in that category; an omitted seed grants no contextual
derivation. A request with all three omitted is valid and grants no data or
cryptographic operations. On replacement, omission removes the corresponding
previous permissions rather than preserving them.

Set locates the installed applet, reads its token hash through the client
identity SIO, and validates every supplied key and the seed when present.
Each key uses the existing APDU Key description, which selects a stored seed
with derivation or an independent curve key. Seed selects a stored 64B seed;
entropy and independent signing keys are not sources for this derivation grant.
The token hash cannot be supplied by the APP. Missing clients/source items and
invalid requests use the existing Monoid error scheme.

Set prepares all values before publishing the replacement and rechecks the
management authorization after the client identity callback. Remove is
idempotent and removes only the grant, retaining ordinary items and source keys.
The three commands use the existing APDU/CBOR transport and receive recommended
field ordering alongside the other commands.

Each fixed key preserves its standard key identity; no domain is injected
into its derivation. The optional seed fixes its source and domain, and the client
supplies only its Monoid-001 context. Exact cryptographic SIO signatures remain
to be settled. Type permissions authorize ordinary record management
independently of these cryptographic grants. Built-in secret/key Types are
excluded from CRUD.

[agent] Proposed fixed-key selection: a zero-based keySlot selects one entry
in the current grant's keys array. It is distinct from a Safe Item index and
lets multiple authorized derivations of the same stored seed be selected.
The slot is scoped to that immutable grant, not a permanent key identifier;
replacement invalidates old sessions and handles. The client cannot submit
an arbitrary source index, path or context for that fixed-key operation.
The selector and exact SIO signatures remain proposals.

## Stable interface CAP

Proposed library package: `monoidapi`, package AID `F06D6F6E6F696403`, with no
applet instance. Existing package IDs 00/01/02 retain their roles. This proposal
does not yet allocate the Security Key package or its standard NFC instance AID.

Move the existing `SafeDataShareable`, `SafeItemShareable` and
`SafeItemIteratorShareable` interfaces from `monoidsafe` to `monoidapi`, retaining
their method signatures. `SafeShareable` remains in the Safe implementation CAP
and imports these interfaces. Monoid returns restricted implementations of the
same interfaces rather than duplicating the data model.

Security Key imports the interface CAP, not the Safe or Monoid implementation
CAP. This Java package/linkage change requires rebuilding Safe, Monoid and
their callers together. The stable interface CAP remains installed while its
consumers use it. The existing `monoid.Monoid` interface is still empty. The
management/data portion of its proposed replacement is below; cryptographic
methods will distinguish fixed-key operations from seed-based Monoid-001
operations. Fixed-key calls select an authorized key slot; seed calls supply
only context and use the single authorized seed/domain.

```java
package monoidapi;

public interface MonoidClientShareable extends Shareable {
  /** Copies SHA-256 of the client's private 32B token; returns 32. */
  short getTokenHash(byte[] dest, short offset);
}

public interface MonoidShareable extends Shareable {
  void authenticate(byte[] token);

  SafeItemIteratorShareable list(short type);
  SafeItemIteratorShareable list(short type, byte[] keyPrefix);

  SafeItemShareable get(byte[] index);

  SafeItemShareable create(
    byte[] index,
    byte[] key,
    byte[] alias,
    SafeDataShareable data,
    boolean secret
  );
}
```

Use shareable parameter 0 for both interfaces. The service object returned by
Monoid is already a caller-bound session; there is no public session factory.
Inputs and outputs across the firewall use global arrays and existing range
read interfaces. The service copies operation inputs into its own storage and
never retains global arrays. Outputs do not contain private keys.

The private-key boundary under discussion is Monoid, not Safe: production
Safe returns authorized key data to Monoid, where derivation, caches and signing
live. Raw source/master/private-key export has not been approved. This draft
keeps those values in Monoid and lets clients request operations; revocation
checks can therefore apply to each subsequent call. Export, if later chosen,
would be a separate capability whose already delivered bytes cannot be revoked.

The returned item retains the existing update/remove methods. Get requires the
item's Type to be listed in the grant and returns a restricted handle. Both
read-only and read/write entries allow list and metadata/non-secret data reads.
Creation, all setters and deletion require writable=true. There are no
write-only or separate create/update/remove permissions. The earlier proposal
that Type grants also allow raw secret reads is withdrawn under 137; granted
Types must not override secret protection. Export remains subject to the
card's export policy; no future lock API is specified here.

List retains the existing Type/category and key-prefix filter semantics, but
intersects them with exact granted Types. Its count, metadata bound and returned
items all reflect that intersection. Index-based operations check the actual
item's Type. Missing get returns null. Do not return original Safe item/data/
iterator objects to the client: every returned proxy checks its client session
and the required live permission before delegating into Safe.

Create and Set accept client-owned data interfaces. Monoid's data adapter checks
the same session and immutable grant both before and after every client
getLength/read callback, before Safe can publish a write. Safe's existing
session check alone is insufficient here: it authenticates Monoid, rather than
the client whose callback just ran. No additional public callback API is needed.

## Registration, invocation and revocation

1. The client generates a random 32B token at installation and stores it
   privately. Its identity SIO exposes only the SHA-256 token hash.
2. The user approves this installed client through SetAppletGrant with Safe
   PIN authorization. There is no persistent pending-registration table.
3. On an everyday FIDO request, Security Key is selected directly. It obtains
   Monoid's SIO into a local variable and calls authenticate with its token.
   Monoid checks the actual JCRE caller, restores its existing Safe session
   authorization, then reads the current grant and checks its hash. Neither
   APP selection nor APP PIN entry is required for each FIDO request.
4. Monoid checks live authorization before each operation, including cache hits
   and item/data/iterator calls, before accessing records or using a signing key.
   FIDO PIN, UV, RP binding and UP policy remain Security Key responsibilities.
5. Grant replacement or removal invalidates old sessions and all their proxies.
   Client replacement changes its token and requires a new approval.
   Monoid replacement preserves Safe-held grants but requires unlocking the new
   Monoid instance with Safe PIN again. Grants do not enter ordinary item backup.

The session is bound to the actual JCRE caller AID object, its first successful
grant and an immutable grant record. RESET state invalidates the session and
all derived proxies; an old session cannot be reauthenticated after reset or
rebound to a replacement grant. A new operation acquires a new session instead.
The service also rejects invocation by another caller holding a forwarded SIO.

Clients retain SIOs only as local variables for the operation. Internal cached
references, if needed during that operation, live in RESET object arrays.
Safe's grant table stores only Safe-owned values, never client AID objects or
client SIOs. This avoids introducing persistent client-to-provider dependencies.
A malicious client can deliberately retain an SIO and obstruct deletion; a
stable interface CAP cannot force it to release that reference.

Authorization checks follow the existing redundant `LibSecurity` conventions.
SIO authorization failures use `6982`; unavailable Safe/seed state uses `6985`,
invalid inputs use `6A80`, and the existing storage guard retains `6A84`.
These standard exceptions keep the client independent of Monoid exception
classes. There is no new proof that a client performed FIDO PIN/UV validation;
approval establishes trust in that client's implementation.

This scheme also trusts Monoid code. Passing the token to a malicious Monoid
replacement could disclose it; the scheme distinguishes client installations
under the trusted provider, rather than authenticating arbitrary installed code.
An additional proof protocol is outside this proposed first implementation.

## Derivation and public-key format

[agent] For the seed grant, preserve Monoid-001's seed-to-master rule and add
the authorized domain to its context. Proposed exact encoding:

```text
master = HMAC-SHA512(key = ASCII("Monoid-001"), data = storedSeed)
context = ASCII("monoid applet: ") || u16be(domain.length) || domain || clientContext
privateKey = Monoid001FromMaster(master, context)
```

Monoid001FromMaster means the existing Expand/rejection-sampling stage, not a
new algorithm or proposed method name. The prefix has exactly one trailing
ASCII space, no terminator, and lowercase letters. Domain and clientContext
are raw bytes with no normalization. Length framing separates the two variable
fields, so distinct domains cannot overlap by choosing a different suffix.
There is no new universal master-generation rule or arbitrary-algorithm branch
in this seed grant. Existing APP callers can reproduce a delegated result by
supplying the complete framed context through the existing Monoid-001 entry.

The domain and source seed must be stable for credential recovery. AID, token,
token hash, grant identity, item index and card identity do not enter the KDF.
Same seed bytes, domain and client context yield the same signing key, even for
different grants. Different domains select different derivation inputs. The later Security Key
profile will define client context from RP/credential information. Caches must
include the complete framed context; current KeyDerivation caches distinguish
the algorithm instance, source kind, source bytes and full input.

Only Monoid-001/P-256 has completed cross-applet lifecycle adaptation and card
validation in 133. Existing BIP32 and SLIP-0010 operations still use DESELECT
working memory and need their own SIO adaptation/validation before exposure.
This applies to any fixed-key grant using those algorithms as well; the
conceptual permission boundary is not evidence that every algorithm already
works through SIO.

Current P-256 code already obtains a 65B point with native PLAIN_XY before
compressing it to 33B. The new SIO should retain the complete point for COSE;
preserve existing 33B APP results and cache reuse when adjusting that internal
representation. No point decompression belongs in the client.
[WebAuthn section 5.8.5](https://www.w3.org/TR/webauthn-3/#sctn-alg-identifier)
requires P-256 for ES256 and prohibits compressed points. The existing signer
continues returning raw r||s; the CTAP implementation performs DER encoding.

## Protected Safe storage interface

Add the following methods to the existing, authenticated `SafeShareable`.
These grant interfaces remain in `monoidsafe`; clients do not import them.

```java
SafeGrantIteratorShareable listAppletGrants();

SafeGrantShareable getAppletGrant(byte[] aid);

void removeAppletGrant(byte[] aid);

public interface SafeGrantShareable extends Shareable {
  /** Checks the Safe session and that this immutable grant is still current. */
  void assertActive();

  byte[] getAppletAID();
  byte[] getTokenHash();
  short[] getTypes();
  byte[] getPermissions();
}

public interface SafeGrantIteratorShareable extends Shareable {
  short getCount();
  SafeGrantShareable next();
}
```

Get returns null for an absent grant. Getters return global copies and require
an active grant/session. Types and permissions are parallel arrays describing
read-only or read/write entries; the internal encoding remains to be settled.
The former four-bit create/update/remove permission scheme is withdrawn.
The atomic setter and source-accessor
signatures must represent optional fixed keys, seed/domain and Type permissions
independently; their earlier flat rootIndex/domain drafts are withdrawn pending
that representation. Monoid validates the source and derivation requirements
of each supplied key and seed.

Safe stores independent immutable grant records in a private directory, applies
the existing persistent-space guard, and publishes replacements in a transaction
after preparing its own copies. `assertActive` checks record identity against
the live directory, so an older session cannot regain authorization after
revocation and recreation. Iteration follows the existing operation-local
contract, without mutations or reset during enumeration. Ordinary Safe Item
commands cannot address this directory.

## Implementation acceptance

After approval, implement and verify the authorization layer before CTAP:

- Safe-PIN-only grant management; Access PIN cannot create or change grants.
- Approved and unapproved callers, wrong tokens, same-AID replacement,
  forwarded interfaces, reset, grant replacement and immediate revocation.
- Exact Type boundaries, category filters, key prefixes and every nested proxy;
  no unauthorized count/metadata leakage or seed/master access through CRUD.
- Read-only entries allow reads but reject create, setters and remove;
  read/write entries permit all of them. Unlisted Types remain inaccessible.
- Callback authorization rechecks and atomic grant replacement on failure.
- Optional types, keys and seed work independently and together; omitted fields
  and empty arrays grant nothing, and an all-omitted replacement removes prior
  capabilities. Multiple fixed keys are isolated by grant-local selection.
- Fixed-key grants cannot change/extend derivation; seed grants only use
  Monoid-001 with the authorized domain. Verify domain framing including
  trailing-zero byte domains, cache hits and independently verified signatures
  and public keys. P-256 uses full points for WebAuthn.
- Isolated real-card calls while Security Key's test client is selected,
  independent Monoid replacement, registry preservation and temporary cleanup.

These are future checks, not additional results of commit 633e4d1. Formal
installation, client package allocation, CTAP commands and the credential
profile remain subsequent work. README should describe the delivered API only
when that approved implementation is ready.
