# Bundle export policy and implementation

The discussion below preserves the superseded design steps. The implemented
contract is summarized at the end of this record; record139 defines the final
Hello shape.

[user] Proposes a Bundle of multiple cards sharing a symmetric key. Once a card
has that key, its exported data must be encrypted through that key. The card's
existing asymmetric identity remains, allowing it to receive data from cards
that have not created or joined a Bundle. The user subsequently authorizes
implementation, including necessary interface changes to review in code, then
asks to outline initialization before starting production changes.

[user] Clarifies that the Bundle key belongs in Identity and cannot be read
externally. The Bundle is fixed once created: additional cards cannot be added.
This supersedes the agent's Monoid-owned key and later re-enrollment proposal.

[user] Accepts recovery through replacement Monoid as an intentional data
escape route, reasoning that it needs a member card and Safe PIN. Initially
considers both full communication crypto in Identity and direct phone APDUs;
after considering the cost, explicitly narrows the scope to moving only
encryption/decryption into Identity. APDUs remain in Monoid.

[agent] The agreed responsibility boundary is therefore: Monoid owns host
transport, PIN authorization, item serialization/storage and signing; Identity
owns full communication encryption/decryption, its asymmetric key and the
sealed Bundle key/policy. Calls between them use SIO. Identity gains no host
APDU protocol, PIN management or Safe record/signing responsibilities. Exact
SIO signatures and Bundle creation/envelope APIs can be implemented under the
user's feature-specific authorization; initialization is being outlined first.

[user] The symmetric key must be generated by one card and initialized through
bidirectional asymmetrically encrypted communication. Explain that workflow
before beginning implementation.

[agent] Earlier proposed workflow: collect the full Identity public keys of every
intended member, then A creates a Bundle and immediately freezes the complete
roster while generating K and bundleId internally. A sends each B a dedicated
HPKE Auth enrollment packet. B verifies the creator, recipient, roster and
authenticated context, atomically installs K/configuration, then returns an
HPKE Auth encrypted receipt to A. The receipt includes a MAC derived from K
with a separate confirmation purpose, proving possession rather than merely
echoing public fields. A verifies it and records setup progress. APP and Monoid
relay ciphertext; only Identity handles plaintext K. Bind version/suite/purpose,
bundleId, canonical roster hash, creator and recipient full public keys and
direction. The full roster must be available to B for membership verification.

[agent] Receipt confirmation is not a second membership-freeze phase. Each
card independently installs atomically; interrupted setup resumes only the
original roster. Same-configuration/key retries are idempotent; conflicting
configuration/key is rejected even if bundleId matches. No all-card atomicity
or rollback is promised; an unavailable intended member does not invalidate
already installed members. Ordinary communication APIs must internally enforce
a different cryptographic purpose so they cannot decode enrollment packets
and expose K. This is a proposed design, not implemented or card-tested.

[user] Proposes simplifying completion: collect all public keys, let any one
card generate K, initialize the other previously listed cards, then compare
each card's Bundle-key hash so their visitation order does not matter.

[agent] Recommend this simplification instead of mandatory encrypted receipts
back to A. During its creation visit, A can generate a recipient-specific
authenticated encrypted enrollment packet for each fixed member; APP retains
these packets and A's expected fingerprint. Each recipient independently
installs and returns a fingerprint computed inside Identity from its actually
stored K and configuration, not an input fingerprint echoed from the packet.
The earlier suggestion bound protocol-purpose/version, bundleId and canonical
roster hash into the fingerprint; the user's refinement below supersedes it.
APP compares the complete fingerprint against
A's value and tracks completed cards. Subsequent cards can be visited in any
order without returning to A. This is an APP consistency check, not an
authenticated receipt verified by A; the earlier reverse encrypted receipt is
unnecessary for this flow. Initialization secrecy, fixed-roster enforcement,
local atomic writes, idempotent retries and purpose isolation remain required.
No production changes yet.

[user] The Bundle hash must cover only the shared key, not configuration.
Compatibility should be determined separately through versions and must not
require identical versions. Add Reset Bundle and expose the hash in Hello;
the response key must be named `bundle`, not `bundleHash`.

[agent] Proposed response is optional `Hello.safe.bundle: byte[]`, present when
a Bundle exists and containing SHA-256(K). It follows the existing `safe: true`
request inclusion rule. Compute/cache it inside Identity from the installed K;
version and roster checks still belong to the initialization/transfer protocol,
not the hash. The natural Reset Bundle semantics are local removal of K and
Bundle configuration, retaining Identity's asymmetric key/ID and Safe data;
it restores ordinary asymmetric export and prevents this card from decrypting
old Bundle ciphertext until the same K is installed again. Other members are
unaffected. This changes the earlier no-reset proposal into a resettable export
policy; it must not be presented as a permanent lock. Normal Monoid management
should require Safe authorization. These reset details are the agent's proposed
interpretation; no source implementation or physical reset has occurred.

[agent] Interpret the first version as one Bundle per card, subject to user
confirmation. Bundle is an export-policy and shared-key boundary, not an item
container or automatic synchronization mechanism. A member can import both
same-Bundle artifacts and the existing Identity-addressed artifacts. Its exports
always use Bundle protection, including newly imported data; supplying an
arbitrary or its own Identity public key must not bypass that rule. One Bundle
artifact can be consumed by any member possessing the same key. Other-Bundle
and nonmember recipients cannot decrypt it without obtaining that key.

[agent] Updated ownership follows the user's clarification: Identity retains
the Bundle key and sealed configuration alongside its original asymmetric key.
Even Monoid should use cryptographic operations rather than receive the Bundle
key. Replacing Monoid clears its Safe items/PINs but does not clear Bundle
membership; keeping Identity can therefore support recovery without admitting
a new member. Deleting Identity still loses its keys. The earlier recommendation
to expose no ordinary interface for clearing the Bundle key is superseded by
the user's explicit Reset Bundle request above.

[agent] Proposed setup collects all member public keys and commits to a fixed
roster before sealing the shared key. Completion/retry for that exact roster
must not admit a newly supplied public key. Setup and envelope formats still
need design; no distributed atomic completion is assumed. Enrollment ciphertext
must not be decryptable through the existing general-purpose
decryptCommunicationKey interface, which returns plaintext key bytes. A
dedicated install method alone is insufficient if the same ciphertext remains
accepted by that general decoder; cryptographic purpose separation must be
enforced internally rather than chosen entirely by the caller. This describes
the earlier open design; the implementation below removes that key-returning
interface and fixes both cryptographic domains inside Identity.

[agent] Existing fresh per-export communication keys and AES-GCM payload
encryption can be reused conceptually, replacing recipient-specific HPKE
protection of the communication key with Bundle-key protection. Separate
cryptographic domains, authenticated mode/Bundle identifiers and existing item
metadata are needed; multi-card use must preserve AEAD key/nonce uniqueness.
Do not simply substitute a long-lived Bundle key into an algorithm whose nonce
assumptions depended on fresh per-export keys. No wire format is specified yet.

[agent] Key secrecy and data secrecy are distinct. Even with a sealed,
unreadable Bundle key, a replacement Monoid admitted only by AID could ask
Identity to decrypt a captured valid Bundle export. If Identity returns its
payload key or Secret plaintext, that replacement can send it to the host
without extracting the Bundle key. This path needs an existing export and
replacement capability; it is not a direct read of the original Monoid's
storage. The user subsequently accepts the escape route; do not expand this
work into trusted-code admission or moving signing/storage into Identity to
prevent it.

[agent] Corrected the precise Safe PIN boundary after source inspection:
CommandExport requires AUTH_SAFE to generate an export from normal Monoid.
Identity.decryptCommunicationKey only checks the caller AID and has no PIN.
An already captured export plus the receiving card and replacement capability
therefore does not require the former Monoid's Safe PIN for decryption. The
PIN protected the original Export, not every later recovery. No Identity PIN
mechanism is approved; do not describe member-card-plus-PIN as an existing
enforced Identity recovery rule.

[agent] Fixed-member setup still trusts the enrolled endpoints: public-key
proof establishes possession, not genuine hardware or approved applet code.
Shared symmetric authentication identifies group possession, not one particular
sender. Dynamic additions, removals and rekeying are outside the clarified
fixed-Bundle model; do not design those as supported operations.

[agent] The initial source review at commit b8898d7 covered ItemCipher, the former
Identity SIO/app implementation and the item-transfer/Identity documents. RFC9180
section5.1.3 distinguishes possession of a sender key from additional identity
claims; RFC5869 section3.2 supports context separation in derived keys. No
production source, public API, card state or APP files were changed during that
initial discussion. The following implementation supersedes that status.

## Initial four-command implementation

This stage was implemented and locally validated before the user simplified the
management API. The final three-command contract below supersedes its command
numbers, creation restrictions and extra Hello confirmation.

[user] Calls out the remaining monoidsafeidentity name after the applet merge.

[agent] The current Identity names are monoididentity, MonoidIdentityApplet and
IdentityShareable, with `MONOID_IDENTITY_*` constants, monoididentity.cap and
doc/identity.md. Identity retains package00/applet01 and its existing AID bytes;
this is a source/artifact naming change, not a new identity namespace.

[agent] Monoid provides four Safe-PIN-authorized commands: CreateBundle0x26
{publicKeys:byte[][]} returns {bundle:byte[]}; ExportBundle0x27
{recipientPublicKey:byte[]} returns {data:byte[]}; ImportBundle0x28
{senderPublicKey:byte[],data:byte[]} returns {bundle:byte[]}; ResetBundle0x29
{} returns {}. Creation requires at least two distinct members including self,
sorts full65B public keys by unsigned-byte order, and freezes the list. An already
enrolled card cannot create another Bundle; export only targets an existing
member. Import checks canonical membership, recipient and authenticated sender;
the same key and membership are idempotent, while differences conflict. Key and
membership publish together in a local transaction.

[agent] Identity generates a32B Bundle key K and stores SHA-256(K). The hash
contains neither configuration nor version. Enrollment packet format is
01 || u16(memberCount) || sortedPublicKeys || HPKE[113], totaling
116+65\*memberCount bytes. HPKE remains RFC9180 Auth, P-256/HKDF-SHA256/AES128GCM;
its info is SHA-256(ASCII("Monoid Bundle Enrollment") || 01 || sortedPublicKeys),
with empty AAD. Ordinary item decryption cannot choose this purpose or release K.
Compatibility is checked through supported packet versions, independently of
the Bundle hash.

[agent] The host collects all intended public keys first. During a single visit,
any member A creates K and exports a recipient-specific enrollment packet for
each other member. Recipients import in any order and the host compares both the
Import response and subsequent Hello.bundle against A's full32B hash. No return
visit to A or encrypted receipt is required. The host tracks per-card completion;
there is no all-card atomicity, dynamic membership or automatic synchronization.

[agent] Export0x36 now has optional recipientPublicKey: without a Bundle it is
required and produces the unchanged asymmetric version01 item; with a Bundle it
is ignored and Identity always selects version02. Import0x37 has optional
senderPublicKey: version01 requires the expected sender; version02 authenticates
the group and does not require an individual sender. Enrolled cards can still
receive asymmetric items. Bundle item format is
02 || SHA-256(K)[32] || salt[32] || nonce[12] || ciphertext(secret[2] || data) ||
tag[16], totaling dataLength+95 bytes. Each export generates salt and nonce.
HKDF-Extract(salt,K), then HKDF-Expand with
ASCII("Monoid Bundle Item Key") || metadataContext and L=16 derives the AES key.
metadataContext remains SHA-256(ASCII("Monoid Item") || versionByte || index10 ||
nullable(key) || nullable(alias)); nullable uses u16 length and FFFF for null.
Version02 uses byte02 in that context. AES128GCM uses empty AAD and a16B tag.

[agent] Full item cryptography moves to monoididentity. IdentityShareable exposes
getId/getPublicKey/getBundle, createBundle/exportBundle/importBundle/resetBundle,
encryptData/decryptData. The former plaintext communication-key methods are
removed. CommunicationDataShareable.getLength/read carries bounded ranges;
completed results admit only their original caller. Monoid keeps APDU transport,
PIN checks, metadata, Safe storage and signing. It copies authenticated imported
data before publishing and preserves exact-item idempotency. Global scratch
arrays remain local variables, never object fields. Nested communication or
Bundle mutations during a data callback are rejected to protect shared crypto
state and the chosen export policy.

[agent] Reset clears this card's Bundle key/membership only, retaining Identity
key pair/ID, items and both PINs. It restores ordinary asymmetric export and does
not change other members or revoke old artifacts; old Bundle data needs the same
K reinstalled for decryption. Keeping Identity across Monoid reinstall retains
the Bundle, but Monoid reinstall still clears items and PINs. This remains a
resettable export policy, not the deferred permanent lock. A replacement Monoid
admitted by AID can recover captured artifacts; no Identity PIN or code/hardware
attestation was added. The implementation supersedes the earlier four-method
SIO, Safe-owned payload crypto, nested/optional Hello.bundle, configuration-bound
hash, encrypted-receipt and no-reset proposals.

## Final three-command contract

[user] Selects three separate commands: Create Bundle, Import Bundle and Reset
Bundle. Creating with a complete member list generates a new key and replaces
the existing local Bundle. Creation returns every recipient packet in the same
response, eliminating a separate Export Bundle command. The user assigns the
three commands consecutively starting at0x23.

[agent] All three commands require Safe PIN authorization. `0x23 Create Bundle`
accepts `{publicKeys:byte[][]}` and returns
`{bundle:byte[],packets:[{publicKey:byte[],data:byte[]}]}`. Packets follow request
list order, omitting self. `0x24 Import Bundle` accepts
`{senderPublicKey:byte[],data:byte[]}` and returns `{bundle:byte[]}`.
`0x25 Reset Bundle` accepts `{}` and returns `{bundle:false}`. Public Export Bundle
and the earlier0x26–0x29 allocation are removed. Recommended CBOR order is publicKeys for Create and
senderPublicKey/data for Import. These commands have no type/action selector.

[agent] Creation still requires at least two distinct65B keys including self.
Identity stores the unsigned-byte-sorted canonical roster and generates fresh K,
even when replacing a Bundle with the same member list. This changes only the
local card; other members retain their current state. Creation is not an
idempotent retry and must not be blindly replayed after an uncertain response.
Import retains same-key/same-roster idempotency and rejects conflicts; reset a
recipient with a different Bundle before importing. Reset preserves its Identity
key/ID, items and both PINs, restores asymmetric export and does not affect other
members or revoke previously exported artifacts.

[agent] The final workflow is: collect every intended public key; on any A call
Create Bundle once and retain its full hash, public key and all response packets;
visit each recipient in any order, call Import Bundle with A's public key and the
recipient's packet, and compare that response's full hash immediately. No return
to A, final extra scan round or additional Hello verification is required. Hello
serves routine discovery. Host per-card progress does not imply all-card atomicity.

[agent] IdentityShareable exposes
`CommunicationDataShareable createBundle(byte[] publicKeys)`,
`byte[] importBundle(byte[] senderPublicKey, byte[] data)` and `void resetBundle()`.
Creation receives concatenated65B public keys and returns all equal-length
enrollment packets concatenated in input order excluding self. All encryption
finishes before the new Bundle is atomically published; failed packet preparation
preserves the previous key/membership. Monoid range-reads the result and pairs
each packet with its recipient for the response. No public setBundle or
exportBundle remains. The complete item crypto boundary, enrollment/item wire
formats, SHA-256(K) identity and no-downgrade export policy remain unchanged.
