# Native SHA-256 token timing

[user] Asked to measure the real-card cost of hashing the proposed 32B client
token. The authorization API in [134](./134.md) remains unapproved; this request
authorizes an isolated benchmark, not that API's implementation. In discussion,
capability was clarified to mean the previously discussed token, and
authorizationId its SHA-256 digest; token/tokenHash are the clearer proposed names.

[agent] On 2026-10-19, card serial `55690320`, ATR
`3B8A800150564A434F503453494471`, ACS ACR1552 PICC, T=1:

**A reused native SHA-256 engine hashes a 32B token in approximately 2.37ms.**
This is a batch-difference estimate including the Java Card method invocation,
not a hardware cycle measurement. Creating a new engine for every operation
adds approximately 21.2ms on this card. The result supports retaining a shared
engine; it does not measure a complete authorization/session implementation.

## Measurements

All table values are milliseconds. Each steady-state cell has seven samples.

| Measurement                                        | Selected provider | Client calling provider through SIO |
| -------------------------------------------------- | ----------------: | ----------------------------------: |
| Single copy control, complete APDU median          |            5.4751 |                              7.1891 |
| Single reused hash, complete APDU median           |            7.6965 |                              9.4357 |
| Fresh engine factory control, complete APDU median |           26.6974 |                             28.4422 |
| Fresh engine plus hash, complete APDU median       |           28.8847 |                             30.5851 |
| Fresh hash minus reused hash median                |           21.1882 |                             21.1494 |
| Estimated hash per call, 16-round batch            |           2.36536 |                             2.36639 |
| Estimated hash per call, 64-round batch            |           2.36814 |                             2.36805 |
| Estimated hash per call, 256-round batch           |           2.37351 |                             2.37270 |

For the batch estimate, each sample subtracts an equal-round local-counter
control from the hash command and divides by the round count. The counter has
an additional local increment, so this is not a cycle-exact subtraction of
identical bytecode. Consistency over 16/64/256 rounds supports the rounded
approximately 2.4ms result. The unamortized one-round subtraction is noisier
and contains fixed branch differences: medians 2.2411/2.2701ms.

The 256-round selected-provider hash command took 618.9388ms median versus
11.3263ms for the loop control; the SIO equivalents were 620.4655/13.0412ms.
These are whole APDU times. A SIO batch acquires the interface and crosses the
context boundary once for the entire batch, not once per hash iteration.

The first selected-provider hash lazily constructed and retained the shared
engine and took 31.6599ms in one sample. This is not a statistical cold-start
benchmark. The later SIO first call reused that engine and must not be described
as cold initialization. Factory-only timings include the APDU and a copy/getLength
control; 26.7ms is not the isolated factory cost.

## Probe and validation

All research source, CAPs, manifests and evidence are under ignored
`.research/sha256-token-20261019/`. Three temporary packages were used:

- `F06D6F6E6F6964E8`: interface-only `tokenhashapi`.
- `F06D6F6E6F6964E9`: provider, instance `F06D6F6E6F6964E9010000`.
- `F06D6F6E6F6964EA`: caller, instance `F06D6F6E6F6964EA010000`.

Provider uses `MessageDigest.getInstance(ALG_SHA_256, true)`, with two 32B
RESET arrays allocated at installation. A command copies the public input
fixture into owned memory once, runs its loop with local counters and no object
allocation or persistent writes, and copies the final output to the global APDU
buffer. The caller keeps its SIO reference only in a local variable.

Mode0 repeatedly copies32B; mode1 performs repeated doFinal using the shared
engine; mode2 creates one fresh engine and copies input using its digest length;
mode3 creates one fresh engine and hashes once; mode4 counts locally; mode5
requests object deletion in a separate APDU. Fresh-object samples have explicit
GC commands before them; GC command durations are excluded. This does not prove
the runtime never performs automatic GC, but the fresh measurements were stable.

The host clock wraps only PC/SC transmit, excluding JS logging, startup and
SELECT. Input is the public fixture `00..1F`, with independent zero, FF and
descending-byte vector checks. Hash and control commands are paired, alternating
the ordering of hash versus loop control. Every returned output/status was
checked: **240 probe commands**, including 84 returned digests independently
verified with host SHA-256. Every batch returns only its final digest, so the
individual intermediate iterations are not separately observed.

The three CAPs converted and verified successfully. Fifteen hashes bind source,
CAPs and harness/helper inputs in `manifest.json`; the check passed before
installation and after cleanup. Complete measured results are in `result.json`,
raw APDUs in `operations.jsonl`, and progress/output in `run.log`.

## Card preservation and scope

Preflight confirmed the serial and vacant temporary AIDs. All two probe instances
and three packages were deleted successfully. Final registry, package ownership,
privileges, versions and management-key metadata match the initial snapshot.
The original legacy Monoid baseline is unchanged: SELECT9000, Hello6F00, already
present before this test. No original data/PIN/management keys were written.
The PC/SC connection was closed and reader released.

Production sources, existing APIs and formal installed applets were unchanged.
This is a reusable primitive benchmark on one card, not a complete token
authentication benchmark or a guarantee for other card models. The proposal's
per-session hash and per-operation live permission checks have not been
implemented or timed.
