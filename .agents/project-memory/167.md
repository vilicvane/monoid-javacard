# Security Key iPhone NFC interoperability

[user] 2026-10-21 reports that the RDP-installed Security Key works in Windows,
but iPhone NFC WebAuthn registration and login sometimes never show the PIN
prompt. The latest prompt took 2–3 seconds; longer waits are also possible.
After entering the same PIN that works in Windows and tapping again, the latest
two attempts reported an incorrect PIN after at least five seconds. iPhone model
and iOS version have not yet been supplied. No PIN value was requested.

## Confirmed response defect and correction

[agent] `ApduTransport.send` capped every reply at 256 bytes, even when the client
requested a larger extended response. It now sends the smaller of the pending
response and the length returned by `APDU.setOutgoing()`. Short requests retain
ISO GET RESPONSE handling. No extra buffer, public interface or PIN behavior was
introduced; the existing response limit remains 1024 bytes.

The new transport regression checks complete extended responses through the
1024-byte limit without a GET RESPONSE helper that could hide fragmentation.
All 69 selected Security Key unit/integration tests pass, and all three production
CAPs compile and verify. These CAPs use the formal package AIDs; they are not a
replacement for the D0/D2/D3 trial installation without a matching build.

An isolated red/green run compiles the unchanged frozen transport to a separate
classpath override and invokes the same final compiled regression test. With
Ne=32767, the old implementation fails on the 325-byte response with 6145 rather
than 9000; the current implementation passes all 67/325/1024-byte cases. Frozen
source hashes remain unchanged. The runner and timestamped evidence are retained
under the research directory as `run-extended-response-red-green.ps1` and
`extended-response-red-green/runs/20261021T144823301Z/`.

jCardSim 3.0.6.0 does not normalize extended Le=0000 to the JCRE limit of 32767.
The regression therefore uses valid extended Ne=32767 and T=1. This does not
validate physical Le=0000 handling or NFC link fragmentation. The initial
Le=0000 test failed even after the fix and is not an isolated pre-fix comparison.

## PIN/session evidence

[agent] An independent JVM host reproducer uses the same correct synthetic PIN:

| Sequence                                                     | CTAP result | Remaining retries |
| ------------------------------------------------------------ | ----------- | ----------------- |
| Get agreement key, deselect/select, submit PIN with that key | 00          | 8                 |
| Get agreement key, power reset, submit PIN with the old key  | 31          | 7                 |
| Get the new agreement key, submit the same PIN               | 00          | 8                 |

Successful returned tokens are independently verified with host JCE HMAC.
This proves the conditional stale-key failure, not that iOS actually follows
that failing sequence. SELECT preserves the ECDH key and PIN token; power reset
regenerates them. CTAP2.0 requires regeneration at power-up, so neither is made
persistent as a speculative workaround. Each PIN submission calls OwnerPIN.check
once; the redundant security checks only read validation state. An empty pinAuth
probe can return 31 without consuming a retry, and token-proof failures return
33, so the displayed message alone cannot distinguish these cases.

## Public platform evidence and limits

- [WebKit CtapNfcDriver](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/WebAuthentication/fido/CtapNfcDriver.cpp)
  uses extended APDUs and its public layer does not collect 61xx responses.
  Private NearField behavior is not visible, so this is a compatibility risk,
  not proof of the observed iPhone failure.
- [WebKit CtapAuthenticator](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/WebAuthentication/fido/CtapAuthenticator.cpp)
  obtains the agreement key before prompting for PIN, then uses the cached key.
  Both PIN_INVALID and PIN_AUTH_INVALID map to the PIN-invalid UI status.
- [CTAP2.0, section 5.5](https://fidoalliance.org/specs/fido-v2.0-ps-20190130/fido-client-to-authenticator-protocol-v2.0-ps-20190130.html#authenticatorClientPIN)
  defines the power-up and PIN protocol behavior.
- [Oracle APDU](https://docs.oracle.com/en/java/javacard/3.2/jcapi/api_classic/javacard/framework/APDU.html)
  defines extended Ne normalization and sendBytesLong buffer handling.

These are public WebKit main sources, not a trace of the user's unspecified iOS
version. SELECT, GetInfo and ClientPIN responses are under 256 bytes, so the
response fix alone does not explain all pre-PIN delays. Record166's performance
numbers come from card55690320/ACR1552, not card51574920/iPhone.

## Correction to record166 cold-start claims

[agent] The full baseline/candidate raw logs contain three host-labelled resets
each. All six preserve the complete ECDH public response across the reset.
The helper calls Card.disconnect(true), reconnects, then reports a synthetic9000;
that result is not a card-side RESET-memory check. Therefore the3075.39→1854.45ms
measurement is a PC/SC reconnect sequence, not a proven RF power-cycle benchmark.
Source inspection confirms reset should regenerate the ECDH public key. Record132
had already observed that disconnect(true) need not clear this reader's marker.
The driver/reader-level cause is not established by these logs. Future cold-start
measurements must actually remove power and verify the agreement key changes.

Warm signature/registration and multi-credential timings remain supported by their
logs. The correction only limits the cold-start interpretation; it does not imply
new functional failures. Reproducible offline analysis is retained as
`analyze-startup.mjs` and `startup-audit.json` under the research directory, with
input hashes and exact log lines. No firmware, installed applet or PIN was changed
during this performance follow-up.
