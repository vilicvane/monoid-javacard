### Diagnosed allocation failures and adopted changes

[agent] The first implementation failed 32B Export after both cryptographic layers
had succeeded. A phase probe returned `6DF2`: the response writer's transient
allocation failed, not HPKE or GCM. Another phase probe identified initial 32B
Import failure as `6C42`, allocating the Monoid wrapper's second global copy of
the sender public key. Generic error-response allocation could itself fail and
mask these causes as `6F00`; ordinary `INTERNAL`/timing alone was insufficient
to locate the allocation.

The current implementation removes these duplicate allocations without changing
the approved protocol or Identity's four-method interface:

- Identity encrypt/decrypt and Safe encrypted export allocate their returned
  bytes directly as global arrays, without local-to-global result copies. Already
  global public keys are passed through instead of copied again.
- CommandImport reads index, senderPublicKey, key and encrypted data directly into
  global arrays using existing reader APIs. Alias keeps its text-read/global-copy
  path. Safe.importItem receives these arrays without another wrapper copy; no
  generalized CBOR API or compatibility layer was added.
- CBORApduWriter borrows the current APDU buffer for responses of at most 256B.
  It obtains that buffer dynamically and does not retain its global reference in
  an object field. Larger responses allocate ordinary retained response storage
  and preserve GET RESPONSE behavior. Commands finish reading before writing.
- The ephemeral P-256 private-key container and selected low-write HPKE/item
  workspaces use persistent storage; the per-block HMAC workspace, AES/GHASH
  state and transient AES keys retain transient storage. Inputs are rewritten for
  every operation. Shared native crypto contexts and existing signing resources
  remain reusable; they are not discarded between Export and Sign.

After these changes, the 256B Import following Ed25519 still failed. The focused
probe returned `6E62`, identifying its 258B Safe-private plaintext allocation.
ItemCipher.decrypt now first tries transient storage and, only for
`SystemException.NO_TRANSIENT_SPACE`, allocates a private persistent plaintext
array. Other allocation errors propagate. The complete tag is checked before
returning this array or publishing an item; unauthenticated plaintext is never
returned through a global result or installed as an item. This is operation-local,
unpublished workspace, not a retained backup session. It becomes unreachable on
completion/failure and is eligible for existing command-end collection; no claim
is made that persistent bytes are immediately erased. This small on-demand fallback
is the implementation that passes the final 256B tests above.

### RAM interpretation and remaining acceptance boundary

Initial-version SystemInfo reset/deselect availability changes from 1880/1872B
before crypto initialization to 667/656B after it. The **same-version reset delta
is 1213B**. In the compact-context version, the matching readings are
2136/2128B before and 1508/1504B after, giving a **628B reset delta**. Thus the
measured initialized-context reset-RAM increment falls by 585B. Do not subtract
the two versions' absolute post-operation readings and call the entire difference
context savings: borrowing the APDU response buffer separately removes the old
256B SystemInfo response allocation. Deselect values also have allocation-granularity
differences; they are recorded rather than treated as an exact component census.

The final passing suite starts at 2136/2128B and ends at 1412/1408B available
reset/deselect RAM. The further 96B after the first Ed25519 key use is consistent
with the separately measured compact-context sequence. These are comparable
**query-time availability readings, not peak live RAM**, and do not prove that
all original RAM is available during a transfer or signature. Persistent
availability saturates at 32767B, so it cannot measure EEPROM consumption or
prove no persistent allocation occurred. GC can collect abandoned request,
response and operation arrays; it cannot reclaim shared native engines or arrays
still referenced by persistent contexts. Reset clears transient contents, not
the capacity reservation of a retained object.
