# 公共 CBOR 库

[user] 同意将 Monoid 与 Security Key 的 Reader、Writer 统一后抽到公共库；Identity 保持独立，不依赖公共库。严格遵循现有代码结构和风格，完成后实卡对比性能和内存占用。

[user] 支持一个 Reader/Writer 通过不同方法变种满足不同场景；功能数量本身不构成拆分理由。

[agent] 采用没有 Applet 实例的 `monoidlib.cap`，包 AID 为 `F06D6F6E6F696404`。Monoid 与 Security Key 依赖该库，Identity 保持原有独立构建。共用 CBOR 编解码和字段索引；各自的 APDU 传输和响应存储实现保留。

[agent] 连续数组经一个读取分支直接访问，批量复制和比较仍使用 Util；分块输入不先拼成完整副本。快照等状态按需分配，保留 CTAP 和 Monoid 各自的校验、错误、字段处理语义。复制位置及游标行为通过明确的方法表达。此次不是外部 APDU/CTAP 协议变更。

[agent] 已在 `.research/cbor-library-20261022/before` 冻结开始时的源码、配置与脚本，`before-caps` 保存对应构建产物。比较基线包含 174 已接受的完整 CTAP 收尾请求 GC 策略，不能用更早的选择性 GC 版本代替。

## 实现与验证

- 公共库包含 CBOR、CBORReader、CBORMap、CBORWriter、CBORBufferReader、ByteSource；只有一套解析和编码实现。Monoid 与 CTAP 的校验语义通过 profile 区分，原有 APDU、CTAP、Shareable 签名不变。
- `bytes()/text()` 保留 Security Key 的持久副本及越过字段的游标语义。Monoid 原分配型调用改为 `bytesTransient()/textTransient()`，仍停在内容起点；`bytesGlobal()` 以及调用方输出缓冲、原位 offset 方法保留。不同存储方法没有暗中改变已有调用方的游标规则。
- Reader 的 CTAP 游标仍为4B transient；Monoid 导航与快照按需分配。没有公共库静态可变解析状态，各调用 Applet 持有自己的对象。Writer 仅共享编码，Monoid 的分块/流式输出与 Security Key 的固定响应数组/APDU窗口分别保留。
- 构建增加 library CAP、exports 依赖与编译时旧 self-export 排除。Inplate 不再生成重复 CBOR/Writer 文件。安装脚本先 `--load monoidlib.cap`，卸载按 Security Key → Monoid → Library → Identity；替换公共库需先卸载依赖包，Identity 可以保留。
- 560项测试、62套测试全部通过，四个正式 CAP 转换及验证均零错误、零警告，Inplate与格式检查通过。新增测试覆盖 profile 差异、跨 chunk 元数据和读取、存储/游标变种、保留的非法编码处理。审查时发现的 additional-info 28/29 误接受已修复。
- Identity 的14个源码文件及正式 CAP 的全部11个组件均与任务开始时一致。仓库中更早未提交的 Identity/其他修改仍保留，此结论不是与 Git HEAD 比较。

## 基线资源限制与独立补测

最初额外脚本为 Ed25519 指定任意 Index，被卡正确拒绝；已改为按 type 创建、使用返回的摘要 Index。旧脚本证据保留，主对照使用重新冻结的 fixed 两轮。

两版在完整 FIDO 预热后执行600B Ed25519签名均返回 INTERNAL；此前32B签名及1536B普通数据读写成功。单独诊断候选只在最终异常处理处把 SystemException 原因映射到 SW，不改变成功路径或分配；同样的基线流程明确返回 **6F02 = NO_TRANSIENT_SPACE**。此时接收分片需要512B transient，叠加签名工作数组超出当前布局的余量。这是基线已存在的多应用资源限制；不把额外脚本 `passed:false` 改成成功，也不将该布局中未完成的1536B签名计作通过。

移除本轮自建 Security Key（仅C401/C4）后，保留 Identity、Monoid及原应用，独立验证32/600/1536B各3次Ed25519签名。基线诊断版与新版各9次均通过，并清理4个额外测试条目。该组用于分片功能验证，不混入完整 FIDO 布局的性能表。

此独立布局中，ViewKey前两版RESET1398B、DESELECT1392B一致；完成ViewKey及各次签名后，基线RESET1302B/DESELECT1296B，新版1286B/1280B，即新版少16B，连续签名无进一步下降。两组在此时的持久余量为49244B/47444B；独立 Monoid 仍需完整公共库，已不具备同时安装 Security Key 时消除两份代码的全部收益，且基线为带异常捕获的诊断候选。该数字不能混入主对照的404B节省，也不能宣传所有布局RAM完全相同。

## 博客兴趣点

- **切入问题**：Java Card 把两个 Applet 的 CBOR 实现放进 library CAP，会同时节省代码、RAM并提速吗？
- **关键事实**：包含新库后正式可加载代码净减829B；完整FIDO布局预热后持久余量增加404B，RAM余量不变，但缓存命中签名增加约29ms。独立Monoid布局没有全部共享收益，Ed25519预热后新版RAM多占16B。共享的是代码，各Applet仍拥有自己的解析对象和上下文。
- **适用边界**：本轮为55690320/ACR39U/T=1的同卡先后安装对照；方法分支、对象布局、GC及包调用成本均可能影响完整耗时，不能仅凭差值判定单个原因。边界可用空间不代表峰值。
- **参考**：本记录的源码组织、计时与内存表，以及112/113的Reader游标实验。
