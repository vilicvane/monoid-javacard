# Reset must also replace Identity state

- [user] Identified the cross-Reset recovery issue, decided that Reset must reset Identity as well, and approved implementing that design.
- [agent] This supersedes record157/a415033's Identity-preserving Reset. Keep its335-test/274-operation evidence historical; it does not validate this change. The implementation and documentation are updated and local checks pass; this change has not been tested on a physical card or committed.

`IdentityShareable.prepareReset(): byte[]` replaces `resetBundle()` together with `reset(): void`. Both require the exact Monoid caller and idle communication. Preparation runs outside a transaction, generates a candidate key pair/random ID/token secret/empty token cache and returns the candidate caller token in a global array without changing the published identity. A reset-scoped reference retains the candidate only after complete preparation.

`reset()` publishes that candidate and clears Bundle and old communication-key references inside Monoid's transaction. Safe synchronizes its binding, empty item store, unset PINs and cleared derivation cache in that same transaction. An abort retains the previous published persistent state. Publication consumes the candidate even if the transaction aborts; a card power reset also discards a pending candidate. Authorization clears only after success. Other applets' old binding tokens become invalid without automatic rebinding.

Ordinary upgrades preserving Identity/Bundle can still recover saved data. Reset makes old encrypted exports/enrollment packets unusable to the new Identity state; it does not revoke other cards' copies or delivered plaintext, or guarantee physical erasure.

- [user] Subsequently pointed out that saving an artifact, replacing Monoid with a same-AID implementation and decrypting the artifact can still recover plaintext.
- [agent] Confirmed: the new behavior only invalidates old local artifacts when `0xFF Reset` actually runs. It does not prevent GP code replacement that retains Identity/Bundle and skips Reset. Record160 subsequently sets the new target: Safe PIN plus a second card when bundled, Safe PIN alone otherwise. This Reset implementation does not achieve that target; concrete protocol/API restrictions remain unapproved and unimplemented.

Record158's self-HPKE path remains unimplemented. The user chose Identity reset to cut off cross-Reset recovery; source Bundle hash binding was an agent suggestion, not adopted. Hello installation proof and GP Token signing are outside this change.
