# Stable Applet AIDs, Identity binding and caller-isolated transfer — 2026-10-20

## Decisions

[user] Initially installed Monoid and Identity are trusted, while additional
applets may be installed. Proposed a private Identity token that Monoid saves and
compares on later calls, without a one-time read restriction: replacing Monoid
first removes its existing data. Then proposed deriving the token with the caller
AID so the getter needs no AID whitelist.

[user] Approved `IdentityShareable.getToken()` with no caller-supplied AID; all
registered callers may encrypt/decrypt within their full runtime AID domain.
Same-AID applets on different cards interoperate, different AIDs cannot decrypt
one another's records. Bundle management remains restricted to Monoid's exact
AID. Explicitly requested per-caller derivation from the Bundle root and removal
of versions from all applet AIDs. Approved changing cryptographic context without
an old-envelope compatibility path; APDU fields stay unchanged.

[user] Confirmed two-card plaintext migration is an accepted boundary and useful
feature, not an attack to block: with two enrolled cards and at least the source
Safe PIN, export from the source, retain the target Identity, replace its Monoid,
and decrypt the records using that replacement. Requested recording this in docs.

## Implementation

[agent] Formal package AIDs remain `F06D6F6E6F696400` and `F06D6F6E6F696402`.
Instance/module AIDs now end at the applet number: Identity
`F06D6F6E6F69640001`, Monoid `F06D6F6E6F69640201`. Inplate generates them and an
independent `Constants.MONOID_VERSION` used by Hello/SystemInformation. Removed
reading the final two instance-AID bytes as a software version and the associated
initialization flag/transient allocation. No old AID aliases or migration branch.

[agent] Identity persists an independent random 32B token secret and returns:

```text
HMAC-SHA256(identitySecret, "Monoid Identity Token" || fullCallerAID)
```

The AID comes from `JCSystem.getPreviousContextAID()`, never an argument. Each
result is a fresh global32 array. A cached SHA-256 engine and 64B RESET HMAC
workspace are initialized on demand without initializing AES/ItemCipher. The root
secret has no read interface and is independent of Bundle changes.

[agent] `Safe.initializeIdentity()` copies the initial token privately before
Monoid processes its first non-SELECT command, before PINs/items can be created.
Every later Identity operation obtains a fresh token and validates it locally
using the existing three-round `LibSecurity.check`. Equal-length tokens are
compared by traversing every byte and OR-ing XOR differences. The saved token is
never sent to the candidate Identity and is never automatically rebound. Candidate
global arrays are copied privately for the validation callback, then the temporary
reference is released. No Identity SIO/global reference is retained. Deleting
Monoid deletes its binding alongside data/PINs, allowing an empty replacement to
bind to the retained Identity for recovery.

[agent] All registered callers may obtain the SIO, public information, their own
token and encrypted-transfer results. Only the exact full Monoid AID can invoke
create/import/reset Bundle, checked on every method call. The previous broad
prefix check is gone. Data results remain readable only by the requesting caller;
the caller AID is captured before callbacks. Token retrieval during an active
communication operation is rejected.

```text
callerBundleKey = HMAC-SHA256(
  bundleRootKey, "Monoid Bundle Caller Key" || u8(aidLength) || callerAID
)

context = SHA256(
  "Monoid Item" || version8 || u8(aidLength) || callerAID
  || index10 || nullable(key) || nullable(alias)
)
```

Bundle payload HKDF now takes `callerBundleKey` as IKM; the original random salt,
payload label and AES-GCM layout remain. Asymmetric HPKE and payload keys bind the
new context. V1/V2 layouts and version values remain unchanged during prototype
development, but previous envelopes are cryptographically incompatible. Enrollment
packets keep their separate domain. Identity retains the shared AES-GCM instance,
16B AES staging and persistent private temporary arrays. A static `LibHMACSha256`
helper is reused by tokens and item derivation; supported keys are the existing
at-most-32B inputs, not a general long-key HMAC interface.

## Accepted recovery boundary

[agent] The target replacement must register the same fixed Monoid instance AID
and preserve Identity/Bundle. Card management authority is needed to replace it;
the target's former Safe PIN is not needed after its Monoid is removed. Source
Safe PIN authentication is needed to obtain a fresh export from a trusted source.
Already obtained ciphertext can be reused without a fresh source authentication.
This does not let another AID directly read retained Monoid storage. Caller
isolation and Identity continuity are not attestation or permanent non-exportability.
Documented in `doc/bundle.md`, `doc/identity.md`, `doc/architecture.md` and the
precise transfer derivation in `doc/item-transfer.md`.

## Validation

[agent] Independent JCE/host SHA-256, HMAC, HKDF and AES-GCM oracles cover both
envelopes and wrong-caller rejection. SIO tests cover runtime caller identity,
forwarding, token stability/copy mutation/reset, Identity replacement rejection,
fresh Monoid rebinding and exact Bundle-manager admission including prefix
lookalikes. The new two-card boundary test uses source Monoid APDUs, a separate
recovery module registered with Monoid's instance AID, and a third-party caller
on both cards; it verifies Safe PIN export gating, allowed recovery and isolation
in both directions.

The simulator rejects shared SHA-256 factories; the existing host-only adaptation
pattern now also covers MonoidIdentityApplet. CAP sources retain shared access.
The simulator's Monoid static state is JVM-wide, so multi-card tests run Monoid
instances sequentially. These tests do not prove physical firewall/GP policy,
peak RAM or timing. No physical card was operated at this initial checkpoint;
the later physical performance comparison is recorded in [149](149.md).

Final validation: all 320 JUnit tests across 41 suites passed, with zero failures,
errors or skips; all five CBOR request-order JavaScript tests passed. Both formal
CAPs converted with zero warnings/errors and passed verification. Whole-repository
Prettier, Inplate generation consistency and `git diff --check` passed. The three
direct HMAC tests use non-shared digest instances because of the same simulator
limitation; production shared factories remain unchanged. No commit or push was
performed.
