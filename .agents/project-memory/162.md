## Current implementation scope

- [user] Rename Safe PIN to Secret PIN. Public fields are `Hello.pins.secret` and Authenticate/Set PIN `secret?: true`. Import requires the receiving card's Secret PIN; ordinary storage/signing still accept Access authorization.
- [agent] Identity owns Secret PIN, retries and real caller-bound verification. Encryption, decryption and Create/Join Bundle check that validation inside Identity; a Monoid success flag or Access authorization is insufficient. PIN check/update clears previous Secret authorization. Identity Secret authorization is caller-bound and CLEAR_ON_RESET, surviving ordinary SELECT; Monoid APDU Command authorization is CLEAR_ON_DESELECT. A different caller cannot borrow Secret validation. Card power reset clears authorization while retaining the PIN and retries.
- [agent] Replacing Monoid clears Access PIN, items and derivation cache, but retains Identity, Secret PIN and Bundle. An existing Secret PIN cannot be initialized over; changing it requires its current authorization. Unauthenticated `0xFF Reset` clears both PINs/tries/auth, items/cache and Bundle while rotating Identity key pair, ID and token secret/cache and atomically updating Monoid's binding. Ordinary power reset and Monoid replacement do not rotate Identity.

The Identity PIN interface is:

```java
boolean isSecretPINSet();

short getSecretPINTriesRemaining();

boolean checkSecretPIN(byte[] pin);

void updateSecretPIN(byte[] pin);

short getSecretPINValidationResult();

void clearSecretAuth();
```

PIN buffers are global arrays. Update is Monoid-only; other registered callers may
verify the same Identity-owned PIN for their own communication domain. This adds
no permission to read Monoid's live item storage or plaintext `secret: true` data.

## Bundle envelope

- [user] Use one sending key per member: a card may encrypt under its own key and decrypt other members' artifacts, but not its own.
- [agent] Derive these keys from the existing shared root rather than store one persistent key per member. Identity selects its actual local public key for encryption; decryption requires another member of the stored fixed list and the same complete runtime caller AID. The symmetric key itself has no encryption-only property; trusted Identity code enforces that policy.

```text
senderKey = HMAC-SHA256(bundleRoot,
  "Monoid Bundle Sender Key" || u8(length(callerAID)) || callerAID || senderPublicKey)

02 || bundleHash[32] || senderPublicKey[65] || salt[32] || nonce[12]
   || ciphertext(secret[2] || data) || tag[16]
```

The overhead is 160 bytes. Existing payload HKDF and metadata-context framing stay
the same. The prototype still uses version `02`; earlier Bundle artifacts are not
compatible and no compatibility branch is introduced. The sender field is bound
to key derivation/tag verification, not trusted as a host claim. A software holder
of the Bundle root could derive every member key; the trusted-peer assumption
still applies.

Without a Bundle, self-addressed asymmetric transfer is allowed. Once enrolled,
Identity also rejects self-addressed asymmetric artifacts, including those made
before enrollment. Record158 is not permission to bypass this restriction.

## Recovery boundary

A fresh Bundle export/decryption chain requires two members and each executing
card's Secret PIN authorization. Existing export artifacts do not require another
source PIN check; this is not simultaneous card presence or a requirement to
present the source again on every later decryption. Other-member artifacts may be
returned to the original card after an authorized chain. Plaintext already released
cannot be revoked.

With GP authority, retaining another member's Identity/Secret PIN/Bundle while
replacing its Monoid still allows Secret-authorized plaintext recovery. This is the
explicit supported boundary, not absolute non-exportability or installed-code
attestation. Without a Bundle, Secret PIN alone permits asymmetric migration.
