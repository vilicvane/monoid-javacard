# Safe lookup keys and List prefix matching — 2026-10-15

[user] Accepted a two-step List then Sign flow for credential lookup and
requested adding the existing data-prefix support to the List command.

[agent] While inspecting the APDU entry point, identified a concrete
authorization mismatch:

- CommandList requires Access authorization; CommandGet requires Safe
  authorization to export raw Data, including custom item data.
- MonoidApplet.checkSafeUnlocked uses its cached Safe PIN to authorize the
  Monoid SIO session, without upgrading the user's AUTH_ACCESS to AUTH_SAFE.
- SafeItem.matches(type, dataPrefix) compares the actual stored Data.
- Exposing arbitrary prefixes through Access-authorized List would let a
  caller track a target index and recover its data one byte at a time. At
  most 256 prefix guesses per byte are needed; this is a data-reading oracle
  even though the response contains only indexes, types and aliases.

[user] Chose a dedicated field named key for matching instead of exposing
Data prefix queries. After reviewing index history, explicitly requested
adding key and replacing the data-prefix overload. Suggested that the
original eight-byte ID may have been intended as a stable hexadecimal
identifier for UI display; this is the user's recollection, not a documented
historical rationale.

[user] Restricted key assignment to creation; Set must not update it.
After briefly considering exact matching, retained keyPrefix so callers can
use common prefixes to define and query their own generic-data formats.

[agent] Historical evidence: 323cd64 accepted indexLength in the storage
interface while Keystore already used type plus an eight-byte digest.
d36cb0a removed indexLength and fixed the Safe contract; 6e0c4b3 documented
a compact type plus identifier; 7044285 extended type to two bytes. The early
storage and List flattened index/data and indexes into byte arrays.
b9eb256 introduced separate fields and Shareable item arrays. No explicit
rejection of arbitrary-length keys or rationale for exactly eight bytes was
found in commit messages.

[agent] Implementation follows the existing item metadata flow:

- SafeItem has an optional binary key, separate from index, alias and data.
  It need not be unique and does not affect index generation or identity.
- The Java/SIO list(type, keyPrefix) overload replaces dataPrefix matching.
  Null or empty prefix applies no key filter, including to items without
  keys. A nonempty prefix requires a present key of sufficient length and
  compares only that key. Type filtering and insertion order are preserved.
- Create accepts optional key bytes; List, View and Get return key when
  present. Key is assigned only at creation; Set continues to update alias
  and data only, and the Shareable interface has no setKey method. An empty
  byte string at creation stores an empty key. Random key creation leaves
  lookup key unset.
- List accepts optional keyPrefix with ordinary Access authorization.
  Raw data export through Get still requires Safe authorization. No
  APDU dataPrefix query is introduced. The previously proposed special
  Safe-PIN requirement for prefix queries is superseded by this separation.
- SIO getKey uses the existing session checks and global copying convention.
  Create persists a copy. Create and the Monoid wrapper's list overload copy
  lookup bytes into global arrays before crossing the applet boundary.
- README changes contain signatures and necessary field comments only.

P-256 contextual derivation and the credential metadata encoding are still
separate, unimplemented design choices. This change defines generic lookup
metadata; it does not define a Passkey credential format.

[user] Requested physical-card validation before committing. Lookup keys
are expected to be short, usually around a dozen bytes and at most twenty
or thirty bytes in the intended use. Record 106 captures the broader rule
to defer large-data support until a concrete use case requires it.

[agent] Physical validation exposed an existing alias-copy omission in both
Safe.create overloads. CBORReader.text returns a Monoid-owned transient
array, which cannot be read directly by the Safe applet. Creation with key
but without alias worked; creation with alias but without key reproducibly
lost PC/SC communication (0x458), requiring the user to re-present the card.
Both wrappers now duplicate a non-null alias into a global array before
calling the Shareable interface, matching the existing Set path. Fixed
custom-index and P-256-type creation with both alias and key succeeded.
The cross-applet access violation is identified; the firmware's internal
reason for losing communication rather than returning an error is unknown.
