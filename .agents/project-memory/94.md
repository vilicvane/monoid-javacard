## What the public documentation establishes

The security target's page76 DAP requirement explicitly covers EC256/SHA256
verification of executable-load signatures, conditional on the corresponding
cryptographic module being present. This is card-management evidence, distinct
from Java Card applet algorithm support. It does not specify the import encoding,
accepted curve references, key identifiers or initialization sequence, and does
not establish an independently switchable GP ECC option on our card. Existing
Monoid secp256k1 operation does not resolve GP provisioning behavior.

The DAP requirement references GP Amendment E v1.0. Its
[section4.7, page20](https://globalplatform.org/wp-content/uploads/2016/11/GPC_2.2_E_SecurityUpgrade_v1.0.pdf)
requires each DGI to fit wholly inside one STORE DATA command. The same rule is in
[v1.0.1, page22](https://globalplatform.org/wp-content/uploads/2018/06/GPC_2.2_E_SecurityUpgrade_v1.0.1.pdf).
This qualifies record93's statement about current GP2.3 allowing splits inside a
DGI: that statement does not establish compatibility with an older provisioning
implementation. However, record93 already tested complete DGI boundaries and
still received6A80 for the public-key Q block, so this difference cannot explain
the remaining failure. The older texts retain B0/B1, F0, Q DGI0036 and uncompressed
point encoding; no applicable alternative import format was identified.

No public vendor provision, erratum or successful APDU transcript was found that
explains this build's6A88/6A80 responses. This is not proof that no special
requirements exist. The full manual remains unavailable in this research.
