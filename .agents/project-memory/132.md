# Applet switching and delegated P-256 signing probes

[user] Requested verification of applet switching before implementing the
Security Key and Monoid authorization proposal in record 131.

[agent] On 2026-10-19, verified a temporary client → Monoid Shareable → Safe
call chain on physical card CPLC serial `55690320`, reader
`ACS ACR1552 1S CL Reader PICC 0`, ATR `3B8A800150564A434F503453494471`.
The adapted research copies support Monoid-001 P-256 public-key derivation and
ECDSA digest signing while the client is selected. Production source, formal
APDU/SIO interfaces and the installed original applications were not changed.
The grant/capability design remains a proposal.

## Transient memory and engine restrictions

A minimal provider/client probe established the real runtime behavior:

- Provider-owned CLEAR_ON_DESELECT memory works while the provider is selected.
- While a different applet is selected, entering the provider through SIO does
  not make it selected. Reading its existing DESELECT array throws
  SecurityException; creating one throws SystemException.ILLEGAL_TRANSIENT.
- Provider-owned CLEAR_ON_RESET arrays can be created and accessed in this call
  chain. Switching back to the provider clears the DESELECT marker to zero but
  retains the RESET marker.
- Current/previous context is provider/client inside the SIO and client/null
  after returning. Nested Safe calls use Monoid as the calling applet.

The integrated probe used current production copies with remapped AIDs and
temporary entry points. Four variants isolated the required changes:

| Variant  | Difference                                                            | Physical result                                                                                                       |
| -------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| baseline | Original memory and crypto-engine policies                            | Direct signing succeeds; cold SIO initialization and warm SIO working allocation fail with ILLEGAL_TRANSIENT          |
| reset    | P-256 path working arrays and transient keys use RESET                | Cold initialization, cached public keys and signatures succeed; uncached seed derivation fails with SecurityException |
| digest   | reset plus SHA-512 MessageDigest externalAccess=true                  | Cached/uncached seed and master derivation/signing, repeated switching and reset recovery succeed                     |
| shared   | digest plus HMAC Signature and P-256 KeyAgreement externalAccess=true | Independent provider replacement, ordinary APDU/SIO switching and reset recovery succeed                              |

The reset adaptation covers the relevant allocations in MonoidApplet,
CurveSECP256r1, WeierstrassCurve, LibHMACSha512, Monoid001Derivation, OneShot,
LibECDSA and Utils. It is not a blanket migration of command authentication,
transport or all algorithms to RESET.

The single-variable digest comparison identifies a second restriction beyond
explicit arrays: a crypto engine created with externalAccess=false may use
internal DESELECT memory. Calling it inside its owning context is insufficient
when that owner is not the selected applet. Oracle explicitly includes this SIO
case in externalAccess=true and forbids internal DESELECT allocation for that
mode. Final shared factories follow that contract; only SHA-512 was demonstrated
to require the flag by the isolated failure comparison. Native HMAC fallback
availability on this card limits conclusions about that branch.

Do not confuse KeyBuilder.buildKey's final keyEncryption parameter with
externalAccess; it remains false. OneShot has no corresponding externalAccess
factory argument and successfully signs in the tested SIO path.

Sources: [MessageDigest](https://docs.oracle.com/cd/E59935_01/api/javacard/security/MessageDigest.html),
[Signature](https://docs.oracle.com/cd/E59935_01/api/javacard/security/Signature.html),
[KeyAgreement](https://docs.oracle.com/cd/E59935_01/api/javacard/security/KeyAgreement.html).

## Authentication, switching and replacement

Both digest and shared completed six cycles of:

1. Select Monoid, authenticate through its ordinary command API, and sign using
   ordinary 0x41.
2. Select the client and sign through Monoid SIO and nested Safe access.
3. Select Monoid again: command authorization is now 0000, and ordinary 0x41
   rejects the request with UNAUTHORIZED.
4. Authenticate again and verify a successful ordinary signature.

All 36 signatures from these twelve cycles verified independently. Command
authentication deliberately remains DESELECT state: exposing an SIO must not
silently preserve the ordinary APDU login after switching applets. Each cycle's
query-time free memory was RESET 2130B / DESELECT 2128B. These readings cannot be
added and are not peak memory measurements. Persistent availability saturated at
32767B and does not establish unchanged actual free storage.

Both adapted variants also passed confirmed card unpower/reset recovery:
Safe authorization was initially 00, then the probe's normal cached Safe PIN
path revalidated access and the state became 01. Public keys and signatures
remained correct. Safe authorization does not survive reset. Java Card
Card.disconnect(true) did not clear the earlier RESET marker on this reader;
the actual reset evidence uses native SCardReconnect with initialization=2
(SCARD_UNPOWER_CARD). Early lifecycle log labels containing after-reset must not
be interpreted as successful physical reset.

The client CAP imports only framework, the standalone interface CAP and
java/lang, with no provider-package dependency. Client fields retain no SIO.
With client, API library, Safe and Identity still installed, the Monoid instance
and package were deleted and replaced successfully. The existing client obtains
the new provider; signing initially rejects because the fresh provider lacks
its Safe unlock state. An explicit test bootstrap unlocks/rebinds the existing
Safe fixture items, after which seed/master public keys and signatures succeed.
This verifies independent replacement, not automatic grant recovery.

A second instance of the client package with another AID was rejected and the
authorized client remained usable. This is caller-AID checking only: the probe
does not implement capability secrets, persisted grants, revocation, Type-scoped
CRUD or protection against malicious same-AID client replacement. No CTAP
registration/assertion or browser/phone interoperability was exercised.

## Verification counts and timing boundaries

Complete physical result files contain:

| Suite                           | Independent signatures | Public-key comparisons |
| ------------------------------- | ---------------------: | ---------------------: |
| baseline main                   |                      3 |                      2 |
| digest main                     |                     17 |                      8 |
| digest after-reset              |                      1 |                      1 |
| digest ordinary APDU/SIO cycles |                     18 |                      0 |
| shared after-reinstall          |                      2 |                      2 |
| shared ordinary APDU/SIO cycles |                     18 |                      0 |
| shared after-reset              |                      1 |                      1 |
| Total                           |                     60 |                     14 |

The adapted variants account for 57 signatures and 12 public-key comparisons;
the reset-only suite's successful prefix is excluded because its uncached case
failed. Public fixtures use seed bytes 00..3F and the corresponding Monoid-001
master. Host HMAC/HKDF and independent P-256 arithmetic/verification check the
returned values; fixture private material is not production card data.

Observed cached SIO signing was roughly 352–365ms; selected uncached seed
public-key requests were roughly 509–524ms. These are complete probe APDU times,
including Safe access, crypto and transport, not isolated context-switch cost.
Ordinary CBOR command timing cannot be subtracted to measure SIO overhead
because request parsing and probe processing differ.

The simulator completed 368 assertions across baseline/reset and native/host
signing modes, with 48 public-key comparisons and 24 verified host-shim
signatures. Native jCardSim lacks the required OneShot ECDSA primitive; the shim
substitutes only that primitive. The SIO runtime adapter models context
restoration but not the transient firewall. Simulator success alone did not
predict the physical DESELECT/engine failures.

## Evidence and preservation

Ignored research files are under `.research/applet-switch-20261019/`, including
source manifests, converter-verified CAPs, lifecycle logs, per-variant integration
results, independent oracles, reset and registry-management scripts. Their
conclusions are recorded here so project memory does not depend on retaining
those temporary artifacts.

Lifecycle packages E4/E5/E6 were removed before integration. Integration uses
Identity E0, Safe E1, Monoid E2, interface E3 and client E7 under prefix
F06D6F6E6F6964; all are isolated from formal AIDs. Management checks card serial
and original registry before deletion and never uses force. The original
Monoid instance F06D6F6E6F69640101 already returned SELECT=9000 and Hello=6F00
before this test; that legacy fault is unrelated to the probe.

Final cleanup removed every integration instance and package. Registry,
ownership, privileges, package versions and management-key metadata exactly
matched the baseline; the original SELECT=9000 / Hello=6F00 behavior also
matched. All reader processes exited. The final manifest check verified 266
frozen production/generated inputs. No production source was modified or
formal firmware deployed; no commit/push was requested.
