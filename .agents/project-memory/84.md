# Physical-fault authentication hardening discussion — 2026-10-14

The user raised Tangem's laser attack and suggested redundant authentication
checks. This is a hardening discussion, not approval of a specific design or
API/session-semantics change. No production code or card state was changed.

Primary research:

- [Ledger Donjon, 2026-07-09](https://donjon.ledger.com/blog/bypassing-tangem-card-security-with-laser-attack/)
  demonstrated unauthorized password reset by faulting the recovery-authorization
  decision inside SetPin. Their recommendations include separate authorization
  checks and fault-resistant state encoding. The target was a permission branch,
  not simply the number of password comparisons.
- [Tangem's response](https://tangem.com/en/blog/post/lfi-response/) emphasizes
  physical possession, invasive preparation and specialized laboratory equipment.
- [Oracle SensitiveResult](https://docs.oracle.com/en/java/javacard/3.1/jc_api_srvc/api_classic/javacardx/security/SensitiveResult.html)
  provides assertions of sensitive API results, introduced in Java Card 3.0.5.
  [OwnerPIN](https://docs.oracle.com/en/java/javacard/3.1/jc_api_srvc/api_classic/javacard/framework/OwnerPIN.html)
  documents this for check/isValidated when supported by the platform. Actual
  card support has not been probed. Assertions must be placed before another
  sensitive API overwrites the stored result; cross-applet result ownership
  and reset require care.

Read-only source findings at 239b4cb:

- Command uses one transient auth byte, written as 0, 1 or 3, and checks whether
  required permission bits intersect. It does not validate a redundant state
  encoding. For example, a single-bit change from 1 to 3 changes access-only
  into Safe authorization. Physical exploitability has not been demonstrated.
- CommandSetPIN performs multiple conditions using the same captured auth
  value. MonoidApplet.updatePIN has no authorization check of its own.
- checkSafeUnlocked validates the persistently cached Safe PIN. Safe's own
  checks then use OwnerPIN.isValidated. These storage access checks do not
  independently prove that the current user supplied a valid credential.
- Sign checks user authorization at command entry; Get requires Safe user
  authorization before returning raw item data. PIN mutation, raw-key output
  and signing boundaries are priority candidates for additional checks.

Candidate direction, not yet implemented: strictly validate redundant,
well-separated authorization encodings; check authorization at command entry
and at sensitive effects; use platform SensitiveResult where supported to
validate PIN API results. Preserve attempt-counter semantics: unconditionally
checking a wrong PIN multiple times consumes multiple attempts. Repeating a
check of one corrupted local value is not independent redundancy.

Normal trusted JCRE execution and deliberate physical fault injection are
different assumptions. This discussion does not authorize reverting the
record-75 byte-erasure cleanup or changing external APIs. Simulator tests can
check modeled state corruption and rejection behavior; real resistance still
requires evaluation on target hardware. No laser resistance claim is made.
