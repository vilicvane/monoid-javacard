# Single-fault audit and data-protection fixes

- [user] Requested a review of the Monoid JavaCard applet for remaining
  single-bit fault paths that could disable data protection, followed by a
  temporary audit report and fixes for all findings except low-risk items.
- [user] Subsequently requested an independent review of the findings and
  fixes against project conventions, then authorized the appropriate changes,
  physical-card verification and a commit after the tests pass.
- [agent] Preserved the existing staged/unstaged worktree and records 158-163.
  The audit models individual comparison-result faults and instruction/write
  skips separately from a single-bit mutation of stored data. These are source
  models, not evidence of physical fault resistance. Monoid APP is out of scope.

## Findings and remediation

- F-01 (High under the instruction-skip model, fixed): `SafeItem` now publishes immutable `ItemState`
  containing both the data reference and the exact short secret encoding.
  `setSecret(false)` no longer has a writable old-data/non-secret path, and
  `Safe` preserves the exact imported short state instead of converting it to
  a boolean. A transaction alone did not protect against a skipped field
  assignment; the state-reference publication prevents mixing retained old
  data with a newly downgraded flag. The added tests verify normal paths and
  exact values, not instruction skips.
- F-02 (original bypass not reproduced; optional assertions withdrawn):
  the original code already rejects a successful `OwnerPIN.check` return
  paired with rejecting native validation, and clears authorization when the
  return rejects despite native validation succeeding. Both added tests pass
  against the pre-fix baseline. They do not demonstrate a new protection
  provided by `SensitiveResult`. That API checks a returned value against the
  native saved result; it does not correct an underlying native error when
  both agree on the wrong result. The candidate helpers were corrected to
  `requireSensitiveResult` under record163's naming rule, but the physical
  compatibility comparison below rejects that candidate. Removed its production
  wrappers/imports/call sites and retain the two regressions for the original
  redundant checks. This is not a fixed native-PIN vulnerability.
- F-03 (Medium-high, fixed): `CommunicationData` uses a fresh
  `getPreviousContextAID()` condition on every of three checks before
  `getLength` or `read` releases decrypted bytes. A new regression covers an
  unauthorized caller with one spuriously matching context lookup: length
  and bytes remain unavailable, and the destination stays untouched.
- F-04 (Medium, fixed): `ItemCipher.assertOtherSender` reuses the existing
  array `LibSecurity.check` with `SAFE_TRUE` as the conservative result and
  accepts only exact `SAFE_FALSE`. The dedicated `SenderComparison` interface,
  instance and hand-written three-comparison logic were removed. Existing
  full Bundle/HPKE tests retain self-sender rejection, other-member recovery
  and sender-key binding coverage; the removed hook tests are historical.
- F-05 (Low, deferred): ordinary Bundle membership/member-index comparisons
  remain unchanged by explicit scope.

### Final physical regression

The final production sources were frozen into a new isolated harness under
`.research/fault-review-20261021`. All268 recorded inputs still match after testing.
The rejected SensitiveResult build remains separately preserved under
`rejected-sensitive/`; it is not the final tested firmware.

Card55690320 passed100 recorded events (93 timed logical APDU exchanges and7
memory observations), including12 independently verified P-256 signatures.
The signing samples were560–574ms with transport/probe overhead; these are not
a controlled performance comparison. This round uses one physical card and
independent Node HPKE/GCM/Bundle peers, not a new two-physical-card run.

- Initialization, Access/Secret authentication, wrong-PIN rejection and retry
  recovery pass. Access cannot export, and failed Secret authentication does
  not retain export permission.
- Clearing secret without replacement returns exactly6985, and plaintext Get
  remains denied. Replacing data with a public value succeeds; restoring secret
  and replacing data without a flag retain the expected protection.
- Plain/secret HPKE exports independently decrypt on the host. Reinstalling
  only the isolated Monoid preserves Identity/Secret PIN and rejects
  unauthenticated overwrite/import; the original Secret PIN permits recovery.
- Create/Join/repeated Join, incoming member ciphertext and identical repeated
  Import pass. Own Bundle ciphertext, old self-HPKE after enrollment and Bundle
  replacement return exactly6985. Substituting another valid member's sender
  key fails tag verification with CryptoException/ILLEGAL_VALUE.
- Imported secret data remains unreadable via Get and signs correctly.
  Both ordinary Reset and Reset after exhausting Secret retries clear items,
  PINs and Bundle while rotating Identity; fresh initialization works.

The normal real-card Shareable result path passes; the additional wrong-caller
and spurious-context checks are simulator tests. No physical fault injection,
side-channel, power-interruption or complete single-fault-resistance claim is made.
Temporary E0/E2 and E4 are removed. The original registry and original
SELECT/Hello outcomes match the preflight baseline; existing applications/data
were not changed. The final official CAPs are compiled, but not deployed under
their formal AIDs.
