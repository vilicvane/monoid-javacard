# Identity 检查与调用方隔离的实卡开销 — 2026-10-20

## 范围与方法

- [user] 要求测量新增检查的性能影响，并已放好测试卡。
- [agent] 卡为 CPLC `55690320`、ACS ACR1552 PICC、T=1；仅使用预检为空的 E0/E2 临时包，实例为 `F06D6F6E6F6964E001` / `F06D6F6E6F6964E201`。保留原有应用和数据，不做正式部署。
- 基线为提交 `837bc04`，新版为记录148的当前源码；两版均归一包名和实例 AID 长度。计时版不插桩；内存版移除插桩后与对应计时版源码逐字相同，598个输入冻结并校验哈希。
- 第三个计时版本 `check-bypass` 只将 `Safe.requireIdentity()` 改为直接 `return getIdentity()`。保留首次绑定、token 引擎和工作区，以及新版 AID 上下文和 Bundle 派生；因此它用于隔离整条重复检查路径，不能用于衡量安全性。
- 三个计时版本各108次命令、两个内存版本各30次，合计 **384/384** 通过。三个计时版本各78个测量样本；一般每场景一次预热、五次样本，复位后的 Hello 为三次独立 PC/SC reset 后调用、没有预热。内存每场景只执行一次、不预热。测量32B与256B记录，不包含1024B实卡用例。
- 时间为完整命令所有请求分片和 GET RESPONSE 的 PC/SC transmit 耗时之和，不含主机编码、密码学运算、日志、SELECT 或周边准备步骤。三组顺序安装，未随机化，结论仅限本卡本次样本。
- 数据导入的计时预热先创建条目，五次正式样本是同一密文的幂等导入；普通 Bundle 导入每次先 Reset，幂等 Bundle 导入另测。Create Bundle 预热创建，之后五次创建新密钥替换。内存版的条目导入是首次创建。
- 一个实卡 Identity 与两个独立主机密码学成员组成三成员 Bundle。每次导出、每个入组包均由主机独立解密验证，导入 Bundle 后再导出记录确认实际根密钥。不是两张实体卡互刷。

- 每次重复检查的完整路径净增约 **57–95ms**。Hello 的三次共约263–267ms，Create Bundle 的三次共约235ms；不要将不同命令的净差强行视为一个恒定单次 HMAC 时间。
- Hello、Create Bundle 各调用三次 `getToken()`；Import/Reset Bundle、每次记录 Export/Import 各一次。Bundle 记录额外做一次按调用方 AID 派生的 HMAC。普通 Sign/Get/List 等热态无 token 调用，本次未测试这些命令的性能。
- 新版关闭检查后，Bundle 记录仍比旧版增加约42–56ms，包含调用方派生、上下文和其他变化；本实验没有单独关闭 KDF，不能把全部残差认定为 KDF 耗时。
- 新版与 check-bypass 的所有108条命令在请求/响应长度、分片数、状态码上完全一致，System Information 对照只有0.14ms差额。旧版与新版只有 Hello/System Information 响应少2B：旧版仍将短临时 AID 末尾 `E201` 读作版本，新版版本常量为0。因此精准检查归因以新版内部对照为准。
- 上传非末段增量约0.04–0.17ms，GET RESPONSE 差额约-4至+1.3ms；主要增量在真正执行业务的 APDU，而非多了分片。
- 首次安装后 Hello 单次观察为266.97→622.10ms，含初次绑定和引擎初始化，各仅一次，不代表冷启动均值。reset 后重复 Hello 与热态相近，说明没有重新绑定/创建引擎。

## RAM

下表为检查点的最低可用 RESET 字节，**不是连续原生峰值**。探针使用两包共520B的持久统计数组，无显式额外 transient 分配；两组相同。RESET/DESELECT 是重叠池，不能相加。

| 场景                      |   旧版可用 |   新版可用 | 减少 |
| ------------------------- | ---------: | ---------: | ---: |
| 初始化后空闲              |       2121 |       1942 |  179 |
| 密码上下文预热后空闲      |       1596 |       1417 |  179 |
| 首次 Hello                |       2036 |       1745 |  291 |
| 普通 Hello，无 Bundle     |       2052 |       1777 |  275 |
| 普通 Hello，有 Bundle     |       1495 |       1220 |  275 |
| 非对称 Import，32B / 256B |        761 |        550 |  211 |
| 非对称 Export，32B        |       1281 |       1070 |  211 |
| 非对称 Export，256B       |        769 |        558 |  211 |
| 三成员 Create Bundle      |        648 |        373 |  275 |
| 三成员 Import Bundle      |        676 |        465 |  211 |
| Bundle Import，32B / 256B | 1400 / 888 | 1189 / 677 |  211 |
| Bundle Export，32B / 256B | 1406 / 894 | 1195 / 683 |  211 |

- 固定上下文实测多占179B，包含64B HMAC工作区及摘要引擎等实际运行时开销；不是只多64B。两版进一步初始化加密上下文均减少525B，之后空闲量稳定，没有观察到随命令次数累计下降。
- 每次检查还返回一个32B global数组：一次检查的操作比旧版少 `179+32=211B`，三次少 `179+96=275B`。首次 Hello 四次 token，旧版的16B版本读取数组被移除，因此差额 `179+128-16=291B`；采样结果与之吻合。
- 通用 `privateArray.persistentResult` 检查点也会被新增的token复制调用，Create Bundle中同名点因此覆盖了不同的执行位置，不能逐点机械对比；整条操作最低值及固定阶段的采样吻合上述模型。
- 新版最紧张的已测场景为三成员 Create Bundle，最低 RESET373B / DESELECT368B；正常 Bundle 导入为465B / 464B。当前卡可完成，但余量更小，不能据此保证更低RAM卡片、签名上下文已常驻、更多成员或其他顺序可用。
- persistent可用32767是查询饱和值，不是实际剩余容量；本次未测满卡、写入耐久或故障注入。

## 产物和清理

- 实验位于被gitignore的 `.research/identity-check-performance-20261020/`。`manifest.json`冻结两版及插桩源码，`build-artifacts.json`保存8个主CAP哈希；`bypass-manifest.json`和`bypass-build-artifacts.json`保存独立两个CAP。10个CAP全部转换零错误/警告且通过Verifier。
- `harness-manifest.json`记录传输、oracle、管理和统计脚本及依赖哈希。`comparison.json`明确列出五份报告路径和统计；各报告保留完整样本/APDU耗时和内存页。为纠正沿用脚本中“1024B、三次、peak有预热”的旧描述，保存原始 `report.original.json`，只修正 `report.json` 描述字段，原操作和数值不变。
- 每次换版本都清理本轮确认安装的E2/E0实例及包并核对注册表。最终 ownership ledger 为 `cleaned`，注册表的AID、所属包、权限和版本与起始一致；原有 `F06D6F6E6F69640101` 的SELECT9000/Hello6F00亦与起始一致。该旧Hello失败是预存状态，不能将前后相等称为原有业务健康验证。
- 已释放PC/SC连接。本轮不修改生产实现、不提交或推送；结果提示重复token获取是值得优化的开销，但尚未实施优化。
