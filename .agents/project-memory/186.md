# OTP 入口与职责划分

[user] 开始实现 OTP，倾向由 Monoid 保存密钥和提供计算能力，另一个独立 Applet 通过授权调用 Monoid，并拥有自己的 Command。若现有 Monoid 命令（例如 Sign）容易满足需求，也可以考虑直接复用；要求先比较几个方案。

[user] 比较后选择方案 2：HMAC 是通用能力，放在 Monoid；完整 OTP 业务会扩大 Monoid 的范围，应留在独立 OTP Applet。另要求 APP 能一次取得近期多个时间窗口的 OTP。

[agent] 尚未确定命令编号、请求/响应、Shareable 签名、授权字段或采用 YKOATH。独立 Applet 的方向不等于批准了具体公共接口。

## 初期代码边界（实现前）

- `CommandSign` 和 `Key` 只接受现有非对称密钥及 ECDSA、Ed25519、BIP340；没有 HMAC 分支，也没有通用对称密钥类型。现有 HMAC 辅助类服务内部派生/协议，不能直接作为外部 OTP API 使用。
- `Monoid` Shareable 提供授权 seed 的 Monoid-001/P-256 签名及受 Type 限制的数据操作，没有 HMAC/OTP 计算方法。`SafeSessionItem.getData` 和其他数据读取入口拒绝 secret 条目。
- Type 可写授权已经允许以 `secret:true` 创建记录；新增 OTP 计算权限不应被误称为已有通用读权限，也不能为方便计算而把共享密钥存为非 secret。
- Safe Item 的 alias/key 可公开读取，data 可设为 secret 并沿用加密导出/导入；key 创建后不可更新。HOTP 可变计数器不能依赖 immutable key 或以整个可变记录摘要确定 index。

## 方案比较与选择

1. 扩展现有 Sign 为 HMAC：新增对称密钥和 HMAC 请求分支，由 APP/客户端完成 OTP 截断和格式化。减少命令编号，但 Sign 的契约从非对称签名扩大到 MAC，HOTP 状态仍需另定。
2. Monoid 提供独立 HMAC 服务，OTP Applet 负责算法配置、截断、计数器及自身协议：更接近现有 Security Key 的职责划分，Monoid 不解析完整 OTP 账户格式；需受限计算 SIO，不能复用已有数据读权限作为计算授权。
3. Monoid 提供完整 OTP 服务，OTP Applet 负责协议与自身认证：Monoid 持有密钥、配置及 HOTP 计数器，完成计算和计数推进；OTP Applet 较薄，但 Monoid 增加 OTP 业务语义。

方案 2 已获选择，具体接口仍待确认。采用独立 Applet 也不强制采用 YKOATH；YKOATH 兼容需要单独确认协议及密码/Reset 语义，并实测客户端。

## 批量 TOTP

[agent] APP 提供时间信息；卡无独立时钟。协议可由 APP 先换算起始时间窗口，OTP Applet 对连续窗口调用 Monoid HMAC 后截断并返回多组验证码，避免每个窗口重新刷卡。时间窗口、数量、位数、有效区间均属于 OTP 层，不进入通用 HMAC API；请求的具体字段和编码尚未批准。

- 每个验证码仍对应自身窗口，提前计算不会改变服务端有效期；APP 应按实际时间显示对应组。
- APP 缓存未来验证码后，在覆盖的窗口内可不再刷卡。卡无法验证主机时间，因此即使只提供单次计算，授权客户端也可请求未来窗口；批量数量限制主要控制资源和交互规模，不能充当可信时间边界。
- 批量按时间窗口针对 TOTP；HOTP 批量会消耗计数器，应另行定义，不能照搬相同语义。

## 数量限制与可信时间讨论

[user] 提议一次上电最多领取有限组 OTP，时间不能倒序；澄清希望跨断电也禁止回退，随后要求重新评估其必要性。接着提出可信时间及加密传输，并建议卡上预装证书，在一次持续贴卡期间通过多次握手完成验证。

[agent] 这些是设计约束和讨论方向，尚未确定配额数值、按账户还是全局计数、时间回退字段语义、凭据格式或可信时间服务。跨断电单调限制尚未据此实施。

- 仅使用主机时间时，持久最大时间不能证明时间真实，也不能阻止第一次请求未来窗口；误传未来时间反而可能阻断正常使用。严格记录批量末尾会妨碍同窗口重试和重叠批量，需区分请求起点与已经生成的末尾。
- 每次上电配额限制一个运行周期，不能把软件复位/重新断场当成人类再次确认。原有通用 HMAC 授权边界也必须保留清晰：若同一密钥授予其他 HMAC 调用方，OTP 层限制不能约束该调用方。
- 可由 OTP Applet 固定可信时间服务验签公钥（或证书），生成随机挑战；APP 将挑战送到服务，服务对用途标识、挑战及自己的当前时间签名，APP 将结果转回卡片验证。单独加密 APP 自填时间不能建立可信时间。
- 验证后只能计算签名时间附近的有限窗口；挑战绑定当前操作并单次消费。同次上电重新握手、切换 Applet、重新认证均不能刷新上电配额。配额的具体生命周期仍需接口设计和实测。
- 时间凭据可以明文签名，OTP 密钥和账户信息无需送给时间服务；暂不引入完整 TLS，也未决定是否额外加密。一次持续 NFC 会话可承载多轮 APDU，联网转发期间需维持会话，手机行为仍需实测。
- 随机挑战可防止其他会话的旧凭据重放，但无时钟卡仍无法度量服务响应被延迟多久。签名证明服务签发时的时间；延迟会让允许的窗口变旧，不能让 APP 自行选择任意未来窗口。时间服务可用性、信任密钥更新是新增依赖，尚未定实现。

参考：RFC 3161 的签名时间戳和 nonce 机制支持该基本思路，但不表示本项目将实现完整 TSP：<https://datatracker.ietf.org/doc/html/rfc3161>。

## 算法及协议要点

- OTP 通常使用网站提供的共享密钥，不能任意替换为钱包 seed 派生值；服务器必须持有相同密钥。
- TOTP 时间窗口由主机提供，卡无可信墙上时钟。相同密钥/配置/窗口在多卡上结果相同。
- HOTP 计数器需要持久保存；应在成功响应前提交推进，失联可能跳号。复制后的多卡计数器独立，不能承诺自动同步。
- OATH 的算法标准与 Yubico 的公开 APDU 协议是不同层次。协议资料：<https://developers.yubico.com/OATH/YKOATH_Protocol.html>；算法资料：<https://www.rfc-editor.org/rfc/rfc4226.html>、<https://www.rfc-editor.org/rfc/rfc6238.html>。

```text
POST /v1/time {challenge: base64url(32B)}
-> {publicKey, data, signature}  // canonical unpadded base64url

data = 01 || unixSeconds_u64_BE || challenge[32]  // 41B
message = UTF8("Monoid Authority Time") || data  // 62B
signature = ECDSA-P256-SHA256(message)           // 64B r || s
```

[agent] 本节为首轮实现历史；其中 `grant.hmac` 和账户直接保存共享密钥的模型，已由文末“内置 HMAC Key”取代。时间证明、一次使用许可及 OTP 命令流程不变。

[agent] 实现采用启动时消费。Monoid 只存当前 grant 的一次使用许可，OTP 自己负责批次和时间窗口；不把前面的“所有资源版本/算法/消息均由 Monoid 绑定”的候选扩展成通用任务编排。新增接口如下：

```text
Monoid Authenticate21 {pin, secret?:true, aid?:bytes} -> {}
AppletGrantOptions 增加 hmac?: signed-short[]（精确自定义Type，与types独立）
Monoid.consumeUserAuthentication() / revokeUserAuthentication()
Monoid.hmac(algorithm,index,indexOffset,message,messageOffset,messageLength,dest,destOffset)
IdentityShareable.verifyAuthorityTime(data,signature,challenge)

OTP package F06D6F6E6F696405, instance F06D6F6E6F69640501
Hello20 {} -> {version:bytes2,batchSize:3}
Challenge21 {} -> {challenge:bytes32}
Prepare22 {data:bytes41,signature:bytes64,indices:bytes10[]} -> {}
Calculate23 {} -> {time:bytes8,items:[{index:bytes10,period,codes:string[3]}]}
```

- 普通 Command.auth 仍在 deselect 清除。新增单槽许可绑定 immutable grant，由CLEAR_ON_RESET数组保存，客户端各SIO共享；必须已有AID/token/current-grant认证才能consume/revoke。Authenticate替换/清空旧许可（即使本次失败）；本grant替换/删除、PIN更新、Reset也失效。另一个grant不能消费或撤销它。
- HMAC只检查实际caller/token/current grant和独立hmac Type，支持SHA1/256/512算法编号1/2/3，返回20/32/64B；不自动消费用户许可，不包含OTP时间策略。storedData留在Monoid，输入全部读取后再输出，支持global数组区间重叠。其他被明确授权HMAC的Applet可以选择自己的策略。
- OTP先Challenge，再验证Authority proof并固定time+indices，再SELECT Monoid Authenticate(aid)，最后SELECT OTP Calculate。Challenge/Prepare撤销自身旧许可；准备/计算尝试即消耗批次；计算开始即消费许可，异常后清writer，不留下半段可读取响应。pending私有对象由RESET transient引用保存，SELECT保留，reset清空。
- 首版具体限制由agent收敛为1–16个不同F201账户，每账户当前+后两窗；配置key为01/algorithm/digits/periodBE共5B，digits6/8，period1..32767，T0=0，时间按完整u64计算。data为网站Base32解码secret，alias公开。需types:[[F201,false]]及hmac:[F201]；不新增OTP CRUD命令。
- key创建后不可修改，但删除重建/修改secret仍是用户管理能力。Prepare并未冻结记录revision；计算时读取实际配置和secret。未消费许可没有时间过期；延迟只得到已准备旧窗口。无持久时间高水位或每次上电总配额，新一次用户认证可取下一批。以上替代前面的未定配额/候选描述，不宣称固定3窗本身就是全局HMAC限制。
- 时间验签遵循上述Worker格式，Identity用自身安装key，无Authority报6982；native Signature使用externalAccess=true，工作区持久且按需创建。Identity仍无公共库依赖。未改APP、Worker或线上服务。
- 文档拆分：README仅补Authenticate.aid和grant.hmac；doc/otp.md给出完整安装/授权/刷卡/数据格式，doc/authority.md记录时间协议，doc/security.md记录边界。Inplate加入05包与AID，生成第五CAP；uninstall先删OTP依赖。

## 博客兴趣点

- **切入问题**：大部分临时数据搬到持久空间能省RAM，但为何几十个TOTP计算会突然耗时几十秒？
- **关键事实**：初版软件HMAC逐字节修改持久pad，截断也反复写持久4B对象；16账户48码实测25.25s。原生HMAC优先、fallback热pad按需RAM、截断4B批内RAM后，同卡同数据降为5.37s，单账户降至0.46–0.53s。普通输入和输出仍可持久化。两种优化一起比较，不能把全部收益单独归给native或4B scratch。
- **适用边界**：D321/ACR1552，完整APDU响应含GC/GET RESPONSE，排除SELECT/人/网络；原生工厂是否支持需要实际运行，软件fallback正确性另由独立向量测试。RAM数值为操作边界，不代表峰值。可信时间握手和三窗口消费策略本身不等于卡有时钟。
- **参考**：本记录实卡对照、`monoid/HMAC.java`、`monoidotp/LibTOTP.java`与`OTPBatch.java`；热工作区和只读输入应按写入频率区分，不能把“优先持久化”扩大为所有运算都写持久数组。

## 内置 HMAC Key（当前模型）

[user] 预期 HMAC Key 是内置支持的密钥，而非给任意自定义 Type 的 data 增加计算权限；批准按该方向调整。密钥通过 `keys` 授权，OTP 记录保存配置和密钥引用，删除独立的 `grant.hmac`。

[agent] 当前实现：

- 内置类型 `hmac`，索引为 `0x05LL || SHA256(key)[0:8]`，`LL` 为 1–255 字节长度；导入、按长度随机生成、List、Secret 和加密 Export/Import 沿用既有路径。空密钥不允许存入该类型；HMAC 算法内部的空密钥测试仍保留。
- `KeyHMAC = {index, type:'hmac'}`，在 `grant.keys` 中按完整 10B index 授权，不支持派生。Type 读写授权不赋予 HMAC 能力，Key 授权也不返回 Secret 明文。SHA-1/256/512 在计算时选择；Sign/ViewKey APDU 仍只接受原有非对称 Key。
- `Monoid.hmac(...)` 签名和用户鉴权流程不变，计算前检查实际调用方、安装 token、当前 grant、内置 HMAC 类型和精确 index。引擎在 `Keystore` 内按需复用，以原生 SHA-1/256/512 MessageDigest 组合 HMAC，共用 128B RESET pad 和 64B 持久结果；不再构造原生 HMAC Signature／HMACKey 或选择回退后端。Reset 清除条目及 grant，旧会话不能使用保留的计算实例。
- F201 账户为公开元数据：`key` 仍是 5B 配置，`data` 改为 10B HMAC Key index，`secret:false`。共享秘密单独存为 `hmac` 条目，通常 `secret:true`。多个账户可引用同一 Key；跨卡复制需同时复制账户和引用的 Key，并在目标卡授权该 Key。
- OTP 仍先 List F201、再选账户 Prepare；计算读取实际配置和引用，替换成未授权 Key 失败。使用现有 `Monoid.readData` 一次读取引用，避免每账户创建数据快照及额外 transient 引用数组；未增加 SIO。

[agent] 当前摘要组合实现通过全量 668 测试／77 套件、五份正式 CAP 转换／校验（0 errors/0 warnings）、Inplate、相关格式、CBOR 顺序 JS 6 项及 diff 检查；更新后的 J3R452 实卡结果见下节。早期本地 669／670 测试包含现已删除的原生 HMAC 后端专用测试，不是当前测试总数。上面的 D321 时间、RAM 和 registry 结果只代表旧账户模型及组合优化，不能作为当前模型性能。暂存区未改，未提交或推送。
