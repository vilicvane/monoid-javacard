## 组织与边界

Monoid 与 Security Key 共用 `monoidlib.LibSecurity` 和 `monoidlib.Utils`。安全真假值在 LibSecurity 定义，两个 Applet 的 Constants 引用编译期常量；三轮检查、保守方向、调用顺序和实际 PIN 操作保持不变。Condition、授权状态和私有数组仍属于调用方；global 数组沿用 JCRE 的跨 Applet 规则。公共库不持有可变静态对象或缓冲。

原 Security Key 的 global 分配/复制改用公共 Utils。Monoid 的 SafeDataSource 改为抽象类，自身提供 `duplicateAsPersistent(short length)` 和无参重载，维持256B分块；已有长度的 Create/Set 不重复查询长度。SafeData继续表示数据视图，SafeStoredData、SafeSessionSource、ItemCipher.Result继承同一基类。公共工具不反向依赖Monoid类型。读取输入优先持久、会话有效性及高频工作区留 RAM 的策略不变。外部 APDU、Shareable 签名、凭证数据和传输格式均不改变；SafeDataShareable仍是独立SIO接口。

Identity 继续独立，不依赖公共库。其 LibSecurity 由 Inplate 从公共源生成；模板配置同步更新，Security Key 不再保留生成副本。LibSecurityTest 随实现移到 monoidlib，其余测试引用随包迁移。

[user] 指出SafeData不应承接通用复制工具、公共库不应依赖Monoid类型；同意把复制操作放到SafeDataSource自身，并要求检查类似职责问题；要求把formatter开关纳入Inplate。[agent] 原先依赖SafeDataSource的是Applet内的monoid.Utils，公共库从未导入这个类型。最终删除中间的LibSafeData，Safe.readData的物化行为也归并到数据源复制方法；32B标量校验与取签名密钥继续查询长度后读取。公共Utils的makePrivateByteArray仅包装new，duplicateAsPrivate与duplicateAsPersistent完全等价，删除这两个旧别名并归一调用；数组存储类型不变。Constants对LibSecurity安全真假值的编译期别名继续遵循现有常量组织，不引入运行时转发。P-256模板连同源片段的 `@formatter:off/on` 一起生成，目标文件不再分别维护开关。

P-256 参数暂不抽取。Java Card 3.0.5 VM Specification §6.10、印刷页116要求 library CAP 的 `array_init_count` 为0，不能直接迁移当前静态参数数组。按调用方创建参数实例仍需各自存储，每次构造数组则增加分配；本轮没有引入这种替代实现，也不声称节省了参数数组空间。依据：[Oracle Java Card 3.0.5 VM Specification](https://docs.oracle.com/cd/E59935_01/JCVMS.pdf)。

COSE 编码、ECDSA low-S 处理、协议调度并非相同功能，保留各自实现。Identity 独立意味着只迁移 Security Key 的 HMAC 不会消除两者副本，本轮不改。

## 博客兴趣点

- **切入问题**：Java Card 公共库为什么适合无状态算法，却不能直接接收曲线常量的静态数组？
- **关键事实**：library CAP 的静态数组初始化受规范限制；共用方法与共用可变状态是两个不同问题。数组分配仍遵循当前 Applet 上下文，global 数组属于 JCRE。
- **适用边界**：抽取代码不自动减少 RAM；LOAD、持久空间和命令耗时分别验证。
- **参考**：上述3.0.5规范、记录175/176/180及本轮CAP与实卡对照。
