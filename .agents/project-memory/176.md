## 当前结构：组合公共 Reader / Writer

- `monoidlib.CBORApduReader` 统一物理 APDU 接收循环和数据存储，支持借用 APDU / 按需分块及固定持久缓冲；接收长度复用 Reader 结束位置。
- 两个 Applet 都由各自 `ApduTransport` 组合公共 Reader / Writer。Monoid 保留 SINGLE/FIRST/MORE/LAST、命令头一致性和 GET RESPONSE；Security Key 保留 CTAP 链接、命令选择、状态前缀和错误映射。
- Monoid 不再保留自己的 Reader / Writer 子类；`ApduTransport` 组合 `Command` 持有的公共 Reader / Writer，接收完成后重置解析游标，再执行业务命令。逐字节路径不再经过 Monoid 的 READY 检查；传输状态由 `ApduTransport` 在命令执行前检查。`Command` 保留解析和业务执行；`MonoidApplet` 在 install 创建 transport、SELECT/deselect 清理、uninstall 释放静态引用。
- `CBORBufferWriter`、`CBORApduWriter`、`CBORResponse` 迁入公共库，统一逐字节窗口、缓冲扩展、流式枚举、GET RESPONSE 和发送进度；仅分配当前存储模式需要的结构。
- 固定响应缓冲模式尊重 Le 和扩展响应；Monoid 普通响应及流式响应继续保留各自现有发送规则。

## 前一轮工具链与验证：unified-direct

`unified-direct` 的 `check buildJavaCard` 已通过：573项测试、65个测试套件，四CAP转换零错误零警告并通过验证。该轮日志为 `.research/apdu-library-20261022/reader-direct-check.log`。

- 公共 BufferWriter 显式委托 `reset(short)`、`getLength()`，让下一级 Writer 的 `super` 调用引用直接声明的方法；否则 Converter 报 undefined virtual method。逐处附有原因注释。
- 类迁移后，Monoid CAP 的异常表出现连续 catch-all 项，随后 `SafeSessionData.begin` 的类型引用间距为264B；Converter 的 `ReferenceLocationComponent.addException` 未处理超过255的间距而抛出 `IllegalArgumentException`。将 Reader 接收失败的 `finally` 清理改为 `catch (RuntimeException)` 清理重抛，打断该排列并通过完整验证。这不是解析错误或实卡运行错误，也没有修改 SafeSessionData。诊断反汇编及复现保存在 `converter-reader/DIAGNOSIS.md`。
- 首轮额外APDU测试错误地通过type创建自定义条目，收到INVALID_PARAMETER；已修正为明确的10B Index，保留失败输出，重新冻结baseline-fixed。临时AID生成脚本另补了限定名称的父类包重映射，候选为unified-fixed；正式源码不需要该重映射。
- 首个完整候选 `unified-fixed` 功能测试通过，但小条目 Create 平均额外111ms。共享 Reader 的逐字节访问叠加了 `getBuffer()` / `hasChunks()` / 长度转发。沿用 Writer 的 protected 字段方式直接访问 buffer、state和END，当时仍保留 Monoid 的 READY 检查，形成该轮候选 `unified-direct`；没有更改解析算法、存储布局或协议。实卡同负载增量收敛至约25ms。

## 博客兴趣点

- **切入问题**：只移动公共代码，为什么会让另一个完全没有改动的方法导致CAP转换失败？
- **关键事实**：Java测试通过后，3.1.0 Converter在为3.0.5生成CAP时失败；JDB定位到异常表引用间距264B，而异常表编码路径未处理超过255的间距。调整Reader的失败清理为有类型的catch后通过，SafeSessionData无需改动。另一个独立问题是间接super调用需要中间类明确声明方法。
- **适用边界**：这是本项目工具链的可复现转换期问题，不是卡片异常处理或GC的实测缺陷；不能以模拟器通过代替CAP转换和卡上验证。
- **参考**：本记录“工具链与验证”，忽略目录 `converter-reader/DIAGNOSIS.md` 和对应反汇编、JDB及转换日志。
- **另一切入点**：Java Card上的公共库抽象是否免费？逐字节路径叠加访问方法曾使小Create多约111ms；直接访问继承字段后降至约25ms，最终将协议状态检查留在组合的transport中，小Create比原版少约27ms。各轮RAM策略不变，最终FIDO热登录多约6ms、正式LOAD总量增加422B。区分共享代码的维护收益、方法分发成本、不同存储模式的代码体积，以及边界内存余量；这些是同卡小样本观察，不把每一毫秒差值都归为单个方法调用。
