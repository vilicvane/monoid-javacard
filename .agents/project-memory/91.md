# GP ECC community research, 2026-10-14

Scope: follow up record 90's ECC provisioning failures using original community
sources and vendor documentation. No card access or production-code/API changes
were made during this research.

## Reusable implementation

[GPShell / kaoh/globalplatform 3.0.0](https://github.com/kaoh/globalplatform/releases/tag/3.0.0),
released 2026-08-14, announces ECC DAP and Delegated Management support. Inspected
source revision: `877bbe17cd420dcd06ed5d0e270269b9de1bbaa1`.

Its [PC/SC integration tests](https://github.com/kaoh/globalplatform/blob/877bbe17cd420dcd06ed5d0e270269b9de1bbaa1/globalplatform/src/globalplatformTest.c)
include ECC Token and ECC DAP provisioning, signing, loading and installation;
the file states that JCOP 4.5 is required to run all tests. The public-key fixture
was parsed offline as P-256 / prime256v1. This is a concrete implementation and
test suite, not a published successful APDU transcript on record 90's card. The
personalized-domain test setup uses SCP03; it does not establish the equivalent
SCP02 result on our card.

Three implementation differences merit controlled comparison:

1. [Explicit curve encoding](https://github.com/kaoh/globalplatform/blob/877bbe17cd420dcd06ed5d0e270269b9de1bbaa1/globalplatform/src/globalplatform.c#L1437)
   omits B7 when cofactor h=1. P-256 public key plus full parameters therefore
   uses 272B, versus our 275B including `B7 01 01`. This behavior dates to
   [ac63f1de](https://github.com/kaoh/globalplatform/commit/ac63f1de9ebd6938768a8dc63e7c890905afcffa);
   its explanation does not identify a JCOP-specific requirement. Do not assume
   this difference alone fixes 6A80/6A86.
2. [Chained transport](https://github.com/kaoh/globalplatform/blob/877bbe17cd420dcd06ed5d0e270269b9de1bbaa1/globalplatform/src/connection.c#L569)
   includes Le only on the last fragment. GPPro's GPSession.transmit adds Le to
   each reconstructed fragment. Both use PUT KEY P1 bit 80 for non-final data
   and clear it on the last fragment. Record 90's exact-transmit bridge fixes
   STORE DATA case 3; inspect its actual PUT KEY wire trace before asserting the
   non-final-Le difference was or was not covered by the previous experiment.
3. The same transport constructs and wraps the complete logical command before
   splitting it into short APDUs. Its [SCP02 implementation](https://github.com/kaoh/globalplatform/blob/877bbe17cd420dcd06ed5d0e270269b9de1bbaa1/globalplatform/src/scp.c#L1047)
   accepts a long logical command, unlike GPPro's short-input wrapper limit.
   For i55 C-MAC, the logical MAC input uses modified CLA, three-byte Lc including
   MAC length, and final P1; the resulting MAC accompanies the final fragment.
   Host-internal extended encoding does not require an extended APDU on the
   wire. Record 90 used authenticated CLR for long PUT KEY, so did not test this
   protected path. No successful real-card trace for this long SCP02 path was
   found; source support is not hardware validation.

The [curve lookup](https://github.com/kaoh/globalplatform/blob/877bbe17cd420dcd06ed5d0e270269b9de1bbaa1/globalplatform/src/crypto.c#L2891)
contains NIST, Brainpool and SM2 curves, not secp256k1. Even the full-parameter
import path [requires that lookup](https://github.com/kaoh/globalplatform/blob/877bbe17cd420dcd06ed5d0e270269b9de1bbaa1/globalplatform/src/crypto.c#L4018).
Therefore an unmodified GPShell failure on secp256k1 would be a host restriction,
not evidence of rejection by the card's GP verifier.

## Independent evidence and discarded leads

- [NXP JCOP4 P71 FIPS security policy](https://csrc.nist.gov/CSRC/media/projects/cryptographic-module-validation-program/documents/security-policies/140sp3746.pdf),
  dated 2020-10-26, p13 Table 10 explicitly assigns RSA2048 or ECC P-256 DAP-PUB
  to Card Manager. Pages 16 and 18 describe its use for patch/applet verification
  during LOAD. This is GP/card-management evidence, distinct from Java Card API
  support. It describes a specified FIPS configuration, not record 90's precise
  card configuration, and does not prove secp256k1 or Token support there.
- [GPPro PR208](https://github.com/martinpaljak/GlobalPlatformPro/pull/208)
  added ECC DAP import in 2020 with P-256/reference00 hardcoded. No card-specific
  successful transcript accompanies it.
- [GPPro issue248](https://github.com/martinpaljak/GlobalPlatformPro/issues/248)
  contains JCOP3/J3H145 capability data with tag88 `0102030405`, but its DAP flow
  is RSA. GP 2.3, Amendment E and CIC 2.1 all assign P-256 reference00. No evidence
  supports an alternate JCOP numbering scheme; do not blindly try 01..05 or
  present this issue as successful ECC provisioning.
- [GPPro issue305](https://github.com/martinpaljak/GlobalPlatformPro/issues/305)
  includes explicit JCOP4 SD parameters `810202558202202087022020`. Its SCP02
  installation-parameter issue was already addressed by record 90 and does not
  explain the remaining ECC import failure.
- [suut's JCOP4/4.5 identification parser](https://gist.github.com/suut/5f81b465b43051dedd194dae27beed93)
  uses GET DATA IDENTIFY `80CA00FE02DF28`; NXP's policy pp7-8 documents the command
  with trailing Le00. It can identify platform build, ROM, patch and configuration
  more precisely than ATR/CPLC alone. This command was not sent in this turn.

Within this search, no public successful secp256k1 GP Token/DAP transcript on
JCOP4/P71, and no resolved case matching our P-256 reference00/6A88 failure, was
found. This is a search limit, not proof of incompatibility. The useful next
experiment is P-256 as a control in a disposable SD, matching the GPShell full
parameters and protected short-APDU chaining, followed by secp256k1 only after
separating host curve restrictions from card behavior. Exact build identification
would also help match vendor personalization documentation. Do not run upstream
integration tests wholesale: their cleanup and management mutations assume a
dedicated test card and do not preserve this user's existing applets by default.
