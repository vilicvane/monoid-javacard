# Complete-path derivation cache and Solana timing

## Request and decisions

- [user] Cache the complete derivation path, including seed and public key.
- [user] Determine whether current Solana signing latency matches historical
  normal performance and whether there were regressions.
- [agent] Extend the existing global 32-entry FIFO rather than introduce
  separate master, path and public-key pools. No request, response or Safe SIO
  changes; work remains in the Java Card project.

## Implementation

`KeyDerivation.derive` and `deriveFromSeed` return a persistent `DerivedKey`.
Identity includes the derivation instance, original source bytes, seed/master
kind and complete path/context. A seed hit skips both master HMAC and final-node
derivation. Distinct paths from one seed still derive their own master on a miss;
intermediate path prefixes are not separately cached.

The result stores the final node and lazily computes public material. Weierstrass
ViewKey caches the compressed public key. Ed25519 caches 96 bytes containing the
expanded scalar, signing prefix and public key; both ViewKey and Sign restore
fresh operation-local `ED25519Key` buffers from that result. Nonce multiplication
is never cached. Reset/deselect still invalidate transient keys, and operation
cleanup retains the existing invalidation behavior.

Safe authorization, current source retrieval and item existence checks precede
cache lookup. Source replacement therefore misses and deletion cannot reuse an
old entry. Retained bytes are not immediately erased on source replacement or
deletion, matching the existing trusted-runtime policy. Taproot works on a
transient node copy and cannot mutate the cached base node/public key.
Weierstrass public-key caching serves ordinary ViewKey; BIP340/Taproot still
compute the public keys used for normalization and adjustment. The complete
expanded-key reuse in this change applies to Ed25519.

Entry construction finishes before transactional FIFO publication. Lazy public
and expanded results are copied completely before their reference is published.
The cache consumes persistent storage; Safe's 4KiB admission guard is not a quota
that prevents other allocations. This change introduces no low-space cache
fallback or larger capacity.

- 281 JUnit tests plus three manual harness checks pass with Java 11.

- Prettier, Inplate and diff checks pass before hardware preparation.
- New counting tests cover seed/master lookup separation, skipping both

  derivation instances. RFC 8032 tests prove restored keys/public keys and exact
  signatures after reset, while each signature still multiplies its nonce.

  transient copies; existing Taproot, source replacement/removal and reset tests
  continue to pass.

## Historical timing comparison

Comparable complete Sign measurements on card 55690320 use a cached four-level
SLIP-0010 path and a 300B message:

| Version / change                              | Median or recorded sample |
| --------------------------------------------- | ------------------------: |
| 32-entry cache, before Reader fix (112)       |                 3409.87ms |
| Reader cursor state moved to RAM (112)        |                 2746.37ms |
| One CBOR map scan/index (113)                 |                 2533.98ms |
| Later item-transfer integration, cached (116) |                    2550ms |

Record 116 also reports 2717ms for an uncached four-level 300B Sign. The parser
fixes were committed in `1bb6f1b`; the preceding cache commit is `9e9d45c`.
These controlled comparisons establish avoidable parsing overhead, but do not
bisect a single introducing commit or account for every older increase. Record
108's 3.46–3.68s Sign observations followed the explicit Key API work (`59f6e04`).
An earlier smaller change is also recorded: four-level seed/150B full Sign
took 2.634–2.660s in record 63 and 2.750–2.775s after chunked processing in record
65, roughly 0.1s more; 512B was essentially unchanged. Both were included in
`8abf0c5`, so that record does not isolate one introducing source change.

Record 47's 1417ms signing figure is an isolated component benchmark with a
previously imported key and shared context, excluding derivation and the full
Monoid command. It is not a whole-command regression baseline. Record 119's APP
card 51433520 samples are 2600.24ms direct Ed25519 and 2644.95ms SLIP-0010, both
300B/10 fragments; a different card and fragmentation prevent strict comparison.

Whole-command timers sum PC/SC transmissions, including request fragments and
GET RESPONSE. They exclude separate Hello/PIN/ViewKey commands, host encoding
and independent signature verification. An APP flow taking 3–4 seconds cannot
alone establish a new signing regression.

Thus the firmware comparison observes about 43% less warm ViewKey time and 20%
less warm 300B Sign time. First-time paths still do the derivation and expansion;
the cache does not make all new-path operations take the warm time. The baseline
2616.65ms is near historical 2533.98–2550ms, but this cross-session comparison does
not isolate the roughly 67–83ms difference. A ViewKey plus Sign readily explains
the previously reported 3–4s combined flow without a new seconds-scale regression.

Both versions read available RESET/DESELECT memory as 2132/2128B after setup and
2036/2032B after the suite. These are query-time values, not peak RAM. Persistent
availability saturates at 32767B and does not measure cache storage consumption.
The complete cache result occupies persistent memory, including an additional
96B Ed25519 expansion payload per populated path; headers and runtime overhead
are not measured.

### Direct-key control and attribution

Direct Ed25519 does not use the derivation cache, yet its measured Sign fell by
91.81ms and ViewKey by 40.23ms. Identical frozen source hashes for LibMath,
LibED25519, ED25519Key, Signer and the transport/parser exclude an intentional
algorithm change there. Cold reset preserves the difference (2400.42→2305.50ms).
An additional five-signature final control gives 2306.18ms median; reinstalling
the exact sealed baseline CAP and initializing only the direct fixture gives
2386.12ms median over the last four signatures. All ten signatures independently
verify. Main and supplementary runs total 118 verified signatures.

The difference approximately scales with modular exponentiations: direct ViewKey
uses eight and Sign eighteen, corresponding to about 5ms per call. Each call
sets exponent/modulus on a persistent RSA key before Cipher.init/doFinal.
An independent BD Applet then checks four persistent RSA512 key instances with
retained 0/16/32/48B allocations before construction. It runs the same public
base/exponent/modulus with 0/1/8/18 repetitions, one warmup plus three measured
samples per case, and rotates instance order. All 192 operations verify their
expected responses. No per-command allocations or GC are requested in this
probe. The slopes in milliseconds per repetition are:

| Mode                            | Instances 0/2/3 | Instance 1 |
| ------------------------------- | --------------: | ---------: |
| Set parameters + init + doFinal |     23.29–23.30 |      28.63 |
| Set exponent and modulus only   |       7.17–7.18 |      12.51 |
| Init once, repeat doFinal       |            9.89 |       9.89 |

The approximately 5.33ms instance-dependent difference is reproduced entirely
in parameter-setting cost; repeated doFinal has equal slopes. The init-once
mode instead has an approximately 5ms higher intercept for that instance.
This establishes a native persistent-key parameter-setting mechanism with the
right scale to explain the direct-operation variation. The precise physical
address/alignment and its mapping to the two production installations are not
observable in this probe, so EEPROM page alignment remains an inference, not a
verified fact. Do not attribute the entire observed firmware speedup to caching
or promise identical absolute times after every installation. Counting unit
tests separately establish that cached Ed25519 skips expansion/public-key work
while retaining the required nonce multiplication.

The main A/B installations and the unchanged-baseline control installation have
all been removed, as has the independent RSA BD probe. Each cleanup preserves the complete original registry and
original Monoid SELECT 9000 / Hello 6F00 behavior. No formal application was
replaced. Raw snapshots, manifests, reports and scripts remain under ignored
`.research/full-path-cache-20261018/`; this record retains the durable results.
The final reader session is released. Production source hashes still match the
tested final CAP. The user subsequently requests committing and pushing this
implementation together with its verification records.
