# J3R452 同固件跨卡验证

[user] 将J3R452换到ACR39U，要求与前一张测试卡比较相同固件的性能，并将GP管理密钥改为默认值。

[agent] 当前目标是 `ACS ACR39U ICC Reader 0` 上的CPLC28767821，CPLC声明IC Fabricator4790、IC TypeD600，GP2.3 / SCP02 i=55，接触T=1。产品名J3R452由用户提供。本轮不访问另一会话的ACR1552，也不改前一张CPLC55690320的记录176结果。

## 已完成的管理操作

使用用户提供的管理密钥认证后，将三把GP管理密钥更换为默认值；另起只读会话通过默认认证执行info/list，核对密钥模板只剩KVN01、IDs1/2/3，原FF已不在。证据为忽略目录 `.research/j3r452-comparison-20261022/default-key-verified.log`。不保存原管理密钥或照片中的内容。

更换发生在本轮预检/安装之前。预检记录该卡独立的原GP registry，并确认C0/C2/C4/C5隔离槽为空；没有复用上一张卡的ownership ledger。

## 同固件基线与首次失败

`unified-j3r452` 直接复制记录176最终 `unified-transport` 的120个冻结生产源码和四个已验证隔离CAP，逐一SHA核对一致，没有重新编译或改变固件。主机仅调整研究目录、workspace和CPLC绑定；GP管理使用独占PC/SC，计时Java传输仍沿用上一轮相同的非独占实现。帧大小、负载、统一收尾GC及计时口径不变。

四个包安装成功，但首次provision在第一条 `fresh-hello` 就返回CBOR `INTERNAL`，SW9000，耗时420.563ms；尚未进入设置PIN或创建测试seed。保存的失败为 `variants/unified-j3r452/28767821-provision-1792680516387.jsonl`。该轮不是初始化通过，更不是完整FIDO/性能测试通过。

随后另开只读连接，Hello和SysInfo成功，分别为278.999/210.966ms。内存探针前后均为RESET226B、DESELECT256B、持久117392B，见 `diagnose-hello.json` / `.jsonl`。这是命令边界可用量，RESET/DESELECT不能相加，不是内存峰值；仅这些读数尚不足以解释异常，后续通过诊断版本确认如下。

## 已确认的四CAP布局限制

重新安装 `unified-j3rtrace` 后，首次Hello在阶段0x0621，即 `safe.getPINSetResult(SAFE_FALSE)` 查询Secret PIN状态时，记录SystemException、reason2（`NO_TRANSIENT_SPACE`）。探针在该次Hello前为RESET403/DESELECT432B，之后为226/256B；随后预热后的Hello成功，trace无异常。见 `hello-trace.json` / `.jsonl`。因此首次Hello的直接失败原因是transient空间分配失败，不能把后一次成功当作冷启动成功。

继续该诊断布局的provision，设置Secret PIN同样发生SystemException reason2。失败后只读Hello确认Access/Secret PIN均仍未设置，见 `pin-trace.json` / `.jsonl` 及 `variants/unified-j3rtrace/28767821-provision-1792681243547.jsonl`。这说明完整四CAP布局连当前初始化流程也无法完成，尚不能做FIDO性能对照。PIN命令的trace阶段值沿用前次Hello标记，不据此定位PIN内的具体分配点。诊断CAP额外记录异常，其时间和体积不当作未修改固件的性能基线。

## 独立Monoid布局的局部结果

诊断布局结束后，重新安装原 `unified-j3r452` 的相同CAP，只删除本轮拥有的Security Key C4/C401。独立Identity/Monoid/library布局的fresh Hello、Secret/Access PIN设置与认证通过，64B条目创建及三轮Get/Set通过。边界RAM为RESET519/DESELECT512B；持久可用量从136380降为存入64B后的136164B。

接着600B Create返回完整CBOR `INTERNAL`（SW9000），测试立即停止，保留失败及intent；1536B、后续List和所有Ed25519操作均未执行。原始结果为 `variants/unified-j3r452/runs/1792681717805-monoid-only/result.json`，`passed:false`、`verifiedSignatures:0`。此处尚未用trace确认600B失败的具体异常，不能仅凭RAM余量将其等同于前述PIN错误。

## 最后一次签名尝试与证据边界

全部失败与未完成intent保留在独立账本历史中。第一次小签名尝试认证成功，但用于确认存量的List返回CBOR `INTERNAL`，立即停止，没有删除或导入条目，没有执行ViewKey/Sign；结果为 `variants/unified-j3r452/runs/1792681938544-small-signing/result.json`，仍是0签名，不能计作Ed25519失败或成功。

最后改用已知Index直接Get：64B内容与预期一致，600B项返回NOT_FOUND；随后删除64B项、导入公开RFC8032 seed均成功。未预先调用ViewKey，第一次32B Ed25519 Sign仍返回CBOR `INTERNAL`，立即停止，0次成功签名，后两次未执行。签名前边界RAM519/512B、持久136212B；见 `variants/unified-j3r452/runs/1792682136466-small-signing-direct/result.json`。不把失败响应耗时当作签名性能，也不重放先前失败的List或600B Create。

本轮可确认的实际工作集是：移除Security Key后的冷Hello、两种PIN初始化/认证、64B条目创建/读写/删除、已知不存在Index查询，以及RFC Ed seed导入。四CAP初始化、600B Create、非空List及32B Ed Sign均有失败；没有取得新卡FIDO或Ed25519成功性能样本。只有冷Hello/PIN设置通过trace确认NO_TRANSIENT_SPACE，其他三个INTERNAL的具体异常未跟踪，不能据此断言全部同因，或断言该芯片永远不能运行相关算法。

各次失败和意图保留在历史中，最终cleanup与verify均成功：C0/C2/C4/C5临时包全清，原GP registry逐项保留，账本为cleaned、confirmed为空、无待处理intent。120个生产源码哈希仍匹配已测试快照；Git暂存补丁SHA仍为 `B3EFC9B2586E801762D95CCB21C029E6379CA5BA55AB6664C49452E1C5C4F12B`，与此前一致。正式CAP/source及APP未改，未提交或推送；本轮没有为得到性能数字而修改固件或隐藏兼容性失败。现有局部表格的不同布局限制必须随数字保留。

## 博客兴趣点

- **切入问题**：为什么相同CAP能LOAD/INSTALL，第一次Hello或PIN初始化却失败？
- **已验证事实**：四CAP与前一卡逐字节相同、安装成功，诊断仍发现冷Hello与PIN设置的NO_TRANSIENT_SPACE；移除测试Security Key后PIN初始化与64B读写可用，后续600B Create、List及不预先View的32B Ed Sign仍返回INTERNAL。
- **证据边界**：LOAD兼容不等于实际多Applet布局有足够运行资源；不能把暖Hello成功当作冷初始化成功，不能把不同布局的局部性能当成完整产品对照。600B Create、List和Ed Sign的具体异常尚未跟踪，不由前一个reason2推定全部同因。
- **材料**：本记录的原始失败、trace阶段/原因和局部结果；研究目录中的CAP/source哈希、各次失败账本及完整PC/SC日志。尚无可发布的完整新卡FIDO或Ed25519性能结论。
