# Independent Ed25519 items — 2026-10-12

This record describes the initial 0x0402 implementation and its physical-card
evidence. Record [74](./74.md) supersedes the category/encoding and splits the
direct public-key methods; the validation evidence below remains historical.

The user approved adding an independent Ed25519 key type following the existing
secp256k1 item structure. The new type is 0x0402 (`ed25519`), in the existing EC
category. Its data is exactly a 32B Ed25519 private-key seed, including zero as a
valid value. This differs from the generic HD `seed` item and the 64B `master`
item: independent keys do not run seed-to-master conversion or SLIP-0010.

Implementation stays in Monoid's Safe wrapper and Keystore. The Safe applet and
Shareable storage interfaces are unchanged. Type parsing, listing, random key
creation and explicit-index validation use the existing command paths. The index
is type 0402 followed by the first eight bytes of SHA-256 of the stored seed.
Independent ViewKey accepts only index and returns publicKey without chainCode.
Independent Sign accepts index, cipher eddsa and message, without curve/path/seed
derivation fields. Generic seed/master derivation retains its existing behavior.
Keystore clears Ed25519 expanded keys and fetched private material in finally;
the shared curve remains reusable.

The old Safe.type(CBORReader) fixed 6B buffer could not read ed25519 or secp256k1.
It now delegates to the existing text-array overload. The internal length
argument uses short instead of byte so a 263B string beginning with ed25519
cannot wrap to seven bytes and be accepted as a valid type.

All 72 simulator tests and production Java Card 3.0.5 CAP conversion/verification
passed. Three new integration tests create and clean up their own items without
changing the earlier nine-item fixture. They cover string/integer/explicit-index
imports, RFC8032 and all-zero seeds, random creation, List/Get/ViewKey/Sign/Remove,
and exact independent Node/OpenSSL public-key/signature comparison. Invalid
0/31/33/64B data, mismatched index digest, wrong cipher and 263B type names for
List/Create/CreateRandomKey are rejected. Existing secp256k1 and derived Ed25519
regressions pass. README documents the new item and direct-key request behavior.

The same ACS ACR1552 T=1 card (ATR 3b8a800150564a434f503453494471) passed six
physical groups with seven independent Node/OpenSSL signature checks, including
two RFC8032 vectors, a randomly generated/exported disposable key, all-zero seed,
error recovery, a 1024B fragmented message and cancelled-request recovery.
Text/numeric/explicit-index creation and public-key queries pass. Invalid lengths,
index digest, cipher and a 263B type name are rejected. No curve/path/seed
derivation fields are sent for direct signing.

Complete direct Sign takes 2.240–2.309s for the tested 0–26B messages and 2.517s
for the 1024B Message (1066B request, five APDU frames). These include request
transport, key import and signing, excluding authentication, earlier public-key
queries and memory queries. Fresh idle transient memory reads 2416B; after each
test group it is 2320B, including the query's own response allocation. These are
not peak measurements. Persistent readings saturate at 32767B and cannot prove
zero persistent-memory growth.
