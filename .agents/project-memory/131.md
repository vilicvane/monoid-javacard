# Security Key applet and delegated authorization

[user] Requested a design for a card-resident Security Key applet, referring to
an existing FIDO2 Java Card applet, with Monoid authorizing other applets and a
future APP interface for managing those grants.

[user] Suggested managing credential records by authorizing Safe Item Types,
and explicitly confirmed that the Security Key applet itself should store and
verify the FIDO PIN.

[user] Wants declarations without hardware verification, primarily user
presence (UP), enabled by default to avoid blocking early integration/debugging.
Later, the APP should let users disable such declarations. The user explicitly
clarified this scope rather than requesting all FIDO capabilities be advertised.

[agent] Use a software UP compatibility policy by default; do not block initial
integration on adding hardware presence detection. This does not bypass FIDO
PIN verification or Monoid authorization, fabricate UV, or advertise missing
capabilities. Treat GetInfo options and authenticatorData flags according to
their individual semantics, not as a blanket true value. Configuration APIs
and the exact behavior when the policy is disabled remain to be designed.

[agent] The remaining design is a proposal, not an approved API or an implementation. No card was
accessed. The likely reference is
[BryanJacobs/FIDO2Applet](https://github.com/BryanJacobs/FIDO2Applet); the user has
not supplied an exact repository URL. Its MIT license, CTAP/PIN/NFC processing and
tests are useful references, but its random private-key/wrapped credential-ID
backend and large main class should not dictate Monoid's organization.

## Proposed boundaries

- Security Key implements standard CTAP over NFC, RP binding, credential lookup,
  PIN/UV, user presence, COSE keys and DER ECDSA signatures.
- Monoid exposes a restricted Shareable service for granted derivation/signing
  and Safe Item Type-scoped data access. Root secrets and derived private
  keys do not leave this boundary for the client applet.
- Credential storage reuses Safe Items instead of a separate credential CRUD
  API or client namespace. Proposed grants specify allowed Types and read,
  create, update and delete operations; index-based operations check the actual
  item's Type, and enumeration stays within granted Types. Granting the same
  Type to multiple applets deliberately shares that data according to their
  respective permissions. Exact Types, rights and signatures remain undecided.
- Safe retains roots, credential records and a separate protected grant registry.
  Current Create/Set/Remove accept Access authentication, so ordinary editable
  Safe Items cannot serve as authoritative grant records without additional
  protection. Grant creation/change/revocation requires explicit Safe PIN
  authentication at Monoid's management entry point.
- Identity keeps its existing identity/communication role.
- Prefer a small stable interface-only library CAP for new client SIO contracts.
  Importing Monoid's CAP would prevent independently replacing that package.
  Avoid persistent cross-applet SIO references; sessions/references expire on
  reset, and grants store bytes rather than client-owned objects.

## Proposed authorization and credential flow

Authorize a specific installed client for a selected seed or Monoid-001 master,
fixed derivation domain/algorithm and permitted operations. A card-internal
random capability secret, stored privately by the client and checked with the
actual JCRE caller AID, can distinguish authorized installations; a public AID
or self-reported instance ID alone cannot. Issuance/replacement requires approval;
neither the APP nor ordinary CTAP commands receive the secret. Safe can retain
its hash. Recheck the live grant before every operation, including cache hits.
This authenticates an enrolled instance, not its code: initial installation and
approval still establish trust in the client and in Monoid.

Keep this card-local authorization independent of the derivation identity. A
stable profile/domain, RP ID hash and random credential identifier feed
Monoid-001 with unambiguous encoding; mutable grant IDs, tokens, AIDs and card
IDs must not change existing credentials after reauthorization or recovery.
Credential records retain RP, user handle/display metadata, discovery/protection
flags and lifecycle state. A known credential ID uses direct lookup; discovery
enumerates only eligible records for that RP. Root backup alone is insufficient.

The user confirmed that the Security Key applet owns FIDO PIN storage and
verification, separately from Safe/Access PIN. Standard ClientPIN verification
normally supplies an encrypted PIN hash, not the original Safe PIN. The trusted
Security Key code enforces per-operation CTAP authorization; a Monoid grant does
not itself establish UV or UP. Normal website login uses the system's CTAP path
without opening the Monoid APP. Replacing Monoid preserves Safe-held grants but
requires unlocking its new instance with Safe PIN again. Replacing the client
loses its capability and requires fresh authorization. Grants are local and must
not silently migrate with encrypted item copies to a second card.

Credential deletion/reset must prevent old IDs from recreating usable keys.
Plan directory validation and a profile generation/root change for FIDO reset;
never reset the entire Safe. Backup/restore also needs explicit counter and
WebAuthn backup-flag semantics before claiming portable passkey restoration.

## Implementation constraints verified in the current source

`monoid.Monoid` is currently an empty Shareable interface. SafeSession already
binds access to the previous caller and uses CLEAR_ON_RESET for SIO execution.
Monoid's signing/derivation path uses CLEAR_ON_DESELECT arrays and keys; it cannot
be exposed unchanged while another applet is selected. The first integration
probe should exercise real cross-applet P-256 public-key derivation/signing,
grant revocation, same-AID replacement, reset and package deletion under temporary
AIDs, then verify browser/phone discovery and registration/login.

The reference applet assumes user presence. The user chooses a default software
UP policy as described above. CTAP NFC presence consumption/time limits and
contact-reader behavior remain separate conformance considerations, rather than
prerequisites for the initial compatibility implementation. CTAP NFC framing
also differs from Monoid's proprietary APDU fragmentation. Reuse CBOR utilities
where applicable, not the existing wire protocol. The existing ES256 primitive
returns raw r||s; WebAuthn requires DER and a COSE EC2 public key.

Subsequent isolated physical switching and P-256 SIO results are in [record
132](./132.md). They confirm the need for RESET working memory and crypto-engine
externalAccess, plus independent provider replacement. They do not implement
or validate this proposal's capability/grant management or CTAP frontend.
