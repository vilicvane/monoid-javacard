# J3R452 完整布局内存整理

[user] 暂缓引入 Curve25519-JavaCard，先调通现有 Ed25519，并独立完成完整流程及之前遗漏的内存优化。

## 定位与修改

使用 ACR39U 接触式读卡器、T=1、记录177的 J3R452。只操作本轮隔离 C0/C2/C4/C5 包；原有卡片布局保留。研究材料在忽略目录 `.research/j3r452-memory-20261023/`。

对记录179结束时的120个生产源文件冻结一次诊断构建：完整四包首次 Hello 在查询 Secret PIN 状态时抛出 SystemException reason2（NO_TRANSIENT_SPACE）；阶段前后RESET29/DESELECT48B。明确确认失败后只卸载隔离Security Key，保留同轮Identity/Monoid/library继续定位：导入RFC8032 seed后直接签32B消息，失败在 LibED25519 的 response32 transient 数组申请，RESET23/DESELECT16B。此时已完成展开私钥和公钥运算，不将问题归因于Wei25519原语不兼容。两次诊断均只跑到首次失败，不作性能样本，也未用重复预热掩盖冷失败。

证据：`variants/unified-diag-01/runs/1792686146527-diagnostic-hello/result.json`、`1792686170134-diagnostic-ed/result.json`；trace阶段、异常及边界RAM保留。随后清理本轮隔离包。

[agent] 沿用低写入私有数据优先持久的项目策略：签名结果、公钥、展开密钥、读取输入、元数据、凭证工作数据、派生中间结果和上下文改用持久数组；保留有效性、授权、游标和会话状态的transient生命周期，保留跨Applet必须使用的global数组。LibMath、Ed25519/BIP340的高频算术临时区仍使用RAM。

软件HMAC-SHA512的128B pad改由共享引擎按需创建并复用；原生后端不分配该pad。BIP32只保存必要的32B父私钥，三个派生器的低写入数据改持久。压缩公钥产生前的65B完整点不再每次占RAM。保留现有外部APDU和Shareable接口、缓存与GC策略。

后续完整布局暴露了两个不同问题，分别处理：原生HMAC-SHA512的KeyBuilder长度单位是bit，64B输入须配置512bit；错误容量在Monoid-001派生时返回CryptoException reason1，而非RAM不足。低写入的共享HMAC密钥改为持久对象。Bundle响应从Identity复制到Monoid时，目标已经是APDU缓冲，可以直接经SIO写入，不再分配中转global数组；这是响应路径优化，不改变Bundle发布时机或协议。

最终 `unified-final-05` 进一步复用Identity内64B HMAC pad，并将两个AES密钥对象改为持久对象。三个曲线共享ECDH引擎的实验已完整撤回，不能将该实验记为最终优化。高频算术临时区和真正的会话失效标记仍留RAM。

## 博客兴趣点

- **切入问题**：同一算法在单独Applet中能运行，为何装入完整布局后连查询PIN都可能失败？
- **关键事实**：低写入缓冲、共享密钥容器和响应中转逐层整理后，同一四包安装能连续完成Ed/FIDO、通信、三成员Bundle和再次签名；授权失效状态仍留transient。KeyBuilder的bit单位不能与内存不足混为一谈。Create响应失败时状态可能已发布，先读状态而非盲目重发。
- **适用边界**：阶段采样不等于连续峰值；软件对端不等于多张实卡；接触复位后的通信协商变化可能影响全部计时，不能简单归因于数组持久化。
- **参考**：记录177–179、本记录trace证据、数组分配与生命周期测试。
