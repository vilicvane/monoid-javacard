# Consolidated security audit baseline

- [user] Wants a dedicated document recording security boundaries, including prior accepted decisions, as the baseline for future audits.
- [agent] No dedicated document existed. Added `doc/security.md`, linked briefly from README and architecture, consolidating current source and project decisions without changing APIs or production behavior.
- [agent] The baseline covers the merged Monoid/Safe trust boundary, initially trusted applets and platform with arbitrary additional applet installation, host/GP authorization boundaries, Access/Safe permissions, Secret semantics, stable runtime-AID domains and Identity token binding, fixed Bundle membership, accepted recovery, state/transaction scope and validation limits.
- [user, prior decisions75/98/137/148/154/157] Trusted card execution permits private persistent state and omitting purely defensive erasure. Three conservative checks target single-fault hardening without claiming complete physical fault resistance. Export lock remains deferred. Same-AID recovery on another Bundle card with a fresh source-Safe-authorized artifact is intentional. Create/Join manage enrollment;0xFF Reset clears local items/cache/Bundle, both PINs and authorization while preserving Identity, and GP remains a distinct reinitialization alternative.
- [agent] Explicitly distinguishes fresh exports needing source Safe PIN from previously obtained artifacts, which need no new source authentication. Two cards describe the accepted fresh migration workflow, not a cryptographic two-card requirement once ciphertext exists. No raw existing-item database is held in Identity; a new same-AID Monoid cannot recover deleted items without their transfer artifacts.
- [agent] Documents that Access authorization can mutate/delete/sign, Secret only blocks plaintext Get of original data, metadata is public, peer public keys are not card attestation, and normal PIN/APDU transport is not encrypted by the transfer protocol. Future third-party grants/Security Key and permanent export lock are not current controls.
- [agent] Source review preserves actual lifecycle distinctions: APDU authorization clears on deselect/reset, not every response or every failed PIN attempt; Set data/secret and alias are separate publications; initial Safe/Access PIN writes are separate. Current PIN length narrowing and absent nonempty request validation are an explicit audit item, not an accepted security exception. No PIN behavior was changed or newly tested here.
- [agent] Updated the baseline for record157's correction: no PIN authorization, atomically clear local items/derivation cache/Identity Bundle and replace both PINs with unset state, then revoke current authorization. Reset clears failed-attempt/blocked state so new PINs can initialize the empty card; preserves Identity and requests GC after success without erasure/revocation guarantees. Saved asymmetric artifacts and original Bundle enrollment packets remain usable with the retained Identity. Anyone with APDU access may erase and reprovision local storage, but cannot retain old live items while removing their PIN/Bundle protections. Reset does not replace code or the applet instance.
- [agent] Selected Bundle-absence decisions use three conservative checks before Create, initial Join publication or asymmetric export. Encoded mode values are validated; display/decryption missing-key comparisons stay ordinary. This is scoped software hardening and not physical fault-injection evidence.

Sources for current policy are records75,98,116,129,137–139,148,152–154,157 and current source, README, Identity/Bundle/transfer documentation.
