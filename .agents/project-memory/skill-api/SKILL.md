- Records 86–87 implement independent caller authorization. Each SafeSession owns a CLEAR_ON_RESET short/complement grant; A and B authenticate independently and retain their grants across SELECT. Repeated interface acquisition returns the same active session and preserves its item views, without clearing auth. A new PIN check revokes only that caller before verifying; failure preserves other callers until shared tries reach zero. OwnerPIN owns the shared PIN/try budget, and its comparison result plus native validated flag are checked before publishing a grant. Later checks use session state, caller identity and lock state rather than the global native flag. PIN update (including an oversized failed update), lockout and real reset revoke all sessions. A transient head/next list retains active sessions without static references or a persistent caller registry. SafeItemSession checks its issuing session on each access. Signatures/APDUs remain unchanged. Record 87 verifies the separate-CAP A/B flows, forwarding rejection and cold-reset revocation on the physical card with ATR 3B8A800150564A434F503453494471. Continuous-power reinstall of the same AID produces a fresh JCRE AID object: new A is unauthenticated and B stays authorized. A runtime that instead reuses the identical AID object without clearing transient state is not protected against this replacement path; document this compatibility requirement. Earlier jCardSim exact-reference reuse was caused by supplying the same static AID object during reinstallation. All temporary applets/packages were removed and the original registry restored. Warm PC/SC reset did not reset JCRE state on this reader; verified cold reset did. The simulator SIO adapter is still not a full firewall/GP emulator. See 87.md for final validation and limitations; no physical fault-resistance claim is made.

- The user accepts the record-86 boundary as isolation between applets whose source the owner may not inspect. The owner knowing a PIN does not authorize every installed applet. Access-authenticated signing uses Monoid's cached Safe PIN internally; raw-data export through CommandGet and PIN changes require Safe user authorization. Therefore another applet borrowing Safe's previous global validation could escalate from signing to raw-key export. If the attacker already knows the Safe PIN, there is no credential privilege gain; do not use that scenario alone to justify the isolation.

All 101 simulator tests and production CAP checks pass; no card was accessed and no physical-fault resistance is established. Cached Safe PIN validation is storage access, not independent user authentication; this does not undo record 75's cleanup choices.

- Obtain the user's explicit approval before changing an external API or protocol. Internal refactoring within an approved change does not require a separate approval.
- The user approved nesting ciphers under each curve in capability declarations: features.curves is an array of {name, ciphers} objects. Preserve signing request fields and semantics; this approval only reorganizes capability reporting.
- Use the Lib prefix for classes exposing static methods. LibSLIP10Ed25519.derive is static and allocates scratch once per call, reusing it through the path. LibED25519.sign is also static: it accepts the shared CurveED25519 and expanded key, allocates three local transient arrays, and resets the hash in finally. Signer selects the implementation; no signer instance is retained.
- Keep this work in Monoid Java Card. Changes to the Monoid mobile APP are outside the approved scope.
- Keep README concise and focused on command definitions. Client transport details belong in doc/apdu.md. doc/cards.md is a card-buying guide; retain vendor links, hardware information and relevant compatibility summaries there. Research history, benchmark details, CAP hashes and test/cleanup evidence belong in the corresponding numbered Project Memory files, not user-facing guides.
- Use API availability to select implementation branches, rather than card-model or version profiles. Do not add on-card behavior validation or compatibility self-tests. The supported-card list and implementation compatibility results belong in documentation; imported upstream card names must not imply support for unverified cards.
- Treat the Ed25519 code in `af4f994` as a milestone prototype whose internal structure can be refactored to match the existing project. Do not treat `ED25519Signer` ownership or its prototype interfaces as fixed architectural constraints. This does not override external API approval requirements.
- The byte-array refactoring milestone is complete: `ECCurve`, `ECPoint`, `BigNat`, `BigNatInternal`, `MathAllocator` and `MathStatus` are removed. `CurveED25519` directly uses native XY ECDH, following `CurveSECP256k1`; values are byte arrays and needed modular arithmetic lives in `LibMath`. `MathResources` has since been removed: `LibMath` privately owns its shared RSA engine/key and 160B scratch, with Applet init/dispose and scratch initialized as required by each calculation. Preserve source attribution and complete third-party licenses in `third-party/jced25519` and include them in distributions; basic `LibMath` operations do not need repeated attribution headers. The byte-array refactor has simulator, CAP and isolated physical-card verification; the subsequent LibMath ownership/cleanup change has simulator and CAP verification only. Keystore integration is subsequently connected and simulator-tested in record 49; record 63 subsequently verifies selected integrated signing and key-query flows on hardware, with explicit long-request RAM limits.
- The approved extension to existing `0x41 Sign` accepts `cipher: 'eddsa'` with raw `message` bytes. ECDSA continues to accept `digest`. The key description and `{signature}` response remain unchanged.
- Record 73 adds the approved independent `ed25519` item: TYPE_EDWARDS_ED25519 = 0x0501 (record 74 supersedes the initial 0x0402 encoding) with exactly 32B of private-key seed, including all-zero as valid. It follows the existing secp256k1 storage/index, creation, random generation and listing paths. ViewKey takes only index and returns publicKey without chainCode; Sign takes index, cipher eddsa and raw message, without curve/path/seed. Independent private-key seeds are not generic HD seed items and do not undergo SLIP-0010. The underlying Safe applet and Shareable storage interfaces are unchanged. Internal type-name lengths use short and dynamic CBOR text reading, avoiding the former 6B limit and byte-length wraparound.
- Keystore has `signECDSADigest` for ECDSA digests and a `signEDDSAMessage` entry point; neither takes a cipher argument. `Signer` now uses these same explicit names instead of `sign` overloads, distinguishing a precomputed digest from the original message. Discuss alternatives before forcing either curve's signing workflow into an unsuitable shared structure.
- Record 74 distinguishes TYPE_WEIERSTRASS / TYPE_WEIERSTRASS_SECP256K1 (0x0400 / 0x0401) from TYPE_EDWARDS / TYPE_EDWARDS_ED25519 (0x0500 / 0x0501). Direct public-key queries use getWeierstrassKeyPublicKey(index) and getEdwardsKeyPublicKey(index); the index determines the concrete curve, so no redundant curve argument is added. CommandViewKey dispatches by category.
- Keep one `Keystore`. Use overloads accepting `WeierstrassCurve` or `EdwardsCurve` for the corresponding public-key derivation flows; do not introduce two Keystore subclasses at this stage.
- Follow the existing BIP32 responsibility split: `LibSLIP10Ed25519.derive` now accepts a 64-byte master (key + chain code) and only derives along the path. Seed-to-master generation belongs in Keystore; do not add a parallel full derivation entry point. The EdDSA Keystore branch now calls the deriver in place on its master copy, imports the resulting seed and signs. It invalidates the expanded key in finally; record 75 removes byte erasure of the temporary copies.
- The approved curve structure uses parallel `WeierstrassCurve` and `EdwardsCurve` abstractions, each with its own key representation. `WeierstrassCurve` retains `getSharedPrivateKey`, `derivePublicKey` and `ECPrivateKey`. `EdwardsCurve` now uses the same method structure with `ED25519Key`; `CurveED25519` owns seed expansion and public-key arithmetic; LibMath owns shared math resources. `ED25519Key` stores the expanded scalar, prefix and public key. `LibED25519.sign` signs a complete message synchronously using that context, called by `Signer.signEDDSAMessage`. The prototype signer/session responsibilities have been split; signing is now a static library operation. `EdwardsCurve` now mirrors the existing shared lookup structure: `init` creates `ed25519`, `getSharedCurve` returns it for the matching name, `requireSharedCurve` throws `UNSUPPORTED_CURVE` when no instance matches, and `dispose` drops the reference. Applet installation now calls `init`, and uninstallation calls `dispose`. Keystore uses `requireSharedCurve`; SLIP derivation and signing are connected in Keystore; Signer accepts EdwardsCurve and selects the concrete Ed25519 implementation internally; do not introduce a common curve base merely for symmetry.
- Preserve the `WeierstrassCurve` / `CurveSECP256k1` inheritance structure. A naming change authorizes identifier and necessary reference updates, not deleting the base class, merging responsibilities or broadening the refactor. The earlier consolidation and lower-level method renames were withdrawn.
- Multipart requests belong to a shared transport layer. Business commands and their callers exchange complete requests and responses and do not distinguish short and fragmented requests.
- CBORReader implements the read-only ByteSource interface: getChunk/getChunkOffset/getChunkLength map logical positions to contiguous array ranges; getOffset returns a logical offset. Parsing checks complete ranges before copying or skipping and handles cross-block keys, length headers and values. bytesLength validates the byte-string header and leaves the offset at its content. CommandSign, Keystore and Signer pass the source and Message range to LibED25519, which traverses it twice without concatenation. Do not store the borrowed APDU buffer in fields or change input before signing finishes. Other decoded fields still use copies.
- CBORApduReader receives each short APDU completely. Whole single frames borrow the APDU buffer; partial single delivery and multipart requests use fixed 256B chunks. The first two chunks use transient RAM; further chunks are plaintext persistent arrays allocated on demand, with no migration or copy of earlier chunks. The 512B budget counts the entire CBOR request, including metadata, and is an internal storage choice. A persistent Object[32] retains references across reset so SELECT can release every chunk even after transient state has cleared. Completion/errors/replacement/SELECT/deselect release every owned chunk. Replacement requests GC so abandoned chunks can be reclaimed before the next APDU. Internal chunk boundaries remain independent of APDU boundaries. EncryptedBuffer remains removed. Record 71 verifies 69 simulator tests, CAPs and nine physical groups, including independently checked signatures for the complete 8192B request limit, plus cancellation, invalid continuation, physical reset, oversized-request recovery and signing after a large response. This is still complete-request buffering; it does not authorize client replay or change the protocol ceiling. Actual repeated receiveBytes delivery within one short APDU remains unverified.
- Distinguish single, first, middle and last frames. A new single or first frame replaces an unfinished request, including when the new request uses the same command. Middle and last frames must match an active request.
- Use short APDUs; Extended APDU support cannot be assumed on the user's cards.
- Record 68 fixes response capacity retention without changing the API: lazy allocation, retention through pending GET RESPONSE, and erasure/release after completion/cancellation/deselect/send failure. Six physical groups confirmed seed 1184B/master 1458B signing after a 600B response, with memory readings recovering to baseline. That fix was committed as ecae74d before the persistent extension. Record 69 establishes that persistent storage alone does not require EncryptedBuffer; records 70–71 approve and implement RAM-first, on-demand persistent overflow without changing the API. The following record 67 limits describe the earlier RAM-only implementation.
- Record 67 measured historical RAM-only Message capacity for the same card, warmed contexts and m/44'/501'/0'/0': seed 1184B / stored master 1458B normally, dropping to 928B / 946B after a 600B value response. Retained response buffers and request metadata affected these scenario-specific limits. Records 68 and 71 supersede that storage behavior. The complete-request protocol ceiling remains 8192B; record 71 verifies seed 8096B/master 8114B Messages at that ceiling for its tested metadata and path, not a universal Message-length guarantee.
- GET RESPONSE is separate from request reception: during an incomplete request it returns 6883 without discarding it; absent a pending response it returns 6985. Invalid GET RESPONSE headers preserve pending transfers. Other request reception errors cancel assembly. New business requests discard unread responses. The current receiver executes synchronously after the last frame and does not insert the historical empty-6100 GC boundary.
- Handle GET RESPONSE in Command.process before resetting the response writer or receiving a new request. Writer reset releases the cancelled response buffer; sending advances sentOffset and releases the buffer after the final chunk. Record 75 removes byte erasure. Command.dispose only releases static references for uninstall and does not call clearTransport.
- Always send GET RESPONSE with CLA `00`; disable middleware that automatically copies the last request's CLA.

- Preserve parent lifecycle calls when overriding them: MonoidApplet.deselect calls super.deselect before its own cleanup; do not omit the call merely because the documented default implementation is empty.
