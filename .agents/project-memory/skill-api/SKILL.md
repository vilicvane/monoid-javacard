- Records 86–87 implement independent caller authorization. Each SafeSession owns a CLEAR_ON_RESET short/complement grant; A and B authenticate independently and retain their grants across SELECT. - The user accepts the record-86 boundary as isolation between applets whose source the owner may not inspect. The owner knowing a PIN does not authorize every installed applet. Access-authenticated signing uses Monoid's cached Safe PIN internally; raw-data export through CommandGet and PIN changes require Safe user authorization. Therefore another applet borrowing Safe's previous global validation could escalate from signing to raw-key export. If the attacker already knows the Safe PIN, there is no credential privilege gain; do not use that scenario alone to justify the isolation.

- Obtain the user's explicit approval before changing an external API or protocol. Internal refactoring within an approved change does not require a separate approval.
- The user approved nesting ciphers under each curve in capability declarations: features.curves is an array of {name, ciphers} objects. Preserve signing request fields and semantics; this approval only reorganizes capability reporting.
- Use the Lib prefix for classes exposing static methods. LibSLIP10Ed25519.derive is static and allocates scratch once per call, reusing it through the path. LibED25519.sign is also static: it accepts the shared CurveED25519 and expanded key, allocates three local transient arrays, and resets the hash in finally. Signer selects the implementation; no signer instance is retained.

- The byte-array refactoring milestone is complete: `ECCurve`, `ECPoint`, `BigNat`, `BigNatInternal`, `MathAllocator` and `MathStatus` are removed. `CurveED25519` directly uses native XY ECDH, following `CurveSECP256k1`; values are byte arrays and needed modular arithmetic lives in `LibMath`. `MathResources` has since been removed: `LibMath` privately owns its shared RSA engine/key and 160B scratch, with Applet init/dispose and scratch initialized as required by each calculation. Preserve source attribution and complete third-party licenses in `third-party/jced25519` and include them in distributions; basic `LibMath` operations do not need repeated attribution headers. - Keep one `Keystore`. Use overloads accepting `WeierstrassCurve` or `EdwardsCurve` for the corresponding public-key derivation flows; do not introduce two Keystore subclasses at this stage.

Seed-to-master generation belongs in Keystore; do not add a parallel full derivation entry point. - The approved curve structure uses parallel `WeierstrassCurve` and `EdwardsCurve` abstractions, each with its own key representation. `WeierstrassCurve` retains `getSharedPrivateKey`, `derivePublicKey` and `ECPrivateKey`. `EdwardsCurve` now uses the same method structure with `ED25519Key`; `CurveED25519` owns seed expansion and public-key arithmetic; LibMath owns shared math resources. `ED25519Key` stores the expanded scalar, prefix and public key. `LibED25519.sign` signs a complete message synchronously using that context, called by `Signer.signEDDSAMessage`. The prototype signer/session responsibilities have been split; signing is now a static library operation. `EdwardsCurve` now mirrors the existing shared lookup structure: `init` creates `ed25519`, `getSharedCurve` returns it for the matching name, `requireSharedCurve` throws `UNSUPPORTED_CURVE` when no instance matches, and `dispose` drops the reference. Applet installation now calls `init`, and uninstallation calls `dispose`. Keystore uses `requireSharedCurve`; SLIP derivation and signing are connected in Keystore; Signer accepts EdwardsCurve and selects the concrete Ed25519 implementation internally; do not introduce a common curve base merely for symmetry.
- Preserve the `WeierstrassCurve` / `CurveSECP256k1` inheritance structure. A naming change authorizes identifier and necessary reference updates, not deleting the base class, merging responsibilities or broadening the refactor. The earlier consolidation and lower-level method renames were withdrawn.
- Multipart requests belong to a shared transport layer. Business commands and their callers exchange complete requests and responses and do not distinguish short and fragmented requests.
- CBORReader implements the read-only ByteSource interface: getChunk/getChunkOffset/getChunkLength map logical positions to contiguous array ranges; getOffset returns a logical offset. Parsing checks complete ranges before copying or skipping and handles cross-block keys, length headers and values. bytesLength validates the byte-string header and leaves the offset at its content. CommandSign, Keystore and Signer pass the source and Message range to LibED25519, which traverses it twice without concatenation. Do not store the borrowed APDU buffer in fields or change input before signing finishes. Other decoded fields still use copies.
- CBORApduReader receives each short APDU completely. Whole single frames borrow the APDU buffer; partial single delivery and multipart requests use fixed 256B chunks. The first two chunks use transient RAM; further chunks are plaintext persistent arrays allocated on demand, with no migration or copy of earlier chunks. The 512B budget counts the entire CBOR request, including metadata, and is an internal storage choice. A persistent Object[32] retains references across reset so SELECT can release every chunk even after transient state has cleared. Completion/errors/replacement/SELECT/deselect release every owned chunk. Replacement requests GC so abandoned chunks can be reclaimed before the next APDU. Internal chunk boundaries remain independent of APDU boundaries. EncryptedBuffer remains removed. Record 71 verifies 69 simulator tests, CAPs and nine physical groups, including independently checked signatures for the complete 8192B request limit, plus cancellation, invalid continuation, physical reset, oversized-request recovery and signing after a large response. This is still complete-request buffering; it does not authorize client replay or change the protocol ceiling. Actual repeated receiveBytes delivery within one short APDU remains unverified.
- Distinguish single, first, middle and last frames. A new single or first frame replaces an unfinished request, including when the new request uses the same command. Middle and last frames must match an active request.
- Use short APDUs; Extended APDU support cannot be assumed on the user's cards.

- GET RESPONSE is separate from request reception: during an incomplete request it returns 6883 without discarding it; absent a pending response it returns 6985. Invalid GET RESPONSE headers preserve pending transfers. Other request reception errors cancel assembly. New business requests discard unread responses. The current receiver executes synchronously after the last frame and does not insert the historical empty-6100 GC boundary.
- Handle GET RESPONSE in Command.process before resetting the response writer or receiving a new request. Writer reset releases the cancelled response buffer; sending advances sentOffset and releases the buffer after the final chunk. Record 75 removes byte erasure. Command.dispose only releases static references for uninstall and does not call clearTransport.
- Always send GET RESPONSE with CLA `00`; disable middleware that automatically copies the last request's CLA.

- Preserve parent lifecycle calls when overriding them: MonoidApplet.deselect calls super.deselect before its own cleanup; do not omit the call merely because the documented default implementation is empty.
