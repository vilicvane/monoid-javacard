# Monoid Java Card API decisions

Source: `../records.md`, records 1–3, 6–10, 17–40, 42, 45–61 and 63–65.

Implementation status: the integration draft was stashed as `285d6abd37951dd46bf57b5cb5baf18ebe635525`; incremental rewriting starts from `af4f994`. The current code parses `ecdsa`/`digest` and `eddsa`/`message`. The EdDSA branch loads the key, converts a stored seed to master using the supplied HMAC label, validates the master type and length, and resolves `curve: 'ed25519'` through `EdwardsCurve.requireSharedCurve`. Other curve names return `UNSUPPORTED_CURVE`; valid input now follows hardened SLIP-0010 derivation, shared Ed25519 key import and signing. Existing 0x40 ViewKey also accepts ed25519 for stored seeds/masters through EdwardsCurve Keystore overloads, returning the same {publicKey, chainCode} map with a 32-byte encoded public key and 32-byte chain code; fetched copies and private material are erased in finally. Authenticated short-APDU seed/master signing and public-key queries are verified in the simulator and on the physical card against independent results. Hello and SystemInformation now advertise features.curves as [{name: 'secp256k1', ciphers: ['ecdsa']}, {name: 'ed25519', ciphers: ['eddsa']}], with no separate features.ciphers; both responses are simulator-tested. Short-APDU multipart reception is now implemented and simulator-tested: CLA 00/90/B0/A0 represents single/first/middle/last, with an 8192-byte protocol ceiling and transient request assembly. Ed25519 signing borrows the Message range directly from the request. The simulator passes 512/1167-byte signing and 600-byte Create/Get. Record 65 supersedes the contiguous buffer with fixed 256B transient chunks and a ByteSource interface. All 60 simulator tests and 14 physical groups pass, including 1167-byte signing and 600-byte Create with 255-byte frames. The complete Message still resides in RAM; the 8192-byte protocol limit does not guarantee physical capacity, and response capacity remains retained. The approved API requirements below remain valid. Descriptions of draft transport behavior are historical references, not claims about the current code or requirements to reproduce its internals.

- Obtain the user's explicit approval before changing an external API or protocol. Internal refactoring within an approved change does not require a separate approval.
- The user approved nesting ciphers under each curve in capability declarations: features.curves is an array of {name, ciphers} objects. Preserve signing request fields and semantics; this approval only reorganizes capability reporting.
- Use the Lib prefix for classes exposing static methods. LibSLIP10Ed25519.derive is static and allocates scratch once per call, reusing it through the path and erasing it in finally. LibED25519.sign is also static: it accepts the shared CurveED25519 and expanded key, allocates three local transient arrays, and erases them plus curve scratch in finally. Signer selects the implementation; no signer instance is retained.
- Keep this work in Monoid Java Card. Changes to the Monoid mobile APP are outside the approved scope.
- Use API availability to select implementation branches, rather than card-model or version profiles. Do not add on-card behavior validation or compatibility self-tests. The supported-card list and implementation compatibility results belong in documentation; imported upstream card names must not imply support for unverified cards.
- Treat the Ed25519 code in `af4f994` as a milestone prototype whose internal structure can be refactored to match the existing project. Do not treat `ED25519Signer` ownership or its prototype interfaces as fixed architectural constraints. This does not override external API approval requirements.
- The byte-array refactoring milestone is complete: `ECCurve`, `ECPoint`, `BigNat`, `BigNatInternal`, `MathAllocator` and `MathStatus` are removed. `CurveED25519` directly uses native XY ECDH, following `CurveSECP256k1`; values are byte arrays and needed modular arithmetic lives in `LibMath`. `MathResources` has since been removed: `LibMath` privately owns its shared RSA engine/key and 160B scratch, with Applet init/dispose and per-arithmetic-call cleanup. Preserve source attribution and complete third-party licenses in `third-party/jced25519` and include them in distributions; basic `LibMath` operations do not need repeated attribution headers. The byte-array refactor has simulator, CAP and isolated physical-card verification; the subsequent LibMath ownership/cleanup change has simulator and CAP verification only. Keystore integration is subsequently connected and simulator-tested in record 49; record 63 subsequently verifies selected integrated signing and key-query flows on hardware, with explicit long-request RAM limits.
- The approved extension to existing `0x41 Sign` accepts `cipher: 'eddsa'` with raw `message` bytes. ECDSA continues to accept `digest`. The key description and `{signature}` response remain unchanged.
- Keystore has `signECDSADigest` for ECDSA digests and a `signEDDSAMessage` entry point; neither takes a cipher argument. `Signer` now uses these same explicit names instead of `sign` overloads, distinguishing a precomputed digest from the original message. Discuss alternatives before forcing either curve's signing workflow into an unsuitable shared structure.
- Keep one `Keystore`. Use overloads accepting `WeierstrassCurve` or `EdwardsCurve` for the corresponding public-key derivation flows; do not introduce two Keystore subclasses at this stage.
- Follow the existing BIP32 responsibility split: `LibSLIP10Ed25519.derive` now accepts a 64-byte master (key + chain code) and only derives along the path. Seed-to-master generation belongs in Keystore; do not add a parallel full derivation entry point. The EdDSA Keystore branch now calls the deriver in place on its master copy, imports the resulting seed and signs. It clears fetched key copies, derived material and the expanded key in finally.
- The approved curve structure uses parallel `WeierstrassCurve` and `EdwardsCurve` abstractions, each with its own key representation. `WeierstrassCurve` retains `getSharedPrivateKey`, `derivePublicKey` and `ECPrivateKey`. `EdwardsCurve` now uses the same method structure with `ED25519Key`; `CurveED25519` owns seed expansion and public-key arithmetic; LibMath owns shared math resources. `ED25519Key` stores the expanded scalar, prefix and public key. `LibED25519.sign` signs a complete message synchronously using that context, called by `Signer.signEDDSAMessage`. The prototype signer/session responsibilities have been split; signing is now a static library operation. `EdwardsCurve` now mirrors the existing shared lookup structure: `init` creates `ed25519`, `getSharedCurve` returns it for the matching name, `requireSharedCurve` throws `UNSUPPORTED_CURVE` when no instance matches, and `dispose` drops the reference. Applet installation now calls `init`, and uninstallation calls `dispose`. Keystore uses `requireSharedCurve`; SLIP derivation and signing are connected in Keystore; Signer accepts EdwardsCurve and selects the concrete Ed25519 implementation internally; do not introduce a common curve base merely for symmetry.
- Preserve the `WeierstrassCurve` / `CurveSECP256k1` inheritance structure. A naming change authorizes identifier and necessary reference updates, not deleting the base class, merging responsibilities or broadening the refactor. The earlier consolidation and lower-level method renames were withdrawn.
- Multipart requests belong to a shared transport layer. Business commands and their callers exchange complete requests and responses and do not distinguish short and fragmented requests.
- CBORReader implements the read-only ByteSource interface: getChunk/getChunkOffset/getChunkLength map logical positions to contiguous array ranges; getOffset returns a logical offset. Parsing checks complete ranges before copying or skipping and handles cross-block keys, length headers and values. bytesLength validates the byte-string header and leaves the offset at its content. CommandSign, Keystore and Signer pass the source and Message range to LibED25519, which traverses it twice without concatenation. Do not store the borrowed APDU buffer in fields or change input before signing finishes. Other decoded fields still use copies.
- CBORApduReader receives each short APDU completely. Whole single frames borrow the APDU buffer; partial single delivery and multipart requests use fixed 256B transient chunks backed by a transient Object[32]. Internal chunk boundaries are independent of APDU boundaries; growth never copies old chunks. Completion/errors/replacement/SELECT/deselect erase and release every owned chunk. Replacement requests GC so abandoned chunks can be reclaimed before the next APDU. All Message bytes still remain in RAM; this is not constant-memory streaming. EncryptedBuffer remains removed. Record 65 verifies 60 simulator tests, CAPs, and 14 physical groups including 1167B signing and 600B Create with 255B frames, superseding record 63's final-frame expansion failure. The 8192B ceiling is not a physical capacity guarantee; retained response buffers and asynchronous GC still matter. Actual repeated receiveBytes delivery within one short APDU remains unverified.
- Distinguish single, first, middle and last frames. A new single or first frame replaces an unfinished request, including when the new request uses the same command. Middle and last frames must match an active request.
- Use short APDUs; Extended APDU support cannot be assumed on the user's cards.
- GET RESPONSE is separate from request reception: during an incomplete request it returns 6883 without discarding it; absent a pending response it returns 6985. Invalid GET RESPONSE headers preserve pending transfers. Other request reception errors cancel assembly. New business requests discard unread responses. The current receiver executes synchronously after the last frame and does not insert the historical empty-6100 GC boundary.
- Handle GET RESPONSE in Command.process before resetting the response writer or receiving a new request. Writer reset clears cancelled response contents; sending clears the sent range. Command.dispose only releases static references for uninstall and does not call clearTransport.
- Always send GET RESPONSE with CLA `00`; disable middleware that automatically copies the last request's CLA.

- Preserve parent lifecycle calls when overriding them: MonoidApplet.deselect calls super.deselect before its own cleanup; do not omit the call merely because the documented default implementation is empty.
