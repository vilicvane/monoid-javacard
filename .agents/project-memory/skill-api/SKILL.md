# Monoid Java Card API decisions

- Record182 defines A Extend, B Approve, C Join, with no return to A for interoperability. Create23 receives only other recipient public keys and returns {bundle, data:byte[][]} in the same order. Extend25 accepts {publicKey}->{data}; Approve Bundle Extension26 accepts {data}->{publicKey,data}, with B's actual Identity key, so its complete response forwards directly to Join24 {publicKey,data}->{bundle}. All require Secret PIN; there is no action discriminator. Create omits its already known public key. Only Bundle Join changes senderPublicKey to publicKey; item Import keeps senderPublicKey. Identity mirrors extendBundle(publicKey)/approveBundleExtension(request). Root-HMAC plus another Identity signature binds Bundle, actual initiator and target; data decryption uses authenticated sender-key possession and rejects self without roster lookup. Enrollment snapshots are not authorization rosters; same-root Join is idempotent. See182 for current interfaces and the boundaries of earlier physical validation.

Source: `../records.md`, records 1–3, 6–10, 17–40, 42, 45–61, 63–65, 67–110, 114–141, 147–170 and 181–183. Treat `records.md` and its numbered references as authoritative; keep them up to date when maintaining this snapshot.
