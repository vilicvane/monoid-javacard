# Removing public master support

[user] While narrowing applet grants to fixed keys or seed-based Monoid-001
derivation, questioned whether master support is redundant and clarified that
this concerns the entire Monoid project, not only the authorization API.
The subsequent user decision explicitly approves removing public master support
and shifting the following built-in item types forward. APP changes are assigned
to another conversation; this implementation is limited to Java Card.

[user] Recalled that master import likely came from earlier work on Megnat
using Tangem SDK, where the application prepared a master before importing it
into the card. This is the user's recollection of the design's origin, not a
confirmed historical Monoid commit rationale.

[agent] Current official Tangem Android SDK source corroborates that workflow:
TangemSdk.importWallet(mnemonic, passphrase, curve) creates
AnyMasterKeyFactory(mnemonic, passphrase), calls makeMasterKey(curve), and passes
the result to CreateWalletTask. That task accepts ExtendedPrivateKey and sends
it through CreateWalletCommand. Thus the SDK's card-facing import boundary is
an extended private key, even though the public convenience API accepts a
mnemonic. This confirms present SDK behavior, not the exact historical Megnat
version. Sources inspected on 2026-10-19:

- [TangemSdk.kt](https://github.com/tangem/tangem-sdk-android/blob/master/tangem-sdk-core/src/main/java/com/tangem/TangemSdk.kt#L383-L400)
- [CreateWalletTask.kt](https://github.com/tangem/tangem-sdk-android/blob/master/tangem-sdk-core/src/main/java/com/tangem/operations/wallet/CreateWalletTask.kt#L29-L40)

[agent] Public master items/Key selectors can be removed independently of the
internal seed-to-master computations required by BIP32, SLIP-0010 and Monoid-001.
Internal algorithms and caches can continue using their master/PRK values.
Affected public surfaces include the master Safe Item type, Create and
CreateRandomKey, Key descriptions used by ViewKey/Sign, public Keystore
from-master entry points, documentation and examples/tests for saved masters.

The capability lost would be directly importing and using externally supplied
extended-private-node/master material without its source seed. Existing stored
masters cannot be inverted into their original seeds; treating the same bytes
as a seed produces different keys. The user approved renumbering, not migration
or card mutation. Indices and exported items using the former master or curve
types cannot be reused unchanged: the former secp256k1 type 0x0401 now denotes
Ed25519. No compatibility layer or migration is introduced.

## Implementation

- Remove the master Safe type, textual mapping, length encoding, random creation
  and public Keystore from-master entry points. ViewKey/Sign accept stored seeds
  with explicit derivation or independent curve keys, without a master selector.
- Keep entropy 0x0100 and seed 0x0200; shift Weierstrass to 0x0300, secp256k1 to
  0x0301, secp256r1 to 0x0302, Edwards to 0x0400 and Ed25519 to 0x0401. Generic,
  custom and reserved ranges are unchanged.
- Keep internal seed-to-master computations, algorithm vectors and
  KeyDerivation's internal master/node API and cache. Removing a stored master
  input does not change BIP32, SLIP-0010 or Monoid-001 outputs from a seed.
- Update README, Bitcoin/Monoid-001/architecture documentation and test-key
  fixtures. Negative tests reject the removed textual master selector and old
  0x0320 stored-master type; positive tests check new textual/numeric type mapping
  and category listing.

Validation: all 304 simulator tests pass with zero failures/errors/skips,
including the 83 tests in the five changed suites. Gradle check completes;
all three production CAPs build and verify with zero converter warnings/errors.
Repository-wide Prettier, Inplate assertion and git diff --check pass. Independent
production/documentation and test-diff reviews found no task-related defects.
No physical-card access or installation was performed. The user accepted the
local validation as sufficient for this change and requested committing it.

## Entropy clarification

The user also asks to clarify entropy/mnemonic/passphrase ordering. In BIP39,
entropy corresponds to the mnemonic alone under a fixed wordlist; passphrase
is a separate input to PBKDF2 when computing the 64B seed. Correct diagram:

```text
entropy <-> mnemonic (fixed wordlist and checksum)
              |
              + passphrase -> PBKDF2-HMAC-SHA512 -> seed
```

Changing passphrase does not change entropy or mnemonic; it changes seed.
Absent passphrase means an empty string, not the card PIN. The current Java
Card code stores entropy but does not implement BIP39 conversion/PBKDF2.
Source: [BIP39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki)
and the current source audit in 107. The earlier diagram placing mnemonic and
passphrase together under a reversible entropy arrow was ambiguous and is
superseded by the diagram above.
